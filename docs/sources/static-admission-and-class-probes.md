#### A typedef field is its base kind at every gate measured, which makes `spec/01`'s expansion exclusion sound rather than merely assumed, measured locally 2026-09-07

- `revision`: one `dmtool batch --observations`, ten `rule check` children over one model, at a12-dmkits `4178ef6d11ec7d31f5f2cfb956d12b1fb3f925ea` in the pinned measurement checkout, `source.state: CLEAN`, both checkouts `git status --short` empty before and after. `dmtool` 0.13.0, Kernel `30.8.1` built and runtime, every envelope `KERNEL_CONFIRMED`.
- `question`: the 2026-09-07 handback measured that a typedef resolves to its **base** kind at the extrema, and this project's `FieldKind` carries no typedef arm at all. Before writing one, the premise worth measuring is whether base-kind resolution is a declaration-layer rule or one gate's behaviour — because that decides whether the representation is a new kind arm or nothing at all.
- `prediction`: recorded before the run. If resolution is declaration-layer, every typedef row equals its plain-base-kind control at every gate; if it is gate-specific, some gate treats the typedef differently.
- `claim`: **it is declaration-layer.** At three independent gates each typedef row matches its plain control exactly: a numeric aggregate's kind gate admits a NUMBER-based typedef and refuses a STRING-based one `MVK_NO_NUMBER`; the distinct count's homogeneity gate admits a STRING-based typedef beside a String and refuses it beside a Number `MVK_STRING_ENUM_AND_NON_STRING_ENUM`; and a comparison against a numeric literal admits the NUMBER-based one and refuses the STRING-based one `MVK_INVALID_TYPE_FOR_COMPARISON`.
- `separator`: **each gate carries its own plain-kind control and the three gates report three different codes.** A typedef treated as an opaque kind would refuse uniformly; one silently admitted everywhere would pass no control. Both rival readings die on the spread.
- `representation-consequence`: **no Lean work is owed, and the exclusion this project already declared is now measured rather than assumed.** [`spec/01`](../../spec/01-data-model.md) puts model include/expansion out of scope and assumes an already-expanded model. That is only safe if a typedef has no gate-specific effect — which is what these rows establish. Had any gate differed, the exclusion would have been silently unsound, so this retires the open row rather than scheduling a capsule.
- `corroborates-inbound`: the last pair independently reproduces the handback's §10 orderability mechanism on this project's own fixture — `[PlainStr] > 0` draws `MVK_INVALID_TYPE_FOR_COMPARISON` because STRING is not orderable and ordering reports the orderability class before any kind match. Taken as corroboration rather than as the discharge of that entry, which remains the peer's measurement.
- `denominator`: searched NUMBER-based and STRING-based typedefs at three gates — `Sum`'s kind gate, `NumberOfDifferentValues`' homogeneity gate, and an ordering comparison against a numeric literal — each against a plain-base-kind control on the same model, arity 1 or 2, `en_US`, validation arm.
- `not-searched`: a typedef over a config-bearing base kind such as DATE or ENUM, where a declared format or domain might not survive resolution; a typedef imported from a separate `_TDM` model rather than declared inline; and the computation arm.
- `bytes`: in the retained [typedef base-kind capture](../../evidence/kernel-30.8.1/captures/typedef-resolves-to-base-kind/) — model `TdBase_DM.json` `110f68fa237f451e9921f79ef4ad9e9859183a7544664d344c7ac67a23e3ebc4`, batch `ops.json` `fab610c094f9aab0b2a139509dd2204deb344bafd5d290b88e6c1e78b3f7dd96`, observations `obs.json` `16b844f60fc6514ea9862f910fac64f103a3ee2bd12cd1ea9a7594c48d6436ff`.
- `sync`: behavioral. No clause states that a typedef resolves to its base kind; `spec/01` states the expansion exclusion without saying what makes it safe.
