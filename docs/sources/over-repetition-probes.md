# Over-repetition source checkpoints

The structural over-repetition family: which findings an over-capacity row draws, how deep its absorption and suppression reach, and which physical rows the starred numeric domains then exclude. Split out of [`group-and-iteration-probes.md`](group-and-iteration-probes.md) when that document reached its size ceiling; the checkpoints are unchanged and keep their anchors.

<a id="src-over-limit-absorption-depth"></a>
#### The absorption is transitive and the suppression covers the whole written subtree, measured locally 2026-08-30

- `revision`: a12-dmkits `1be2d603c90be578fe7ea0de0b8c515cb2a479c4` (clean before and after; the artifact records `state: CLEAN`), `dmtool` 0.13.0, Kernel `30.8.1` built and runtime. One `:adapter:kernelProbe` request, four documents, `validateFull` and `compute` on both codegen strategies, the two engines' message sets compared element-wise.
- `question`: the three residuals the [attribution checkpoint](#src-nested-over-limit-attribution) named for itself — three nested over-limit levels, whether an ordinary VALUE error on an in-capacity sibling is affected, and, added here because the pairing makes the negative interpretable, whether the same malformed value inside the over-limit subtree is reported. Measured before the entry was handed off, per [`LF114`](../LEAN-FINDINGS.md#lf114--both-sides-sampling-one-side-of-an-unnamed-boundary-agree-and-re-derivation-cannot-break-the-tie).
- `model`: the multiplicity capture's `Probe_DM`, byte-identical (SHA-256 `2e23c9d45b36f3f9ba1452bf7739406dd667655933782775510cf7bed016cef4`).
- `transitive`: **the outermost violation absorbs every nested one, not only its immediate child.** With `A[3]`, its `B[3]`, and that row's `C[2]` and `C[3]` all beyond their own capacity of 2, the document draws exactly one `zuGrosseZeile`, on `A[3]`, and all fourteen messages name `/Probe/Tri/A` with index 3. A per-level reading gives the third level its own code and is refuted. The fourteen are one row code plus the thirteen rows and cells the document writes beneath `A[3]`, so the node rule is unchanged at three levels of violation.
- `suppression-reach`: **the over-limit row's ordinary checks are suppressed across its whole written subtree, not only its direct cells.** A non-numeric `"abc"` in the leaf `DeepValue` two levels below the over-limit `Mid[4]` produces no format finding at all; that row reports its four over-repetition findings and nothing else.
- `sibling-control`: the same `"abc"` in the in-capacity `Mid[1]` row *does* report, as `zahlHatUngueltigeZeichen` — *"The value must be integer."* — beside the unchanged four findings of the over-limit row. That pairing is what makes the silence above a measured suppression rather than an input the Kernel ignored, and it confines the suppression to the violated subtree.
- `control`: the negative control instantiates one in-capacity row at every level and reports zero messages. `TallyStar` reads `3` on both four-row documents, so a malformed value in an in-capacity row does not move a group count that reads row structure rather than cell values.
- `local-consequence`: none for the Lean cell account, which already collapses any number of violated axes to one `.overRepetition` and suppresses the scalar reading with it. Message attribution and the cross-row suppression reach belong to [SG10](../SEMANTICS-GAPS.md#sg10--message-construction-and-formal-output-integration).
- `limit`: three nested over-limit levels, capacities 2 and 3, scale-0 Numbers, one malformed spelling, `en_US` only. Not measured: an ancestor over-limit by a different margin, a required-field or custom-validator finding in place of the format one, and the German texts.
- `bytes`: [`over-limit-absorption-depth/`](../../evidence/kernel-30.8.1/captures/over-limit-absorption-depth/); SHA-256 request `32c0a6c08d6e3070d0ad7b11bc61cb37310e8e993840ce4353c45196b6fe3539`, model `2e23c9d45b36f3f9ba1452bf7739406dd667655933782775510cf7bed016cef4`, artifact `17fe75264e6b906462ae8ad5e3992ff11875411bc7af7e991809f37e6d597329`. A bounded raw calibration capture with no typed consumer: it does not run under `lake test` and establishes neither `L` nor `C` coverage.
- `sync`: locally originated and behavioral. It extends the same pending [`SPEC-2026-08-30-10`](../A12-DMKITS-SPEC-SYNC-LEDGER.md#spec-2026-08-30-10) rather than opening another entry; unlike the previous two rounds it corrects nothing, which is the first round of this rule that a residual failed to falsify.


<a id="src-nested-over-limit-attribution"></a>
#### An inner over-limit row is invisible: every finding beneath the outermost violation names that violation, measured locally 2026-08-30

- `revision`: a12-dmkits `1be2d603c90be578fe7ea0de0b8c515cb2a479c4` (clean before and after; the artifact records `state: CLEAN`), `dmtool` 0.13.0, Kernel `30.8.1` built and runtime. One `:adapter:kernelProbe` request, four documents, `validateFull` and `compute` on both codegen strategies, `enginesAgree: true` on every row, and the two engines' message sets compared element-wise rather than taken from that flag.
- `question`: the three residuals the [multiplicity checkpoint](#src-over-limit-finding-multiplicity) named for itself — an over-limit row beneath another over-limit row, two independently over-limit rows in one document, and whether a valued cell stamps like a `null`-valued one. The nested shape was the one a consumer was most likely to get wrong, and it did not behave as the published rule predicted.
- `model`: the multiplicity capture's `Probe_DM`, byte-identical (SHA-256 `2e23c9d45b36f3f9ba1452bf7739406dd667655933782775510cf7bed016cef4`).
- `absorption`: **an over-limit row inside an already over-limit subtree reports neither its own row code nor its own group.** With `A[3]` beyond `max 2` and its `B` running to three rows beyond `max 2`, the document draws exactly one `zuGrosseZeile`, on `A[3]`. `B[3]` draws only a `zuGrosseKontextnummer`, and that message reads *"The index for group '/Probe/Tri/A' was specified with 3"* — the **ancestor's** group and index. All ten messages in the row carry that same text.
- `consequence`: the inner violation is unreportable while the outer one stands, so the formal channel is not monotone in the document: fixing `A` reveals a violation of `B` that no message had named. A consumer deriving the set of violated groups from the message texts sees one group where two are violated.
- `nodes`: the same row settles what a node is. Three `B` rows beneath `A[3]` give nine context-number findings, three per row — `A[3]/B`, `A[3]/B[2]`, `A[3]/B[3]` and their `C` and `TriValue` descendants. A per-group-key reading predicts one `A[3]/B` entry whatever the row count, so the node is the instantiated **row**. `A[3]/B` is row 1 with its index elided, which is this route's rendering and is measured here on three levels at once.
- `independence`: two over-limit rows in **disjoint** subtrees do not interact. `Mid[4]` and `A[3]` together draw eight findings, exactly the sum of the four each draws alone, each with its own `zuGrosseZeile` and its own group named in its own descendants' texts. So the absorption above is about containment, not about a per-document cap.
- `value`: a cell holding a value stamps exactly as a `null`-valued one. The four-row `Mid` document with `11` and `22` in the over-limit row's cells draws the identical four findings and no Number-format finding, which is the suppression of ordinary row checks showing through on a cell that would otherwise be checked.
- `control`: the negative control instantiates one in-capacity row at every level and reports zero messages. `TallyStar` moves to `3` only on the documents holding four `Mid` rows, replicating the in-capacity domain a third time.
- `local-consequence`: none for the Lean cell account, which stamps `.overRepetition` when **any** axis is over capacity and does not distinguish which one; both a singly and a doubly over-limit cell read the same. The attribution and absorption live entirely in message construction and belong to [SG10](../SEMANTICS-GAPS.md#sg10--message-construction-and-formal-output-integration).
- `channel`: **every count in this record is the full-validation channel's, and the same artifact carries a second channel that disagrees.** A computation's own over-repetition errors arrive in `formalErrorsInOperands`, scoped to what its operands reach: on `nested-over` the artifact holds ten validation findings and **zero** operand errors, and on `two-independent` eight against four, while `valued-cells` happens to agree at four. So a document-wide reading of this rule is right for validation and wrong for computation, and the agreeing row is why the difference was not noticed when the rule was written. The row-level `zuGrosseZeile` does reach the operand channel — it is present in both nonzero rows — so that channel carries a row code and is not field-scoped.
- `limit`: two nested over-limit levels, disjoint subtrees at one level each, capacities 2 and 3, scale-0 Numbers, `en_US` only. The operand channel above is observed but not characterized: nothing here varies which operands a computation reads, so its exact scope rule is unmeasured locally. The depth of the absorption and its effect on ordinary errors were measured next and closed by the [absorption-depth checkpoint](#src-over-limit-absorption-depth); an ancestor over-limit by a different margin and the German texts remain unmeasured.
- `bytes`: [`nested-over-limit-attribution/`](../../evidence/kernel-30.8.1/captures/nested-over-limit-attribution/); SHA-256 request `c2259a4d75c11afc8341135959b97586459530e664257986a319d663db8e748d`, model `2e23c9d45b36f3f9ba1452bf7739406dd667655933782775510cf7bed016cef4`, artifact `a8a6f68ca9dedf9068b88e55a992eaaefe49341b90c25e4d50072ada47aff92d`. A bounded raw calibration capture with no typed consumer: it does not run under `lake test` and establishes neither `L` nor `C` coverage.
- `sync`: locally originated and behavioral. It corrects the rule published hours earlier in the same pending entry, in two ways, so it updates [`SPEC-2026-08-30-10`](../A12-DMKITS-SPEC-SYNC-LEDGER.md#spec-2026-08-30-10) rather than opening a second one.


<a id="src-over-limit-finding-multiplicity"></a>
#### One rule replaces the special cases: an over-limit row stamps every node the document writes beneath it, measured locally 2026-08-30

- `revision`: a12-dmkits `1be2d603c90be578fe7ea0de0b8c515cb2a479c4` (clean before and after; the artifact records `state: CLEAN`), `dmtool` 0.13.0, Kernel `30.8.1` built and runtime. One `:adapter:kernelProbe` request, five documents, `validateFull` and `compute` on both codegen strategies, `enginesAgree: true` on every row.
- `question`: [SPEC-2026-08-30-10](../A12-DMKITS-SPEC-SYNC-LEDGER.md) and the [row-domain checkpoint](group-and-iteration-probes.md#src-group-count-row-domains) both named the same four unmeasured shapes — several placed cells beneath one over-limit row, three or more repetition levels, an over-limit row at the **inner** level, and whether an unplaced declaration contributes. All four are answered here.
- `model`: the row-domain `Probe_DM` with a second scale-0 Number `DeepValue2` beside `DeepValue` in the leaf group, plus an independent three-level chain `/Probe/Tri/A(max 2)/B(max 2)/C(max 2)` declaring `TriValue`. `model check` reports the model valid, `KERNEL_CONFIRMED`.
- `rule`: **one `zuGrosseZeile` on the over-limit row, plus one `zuGrosseKontextnummer` for every node the document instantiates beneath it**, at any depth. That single rule reproduces every row measured here and both earlier shapes, so the flat count and the one-nested-group count stop being separate clauses. Every descendant group here holds exactly one row, so "node" was first written as *group key or cell key*; the [attribution checkpoint](#src-nested-over-limit-attribution) multiplies those rows and shows it is one node per instantiated **row** and per present cell, with repetition-one elided in the rendered address.
- `per-cell`: the multiplicity counts **cells, not groups**. An over-limit row whose one descendant row writes two `null`-valued cell keys reports four findings: the row, `Mid[4]/Rows`, `Mid[4]/Rows/DeepValue`, and `Mid[4]/Rows/DeepValue2`. The earlier three-finding row is consistent with both a per-cell and a per-group reading; a second cell separates them.
- `depth`: the chain is not bounded at two. An over-limit `A[3]` whose `B` and `C` rows are instantiated reports four findings — the row, `A[3]/B`, `A[3]/B/C`, and `A[3]/B/C/TriValue` — so the stamp reaches every level, and a fixed count of three is refuted.
- `instantiation`: **an unplaced declaration contributes nothing.** The same over-limit `A[3]` written as the empty row object `{}` reports the row finding **alone**, although `B`, `C`, and `TriValue` are all declared beneath it. So the multiplicity is read off the document's written subtree, not the model's declaration chain, which closes the open question rather than narrowing it.
- `corpus-enumerated`: **the placed-not-declared rule is now checked against every retained observation of it, re-read locally 2026-08-31 with no new kernel run.** Across all captures carrying `zuGrosseKontextnummer`, 54 over-limit rows resolve to both a model declaration and a written document node, none skipped; the count of placed cells plus placed descendant rows equals the observed finding count on all 54. Four of those rows omit a declared sibling **field** and five more omit a declared sibling **group**, so the corpus separates the two accounts and agrees with this one. The sharpest is `middle-over-3-tasks` in [`over-limit-computation-target`](group-list-and-capacity-probes.md#src-over-limit-computation-target): `Tasks[3]` declares `TaskId`, `Effort`, `TaskDate`, and `Subtasks`, the document writes `TaskId` and two `Subtasks` rows, and the five stamped addresses name exactly those — `Effort` and `TaskDate` are declared, unwritten, and unstamped.
- `inner-level`: an over-limit row at the inner level behaves identically one level down. `A` holding one row whose `B` runs to index 3 over `max 2` reports three findings — `A/B[3]`, `A/B[3]/C`, `A/B[3]/C/TriValue`. The in-capacity outer axis carries **no index** in those addresses, so the stamped path is the authored address rather than a fully indexed one.
- `message-text`: every `zuGrosseKontextnummer` names the **over-limit group's** declaration path and the offending index, regardless of how deep the stamped node sits; `referenced` holds exactly the stamped address and `fillToFix` is empty. `zuGrosseZeile` carries no path in its text. All rows are `severity: ERROR`, `type: VALUE_ERROR`.
- `control`: the negative control instantiates one in-capacity row at every level and reports zero messages, so the gate is live rather than stamping unconditionally. Only `TallyStar` moves anywhere in the batch, to `3` on the four-row document, so the over-limit row is again excluded from the starred operand — an incidental replication of the in-capacity domain, not a new claim.
- `local-consequence`: the Lean cell account already predicts every row: `StarAxes.environmentOverLimit` folds `any` over the whole axis list, so a cell is unavailable when **any** ancestor coordinate is over capacity. The inner-level row exercises a branch no fixture covered — a middle axis over-limit with both the outer ancestor and the nearest axis in capacity — and is now locked in [`CheckedDocument.lean`](../../A12Kernel/Conformance/CheckedDocument.lean) against the two wrong accounts it kills, outermost-only and nearest-only. Message multiplicity itself stays unrepresented and belongs to [SG10](../SEMANTICS-GAPS.md#sg10--message-construction-and-formal-output-integration).
- `limit`: capacities 2, 3, and 5; scale-0 Numbers only; at most two cells under one row and at most three repetition levels; every measured cell key is written with `null`. Not measured: whether a valued cell stamps alike, two independently over-limit rows in one document, an over-limit row beneath another over-limit row, and whether declaration kind changes the stamped set.
- `bytes`: [`over-limit-finding-multiplicity/`](../../evidence/kernel-30.8.1/captures/over-limit-finding-multiplicity/); SHA-256 request `ee0f066c7cfc25ffce47e61f878a2b2fc26cae69ff6a7286e87ad47cacbc0358`, model `2e23c9d45b36f3f9ba1452bf7739406dd667655933782775510cf7bed016cef4`, artifact `48610c0b229b5ae3b2b22420834df8b372f3792429c63894ab106b0d8ed61307`. A bounded raw calibration capture with no typed consumer: it does not run under `lake test` and establishes neither `L` nor `C` coverage.
- `sync`: locally originated and behavioral. It generalizes and closes the multiplicity clause already pending as `SPEC-2026-08-30-10`, whose stated limits it answers, so it updates that entry rather than opening a second one.

- `controls`: changing the second in-capacity premium from `20.00` to `21.00` removes only `SUM_EQ`; emptying that premium removes `NFF_EQ` too while `NFG_EQ` remains; retaining only the first row removes all three codes. - `formal-channel`: the reviewed overload matrix reports exactly `zuGrosseZeile@/Order[1]/Lines` plus `zuGrosseKontextnummer@/Order[1]/Lines[3]/Qty` for the over-capacity row, with no Number, Boolean/Confirm, or String-length code. - `declared-extent`: `NumberOfFilledGroups(G*)` compares structural row count with the declared capacity. Two rows in a capacity-two group are fixed even when one row contains no value; one row or no rows is grow-only; an over-capacity third row changes neither the count nor its movement.

- `mechanism-limit`: the outcomes establish a capacity-bounded evaluation projection beside a complete physical topology. - `limit`: one repeatable level, one Number field, validation-phase `Sum` and filled-field count, and the sole starred-group numeric count. Filtered stars, nested repeatable axes, other aggregates and count families, partial validation, computation, and wider message/reference semantics remain outside.
- `sync`: this is inbound calibration already committed in a12-dmkits. It corrects the local starred evaluation domain and creates no outbound ledger request.

<a id="src-over-limit-finding-text"></a>
#### `zuGrosseZeile` renders no coordinate at all, and two independent over-limit groups report independently, re-read locally 2026-08-31

- `route`: no new kernel run. Every row is re-read from the [capacity consumer sweep](group-list-and-capacity-probes.md#src-capacity-consumer-sweep)'s retained artifact, produced by `:adapter:kernelProbe` at a12-dmkits `5e823edad` on both codegen strategies with `state: CLEAN`. The claim is about bytes already on disk.
- `zeile-text`: **`zuGrosseZeile` renders `The row number is bigger than the maximum allowed value.` and names nothing** — not the group, not the offending index, not the cap. Byte-identical on both strategies and across two documents and two groups. So a consumer that needs to know *which* row overflowed has no choice but to read `field`; the text is not a degraded source of the coordinate, it is no source at all.
- `kontextnummer-text`: its sibling is the opposite and reproduces the earlier reading on a fresh model — `The index for group '/Cap/NShell/NRows' was specified with 3, but at most 2 is allowed.` names the group and states the offending index and the cap as **separate numbers**, so neither has to be parsed out of a coordinate. The group is written in the leading-slash bracket-free declaration spelling while the same message's `field` is the bare instance one, which is the [dialect checkpoint](message-and-pointer-probes.md#src-message-address-dialects)'s third surface on a second model.
- `independence`: **two over-limit groups in one document report independently and completely.** A document instantiating row 3 in both `TShell/TRows` and `NShell/NRows`, each declared `max 2`, emits four structural findings: one `zuGrosseZeile` per violated row addressed at the row itself, and one `zuGrosseKontextnummer` per placed cell in it addressed at the cell. Neither group suppresses or absorbs the other, which the [nested absorption row](#src-over-limit-absorption-depth) cannot show because its two levels are on one path.
- `both-strategies`: all four findings are byte-identical between `kernel-groovy-dynamic` and `kernel-java-static`, texts included, so no part of this is a codegen artifact.
- `not-separated-here`: this model declares exactly one field per repeatable group, so **places** and **declares** predict one finding either way and no row below distinguishes them. That is a limit of this capture, not an open question: the [multiplicity checkpoint](#src-over-limit-finding-multiplicity) settles it for the corpus, on an empty row object and on four partially written rows, and this row previously overstated its own scope into a claim that no retained artifact separates the accounts ([`LF128`](../LEAN-FINDINGS.md)).
- `limit`: `en_US` only, one repeatable level per group, one over-limit index, capacity 2. Not measured here: the German texts and a second over-limit index in one group. A repeatable group carrying more than one field is measured elsewhere, at the [multiplicity checkpoint](#src-over-limit-finding-multiplicity)'s `corpus-enumerated` row.
- `bytes`: [`capacity-consumer-sweep/artifact.json`](../../evidence/kernel-30.8.1/captures/capacity-consumer-sweep/artifact.json), SHA-256 `bc205037d79e102cfda242b86ec635d5fec00666fab4caee926dcd1b67e55b5c`. Re-read evidence with no typed consumer: it does not run under `lake test` and establishes neither `L` nor `C` coverage.
- `sync`: not behavioral for `spec/`. Rendered message text is a locale catalog rather than a semantic clause, and this project records it at a checkpoint exactly as it records the sibling code's text. No ledger entry.
