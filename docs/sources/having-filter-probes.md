- `revision`: one `apply` of thirty-three rules, then `:adapter:kernelProbe` with `observe: ["validateFull"]`. a12-dmkits `acced5d6012b15c0c3145d2a236e61bf2ad74246` on `main` with `source.state: CLEAN`, `dmtool` 0.13.0, Kernel `30.8.1` built and runtime, both codegen strategies with `enginesAgree: true`; the whole batch `verification: KERNEL_CONFIRMED`. - `question`: [SG17](../SEMANTICS-GAPS.md#sg17--having-filter-leaf-and-connective-completion)'s last leaf-domain item. The presence leaf reads a cell *observation* rather than a projected value, so this project admits it over any declared field — but the evidence was Number and String only, and the [presence checkpoint](#src-having-filter-presence-leaf)'s three-state rule was measured on Number operands. A carrier whose invalid state arises from token recognition or range parsing rather than numeric scanning could plausibly read differently.
- `claim`: **it does not. All four carriers reproduce the Number account exactly.** With one row valid, one formally invalid, and one absent, each carrier's `FieldFilled` ladder fires `== 1` and its `FieldNotFilled` ladder fires `== 1`, while `== 0`, `== 2`, and `== 3` stay silent on both and the unfiltered control answers `3`. `Date` with unparseable text, `Enumeration` with an unrecognized token, `DateRange` with unparseable range text, and `Boolean` with non-Boolean text all behave alike.
- `the-sum-is-the-separator`: `1 + 1 < 3` is the whole finding. Two complementary polarities over three rows can only miss a row if that row is non-true under **both**, so the invalid row drops from each — and the two `== 2` rungs staying silent is what rules out either polarity claiming it. An account that read invalidity as absent predicts `1` and `2`; one that read it as filled predicts `2` and `1`; both are refuted four times over.
- `local-consequence`: no clause change and **no new conformance case**. The leaf takes a `FieldId` and delegates to the shared `CellObservation` validation-phase consumers, so it is kind-generic by construction and a per-carrier case would exercise the same function on the same observation — the [presence matrix](../../A12Kernel/Conformance/FilledFieldStarCountHaving.lean) already guards that branch. What this adds is the retained external evidence that the Kernel's own presence reading is carrier-independent too, which is an argument about the Kernel rather than about this code.
- `computation-arm-diverges-identically`: **the same four carriers reproduce the arm divergence too**, measured on the same document. With the invalid operand reached, a filtered `Sum` produces **no outcome** on Date, Enumeration, DateRange, and Boolean alike, while the identical filter over the all-valid document computes `2`. So one document and one filter give an available validation count of `1` and no computed outcome at all, depending only on the arm, on four carriers where only Number and String had been measured.
- `the-sibling-computation-is-the-control`: in every aborting call, two **other** computations in the same model produce their values (`0` each). That is what makes the missing outcome a poison confined to the computation that reached it rather than a call-wide abort, and it is measured four times rather than inferred from the Number case.
- `four-code-families-report-and-do-not-abort`: `formalErrorsInOperands` names the carrier's own class each time — `datumFormatFalsch`, `stringFalschesMuster` for the unrecognized Enumeration token, `datumBereichTrennerFehlt`, and `feldJaNeinFalsch` — while the surviving computations produce values anyway. This re-confirms [`spec/09` §3.3](../../spec/09-computations.md) across four code families at once. The inventory also lists row 2's malformed `Day` in every run, including the three where the filter never names `Day`, which is the eager operand-set behaviour rather than a read trace.

Not measured: `Confirm` and `Custom` declarations, a **present-empty** cell on a temporal or Enumeration carrier as distinct from absent, and an over-repetition row's presence reading.
