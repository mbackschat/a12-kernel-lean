<a id="src-presence-leaf-operand-kinds"></a>
#### The presence leaf reads the same three states on a temporal, Enumeration, DateRange, and Boolean operand, measured locally 2026-09-03

- `revision`: one `apply` of thirty-three rules, then `:adapter:kernelProbe` with `observe: ["validateFull"]`. a12-dmkits `acced5d6012b15c0c3145d2a236e61bf2ad74246` on `main` with `source.state: CLEAN`, `dmtool` 0.13.0, Kernel `30.8.1` built and runtime, both codegen strategies with `enginesAgree: true`; the whole batch `verification: KERNEL_CONFIRMED`. One model, one document, four operand carriers laddered in both polarities against `== 0`, `== 1`, `== 2`, and `== 3`, plus an unfiltered control.
- `question`: [SG17](../SEMANTICS-GAPS.md#sg17--having-filter-leaf-and-connective-completion)'s last leaf-domain item. The presence leaf reads a cell *observation* rather than a projected value, so this project admits it over any declared field — but the evidence was Number and String only, and the [presence checkpoint](#src-having-filter-presence-leaf)'s three-state rule was measured on Number operands. A carrier whose invalid state arises from token recognition or range parsing rather than numeric scanning could plausibly read differently.
- `claim`: **it does not. All four carriers reproduce the Number account exactly.** With one row valid, one formally invalid, and one absent, each carrier's `FieldFilled` ladder fires `== 1` and its `FieldNotFilled` ladder fires `== 1`, while `== 0`, `== 2`, and `== 3` stay silent on both and the unfiltered control answers `3`. `Date` with unparseable text, `Enumeration` with an unrecognized token, `DateRange` with unparseable range text, and `Boolean` with non-Boolean text all behave alike.
- `the-sum-is-the-separator`: `1 + 1 < 3` is the whole finding. Two complementary polarities over three rows can only miss a row if that row is non-true under **both**, so the invalid row drops from each — and the two `== 2` rungs staying silent is what rules out either polarity claiming it. An account that read invalidity as absent predicts `1` and `2`; one that read it as filled predicts `2` and `1`; both are refuted four times over.
- `local-consequence`: no clause change and **no new conformance case**. The leaf takes a `FieldId` and delegates to the shared `CellObservation` validation-phase consumers, so it is kind-generic by construction and a per-carrier case would exercise the same function on the same observation — the [presence matrix](../../A12Kernel/Conformance/FilledFieldStarCountHaving.lean) already guards that branch. What this adds is the retained external evidence that the Kernel's own presence reading is carrier-independent too, which is an argument about the Kernel rather than about this code.
- `computation-arm-diverges-identically`: **the same four carriers reproduce the arm divergence too**, measured on the same document. With the invalid operand reached, a filtered `Sum` produces **no outcome** on Date, Enumeration, DateRange, and Boolean alike, while the identical filter over the all-valid document computes `2`. So one document and one filter give an available validation count of `1` and no computed outcome at all, depending only on the arm, on four carriers where only Number and String had been measured.
- `the-sibling-computation-is-the-control`: in every aborting call, two **other** computations in the same model produce their values (`0` each). That is what makes the missing outcome a poison confined to the computation that reached it rather than a call-wide abort, and it is measured four times rather than inferred from the Number case.
- `four-code-families-report-and-do-not-abort`: `formalErrorsInOperands` names the carrier's own class each time — `datumFormatFalsch`, `stringFalschesMuster` for the unrecognized Enumeration token, `datumBereichTrennerFehlt`, and `feldJaNeinFalsch` — while the surviving computations produce values anyway. This re-confirms [`spec/09` §3.3](../../spec/09-computations.md) across four code families at once. The inventory also lists row 2's malformed `Day` in every run, including the three where the filter never names `Day`, which is the eager operand-set behaviour rather than a read trace.
- `limit`: one invalid state per carrier, one repetition level, one counting operator on the validation arm and one aggregate on the computation arm. Not measured: `Confirm` and `Custom` declarations, a **present-empty** cell on a temporal or Enumeration carrier as distinct from absent, and an over-repetition row's presence reading.
- `sync`: locally originated, and it **confirms** the existing three-state presence rule, the arm divergence, and the report-not-abort rule on four further carriers rather than correcting any of them, so it opens no ledger entry.

<a id="src-bare-outer-reference-redundant-marker"></a>
#### On a level the star does not reopen, the `$` marker is admitted, redundant, and not what satisfies the scope gate, measured locally 2026-09-03

- `revision`: three `rule check` decisions in one `batch`, then one `apply` of four rules and one `:adapter:kernelProbe` run with `observe: ["validateFull"]`. a12-dmkits `acced5d6012b15c0c3145d2a236e61bf2ad74246` on `main` with `source.state: CLEAN`, `dmtool` 0.13.0, Kernel `30.8.1` built and runtime, both codegen strategies with `enginesAgree: true`; every authoring child `verification: KERNEL_CONFIRMED`. A two-level model — `Lines` above `Items` — with a per-row error field at the `Lines` level, so the rule iteration binds `Lines` while the operand `/Nest/Lines/Items*/Qty` stars only `Items`.
- `question`: [`spec/07`](../../spec/07-repetition-and-iteration.md) §3 asserted that "`$` is the **sole** way a filter references an out-of-scope (outer) field", while the same section's [grammar checkpoint](#src-having-filter-condition-grammar) records "a bare outer scalar reference with no `$`" as measured **admitted**. Those two sentences cannot both be right, and [SG17](../SEMANTICS-GAPS.md#sg17--having-filter-leaf-and-connective-completion) carried the resulting discriminator as open. Which is it, and if both spellings are legal, do they read the same row?
- `claim`: **both spellings are admitted on a level the enclosing iteration binds and the star does not reopen, and they read the same row.** `[/Nest/Lines/Cap]` and `[$/Nest/Lines/Cap]`, each beside the same in-scope conjunct, are both kernel-valid; laddered against `== 0` and `== 2` over a document whose `Cap` is `5, 0, 5` across three `Lines` rows, the two spellings fire on **identical** rows — the `== 2` rung on rows 1 and 3, the `== 0` rung on row 2, for each spelling. So the marker is semantically redundant there, and the `sole way` wording is wrong as written.
- `the-gate-is-a-separate-question`: the bare outer reference as the filter's **whole** condition is refused `MVK_NO_ITERATION_FOR_WILDCARD`, exactly as a marked one is. So "unmarked" is not what satisfies the in-scope requirement — being unmarked *at a reopened level* is. This is the row that keeps the correction from over-reaching into the gate.
- `why-it-is-not-vacuous`: the firing addresses carry it. The `== 2` rung fires at `Nest/Lines[1]/Err` and `Nest/Lines[3]/Err` and the `== 0` rung at `Nest/Lines[2]/Err`, so the count genuinely varies with the outer row and the agreement is not two constant answers. A reading that resolved the bare reference against something other than the rule's own row would move at least one rung.
- `local-consequence`: no clause change; the account already inherited the coordinate, and the inheritance is now a **law** rather than a docstring. `resolveAxes` builds each candidate as the bound prefix extended by the reopened axes only, and `starPath_resolve_agreeOutsideReopened` in [`Proofs/StarAddressing.lean`](../../A12Kernel/Proofs/StarAddressing.lean) proves every candidate agrees with that prefix at any level the path does not reopen; `cellAddress_congr_onScope` in [`Proofs/CheckedStarDocument.lean`](../../A12Kernel/Proofs/CheckedStarDocument.lean) turns level-wise agreement into address equality, which is what makes the two spellings the same read. The separating topology — two candidates differing only at the reopened level, and the whole set moving with the captured coordinate — is locked in [`Conformance/StarAddressing.lean`](../../A12Kernel/Conformance/StarAddressing.lean).
- `limit`: one Number carrier, one repetition level above the star, one aggregate, `validateFull` only. Not measured: the same pair on the computation arm, a level **two** levels above the star, a marked reference to a non-reopened level in a *nested* filter, and the group-leaf analogue.
- `sync`: locally originated. The corrected reachability sentence goes outbound as [`SPEC-2026-09-03-07`](../A12-DMKITS-SPEC-SYNC-LEDGER.md#spec-2026-09-03-07); the gate row **confirms** the existing scope-gate account and adds no request.

#### A correlated filter drives a String computed target, and an empty candidate set produces no outcome, measured locally 2026-09-04

- `revision`: a12-dmkits `eded826354916ab71634b204218464a52a06a46b`, the sibling checkout clean before and after, `state: CLEAN` in both artifacts. `dmtool` 0.13.0, Kernel `30.8.1` built and runtime, `validateFull` and `compute` on both codegen strategies with `enginesAgree: true`, `model check` valid with zero diagnostics before and after the write.
- `question`: [SG17](../SEMANTICS-GAPS.md#sg17--having-filter-leaf-and-connective-completion) carried "a correlated filter on a non-Number computed target" as open. The filter's computation arm was retained on Number carriers only, and a carrier boundary is a claim rather than an inheritance ([`LF116`](../LEAN-FINDINGS.md)).
- `carrier-claim`: **the correlated filter drives a String target exactly as it drives a Number one.** `FirstFilledValue(/Str_DM/Rows*/Name Having [/Str_DM/Rows/Key] > [$/Str_DM/Rows/Key])` into a repeatable String target is admitted by `computation add --dry-run`, persists, and re-checks valid. So the correlation, the marker, and the repeatable-target capture all reach this carrier without a second account.
- `value-vector`: the runtime answers **exact per-row values**, not a threshold. Over keys `10, 30, 20` with names `A, B, C` the target computes `B` at row 1 and `B` at row 3, and row 2 gets **no outcome**. The reversed marker reading — candidate against target rather than target against candidate — predicts `nothing, A, A`, so this one document refutes it alone.
- `empty-candidate-shape`: **a target row whose candidate set is empty after filtering produces no computation outcome at all, which is not the cleared shape.** Row 2 above has the maximal key, so nothing survives its filter, and it is simply absent from `outcomes` — where a precondition-cleared or source-invalid producer appears with `cleared: true` at the [dependency diamond](evaluation-and-application-routes.md#src-diamond-dependency-clear-kinds). Two absence shapes therefore exist and a consumer must not fold them together.
- `dependent-reads-empty`: **the cascade has one absence, not two.** A `Length` computation over the same target, added in the same row, answers `1, 0, 1` across the three rows — so the row whose producer reported *no outcome* is read as **EMPTY** by its dependent, exactly as a precondition-cleared producer is at the [dependency diamond](evaluation-and-application-routes.md#src-diamond-dependency-clear-kinds). The two shapes are therefore a property of the reported result, not of the cascade, and neither is poison. This row was taken because the checkpoint's first draft asserted the split was a distinction dependents need, which it is not.
- `addressing-control`: the row identity is measured rather than read off the first run's ordering. A descending-key document `30, 20, 10` moves the empty-candidate row to the front and answers `Rows[2] = A`, `Rows[3] = A`, with **row 1 absent** — so the first run's unindexed `Str_DM/Rows/Out` was row 1, and absence really tracks the empty candidate set rather than a rendering quirk. Without this control the whole `empty-candidate-shape` row would rest on an assumption about how the first instance is addressed.
- `instrument`: the artifact renders the **first** repeatable instance without an index and later ones as `[n]`, so a consumer joining outcomes to rows must treat the unindexed form as row 1. `observe` must include `validateFull` whenever it names any per-row observation; a `compute`-only request is refused with an explicit reason, which is a good refusal rather than a gap.
- `limit`: one String target, one aggregate (`FirstFilledValue`), one comparison operator, one nesting level, three rows, `en_US`, all names filled. Not measured: a Date or Enumeration computed target under the same filter, an empty candidate set on a Number target for the same absence shape, and a filter whose own operand is malformed on this carrier.
- `bytes`: [`correlated-string-target/`](../../evidence/kernel-30.8.1/captures/correlated-string-target/); SHA-256 model `440a93e5f0e5f18f58505c4a28a3146130773d107aa9fd2467dfe2c833a2a097`, documents `a9e9c10786edd1827d6c2917a3c28d07b9260ce54f64991cc98c080c3dbffaf2` ascending and `685237126a96146fd775b2982dfe07060ba51b1fa88a1a31edb5161275301801` descending. **One** model carries both the filtered target and its `Length` dependent, so a single pinned model reproduces both retained artifacts; the earlier dependent-free run was re-taken against it and discarded rather than pinned beside a model that no longer produces it.
- `bytes-requests-and-artifacts`: SHA-256 requests `9db3c4bd78bf7762258ad92627800f3d03a51f2ddc70248a8f26ba202eab91a4` ascending and `cd88412962949ca6d5e43793faf89ca0ddd48b5bd83d74ab2173cf68ac63964a` descending; artifacts `65a1291288f9ffe262264447f85aad3e95e05e2363efa84cdea9fbd133277bdb` and `763b5aa1defc796bf0fa4e8df6927ae3f9fccb66935dd11d589798ce871550fd`, in that order. Both carry the target and its dependent, so the descending run independently reproduces the empty-candidate row at row 1 with its dependent reading `0`. Bounded raw calibration captures with no typed consumer: they do not run under `lake test`.
- `sync`: **mixed.** The carrier generality and the value vector *confirm* [`spec/07` §3](../../spec/07-repetition-and-iteration.md#3-the-filter-having-the--correlation-and-aggregation), which states the filter without a carrier restriction, so they raise no request. The empty-candidate absence shape is **new** to [`spec/09`](../../spec/09-computations.md), which describes `FirstFilledValue`'s stop-at-first reads and its clearing grounds but never the no-surviving-candidate case, and goes outbound as [`SPEC-2026-09-04-04`](../A12-DMKITS-SPEC-SYNC-LEDGER.md#spec-2026-09-04-04).

<a id="src-currentrepetition-host-iteration"></a>
#### `CurrentRepetition` is admitted exactly where the enclosing iteration binds its group, measured locally 2026-09-04

- `revision`: a12-dmkits `eded826354916ab71634b204218464a52a06a46b`, the sibling checkout clean before and after. `dmtool` 0.13.0, Kernel `30.8.1` built and runtime. Five `rule check` verdicts in one `batch`, every one `KERNEL_CONFIRMED`.
- `question`: [SG17](../SEMANTICS-GAPS.md#sg17--having-filter-leaf-and-connective-completion) carried a named-open row neither estate held — what a **non-iterating** rule does with a `CurrentRepetition` operand. a12-dmkits' 2026-09-04 handback measured the *computation* host (a repeatable target binds it, a root target draws `MVK_NO_WILDCARD`) and its shipped catalog asserts the rule-host case in prose, which is not measurement ([`LF132`](../LEAN-FINDINGS.md)).
- `claim`: **the operand is admitted exactly when the enclosing iteration binds the named group.** One model, one operand spelling, two rule placements: `CurrentRepetition(/Rep/Rows)` is **admitted** in a rule whose error field lies in `/Rep/Rows`, and refused `MVK_NO_WILDCARD` in a rule placed at the nonrepeatable `/Rep`. The short spelling `CurrentRepetition(Rows)` gives the identical refusal from the same host, so the verdict follows the host rather than the reference form.
- `controls`: both rule placements carry a plain `FieldFilled` condition that is **admitted** at each locus, so neither shape is refused for an unrelated placement reason and the `CurrentRepetition` operand is isolated as the cause. Without that pair the refusal would be attributable to the root-level rule shape itself.
- `not-about-repeatability`: **`CurrentRepetition(/Rep)` — a nonrepeatable group — is admitted from the rule at `/Rep`.** So the gate is not "the named group must be repeatable" and not "the host must be a repeatable rule"; it is exactly whether the host's iteration binds *that* group, with a nonrepeatable group trivially bound at its own locus and its index constant. That row is what separates the binding account from the repeatability account, which every other row here satisfies equally.
- `two-binding-sources`: **the marker selects which environment must carry the coordinate, and an operand's star is a binding source in its own right.** From the same non-iterating host, an aggregate `Sum(/Rep/Rows*/Base Having CurrentRepetition(/Rep/Rows) > 0)` is **admitted** — the star reopens `Rows` inside the filter and that suffices for the *unmarked* reference — while the identical shape with `CurrentRepetition($/Rep/Rows)` is refused `MVK_NO_WILDCARD`, because the marked form reads the captured environment and only the enclosing iteration fills it. The aggregate with no filter and the same aggregate with an ordinary field leaf in the filter are both admitted, so neither the whole-document rule shape nor the filter position is the cause.
- `two-levels`: **the two sources compose, and a third code separates the scope gate from binding.** With a host iterating the outer level over an operand starring only the inner one, the full 2x2 is: inner unmarked **admitted**, inner marked `MVK_NO_WILDCARD`, outer unmarked **admitted**, outer marked **admitted**. So the candidate environment carries the reopened inner level *and* inherits the bound outer one, while the captured environment carries the outer alone — which is why the marker decides only on a reopened level. The outer row's both-spellings result is the redundant-marker rule of [`SPEC-2026-09-03-07`](../A12-DMKITS-SPEC-SYNC-LEDGER.md#spec-2026-09-03-07) holding for a repetition reference rather than a field one, and an outer *field* reference in both spellings is admitted in the same batch as its control.
- `confound-found`: the first pass ran the outer rows **without** an in-scope conjunct and both came back `MVK_NO_ITERATION_FOR_WILDCARD` — the filter's own scope gate, not a binding verdict, because an outer-only condition carries no reference into the filtered list's reopened level. Recorded because the two gates share a subject and differ by one conjunct, so a reader who takes those rows as binding evidence concludes the outer level is unbindable when it is simply out of scope.
- `explains-the-pair-precondition`: this is why the self-exclusion comparison needs its level *both* star-reopened **and** host-bound: `CurrentRepetition(Rows) != CurrentRepetition($Rows)` contains one reference of each kind, so it needs both sources at once. The conjunction recorded earlier as a topology precondition is therefore a consequence of two simpler rules rather than a rule of its own.
- `group-carrier-closes-a-residue`: **the marker works on a group operand and the group carrier behaves exactly like the field one**, which closes the residue [`SPEC-2026-09-03-04`](../A12-DMKITS-SPEC-SYNC-LEDGER.md#spec-2026-09-03-04) recorded as open — an out-of-scope group leaf as a filter's *sole* condition under the marker. It is refused `MVK_NO_ITERATION_FOR_WILDCARD`, and so is the **unmarked** spelling, so the marker is not the cause and the missing in-scope reference is. Beside one in-scope conjunct **both** spellings are admitted, which is the redundant-marker rule again: the group named sits on a bound-but-not-reopened level. `GroupFilled` is therefore a second construct that reads the captured environment, answering half of [SG19](../SEMANTICS-GAPS.md#sg19--repetition-reference-binding)'s remaining question.
- `route-limit`: `rule check` narrows the kernel deliberately by requiring the error field to lie inside the rule group, so a non-iterating rule the Kernel would admit on other grounds is refused by this verb. That narrowing does not reach these rows, because each placement's own plain-condition control is admitted through the same verb.
- `instrument`: `FieldFilled` takes an **unbracketed** path and brackets denote a value reference, so `FieldFilled([/G/F])` is `MVK_UNEXPECTED_TOKEN`. Three rows measured nothing until the catalog's own `validExample` settled the spelling; recorded because the code names a token rather than the operand form.
- `limit`: one model, one nesting depth, `en_US`, static admission only with no runtime index observed here. Not measured: a two-level host binding only an outer level, a `CurrentRepetition` operand inside a filter whose host is non-iterating, and the index's runtime value from a nonrepeatable group.
- `sync`: **mixed, and the split matters.** The rule-host and nonrepeatable-group rows *confirm* a12-dmkits' catalog prose and complete the computation-host row it measured, so they raise no request. The two-binding-source rows *correct* that same catalog line, which predicts the admitted starred-filter row refused, and go outbound as [`SPEC-2026-09-04-03`](../A12-DMKITS-SPEC-SYNC-LEDGER.md#spec-2026-09-04-03). [`spec/07` §3](../../spec/07-repetition-and-iteration.md#3-the-filter-having-the--correlation-and-aggregation) carries both, and demotes its own earlier pair precondition to a consequence of the two sources.

<a id="src-self-exclusion-and-nested-filter-runtime"></a>
#### `CurrentRepetition` self-exclusion, a correlated filter on a per-row computed target, and a nested `Or`, measured locally 2026-09-03

- `revision`: six `rule check` decisions through two `batch` invocations, then one `apply` of nine ops and one `computation add`, then `:adapter:kernelProbe` with `observe: ["validateFull", "compute"]` over three documents. a12-dmkits `acced5d6012b15c0c3145d2a236e61bf2ad74246` on `main` with `source.state: CLEAN`, `dmtool` 0.13.0, Kernel `30.8.1` built and runtime, both codegen strategies with `enginesAgree: true` on every row; every authoring child returns `verification: KERNEL_CONFIRMED`. Sibling `git status --short` empty before and after each run. One model with one repeatable level, a per-row error field, and a per-row computed Number target.
- `question`: four [SG17](../SEMANTICS-GAPS.md#sg17--having-filter-leaf-and-connective-completion) items were statically admitted with no retained runtime — explicit self-exclusion by `CurrentRepetition`, a correlated filter on the **computation** arm, `Or` nested under `And`, and `Or` mixing leaf kinds. Two carry Lean laws with no external witness, so they are exactly the reuse the [carrier rule](../../CLAUDE.md) says must be measured rather than inherited.
- `self-exclusion-is-a-complement-pair`: **the two polarities partition the candidate set and their counts sum to the unfiltered one.** On three rows with every operand filled, the inequality's count is `2` on every outer row, the reflexive equality's is `1`, and the unfiltered count is `3`, each laddered to an exact value rather than a threshold. The two wrong accounts fall to different halves: an *implicit* self-exclusion makes the reflexive spelling keep nothing, and a marker-blind reading — comparing each candidate against itself — makes the inequality keep nothing and the equality keep everything.
- `the-count-varies-with-the-excluded-row`: the four-row document is the sharper separator, because the inequality's count is no longer uniform. With the fourth row's operand absent, the inequality fires its `== 2` rung on rows 1 to 3 and stays silent on row 4, whose exclusion leaves three filled operands; the reflexive rung fires on rows 1 to 3 and not on row 4, whose own operand is absent; and the unfiltered rung answers `3` on all four. No self-exclusion-blind account produces a count that depends on **which** row is excluded.
- `correlated-filter-on-the-computation-arm`: **`$` binds the computed target's own row**, measured at exact per-row values rather than ladder thresholds. A per-row computed `Sum(Lines*/Qty Having [Lines/Amt] > [$Lines/Amt])` answers `50, 30, 0` over ascending keys `1, 2, 3` with values `10, 20, 30`, and `0, 40, 10` over the rotated keys `3, 1, 2` with the same values. The reversed reading of the marker predicts `0, 10, 30` and `50, 0, 20`, so **each document refutes it on its own** rather than by disagreeing with the other. The all-dropped row answers an available `0` with `cleared: false, errored: false`, the same clean zero the validation arm gives an empty selection.
- `capture-source-is-the-instance-not-the-rule`: that a per-row **computation** supplies the captured environment at all is the load-bearing half, since [`spec/07`](../../spec/07-repetition-and-iteration.md) §3 described the capture as the iterating *rule*'s. The static half is a separate confirmation: `computation add` accepts the correlated filter on a repeatable target, so the Kernel gated the shape before any document was evaluated.
- `nested-disjunction`: a bracketed `Or` under `And`, whose disjuncts are a **presence** leaf and a **String equality**, selects exactly the intended two of four rows — closing the mixed-leaf-kind item in the same shape. Both flattenings are refuted by the ladder: read as one conjunction of three leaves the count is `0`, and as one disjunction it is `4`, and the `== 1` and `== 4` rungs are silent while `== 2` fires.
- `scope-gate-counts-references-not-pointers`: an unexpected result worth its own row. A filter whose **only** condition is `CurrentRepetition(Lines) != CurrentRepetition($Lines)` is admitted, and the same comparison with **both** sides marked is refused `MVK_NO_ITERATION_FOR_WILDCARD`; the reflexive unmarked spelling is admitted too. So the in-scope requirement is satisfied by an unmarked reference of any kind, even one that [`spec/01`](../../spec/01-data-model.md) states contributes no field pointer to the reference expansion. A gate implemented over that expansion refuses all three. The marker is isolated as the whole difference by holding the comparison fixed.
- `local-consequence`: every reading matches the existing Lean account with no clause change. The selection, the two per-row sum vectors, the complement pair, and both flattenings are locked in [`Conformance/Correlation.lean`](../../A12Kernel/Conformance/Correlation.lean); the three static repetition-leaf verdicts, including the exact refusal arm, in [`Conformance/FilledFieldStarCountHaving.lean`](../../A12Kernel/Conformance/FilledFieldStarCountHaving.lean). `reachesReopenedLevel`'s `compareRepetitions` arm already required an inner-origin reference at a reopened level, which is why the pointer-free case needed no repair — but it had no witness, and the all-marked refusal is that arm's negative control.
- `limit`: one repetition level, one Number carrier for the correlated filter, one aggregate operator, presence and String leaves for the nest. The computation-arm rows use clean cells throughout, so they say nothing about poison ordering — the [conjunction](#src-and-order-computation-arm) and [computation-arm](#src-filtered-aggregate-computation-arm) checkpoints own that. Not measured: self-exclusion under a nested filter, a correlated filter on a **non**-Number computed target, three-level nesting of the disjunction, and `CurrentRepetition` naming a group other than the filtered one.
- `sync`: locally originated, two additions. The capture-source generalization goes outbound as [`SPEC-2026-09-03-06`](../A12-DMKITS-SPEC-SYNC-LEDGER.md#spec-2026-09-03-06); the pointer-free occurrence-check fact extends the already-pending [`SPEC-2026-09-03-05`](../A12-DMKITS-SPEC-SYNC-LEDGER.md#spec-2026-09-03-05) rather than opening a third entry. The self-exclusion, correlated-selection, and nested-disjunction rows **confirm** existing clauses and raise no request.

<a id="src-and-order-computation-arm"></a>
#### A filter's conjunction short-circuits on a false operand too, so the computation arm's order sensitivity is not the disjunction's alone, measured locally 2026-09-03

- `revision`: `:adapter:kernelProbe` with `observe: ["validateFull", "compute"]`, sibling `git status --short` empty before and after each run. a12-dmkits `acced5d6012b15c0c3145d2a236e61bf2ad74246` on `main` with `source.state: CLEAN`, `dmtool` 0.13.0, Kernel `30.8.1` built and runtime, both codegen strategies with `enginesAgree: true` on every row.
