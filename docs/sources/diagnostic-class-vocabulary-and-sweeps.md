Split from [`static-admission-and-class-probes.md`](static-admission-and-class-probes.md), which keeps the complementary question of whether a given operand is admitted at a carrier. <a id="src-notind-declaration-properties-are-mapping-provenance"></a>
#### The `@NotInD` declaration properties never reach validation codegen or the runtime — the structural-mapping tool is their sole semantic consumer, source-derived locally 2026-09-07

- `route`: kernel source read read-only, no probe. **Mechanism** claim, discharged by enumerating the consumers rather than by reading the marker; see the trap row below for why the marker itself is not the discharge.
- `question`: [SG6](../SEMANTICS-GAPS.md#sg6--temporal-authoring-calendar-and-target-completion) carried `DateType.notInDCustomFormat` as an unmodelled declaration property with its effect unmeasured, reached by reading the Kernel's model types. It is not one property but a small class, and the class is what makes the answer cheap.
- `the-class`: six `@NotInD` members across five declaration interfaces — `getNotInDCustomFormat` on `IDateType`, `IDateFragmentType`, and `IDateRangeType`; `getNotInDCustomRangeSeparator` on `IDateRangeType`; `getNotInDCustomTrueValue` on `IConfirmType` and `IBooleanType`; `getNotInDCustomFalseValue` on `IBooleanType`. `DateTimeType` and `TimeType` carry a format and annotations and nothing else, so the DATE_TIME and TIME declarations have no member of this class at all.
- `claim`: **no `NotInDCustom*` member reaches `kernel-tool/` or `kernel-rt/`.** Its consumers are the model serializer, the type converter, the five field-type wrappers, the `a12internal` types themselves, the API interfaces, and one file outside all of them — so nothing in condition codegen, the parser's static checks, or the runtime can read it, and this project's validation-and-computation account correctly models none of it.
- `where-it-does-decide`: the exception is `SMMFieldTypeCheckUtils` in the **structural-mapping** tool, and there it is not inert — it *overrides* the ordinary format: `dateFragmentType.getNotInDCustomFormat().orElse(dateFragmentType.getFormatOfFragment())` and the same shape for the DateRange format and its range separator. So the property is an ExtMP-authored format that wins where it is consulted, and the boundary is which tool consults it. That tool produces a mapping structure and is outside this project's scope. Its DATE_TIME arm reads `getFormat()` with no override, consistent with the class not reaching that declaration.
- `trap`: **the `@NotInD` annotation looks like a no-effect marker and is not one.** Its own Javadoc says the annotated information "does not have any effect on the corresponding document" and "will be ignored while generating the validation code" — and `IDocumentModelConfig.getDecimalSeparator` carries the same annotation while reaching `CodeGeneratorService`, `CodeGenMetaModel`, and `JavaScriptLanguageHelper`. So the annotation marks ExtMP information not exported one-to-one to A12 models, which is a *provenance* claim, and its appended no-effect generalization is falsified by one of its own six uses. Cite the consumer enumeration, never the marker.
- `separator`: the enumeration is the whole denominator rather than a sample, and it distinguishes the two readings that matter — "inert everywhere" is refuted by the structural-mapping override, and "affects the semantics this project models" is refuted by the absence from both `kernel-tool/` and `kernel-rt/`. Either reading alone would have been wrong.
- `search-hygiene`: the first enumeration hit generated `/build/` copies and inflated the class with duplicates of its own members; the anchored exclusion this hub already prescribes is what produced the six.
- `local-consequence`: closes SG6's row. This project models no member of the class and now records why, so the row stops carrying an open question and no probe is authored for it.
- `sync`: none, and deliberately so. `spec/` never described the property, so nothing is corrected; a12-dmkits exposes no such key in its field-add schema or interpreter, so nothing there is wrong either. The peer's own Ja/Nein correction sits adjacent — it records that those tokens are not configurable on the A12 path and that the runtime override is `DarstellungsInformationIntern`'s — which agrees with this class never reaching `kernel-rt/` and is why no entry is raised.

#### The Kernel's code-generation check family is reachable from ordinary authoring, because the consistency check runs the generator, measured locally 2026-09-07

- `revision`: one `field add` against a model whose supported-character set was restricted first, at a12-dmkits `4178ef6d11ec7d31f5f2cfb956d12b1fb3f925ea`, `dmtool` 0.13.0, Kernel `30.8.1`, envelope `ok:false`, `valid:false`, `verification: KERNEL_CONFIRMED`. Both checkouts clean before and after.
- `question`: the codegen catalog looked like a separate surface no authoring verb could reach, and a peer estate treats its classes as outside its own denominator on the grounds that it never invokes code generation. Whether those classes are reachable decides whether two estates are counting the same thing.
- `claim`: **they are reachable, and the carrier is the ordinary consistency gate.** `CodeGenerationRule` is a registered `DocumentModelConsistencyRule` whose `checkModel` calls `generateValidationCode` and turns the generator's notifications into consistency problems, so every `checkConsistency` silently re-runs the validation code generator. Measured end to end: with the supported-character set restricted to `A-Z`, adding an Enumeration declaring the value `beta` is refused `MVK_ENUM_VALUE_WITH_INVALID_CHARACTER`, a `NoMetaModelCheckErrorType` class, through `field add`'s ordinary kernel gate.
- `claim`: **the report is per offending character, not per value.** The single value `beta` produces four diagnostics, one for each of `b`, `e`, `t`, `a`. A consumer counting diagnostics as defects would report four problems where one value is wrong.
- `separator`: ordering is the separator and it runs both ways.
