#### The runtime text parser is the declared **format's**, not the declared kind's, measured locally 2026-09-06

- `revision`: one `dmtool model check`, one `dmtool batch --observations` and one `:adapter:kernelProbe` request at a12-dmkits `fc2b3187c43d0ac29cb335628dde676b69464260`, sibling `git status --short` empty before and after, `source.state: CLEAN` in both artifacts. `dmtool` 0.13.0, Kernel `30.8.1` built and runtime, `validateFull`, `enginesAgree: true` on both rows.

Four static carriers already agreed on the format; which **text parser** runs over a cross-kind stored value is a runtime question none of them reaches.
- `prediction`: recorded before the run. If the format's parser runs, `12:30:00` in the DATE-declared field is a clock reading and compares equal to a TIME holding it, while a valid *date* text in that field is a format error. If the kind's parser runs, the opposite holds on both counts.
- `claim`: **the format's parser runs, and its value lands in that format's domain.** A DATE declared `HH:mm:ss` holding `12:30:00` counts as **one value** with a TIME declared `HH:mm:ss` holding `12:30:00`, so the cross-kind pair is not merely admitted but compares equal.
- `claim`: **and the kind supplies no fallback.** Storing `2024-03-05` — a perfectly valid text for the declared *kind* — in that same field draws `datumFormatFalsch` on the field, and the distinct-count rules over it fire at neither 1 nor 2, so the malformed cell leaves the count unavailable rather than answering. A kind-driven parser would have accepted that text.
- `claim`: **the rule is symmetric, and it holds on all three kinds.** The reverse direction agrees: a **TIME** declared `yyyy-MM-dd` and a **DATETIME** declared `yyyy-MM-dd`, each holding `2024-03-05`, both count as one value with a DATE declared the same, and a clock text stored in the TIME-declared *date* field draws `datumFormatFalsch` on that field while the untouched DATETIME/DATE pair still counts one. So neither direction is a special case of a kind that "really is" the other.
- `claim`: **the computation arm agrees, and a malformed cross-kind operand suppresses the outcome rather than clearing or erroring it.** A computed Number `Cnt = NumberOfDifferentValues(DClock, TClock)` reads `1` when both hold `12:30:00` and `2` when they differ; with the kind-valid date text in the DATE-declared clock field the artifact carries **no outcome at all** and reports the finding under `formalErrorsInOperands` instead. So the parser rule is arm-independent, and the formal failure reaches the computation as an operand error rather than as a value.
- `the-kernels-own-message-says-it`: the finding text on that DATE-declared field is *"a text naming the declared clock format as the only admitted one"* — the engine describes the field's rule as **its declared format**, on a field whose declared kind is DATE. That is the engine stating the rule this checkpoint measures, which is a stronger corroboration than a code alone.
- `code-names-the-format-not-the-kind`: the finding on a **TIME**-declared field is `datumFormatFalsch` — the date-format cause — because the declared format is a date one. A consumer mapping that code back to a field *kind* would report a date field; the code names the format the parser applied, and this is the row where the two visibly part.
- `separator`: the two documents differ in **one cell**, and the control pair fires in both. The pair of rows is what makes this a parser claim rather than an admission claim: row one shows the clock text is read, row two shows the date text is *not*, and either alone leaves a lenient two-parser account standing.
- `narrower-than-it-looks`: this **extends** a known rule rather than establishing it. That stored Date parsing is declaration-format aware, with a wrong-format value yielding `datumFormatFalsch`, is already retained ([checkpoint](date-range-construction.md#src-full-date-stored-input)); what was open is whether the format may be a **cross-kind** one and the parser still follow it.
