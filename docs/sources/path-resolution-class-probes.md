- `revision`: two `dmtool batch` runs, sixty-two children (forty-eight `rule check`, fourteen `computation add --dry-run`) over one model, at a12-dmkits `2304a684939621a8848e1261be9ab8e6278dc532` in the pinned measurement checkout (each verdict stamps its source state `CLEAN`), `dmtool` 0.13.0, Kernel `30.8.1` built and runtime. The measurement checkout's `git status --short` was empty before and after the second run.
- `question`: Lean's resolver refusals carried no class beyond the missing wildcard, and nothing here separated an unknown root segment from an unknown field. Do the four ways a plain field name fails — an unknown name below a known root, an unknown root segment, an unknown bare name, and a parent walk above the root — each draw one class whatever carrier reads the name? Does the root class read the first segment or the path's length?
- `prior`: [`kf284`](../../../a12-rulekit/docs/KERNEL-FINDINGS.md#kf284) measured the three classes on the condition carrier and [`kf356`](../../../a12-rulekit/docs/KERNEL-FINDINGS.md#kf356) the segment order on `Sum` over starred paths, a lone `/NoSuchRoot` included. This batch calibrates this project's carrier projections against them and finds no new class.
- `model`: the [entity-list checkpoint](static-admission-and-class-probes.md#src-entity-list-kind-empty-and-root-carriers)'s `ProbeE_DM.json`, same hash. Every rule row is `FieldFilled(Weight) And <operand>` with error field `/Item/Weight`. The computations are `[<path>] + 1` into `/Out/Count` and `FirstFilledValue(<path>, /Item/Title)` into `/Out/Target`.
- `claim`: **every carrier draws the same class for the same failure.** The carriers are the comparison `[F] == 1`, `FieldFilled(F)`, `Sum(F, Weight)`, `FirstFilledValue(F, Title)`, `AtLeastOneFieldValueIncludedInValueList(F In "x")`, `AtLeastOneGroupFilled(F, Title)`, `NumberOfFilledFields(F, Title)`, `NumberOfDifferentValues(F, Title)` and both computations. On each, `/Item/Nope` and `Nope` draw `MVK_INVALID_ENTITY`, `/Nope/Title` draws `MVK_INVALID_ROOT_GROUP` and `../Title` draws `MVK_TOO_MANY_PARENT_GROUPS`. Each `/Item/Title` control is admitted, the computations as previews.
- `claim`: **the root class reads the first segment, not the path's length.** On the comparison, `FieldFilled` and the numeric computation, a lone `/Nope` and `/Rows/Note` (a declared group read at root position) draw `MVK_INVALID_ROOT_GROUP`. `/Item/Nope/Title`, missing a middle segment below a known root, draws `MVK_INVALID_ENTITY`.
- `separator`: `/Rows/Note` refutes "the path has one separator", which predicts the entity class there, and `/Item/Nope/Title` refutes "some group segment is undeclared", which predicts the root class there.
- `carrier-choice`: a lone `/Item`, a declared root in a field slot, resolves to a group rather than failing, and its class is the carrier's: `MVK_NO_GROUPS_ALLOWED` on the comparison and the computation, `MVK_ROOT_GROUP_REFERENCED` on `FieldFilled`. It is not a resolver class, so the resolver projects nothing for it.
- `local-consequence`: `ResolveError` gains `unknownRootGroup`, checked before the path's shape and lookup, and `ResolveError.diagnostic?` projects it together with `invalidEntity` and `aboveRoot`. Every carrier that already delegated its resolver error to that projection now reports these classes, as does `groupListDiagnostic?` through its field arm. The computation projection is scoped to group counts, so its lock reads the class off the carried resolver error. The reference protocol keeps each input's former code.
- `assumption`: the delegating carriers not asked here inherit the classes on the shared-resolver account, which ten uniform carriers here and the two peer findings support. They are the correlation, semantic-index, custom-validity and date-range construction families, and the token and temporal families reached through their shape errors. No row on them is retained.
- `not-measured`: starred-path failures, which the [starred-path checkpoint](#src-starred-path-segment-order) measures; a turning-point label mismatch; and a String-pattern or `RepetitionNotUnique` key operand, which the [pattern and key checkpoint](#src-pattern-and-key-resolver-classes) measures.
- `bytes`: [`resolver-failure-classes-every-carrier/`](../../evidence/kernel-30.8.1/captures/resolver-failure-classes-every-carrier/) retains the model, both ops lists, the fourteen computation specs and both verdicts. The verdicts `obs.json` and `obs-segments.json` hash to `45c785994508afaf32beaeba0a14b248ba7304b9d350c1953af96fe920b20c66` and `19b051af5cca01c7ca480a3a3bc05bab8514b7c17331072e31eea68c10a30494`. They carry codes only, no diagnostic text. These are bounded raw captures with no typed local replay, so they are neither `L` nor `C`.
- `sync`: no clause. [`kf284`](../../../a12-rulekit/docs/KERNEL-FINDINGS.md#kf284) classifies which rejection each carrier issues as checker inventory rather than a language rule, and [`spec/11`](../../spec/11-messages-and-custom.md) already states the first-segment root gate for message arguments.
