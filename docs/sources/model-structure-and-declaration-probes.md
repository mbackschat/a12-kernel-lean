#### The four auto-generated rules carry three projections that partition them differently; source-derived on 2026-09-08

- `revision`: exhaustive reference search over the `../a12-kernel` checkout, by constant name and by string literal, across every tracked file type. **Source-derived, not measured** — this route reads the generator, and no probe here authors a multi-select group or a solitary index.
- `question`: the Kernel generates validation rules from model declarations rather than from authored conditions. Which rules does it generate, and what identity does each carry into a result a consumer reads?
- `claim`: **four generation types, and three projections over them that do not agree.** The runtime formal **code** separates all four. No two of the three are derivable from each other, and only the code is a faithful identity.
- `mechanism`: the generator dispatches each projection over the same closed generation type in its own switch, so the three partitions are independent by construction rather than by accident. It also marks a rule preliminary when and only when it has a generation type, which is the property distinguishing a generated rule from an authored one.
- `unraised`: **five neighbouring runtime formal codes are declared and never used** — an empty-field code, a blank-only-value code, two mandatory-check rule names, and a mandatory **group** code sitting directly beside the four live ones with a comment calling it an auto-generated rule. None is referenced anywhere in the checkout outside its own declaration and the message catalogs, by constant name or as a literal. Searched on this carrier rather than inherited from the parser-catalog result the [unraised vocabulary](../IMPLEMENTATION-MAP.md#cap-unraised-diagnostic-keys) owns ([`LF116`](../LEAN-FINDINGS.md)).
- `not-claimed`: this is a statement about that source tree at its reviewed revision, not a proof that no engine configuration emits the five. The two live codes new here, `uniqueValue` and `solitaryIndex`, are **not** measured on the engine; their identities are read from the generator and the capsule is `external evidence pending` on that half.
- `limit`: the generator's own trigger conditions — which model declarations produce which generated rule — are **not** modelled here; only the identity each carries. Their runtime evaluation is owned separately by the checked preliminary boundary.
- `sync`: **no `spec/` change.** Generator-side identity; the [implementation map](../IMPLEMENTATION-MAP.md#cap-generated-rule-identity) owns the checked slice.
