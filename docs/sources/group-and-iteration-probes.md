<a id="src-filter-condition-carrier-independence"></a>
#### The filter is checked and evaluated identically on every operand carrier, measured locally 2026-09-03

- `revision`: forty-five `rule check` decisions over one model through three `batch` invocations, a12-dmkits `acced5d6012b15c0c3145d2a236e61bf2ad74246` on `main` with `source.state: CLEAN`, `dmtool` 0.13.0, Kernel `30.8.1`. Every child returns `verification: KERNEL_CONFIRMED`, and the model passes `model check` valid with zero diagnostics, so each verdict is the real consistency oracle's on a kernel-valid model. Verdicts are read from each child's `valid` field, never from its exit code, which the batch contract warns does not separate a negative verdict from a failed run. Static admission only.
- `question`: this project lowers every filter through **one** shared step, so admitting a leaf or connective admits it on ten operand consumers at once, while the evidence covered the Number field-list count and the Number value aggregate. A cold review of that slice found the widening reaching nine carriers with no case, no law, and no record — the [carrier rule](../../CLAUDE.md)'s exact failure mode, since a shared call site shows nothing. Is the filter's condition actually checked the same way on every carrier?
- `claim`: **yes, admissions and refusals alike.** Eight carriers spanning every kind family those ten consumers cover — Number `Sum`, String `NumberOfDifferentValues`, String `FieldValuesNotUnique`, Date `NumberOfDifferentValues`, Boolean `NumberOfValueInFields`, Enumeration `NumberOfDifferentValues`, and `AtLeastOneDateRangeOverlaps` on a year-bearing and a yearless declaration — each admit all four filter shapes: the already-measured Number comparison, a presence leaf, a String equality against a literal, and an `Or`. Thirty-two admissions, no divergence.
- `not-vacuous`: an all-admitted matrix is consistent with a harness that tests nothing, so **every carrier carries its own live refusal channel**. A filter with no in-scope reference is refused `MVK_NO_ITERATION_FOR_WILDCARD` on all eight, and an ill-typed leaf — a Number field against a String literal — is refused `MVK_INVALID_COMPARE_TO_ENUM_OR_STRING` on the five carriers it was run against. The refusal **codes are identical across carriers** too, which is the stronger half: not merely that each carrier can refuse, but that it refuses the same condition for the same reason.
- `authoring`: two authoring facts cost a round each and are worth recording. A `DATERANGE` declaration's `(format, separator)` pair is allowlisted rather than the format alone — `yyyy-MM-dd` with `" - "` is rejected "The date range format is invalid" while `/` is accepted — and every shape needs the error field referenced by its condition or all of them collapse to `MVK_ERROR_FIELD_NOT_REFERENCED`.
- `local-consequence`: the shared lowering step is **right**, and now recorded as measured rather than assumed. Keep the two halves apart: that all ten Lean consumers call one selector makes *this project* uniform by construction, which is an argument about this code and not about the Kernel; the Kernel's own uniformity is what the rows above measure. The [coverage row](../implementation/repetition-and-paths.md#cap-star-selection-and-correlation) previously named eight carriers as admitted by assumption with this sweep as its evidence item; that item is discharged.
- `runtime`: **the filter also selects the same rows on every carrier**, measured on one document over seventeen further rules, both strategies agreeing. `Guard` is filled in rows 1 and 2 only, so a presence filter on it keeps exactly those two, and every carrier is read as a filtered/unfiltered **pair** whose two answers differ: String distinct 2 against 3, Date distinct 2 against 3, Boolean count 2 against 3, Enumeration distinct 1 against 2, String uniqueness silent against firing, and both DateRange overlap declarations silent against firing — the overlapping range sitting in the one excluded row. Each unfiltered half **fires**, so no carrier rests on a silent-only observation, and the String carrier's `== 3` spelling stays silent, pinning its filtered count at exactly 2 rather than at "some smaller number".
- `leaf-kind-does-not-change-selection`: on that same carrier, a String-equality leaf and an `Or` select exactly what the presence leaf selects — all three answer 2. So neither the operand's kind nor the leaf's own kind changes which rows survive.
- `unavailable-operand-is-uniform-too`: **a formally unavailable filter operand drops its own row and leaves the aggregate available on every carrier**, which was this sweep's own named residue and is the state where the two arms are known to diverge. With `Guard` malformed in the middle row instead of absent, each counting carrier is laddered against `== 0`, `== 1`, and `== 2`: `== 1` fires and both neighbours stay silent, on String, Date, Boolean, and Enumeration alike, so the surviving count is exactly one rather than an unavailable answer. The competing account — an unavailable operand making the whole aggregate unavailable — predicts every spelling silent and is refuted four separate times. Uniqueness and both overlap predicates answer correctly false over that one surviving row, every unfiltered control still fires, and the `Or` filter reading the same malformed cell drops its row exactly as the presence leaf does.
- `limit`: the runtime rows use one document per state, one selection shape, and `validateFull`. Not covered: `Custom` declarations, a filter on a group operand (refused outright at its own site), the `SumOfProducts` pair aggregate which rejects `Having` by its own rule, and **the computation arm on the non-Number carriers** — the one remaining place where a shape admitted and selected uniformly here could still behave differently, since that arm poisons on the same reached cell that validation merely drops.
- `sync`: locally originated, and it **confirms** the existing account — [`spec/07`](../../spec/07-repetition-and-iteration.md) §3 already states the filter takes the ordinary condition production, which is what predicts carrier-independence. No ledger entry; the sweep is what turns that prediction into evidence.

Does the one-level correlation account extend when a **two-star** operand reopens both levels, so that bare and `$` references to the outer level can actually differ?

- `poison-is-per-instance`: a reached poison is confined to the computed instance that reached it. The two-star correlated filter aborts **every** row, because every row's filter scans the malformed candidate — which is why the single-target rows could not settle this. The discriminator is a row-local aggregate, `Sum(/Nest/Lines/Items*/Qty)`, with one malformed `Qty` inside `Lines[2].Items` only: `Lines[1]` computes 7 and `Lines[3]` computes 5 while `Lines[2]` alone drops out. Both halves are what [`spec/09` §12](../../spec/09-computations.md) already states — a same-group star spans every row and one poisoned sibling aborts each row's dependent computation, against a star that binds the enclosing row above its first star — so this is that clause's direct witness on two contrasting carriers.

So the poison clears the stale value and does not mark the instance erroneous, and the earlier absence was simply a target with nothing to clear — exactly what [`spec/09` §3.1](../../spec/09-computations.md)'s operand table already says. That `limit` line is corrected rather than left standing.
- `captured-operand-invalidity`: on the validation arm a malformed **captured** operand makes every comparison non-true and the aggregate answers an available **zero** rather than becoming unavailable, measured with `Lines[2].Cap` malformed. The earlier rows put the malformed cell in a *candidate* operand, so this crosses the operand-position boundary by measurement rather than by assumption.
- `local-consequence`: none, and the match is structural rather than coincidental. `repeatableScope.any reopenedLevels.contains` gives the any-reopened-level rule, the leaf resolvers' `| _, _ => false` arm makes an outer-origin leaf contribute nothing to the gate, `anyLeaf` makes the check connective-blind, and `wellFormedForEnvironments` refuses `$Items` under an `Items` star exactly where the Kernel reports `MVK_NO_WILDCARD`. `CheckedStarFieldPath.firstStar` is the same mechanism `spec/09` §12 describes. Probed: the two-star correlated filter's Lean equivalent elaborates.
- `limit`: two repetition levels, one Number carrier, `Sum` and `NumberOfFilledFields`, one in-scope conjunct shape. Not measured: three-level nesting, `$` naming a level above the rule's own iteration, an out-of-scope **group** leaf under the marker, and whether a poisoned instance's clear is visible to later validation in the same call.
- `sync`: locally originated. The two scope-gate rules extend [`spec/07`](../../spec/07-repetition-and-iteration.md) §3 and go outbound as [`SPEC-2026-09-03-05`](../A12-DMKITS-SPEC-SYNC-LEDGER.md#spec-2026-09-03-05). The correlation, poison-scope, and clearing rows **confirm** existing clauses and add no request.

- `limit`: one repetition level, one Number carrier, one comparison family, `validateFull` only. Not measured: a correlated filter on the computation arm, `$` on a non-Number leaf or in a presence/String leaf, multi-level correlation where the star reopens a level below the captured one, explicit self-exclusion by `CurrentRepetition`, and whether an unbracketed `$` path is legal in any other position.

- `limit`: one String kind with no declared constraint, `validateFull` only, one literal. Not measured: a present-empty String operand under `!=` — this theory encodes the no-empty-String rule as absence, so it collapses onto the absent row here — an empty literal on the right of `!=`, an Enumeration carrier under the same operator, and the computation arm.
- `sync`: locally originated, and it **confirms** an existing clause rather than correcting one, so no ledger entry. Had `!=` fired, `spec/03`'s primitive default tier would have needed a String exception.
