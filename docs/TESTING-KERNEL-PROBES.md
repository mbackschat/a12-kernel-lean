# Kernel measurement procedures

Read the applicable sections when preparing or interpreting a kernel measurement. These procedures belong to the [testing methodology](TESTING.md); its [command ladder](TESTING.md#command-ladder), [assurance cadence](TESTING.md#default-assurance-cadence) and [tier gates](TESTING.md#tier-gates) remain authoritative. Reading this guide does not itself trigger its commands or authorize external actions.

### Read the kernel source first, then measure only the residual

A source read is free and instant, while a probe costs a JVM start, an authoring round trip, and a wasted window whenever a row is authored wrong. So when a claim is about a **gate** — which inputs a decision actually reads — open the kernel before opening a batch. This estate's two largest corrections were each re-derived in one read after many per-operator rounds: `DateUtils.checkOperationConsistentToDateFormat` gates the entire declared-kind operand class, and `CheckVergleichsBedingungImpl.checkDateType` gates the comparison and computed-target axis, both consulting the declared format and never the declared kind. [`SOURCES.md`](SOURCES.md#kernel-repository-entry-points) owns the location map and the layer-routing table; the method is here.

**Find the locus by its diagnostic code, not by its concept name.** Every static refusal carries an `MVK_*` code, and the method raising it is the gate. Grep the code across the parser's check tree, exclude generated copies with an anchored `/build/` path, then read the raising method's body and the fields it consults. A concept search for "target" or "assignment" returns the vocabulary the reader brought; a code search returns the branch the kernel actually took to that outcome.

**Read the code, not the comment.** The German Javadoc has matched the body every time it was checked here, which is why it is tempting and still not discharge: a comment is unverified prose, and only the method body and the fields it reads settle the claim. Cite a path and a symbol, never a pasted expression — under the clean-room rule source is read to learn which inputs a decision consults, and the Lean is then written originally.

**Read the absences too, and look for the one shared gate.** A directory listing is a checkable fact where a claim about a class's behaviour is not: no `FormatDefinitionZeit` exists, so all three declared temporal kinds share one `FormatDefinitionDatum`, which is why the runtime's computed-date store renders through the target's declared format whatever the kind. When several call sites are narrowed the same way, look for the single function gating them all; the class then collapses at once instead of one operator per round trip.

What a source read settles depends on the claim class, and the differences are not cosmetic:

| claim class | what the source read gives |
|---|---|
| **mechanism** | discharge, because the branch taken *is* the mechanism where an outcome is merely consistent with several. It is not independent of a probe against the same kernel, so a source read plus a matching row is one discharged mechanism and not two witnesses |
| **value** | a prediction worth authoring red. The executable case still lands in the owning conformance module |
| **reachability** | nothing at all. Whether a legal model expresses the shape is measurement-only, and reading a gate never shows that a declaration reaches it |

So the order is source first, then a probe for the residual alone: what a **runtime** stores or renders, whether an admitted shape is authorable, and any cross-class interaction one method body cannot show. Record which half came from which layer, because a checkpoint that merges them overstates both.

### The kernel-runtime probe route

**Scan the local checkpoint headings before building a model, not only the peer's findings.** Each `docs/sources/` checkpoint leads with a `####` line carrying its whole claim, its oracle and its date, exactly as the peer's entries do, so `grep -n '^#### ' docs/sources/*.md | grep -i <carrier>` answers *who already owns this question* in one screen across all of them. Do this even when an earlier search returned a plausible anchor name: an anchor names a topic and a heading states an outcome, and reading past a heading is how a whole probe round gets spent re-measuring a retained result. The failure is silent, because a redundant measurement agrees with the record it duplicated ([`LF175`](LEAN-FINDINGS.md)).

A kernel **runtime** question is checked against the maintained `:adapter:kernelProbe` task before it becomes an `EXP-` request. [`SOURCES.md`](SOURCES.md#engine-routing-rule--pick-the-layer-by-the-question-not-by-habit) owns the route's identity, contract pointers, and claim limits; what belongs here is how to drive it without touching the sibling. Author the model with the structured `dmtool` verbs as usual, keep the request file, its model, its documents, and the artifact **outside** `../a12-rulekit/` or under an already ignored path there, and pass absolute paths so nothing resolves into the sibling's tracked tree. Check `git -C ../a12-rulekit status --short` before and after: it must be empty both times, because `producer.source.state` records `CLEAN` or `DIRTY` into the artifact and a `DIRTY` artifact is exploration only, never retained evidence. Record the reviewed revision, `dmtoolVersion`, and both kernel versions from the artifact header rather than from the environment, and pin retained bytes by SHA-256 together with the request that produced them, since `schemaVersion` alone no longer determines the artifact's shape.

Use it demand-driven, one coherent family at a time, exactly like every other evidence route: an internally closed capsule may still land `external evidence pending`. The route has been exercised from this repository; [`SOURCES.md`](SOURCES.md) owns each family checkpoint and its exact hashes. Every further use must choose a family whose observation shape the artifact plainly carries and include a negative control in the same request.

**Seed every computed target and put the nearest settled form beside the new one in the first run.** A target seeded to a value no document reaches carries both its computed value and its implicit message type in one artifact, where an unseeded target carries the value alone; a settled twin in the same model, such as a fixed group beside a below-star one, decides a form-specific reading in-run instead of across two captures that also differ in model. Tabulate messages by `field` before reading a target's type ([`LF190`](LEAN-FINDINGS.md)). The below-star group-count capsule of 2026-09-24 spent three runs where one run so authored would have answered.

### Five measured throughput rules — apply all five to every sweep

**The instrument is not the bottleneck and never has been.** A `rule check` row costs about 0.12 seconds,
so a 140-row session spends roughly 35 seconds inside the Kernel. Everything else is authoring rows and
writing prose. These five rules each address a measured cost, and they are standing practice rather than
advice; a sweep that skips one is slower for a reason already paid for.

1. **Select the batch from the untouched list, never from the family the session happens to be in.**
   [`CONFORMANCE-COVERAGE.md`](CONFORMANCE-COVERAGE.md) — regenerated in about four seconds — carries the
   untouched refusal classes by catalog with the observation route for each. Working forward from a
   family measures what is convenient; working backward from that table measures what is missing. This is
   the rule with the largest effect on yield per row and it costs nothing.
2. **Generate the rows; never type a matrix by hand.** [`make-probe-ops.sh`](../scripts/make-probe-ops.sh)
   emits `ops.json` from a declarative spec with field/condition/message aliases and a `cross` product,
   plus one spec file per `comp`/`ccross` row for `computation add --dry-run`, so the same authoring effort produces hundreds of rows instead of dozens. It also expands `\n`, `\t`
   and `\u{XXXX}`, which is how a control character or a supplementary-plane scalar reaches the Kernel
   without being smuggled past the shell. Eleven rows were lost to hand-typed repetition in one session
   before this existed.
3. **One checkpoint per sweep, not one per family.** Prose cost is roughly fixed per checkpoint at around
   eighteen keyed rows, so a 400-row sweep across four catalogs costs the same writing as a 40-row batch.
   Widening the sweep is therefore the cheapest way to cut documentation overhead per measured class.
4. **Pay for a missing route once, deliberately, rather than avoiding it repeatedly.** The largest
   untouched block needs a document probe rather than a static one, and it stays untouched precisely
   because no session has set that route up. A session spent opening a route is worth more than the same
   session spent adding rows to a route already open.
5. **Resolve every operator spelling from the catalog *before* generating, then pre-flight the
   conditions.** This is precondition 1 below applied to a generated matrix, where the cost multiplies:
   one wrong spelling in an alias is inherited by every row that uses it. Generation makes the fix cheap
   — correct the alias, regenerate, re-dispatch — but it does not make the mistake cheap. The first
   sweep written under these very rules lost eleven of thirty-one rows to bare field names where the
   expression grammar requires `[Brackets]`, which the catalog's own `validExample` shows; that was the
   fifth recorded instance. Where a row's condition *is* the subject, a plain message makes every row
   its own pre-flight and no separate batch is needed.

Rules 1 and 3 also compose: select several untouched blocks that share one model, generate their rows in
one spec, dispatch them in one `batch`, and write one checkpoint whose `denominator` row names every
block the sweep covered.

**A sixth candidate, kept as a technique rather than built.** A set difference between the `MVK_` codes
named in `spec/` and the codes the theory handles finds a clause that reached prose and never reached an
executable owner:

```sh
grep -oh 'MVK_[A-Z_]*' spec/*.md | sort -u > /tmp/spec-codes
grep -roh 'MVK_[A-Z_]*' A12Kernel/ | sort -u > /tmp/lean-codes
comm -23 /tmp/spec-codes /tmp/lean-codes
```

Run once on 2026-09-22 it returned 29 codes, 28 of them honest scope exclusions — the parser layer and
name legality — and one a real defect: a measured class the theory refused to decide. That ratio is the
reason it stays a technique. Gating on it needs an allowlist for the 28, and an allowlist is maintenance
that rots invisibly; a second audit reaching for this is the signal to build it, and one run is not the
repeated measured cost the standing tooling authorization asks for. It reads best beside rule 1, when the
next batch is being chosen.

### Read the grammar or the checker first, then measure only the residual

**The highest-yield move measured so far is not a wider batch — it is reading the Kernel's own grammar,
localized terminal bundles, or checker method before authoring a single row.** It converts a guess into a
denominator, and the denominator is what makes a batch worth running.

Three instances, each of which changed the result rather than merely confirming it. Reading
`FullChecks_ErrorTextParameterParser.checkIndexFieldRef` replaced a three-arm guess about the index
terminal with the checker's own **ten** classes, four of which fell in one batch. Reading
`GrammarOnly_ErrorTextParameterParser.g4` replaced a list of noticed parameter spellings with the
parser's **eight** alternatives, which is how three live forms that no probe had ever tried were found —
including two that skip a gate every other form carries. Reading `LexerTerminals_de`/`_en` gave the exact
**ten**-terminal bilingual table, so `RootGroup` was identified as the English spelling of `LfdNr` rather
than measured as a mystery.

The method, in order:

1. **Find the production or the checker method** that owns the surface, not the prose about it. A grammar
   file states the alternatives exhaustively; a checker method states its refusals in throw order.
2. **Enumerate what it can refuse**, and write that list down as the batch's denominator before authoring
   any row. A class named with the reason no route reaches it is a result; a class silently absent is not.
3. **Measure the residual only** — the rows the reading could not settle. Reading never discharges a
   reachability or value claim ([the discharge rule](../CLAUDE.md#%EF%B8%8F-hard-rule--discharge-a-claim-before-stating-it-or-flag-it-and-surface-it)),
   so every arm still needs its row; what the reading removes is the rows spent on arms that do not exist.
4. **Keep the reading's denominator in the checkpoint**, as its own `source-first` and `denominator` rows,
   so the next session inherits the list instead of re-deriving it.

The catalogs are the same kind of reading at the level of the whole estate:
`error_messages_en.properties` under `../a12-kernel/` enumerates every refusal class the Kernel can name,
and [`CONFORMANCE-COVERAGE.md`](CONFORMANCE-COVERAGE.md) turns that into the current untouched list with
the route for each block. **Select the next batch from that list rather than from whichever family the
session happens to be in** — working forward from a family measures what is convenient, working backward
from the untouched list measures what is missing.

### Three batch preconditions, each paid for by a wasted round trip

The throughput rules above own why the batch mechanism is not the bottleneck; what costs time is authoring a row wrong and reading a grid wrong. These three preconditions are measured, not stylistic: every one of them has been paid for more than once.

**1. Consult `dmtool operators <id>` before authoring any condition, and treat it as a required step rather than advice.** Every surface failure recorded so far was already documented in that entry's `validExample` or `constraints`: an infix operator spelled as a call, `AtLeastOneDateRangeOverlaps` given a comma list where it takes `A In B`, `AddHours` given a clock where it takes a date-time, a bare `Time` where it takes components. Each cost a batch or a round trip, and each was one command away from being avoided.

**2. Put the liveness control and the diagonal control in the same batch as the question.** A grid whose every cell agrees establishes nothing until something in it fires the other way. All-refused has meant a fixture defect (a separator the format does not take), a reader defect (a computation preview carries no `valid` key when admitted), and a wrong error field (the customary `FieldFilled(Anchor) And` prefix dropped so every row drew `MVK_ERROR_FIELD_NOT_REFERENCED`). All-admitted has meant a gate that was never reached. In each case the control is what distinguished the measurement from the mistake, and adding it afterwards costs a second window.

**3. Read the whole grid before attributing any cell.** The tell for a mis-authored row sits in a *neighbouring* row more often than in the row being read — a bare date literal lexing as a Number was diagnosed from the adjacent cell drawing a scale code, and a spelling defect was identified because its own matching control refused too.

### Measure a gap's premise before weighing its options

When a gap carries a **representation decision** across sessions, the next action is to measure the premise it rests on, not to weigh the options again. Two long-standing decisions dissolved this way rather than being taken: the temporal distinct count's atom question (a checked cell already carries a decoded value, so neither rejected candidate was needed) and the extrema's interval element type (measurement settled it as two ordinary arms over existing orderings, no interval). Both premises were one batch away and had never been measured; both had been re-weighed instead. [`LF157`](LEAN-FINDINGS.md) owns the pattern and [`LF142`](LEAN-FINDINGS.md) the earlier instance. **A dissolution is itself a claim with a scope**: the second one was first dissolved on the wrong ground — a refusal measured on the partially known carrier, read as covering the component-omitting one it does not reach — and only the second measurement closed it, which is the check [`LF159`](LEAN-FINDINGS.md) now owns.

The specific reading error to watch for is an operator's **absence from an upstream restriction list** taken as permission. A list that says "the following restrictions apply" promises a set of restrictions, never the whole set; inferring admission from silence is a positive claim resting on a negative existential, which only measurement discharges.

### Two static routes, not one: `rule check` and `computation add --dry-run`

`dmtool rule check` answers a validation-rule question. A **computation** question has its own static route, and it is the same cost: `dmtool computation add --dry-run <spec.json>` is a read-only, kernel-gated preflight that writes nothing, and `batch` dispatches the `computation` verb exactly as it dispatches `rule` — so a mixed queue runs in one JVM start like any other. Together they put every static gate in the estate, validation and computation alike, on a route measured in seconds.

The spec is `{computedField, alternatives, messages}`, and `dmtool schema computation add` prints the authoritative shape rather than requiring one to be reconstructed; an intentionally empty `{}` also names the missing required properties in its own diagnostics, which is the faster way in. Both `alternatives` and `messages` need at least one entry, and a locale must be full (`en_US`, never `en`).

Two practical notes from its first use. A `--dry-run` outcome of `preview` is the admission verdict — it is not `valid: true`, so an envelope reader keyed on the rule route's field reports nothing. And the spec files are separate arguments, so **write the ops with bare filenames and run from the directory holding them**: an absolute path reaches the retained ops bytes and carries a username into evidence, which the [no-machine-specific-data rule](../CLAUDE.md) forbids in a committed artifact. Sanitise before pinning, then re-run so the retained bytes are the ones that actually ran.

**A rule `rule check` refuses still reaches the Kernel through `model check`.** `rule check` requires the error field inside the rule group and refuses the rest with the instrument's own `RK_ERROR_FIELD_OUTSIDE_GROUP`, which is stricter than the Kernel, so every containment row on the rule arm is out of its reach. Write each rule into a scratch model's JSON instead, as a `Rule` element of its rule group whose `errorEntityRelPath` is relative to the rule, and run `dmtool model check`: each diagnostic names its rule in `where.rule`, so one model carries a whole grid, and a one-rule model confirms the attribution. Retain a code-only projection keyed by rule, never the envelope, whose summaries quote the Kernel's messages ([first use](sources/group-list-and-capacity-probes.md#src-validation-below-star-placement)).

### Structured `dmtool` probes and feedback

Use the unchanged source-shipped `dmtool` route when a bounded capsule needs to author a focused model shape, ask the real kernel consistency oracle whether that shape is legal, or obtain exploratory interpreter corroboration without changing a12-dmkits. Resolve the JVM launcher once per working session with `DMTOOL="$(../a12-rulekit-measure/scripts/prepare-dmtool-source.sh)"`; do not invoke a previously installed path directly, select a native image, download a release binary, or install another copy. **The checkout is `../a12-rulekit-measure`, not `../a12-rulekit`** — the owner-approved read-only measurement clone pinned to the exact a12-dmkits revision [`SOURCES.md`](SOURCES.md) records, whose whole purpose is that a peer session working the primary checkout can no longer close the window ([provenance](SOURCES.md), [carve-out](../CLAUDE.md)). Verified live 2026-09-06: `dmtool` 0.13.0, source `fc2b3187c` clean, kernel `30.8.1` built and runtime, catalog verified against `30.8.1`. Both checkouts must still read `git status --short` empty before and after every run; the Gradle build writes only ignored outputs. The sibling's own tracked `bin/dmtool` shim is one of those paths: it resolves whichever launcher is already installed and never rebuilds, so once the sibling advances it keeps reporting the older revision it was built from while `--version` still reads `clean`. Only the preparation script compares that provenance against the current commit, which is the whole reason to go through it. The preparation command refuses a dirty checkout, reuses an installed JVM launcher only when its reported source is the exact current commit, otherwise rebuilds `:cli:installDist`, then rechecks the revision, worktree state, and launcher provenance before returning its path — which is why a pinned checkout does not weaken provenance: the launcher is still proved to match the exact commit it was built from. Run `"$DMTOOL" --version` before the first probe and record the exact source revision, clean state, `dmtool` version, and built/runtime kernel versions. Read the complete [a12-dmtool skill](../../a12-rulekit/skill/SKILL.md) before the first probe in a working session and follow its structured-authoring boundary: never inspect, export for inspection, or hand-edit raw DM JSON. From the [2026-08-30 handback](SOURCES.md#src-2026-08-30-reconciliation) that boundary is **scoped rather than absolute**, and the skill states the exception itself: to reach the kernel's own verdict on a declaration `dmtool` refuses locally, hand-write that shape into a **copy** of the model and run `model check`. That is measurement, never authoring — never persist from the copy and never keep it — and it is the only sanctioned hand-edit. This route is appropriate only when an existing command exposes the claim's own observation domain; if it does not, leave external evidence pending or request the missing capability upstream instead of copying or patching a harness.

Keep a probe small and reproducible. **Never pipe the output of any command that settles a claim through `head`, `tail`, `cut`, or another viewport command** — the rule is about load-bearing output, not about ceremony, so a `grep` over sibling source counts exactly as a `dmtool` invocation does, and [`LF112`](LEAN-FINDINGS.md#lf112--a-command-whose-output-settles-a-claim-is-an-observation-even-when-it-is-only-a-grep) records the shipped false claim that narrower reading produced. Count the matches with `wc -l` before reading them, and for a claim that something does **not** exist either enumerate exhaustively or state the exact scope and matched count beside the claim: a truncated result is indistinguishable from a complete one, and the tell is weak by construction, because a `head -N` that returns exactly N lines is not evidence that N was the end. Read the whole envelope, or project it through a structural reader such as `python3 -c` over the parsed JSON that fails loudly on a missing key. **Exhaustive is not the same as unfiltered:** name the content roots a negative claim is actually about — `rg -n PAT docs spec A12Kernel evidence` — rather than searching the whole repository, whose `.git` and build caches pollute the denominator the claim then cites. One defect report against a12-dmkits was filed on the strength of an 11-line output read through `head -10`, and cost the peer a full measurement round for a renderer that was never broken. Record the clean a12-dmkits revision plus `dmtool` and kernel versions in [`SOURCES.md`](SOURCES.md), preserve the sibling's exact HEAD and empty status before and after, and discard the evidence if either changed. Write scratch models only beneath an already ignored project-local or sibling path. Orient with `model describe`, inspect exact declarations with `field read`, consult `operators <id>`, apply known setup edits atomically with `apply`, and prefer one caller-tagged `batch` for a read-only separating matrix so JVM startup is paid once. **Re-run [`check-doc-hygiene.sh`](../scripts/check-doc-hygiene.sh) after the commit, not only before it.** Its artifact-hash and revision-citation checks read `git diff HEAD~1..HEAD` rather than the working tree, so a citation introduced by the commit under test is invisible to a pre-commit run and fails only once it has landed. A clean pre-commit pass is therefore not evidence for those two checks; the post-commit pass is. **A `batch` child splits a two-word verb, and the manifest's own spelling does not work**: write `{"verb": "computation", "args": ["add", …]}`, not `{"verb": "computation add"}`, which the dispatcher passes through as a single argv token and every child then fails `exit 2` with an unmatched-arguments stderr and no envelope. A uniform exit 2 across every child — including a control that must be admitted — is that shape, not a verdict; measured at a12-dmkits `9c86459b3` and reported as an instrument note. **Resolve each operator's spelling from `operators <id>`'s own `validExample` before authoring probe expressions**, because a wrong spelling is refused by the parse gate as `MVK_UNEXPECTED_TOKEN` and reads exactly like a semantic refusal: `Length(/Path/Field)` takes a bare reference, and the bracketed `Length([/Path/Field])` is a parse error rather than an admission answer. `batch` is stateless per-operation dispatch and never rolls back: a successful child write remains after a later child fails, so never use it where all-or-nothing mutation is required and always inspect every child exit/result. After full dispatch, `data.dispatched` is true and `data.allExitedZero` records whether every child exited zero. In ordinary batch mode, outer `ok` and process exit 0/1 follow that child-exit aggregate. In `batch --observations`, outer `ok` and the process exit instead report whether every child was dispatched and the observation artifact was written, so a complete capture containing a deliberate negative-control child exits 0 with `ok:true`, `outcome:completed`, `written:true`, and `data.allExitedZero:false`. A preflight refusal reports `outcome:rejected`, writes nothing, and exits 1; an artifact-write failure reports `outcome:error` and exits 70. Always inspect every child verdict and the independent exit aggregate. Persist at least one accepted candidate through a structured write, read it back structurally, and finish with `model check`; pair it with the nearest negative control and exact rejection code. Design each negative control so that only the gate under test can fire: the derived-scale gate precedes the calculated-field self-reference gate, so a self-reference control whose derived scale also mismatches measures `MVK_INVALID_COMPARE_DEC_PLACES` and never reaches `MVK_ERROR_REFERENCE_TO_CALCULATED_FIELD`. That pair is a fixed precedence, but precedence is not the general rule and a diagnostic list is neither a defect count nor a gate order. Measured at a12-dmkits `566edd6f1`, one condition carrying both a comparison defect and an *unreferenced* error field reports the comparison code alone, while the same condition with a *missing* error field reports two codes and suppresses the comparison; the suppression is the Kernel's, not the tool's. So a single code never establishes that only one gate objected, two codes never establish two defects, and a row whose error field or operand is not itself the subject must be re-run with that confound removed before its code is attributed. The [instrument handback](SOURCES.md#src-dmtool-2026-08-22-instrument-handback) owns the measurement and its denominator. This persisted-read-back consistency check is required while `dmtool` remains a comparatively new evidence route, because a successful dry run alone does not establish that the intended structure survived authoring. From a12-dmkits `35c116cd`, a converted read-back whose operand position is not category-threaded returns the verbatim `Opaque` form with a preservation-backstop message rather than a silently different operation; that is an honest refusal of the *conversion*, not a persistence failure, so read the shape from the verbatim text and claim no exact structure for that position.

**First ask whether the verb emits an envelope at all, because `schema result` cannot tell you.** It describes the envelope's inside, so a reader that consults it still assumes the wrapper exists; `dmtool schema <verb>` answers the prior question per verb, as `returns.kind`. Measured at the current pin, 128 of 147 operational profiles are `RESULT_ENVELOPE` and 10 are `RAW_JSON`, alongside 6 `RAW_TEXT`, 2 `EMPTY_STDOUT`, and one `NDJSON_STREAM`. Every `RAW_JSON` verb emits a document that *is* the payload — a model from `model new`/`model expand`/`profile synthesize`, a JSON Schema from `model export-jsonschema`, a catalog from `operators`/`diagnostics`/`manifest` — so there is no outcome for an `ok` to report, which the same contract states as `topLevelOk: EXECUTION_COMPLETED` rather than `OUTCOME_SUCCEEDED`. Reaching for `data` on one of those raises `KeyError` rather than misreading silently, but the assumption that produced it is the one this paragraph exists to stop.

Read `schema result` before writing any envelope reader. Its three orthogonal axes are already exact: `ok` reports whether the operation succeeded, `valid` appears only where a gate actually produced a consistency verdict, and `verification`/`engine` names who vouches for it; which optional keys appear follows what the invocation did, never which verb was called. The first two axes cross in both directions, so `ok` never classifies a child alone: a `rule check` rejection is `ok:true` with `valid:false`, while a kernel-gated `computation add --dry-run` the kernel refuses is `ok:false` with `valid:false` and `verification:KERNEL_CONFIRMED`, because the gate arbitrated even though the operation did not succeed. A child that established nothing carries no `valid` at all, and that is the only failure signature. Guessing a key instead fails silently: a reader that looks for a verdict in the wrong place reports every case as unverified, which reads as "admitted" and can turn a kernel rejection into a false coverage claim. Classify every result by command rather than by the binary name. `model check`, `workspace check`, `rule check`, and computation dry-run validation call the real kernel consistency oracle and can support a static `KERNEL_CONFIRMED` claim. A rule's error text is now reachable read-only through repeatable `rule check --message <locale>=<text>` arguments; the message locale must be declared by the model or dmtool refuses it with `RK_UNDECLARED_MESSAGE_LOCALE`. That front-end refusal is deliberately stricter than Kernel semantics, where undeclared-locale text is silently unexamined. Error-text refusals from `rule check`, `rule add --dry-run`, `model check`, `rule modify`, `computation add`, and `computation modify` use the standard stdout envelope with `ok:false`, `valid:false`, `verification:KERNEL_CONFIRMED`, and one `diagnostics` entry per reported problem. Do not scrape stderr for this channel. `model eval`, `rule eval`, `model compute`, and `model seed` execute the kernel-free a12-dmkits interpreter and provide triangulation only; they do not establish kernel runtime behavior. dmtool identifies that engine as `DM_INTERPRETER`, reports declaration and instance counts separately, and gives every repeatable computation item a canonical instance pointer plus its declaration path; cite those coordinates when retaining interpreter observations and never infer row association from output order. Use exact-pointer `model eval` controls where they help locate malformed inputs. A cause-blind `cleared` computation item does not establish which operand failed first, and a structured operation that dmtool cannot author remains outside this route even when another a12-dmkits surface supports it. The exact instrument revisions are recorded at the [2026-08-23 reconciliation checkpoint](SOURCES.md#src-2026-08-23-reconciliation).

**A malformed model is a fourth channel, and from a12-dmkits `ad4d5ff64` it is distinguishable from the other three.** A model the loader cannot read reports `outcome: refused`, exit 2, one `PRECHECK` diagnostic coded `RK_MODEL_INPUT_INVALID`, and **no** `valid` or `verification` key — truncated JSON, an unknown property, a wrong value type, and an absent required rule or computation reference all land there. That absence is the axis to key on: loading failed before any gate ran, so a row from such a run establishes nothing about the Kernel and must never be recorded as an admission or a refusal. This matters most to the sanctioned hand-edit-a-copy route, where a slip in the edit and a Kernel refusal previously arrived as the same undifferentiated failure; before that revision the same input reported `outcome: error` and exit 70 under a summary asserting an internal tool defect ([provenance](SOURCES.md#inbound-2026-09-08-instrument)).

Treat any contradictory schema, misleading catalog entry, missing observation coordinate, ambiguous engine provenance, malformed diagnostic, nonportable environment requirement, or output that fails an independent structured cross-check as a blocker for the affected evidence claim. Stop using that route for the claim, report the blocker to the user, and either narrow the claim to what was independently verified or leave it external-evidence pending. An ordinary kernel rejection is not a `dmtool` defect; report a tool issue only when the catalog, command envelope, schema, structured round trip, or operating contract misstates or obscures what happened.

Give a12-dmkits feedback as soon as a tool or skill defect makes semantic attribution unsafe, causes avoidable probe cycles, or blocks an observation this route's own contract already promises. **This channel is for the instrument only.** When the kernel's behavior is itself the open question and no route can reach it, the request is an `EXP-` experiment request under [the ledger's kinds of entry](A12-DMKITS-SPEC-SYNC-LEDGER.md#entry-kinds-and-routing), which owns the complete routing test; a note carries no acceptance condition or reviewed-revision receipt and therefore cannot hold a representation-blocking question. One blocker may split across both: the missing tool capability is a note, the semantic question it blocked is an entry. A useful report names the exact a12-dmkits revision, `dmtool` and kernel versions, command family, minimal structured reproducer, expected and actual behavior, semantic-evidence impact, safe workaround if one exists, and concrete acceptance criteria.

**Deliver it to the a12-dmkits session directly**, in a message carrying those facts, and record nothing further. That is the default because the peer reads it in the same session, disposes it there, and reports back — where a note only reaches the peer if someone carries it. See [peer-session coordination](TESTING-PEER-COORDINATION.md#peer-session-coordination) for how to reach that session and what to do when it is unreachable.

Write a dated Markdown note **only** when no peer session is reachable, or when the user asks for a handoff artifact. Once a note has been handed off, treat it as immutable: a later finding from the same date receives a new sequenced note such as `A12-DMTOOL-FEEDBACK-YYYY-MM-DD-02.md` rather than changing the bytes already under review.
