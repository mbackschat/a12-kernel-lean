## Calendar-day probe

An isolated Python standard-library consumer implemented one two-level `Europe/Berlin` field-backed `AddDays` route with an enclosing DateTime source, leaf Number amounts, exact addresses, source-first poison, complete outcomes, source-relative actions, and separate-destination application. Four wrong accounts covered elapsed shifting, flattened addresses, eager amount poison, and destination-relative classification.

The first implementation self-reported PASS but produced `03:30` for the adjacent spring-gap row. Lean required `01:30`. The handover described the exact result only in a distant DifferenceInDays paragraph, so the owning calendar-day clause was made retrieval-safe and the run repeated from a fresh context.

| Run | Status | Cost | Result |

| `execute-datetime-day-01` | red | about 15 minutes | Cheap implementation and four passing mutations, but authoritative reconciliation rejected the spring-gap result. |
| `execute-datetime-day-02` | green | about 30 minutes | Correct `01:30`, zero-preserving `02:30`, and historical `22:30`; exact result/application; all four mutants killed. |

The accepted consumer used 291 nonblank implementation lines, 78 natural-test lines, and 76 mutation-runner lines with no dependency beyond Python's standard library. No renewed A12 research or semantic guessing remained. Kernel correspondence, wider temporal profiles, topology, later validation, protocol, research closure, and shipment remain outside this result.
