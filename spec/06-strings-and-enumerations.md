## Part A — §7 Strings and patterns

- **`Length` and min/max-length checks count UTF-16 code units exactly.** There is no code-point folding or grapheme clustering in any length-bearing path. A decomposed combining sequence `e` + `U+0301` counts 2, and a supplementary-plane character would also count 2 code units, although realistic legal-character policies reject it first. Grapheme clustering appears only in legal-charset acceptance, never in a count.
- **`PatternMatched` / `PatternViolated`** evaluate the **whole** value (implicitly **anchored** — the pattern must match the entire string) with Java `Pattern` semantics under the Groovy-dynamic observation anchor. A fired pattern comparison is always a **VALUE** error (there is no fillable branch); an empty string violates no nonempty authored pattern ([§2](03-empty-and-required.md)). Length and pattern consumers see the evaluation-normalized text: a permitted `"AB\r\nCD"` measures 5 UTF-16 code units and a whitespace-class pattern sees one `\n`, while the stored text remains unchanged ([§3](02-logic-and-formal-errors.md#b3-what-puts-a-cell-in-the-third-state)). Patterns can still be a performance/security risk if written to backtrack, for example `(a+)+`.
- **`+` is overloaded** — numeric **addition** between Number operands, string **concatenation** between strings. **There is a general dispatch rule, and `+` is the one infix operator that does not ask the arithmetic question at all** ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-21-corrections)). `*`, `/`, `-` and `^` each demand a number of *both* operands and refuse anything else `MVK_NO_NUMBER_FOR_CALC`; `+` demands neither, admitting two numbers or two string-**like** sides and refusing a mixed pair `MVK_NO_STRING_OR_NUMBER_FOR_ADD`. String-like means STRING together with a **CUSTOM** declaration and a predefined type; a date, a range, a Boolean and a Confirm are neither numeric nor string-like and so fail both of `+`'s arms — measured over all seven declared kinds against each of the four numeric operators. A direct Enumeration field with **effective display remapping** is refused under that same addition class; absent labels and identity-only labels pass this gate, as does category access. The restriction concerns the immediate operand shape, not every Enumeration result. Two consequences of ordering: the kind walk **pre-empts** both arity gates at the node it types, so a text in a two-division chain draws the kind class alone where the same chain with a number there draws `MVK_TOO_MANY_DIV_FOR_CALC`, while an inner node that already failed its own division walk answers first (`[a] / [b] / [a] + [s]` draws the division class); and `^` asks the kind question **before** the exponent's scale, so a non-numeric exponent never reaches `MVK_INVALID_NUMBER_FOR_EXP` ([§5](04-numbers-and-decimals.md)). An inner operation's **result** type is what the outer operator judges. The pitfall stands beside the rule: a string literal shaped like a date parses as a *date constant* and cannot be concatenated ([§6](05-dates-and-time.md)).

`CheckOperationImpl.checkWithoutDisplayValues` inspects an immediate field-value operand only. `{[E]} + "x"` therefore passes the display restriction even when `[E] + "x"` fails, while `{[E] + "x"}` still fails at the inner addition. Grouping retains the Enumeration result type; only the completed concatenation has String type. The same distinction holds for key-selected Enumeration fields. An admitted Enumeration operand contributes its stored value, not its display label; a category contributes its projected category value. An empty operand contributes no text, and a wholly empty concatenation clears a computed String target. Two grouped Enumerations concatenate by the same rule, and first-filled over Enumeration operands contributes its selected stored value ([reviewed handback](../docs/sources/inbound-handbacks.md#inbound-2026-10-09-extensions)).

### Pattern admission and execution

Condition-literal patterns (`PatternMatched` / `PatternViolated`) and declared STRING or predefined-type patterns have the same observed model-legality contract: the source must compile as a Java `Pattern` and then pass the `PatternUtils.isPatternValid` check, whose finite blacklist is below. **That blacklist is the whole of the second gate, and it reads the pattern's SOURCE TEXT rather than the pattern the source spells.** An earlier version of this clause said a full-kernel model *additionally* rejects uppercase `\P{L}`, and took that as evidence of an undiscovered exclusion behind the displayed expression; the refusal was real but the subject was wrong, and both halves are now measured ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-21-corrections)). The refused source was `\P{L}+`, caught by the possessive alternative because it ends in `}` followed by `+`, and the escape takes no part: bare `\P{L}` is **admitted** while bare `\p{L}` is refused, the escape held fixed across the pair. Two rows confirm the textual reading from the other side — `a\*+` is refused because the source carries `*` then `+`, although it spells an ordinary escaped star with a quantifier, while `a\+\+` and `\[a\[b` are admitted because neither spells a listed adjacency. The nested-opener scan ends at **any** `]`, escaped or not: `[a\][b]]` is admitted, although Java reads its second `[` as a nested class, because the escaped delimiter ends the scan before it ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-30a-regex-operands)). **The two loci draw different codes, the same two words swapped**: a refused condition literal is `MVK_INVALID_PATTERN` and a refused declared field pattern is `MVK_PATTERN_INVALID`, so a consumer keying on one sees nothing at the other. Passing this gate establishes Java legality and nothing about portability to another regex host.

For either condition operator, the [shared constant-pair gate](05-dates-and-time.md#comparison-entry-and-grouping) runs first. The pattern checks then require an ungrouped field-value operation on the left (`MVK_INVALID_PARAMETER_FOR_PATTERN_COMPARISON` otherwise), String result types in both slots (`MVK_INVALID_TYPE_FOR_PATTERN_COMPARISON` otherwise; a constant is typed first, so a valid date or `HH:mm:ss` literal, `True` and `Today` on the right each draw it, while `"12:30"` is a String there and admitted, [inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-26d-constant-typing)), and a constant on the right (`MVK_MISSING_CONST_IN_PATTERN_COMP` otherwise), before validating the pattern source. A grouped String field and a String concatenation fail the left-shape gate; a grouped String literal is legal on the right. A Number field against a String field reports the type refusal before the missing-constant refusal. A pair of String literals reports the earlier constant-pair refusal ([checkpoint](../docs/sources/static-admission-and-class-probes.md#src-comparison-entry-gates)).

```text
[?+}*]\+                 possessive quantifiers
(?<...                   every such prefix, including lookbehind and named capture
(?>...)                   atomic/independent groups
\A \G \Z \z \a \e \p \Q \E
an unescaped [ after an earlier unescaped [ with no ] between them
```

Ordinary positive and negative lookahead (`(?=...)` / `(?!...)`) are not categorically blacklisted. Nor does passing kernel admission imply JavaScript portability: known legal separators include inline flag forms, `\R` / `\h`, Unicode `\s`, dot/code-point differences, unmatched backreferences, non-nested class intersections, `\x{…}`, `\N{…}`, `\X`, and `\b{g}`. Generated static-Java agrees with the normative Java runtime on the exercised cases. The kernel TypeScript target instead wraps the raw source as `new RegExp("^(?:" + p + ")$")`; any resulting difference is a characterized strategy split and is never adopted over the Groovy-dynamic result.

An **empty authored condition pattern** is admitted statically but fails when its call is reached, before the supplied String's availability is inspected. This is a runtime failure, not either operator's ordinary match result: a preceding false guard hides it, while a subsequent false condition cannot suppress it. Validation catches it at the enclosing rule and emits that rule's VALUE error; partial validation still applies error-field dispatch relevance, but operand nonrelevance alone does not hide a reached call. Computation clears the affected target and blocks alternative fallback; formal-input prechecking can prevent the call first, while independent computations continue. Having filters carry the same failure to their enclosing rule or computation, including a reached declared-but-uninstantiated candidate. These outcomes are measured for both operators against nonempty twins ([checkpoint](../docs/sources/computation-scheduling-probes.md#src-empty-pattern-execution)). This authored-condition behavior is distinct from the inactive empty declaration pattern below.

For a nonempty ordinary STRING input, the declaration-owned formal check applies its first-failure clauses in this order: forbidden CR/LF on the raw text; CRLF→LF normalization when line breaks are permitted; the effective declared pattern against the complete normalized value; positive minimum length; positive maximum length. Pattern failure therefore wins over either simultaneous length failure. An absent or explicitly empty declared pattern source constructs no runtime matcher at this declaration locus; this is distinct from using the empty source as an authored `PatternMatched`/`PatternViolated` condition. Empty input bypasses the pattern and length clauses through the ordinary empty-value boundary, and every declared-format failure makes later value consumers observe formal unavailability.

### A.1 Raw-type Strings (`noValueValidation`)

The String-only `noValueValidation` option declares a **raw type**. Its value remains in the document but is never interned for evaluation. Model validation closes every value window:

- comparisons, value lists, computation operands, coercions, and any other value operation are rejected with `MVK_INVALID_RAW_TYPE`;
- message interpolation of the value is rejected;
- `Length` is authorable only as the whole rule condition `Length(f) > c`, or the mirrored `c < Length(f)`, using strict GT/LT and a constant written without a decimal point whose exact integer value lies in `-2147483648..2147483647`;
- the same strict whole-rule shape with a decimal-point spelling, a fractional value, or an integer outside that interval is rejected with `MVK_INTERNAL_ERROR`;
- every other `Length` shape, including computation preconditions, is rejected with `MVK_INVALID_LENGTH_OF_RAW_TYPE`.

Shape admission precedes bound admission: an overlapping form such as `Length(f) >= 5.0` reports `MVK_INVALID_LENGTH_OF_RAW_TYPE`, not `MVK_INTERNAL_ERROR`.

The one legal `Length` shape is **not a runtime rule**. Code generation eliminates it in both strategies and lifts `(field, c)` into the generated meta-model's maximum-length metadata, so it never fires for either filled or empty values. Presence semantics over the same cell remain ordinary: `FieldFilled`, quantifiers, and counts can observe whether content exists without reading its value.

The JVM/JavaScript rule is UTF-16 code-unit length. a12-dmkits' [`AbsLengthDiffTest`](../../a12-rulekit/adapter/src/test/kotlin/io/github/mbackschat/a12/dm/adapter/laws/AbsLengthDiffTest.kt) differentially locks the BMP combining-sequence discriminator—decomposed `e` plus U+0301 counts as two rather than one grapheme—while supplementary-plane characters counting as two UTF-16 units is source-characterized and internally locked by Lean's [`StringLength` conformance cases](../A12Kernel/Conformance/StringLength.lean), not by retained kernel differential evidence. CRLF ingestion and raw-type closure are differentially locked by [`CrlfLengthNormalizationDiffTest`](../../a12-rulekit/adapter/src/test/kotlin/io/github/mbackschat/a12/dm/adapter/laws/CrlfLengthNormalizationDiffTest.kt) and [`NvvRawTypeDiffTest`](../../a12-rulekit/adapter/src/test/kotlin/io/github/mbackschat/a12/dm/adapter/laws/NvvRawTypeDiffTest.kt).

> **Non-normative implementation note.** Represent String length as UTF-16 code-unit count after the ingestion normalization described in [§3](02-logic-and-formal-errors.md#b3-what-puts-a-cell-in-the-third-state); do **not** use Unicode scalar count or grapheme clusters. Do not turn the bounded admission evidence into an invented portable grammar: a faithful pattern capsule must separate Java compilation plus the source-text blacklist specified under [Pattern admission and execution](#pattern-admission-and-execution) from whole-value Java-Pattern execution and record target splits explicitly, or fail closed outside its declared fragment. The checked elaborator rejects every raw-type value window, while the one admitted strict `Length` declaration desugars to metadata and produces no core runtime rule. No additional runtime value state is needed because legal evaluation cannot read the raw value.

### A.2 Legal charset definitions and atomic matching

The model's `supportedCharacters` is a cross-kind baseline for stored/input values under the full formal check, except raw Strings declared with `noValueValidation`, which bypass formal value checking. Within full-format checking, a technical length guard runs first: authored text longer than 99,999 UTF-16 code units is refused `wertZuLang`, whatever the declaration says. It counts the text before line-break normalization, so a supplementary character and a CRLF pair each count two, and it is distinct from a declared maximum length. Charset acceptance follows, then leading/trailing ASCII-space rejection, then the basic declared-format check. A failure stops that sequence: an unsupported character preempts a pattern or custom-validator finding, including a reserved custom report. These are input gates, so a custom validator receives the original text only after they succeed ([ordered-input checkpoint](../docs/sources/domain-ingestion-probes.md#src-checked-string-ingestion-k13)). Computed-result target checking uses the reduced basic check and deliberately omits the technical length guard, this charset and the leading/trailing-blank baseline ([§11](09-computations.md#4-the-stored-form--a-computed-value-lands-as-a-string-in-the-targets-shape)).

An absent definition or an empty list selects the default non-surrogate Basic Multilingual Plane policy. This is different from a list containing an empty string: `[]` is the default, while `[""]` is a malformed definition. A nonempty entry is legal only in one of these forms:

- one non-surrogate BMP UTF-16 unit, defining a singleton;
- exactly three UTF-16 units `X-Y`, where `X` and `Y` are non-surrogate BMP endpoints and `X ≤ Y`, defining an inclusive range; or
- a surrogate-free combined atomic entry of two or three UTF-16 units whose Unicode grapheme-cluster decomposition is shorter than its UTF-16 representation, so the entry contains a combining sequence. The entry may contain more than one cluster, but matching consumes the whole configured entry atomically.

An empty entry, a surrogate-bearing entry, a reversed range, a combined entry longer than three UTF-16 units, or a plain multi-character sequence such as `ab` with no combined grapheme is malformed. Shared prefixes are otherwise legal: configured `e`+combining-acute and `e`+combining-grave may coexist, and a complete atomic entry may be a terminal prefix of a longer one. The pinned ambiguous-overlap rejection is narrower than “no overlap”: for a combined entry whose grapheme-cluster decomposition is `p₁ … pₙ · s` with at least one prefix cluster, reject it only when every prefix cluster is independently representable by a configured singleton, range, or atomic entry and the final cluster `s` is a proper, different-length UTF-16 prefix of another configured atomic entry. This is why the focused `q`+combining-acute+`r` entry is rejected when `q`+combining-acute and `r`+combining-grave are also configured, without making the legal shared-prefix cases illegal.

Runtime matching proceeds left-to-right. At each input position, walk the configured atomic-entry trie and consume the longest complete terminal entry selected by that bounded walk. If no complete atomic entry matches, test exactly the leading code point against singleton/range membership and consume it only when admitted; otherwise the value fails the charset formal check. Every successful step advances because empty entries are forbidden and every accepted atomic entry is bounded. A configured combined entry admits only its complete sequence: its base, combining mark, reversed sequence, suffix, or repeated component is not independently legal unless another singleton, range, or atomic entry admits it.

Charset matching does not alter length semantics. `Length` and min/max checks continue to count UTF-16 code units, never grapheme clusters.

a12-dmkits' [`SupportedCharactersDefinitionDiffTest`](../../a12-rulekit/adapter/src/test/kotlin/io/github/mbackschat/a12/dm/adapter/laws/SupportedCharactersDefinitionDiffTest.kt) and [`SupportedCharactersGraphemeDiffTest`](../../a12-rulekit/adapter/src/test/kotlin/io/github/mbackschat/a12/dm/adapter/laws/SupportedCharactersGraphemeDiffTest.kt) lock the definition discriminators and atomic matching against both kernel strategies; [`LegalCharsetDefinitionTest`](../../a12-rulekit/interpreter/src/commonTest/kotlin/io/github/mbackschat/a12/dm/interpreter/LegalCharsetDefinitionTest.kt) and [`LegalCharsetGraphemeTest`](../../a12-rulekit/interpreter/src/commonTest/kotlin/io/github/mbackschat/a12/dm/interpreter/LegalCharsetGraphemeTest.kt) provide the peer portable controls.

### A.3 Custom field-type validation

A declared `CustomFieldType(name, minLength?, maxLength?)` delegates its value-specific acceptance decision completely to the named registered validator. The raw declaration preserves whether each length bound was authored; the bounds are callback context, not generic predefined-String minimum/maximum checks. The callback receives an effective minimum of the authored value or `1`, an effective maximum of the authored value or `999`, the effective locale, and the stored/display-value mode. The ordinary stored-document formal-check path supplies `isDisplayValue = false`; no behavior is claimed here for the unevidenced display-value mode.

The ordinary stored-document validator receives the original stored text. After acceptance or a reserved report that admits the value, evaluation caches exactly one non-overlapping CRLF-to-LF normalization pass; a lone CR is preserved. Value reads, `Length`, and computations consume that evaluated payload without repeating ingestion. Raw storage remains unchanged until a computation explicitly writes its target. The [custom-ingestion matrix](../docs/sources/custom-field-probes.md#src-custom-ingestion) distinguishes callback input from evaluated text, including repeated CR prefixes and dependent computations. Conversion-enabled presentation profiles remain outside this account.

For each relevant concrete-valued cell, the semantics obtains one custom-validation observation from a named pure, total oracle and reuses it for every consumer: automatic formal-message emission, authored-rule and candidate suppression, computation poison, and `RepetitionNotUnique` key filtering. An empty or nonrelevant cell is excluded before the oracle is sampled. **The sampling unit is the cell, never the distinct value:** two cells holding the same value are two observations, reported at their own pointers. Because the oracle is pure and total, that cardinality changes no verdict, and an implementation may memoize on the complete declaration/context/value key; keying on the bare value across declarations or contexts is wrong even for a pure oracle, and an oracle that is not in fact pure, such as a counting or logging validator, observes the per-cell count directly. The observation is either accepted or a project rejection carrying a required project error code and an optional message template. The project code is preserved verbatim in the formal report and, for an unavailable value, its suppression cause; it does not collapse to a generic constant.

The exact callback code `testIDNummer` reports a `VALUE_ERROR` with severity `ERROR` while admitting the normalized value. Case changes, suffixes and whitespace variants are ordinary rejections. The report does not add the cell to the custom-condition invalid-pointer set and does not itself exclude a message-cache key; a later duplicate-index finding can still make the cell unavailable. Full examination continues through either kind of custom finding. The core abort-on-formal-errors mode stops after either kind, including the readable reserved report. These are separate decisions: readability alone does not determine continuation. This account applies to the modern expanded-A12 profile; the legacy unique-entity profile has the separate [verified host boundary](../docs/sources/custom-field-probes.md#src-custom-legacy-profile).

In a supplied rejection template, every literal token naming the field as `$<fieldName>$` is replaced with that field's localized label under the established [label-resolution rule](11-messages-and-custom.md#part-a--13-error-message-interpolation); all other text remains unchanged. This implicit declaration-driven formal check is distinct from the explicit `Valid(field, "Name")` rule predicate, which invokes the registered validator as an authored condition, and custom field validation is distinct from [`CustomCondition`](11-messages-and-custom.md#part-b--14-customcondition--the-escape-hatch).

The checked Lean account requires every referenced validator name to exist in `World`; absence is a well-formedness/elaboration failure. Kernel 30.8.1 does not reject the missing registration while parsing the model — `checkConsistency` reports nothing — and **the loud failure belongs to the full check specifically**: `validiereFormat` returns valid and never consults the factory when its full-check argument is false, and the lookup that raises sits after that return. The computed-target basic checker also invokes custom format validation with this flag enabled; “basic” does not imply bypassing the registered validator. So a relevant concrete cell reaching an unregistered validator **under a full check** fails loudly, with a validator-missing exception in the cause chain naming the declared type; it is neither accepted nor converted into a generic formal rejection. **The failure escapes the full-check call, so the document receives no validation result at all:** the offending cell does not contribute a formal message beside the other fields', and every message that same document produces when the cell is empty is lost with the call. What the caller observes at the runtime API boundary is a generic invocation failure; the declared type name is one level below it, in the cause. An **absent** cell raises nothing and never calls the validator at all. Unqualified, the old phrasing over-claimed by omitting the full-check condition ([source checkpoint](../docs/sources/evaluation-and-application-routes.md#src-custom-field-type-spi)); the raise, its full-check site, its named cause, and the whole-call abort are separately measured on the engine here, with a value-absent and a field-absent control ([runtime checkpoint](../docs/sources/having-filter-probes.md#src-presence-confirm-custom-carriers)). The separate declarative predefined-type fallback continues to use the fixed `customFieldTypeInvalid` code; that fallback cannot replace or reinterpret the registered-oracle result.

**The supplied factory and the static registry are alternatives, not a fallback chain.** The registry is consulted only when no factory was supplied at all, so a static registration does not rescue a factory that answers empty. The explicit `Valid`/`Invalid` predicate differs from declared-field validation at its enclosing handler: a reached, nonempty valid String with an unregistered type name raises a lookup failure inside the condition, which aborts the rule and becomes one `VALUE_ERROR` message. It does not become a true predicate. Both standalone polarities therefore produce VALUE, but Boolean composition must preserve the failure until the rule handler; an unreached branch or empty/formally unavailable operand avoids lookup. Inside `Having`, this abort happens before the selected target read, including when that target is malformed; the resulting rule message has empty `referenced` and `fillToFix` sets. [Runtime calibration and source handler](../docs/sources/having-filter-probes.md#src-having-predicate-family) settle the mechanism behind the earlier [standalone observations](../docs/sources/evaluation-and-application-routes.md#src-custom-validity-route).

In a computation precondition, the same missing validator has a different effect: a filled valid operand makes both named-type polarities fail with target-local `berechnungsWertFehler`, clearing the target and poisoning dependent reads. Empty input bypasses registry lookup and clears cleanly; an already formally invalid operand propagates its own invalidity before lookup. An unreached guard does not invoke the validator. Both predicates pass the stored XML value to a registered validator; an Enumeration therefore supplies its stored token rather than its display label. [Named-type guard observations and source](../docs/sources/computation-scheduling-probes.md#src-type-validity-computation-guards) distinguish these boundaries.


**A registered custom field type is a triple, not a predicate, and a consumer that must host one owes all three operations.** Beside the acceptance decision above, the kernel 30.8.1 SPI declares a bidirectional representation codec: display-to-internal and internal-to-display, each mapping one string to a converted string plus an optional error message. The validator's own parameter object carries only the error-message locale and the two declared length bounds, so acceptance is decided from the value, that parameter, and the stored/display flag and from nothing else — no document, no sibling cell, no repetition context. That is what makes the per-cell reading above structural rather than assumed; the separate question of whether a given validator is also *pure* is treated below. **The codec has exactly one engine-side caller in the Java runtime, and it is opt-in.** `FormatDefinitionVordefiniert.convert` is the sole site, gated on the caller's own presentation information requesting custom-field-type conversion; the direction follows the ingress, XML selecting internal-to-display and everything else display-to-internal. **Neither arm runs on the ordinary `validateFull` path**, on either codegen strategy, where acceptance is called once with the stored-value flag false. So a custom-typed cell has two texts only for a caller that asked for them, and an implementation offering acceptance alone is complete for the default path rather than merely unrefuted ([checkpoint](../docs/sources/evaluation-and-application-routes.md#src-custom-field-type-spi)). The source-owned invocation order is full-input charset/blank checking, registered acceptance with the declared length bounds, then optional conversion of once-normalized text after acceptance. Custom bounds belong to the validator context; there is no independent ordinary-String min/max check before it. The presentation flag also supplies the acceptance call's stored/display mode. Conversion selects the converted string from the two-argument codec result; that caller does not consume the result's optional error message. Empty values bypass this path. These conversion-enabled invocation and result-selection rules are source-grounded, not a retained runtime calibration of host codec algorithms ([source checkpoint](../docs/sources/domain-ingestion-probes.md#src-checked-string-ingestion-k13)). The enumeration covers the Java runtime; the TypeScript runtime carries its own mirror site. The current interface is `ICustomFieldValidator`; the predecessor carrying a per-declaration configuration map is deprecated for removal in the pinned version, and a consumer should target the former.

Two consequences a consumer can rely on now. An evaluator or interpreter must accept a **registry** of these triples as host input, exactly as it accepts a clock, because acceptance is not derivable from the model. An analysis or SMT consumer may model the acceptance decision as an **uninterpreted predicate over the cell's text**, further parameterized by the two declared bounds, the effective locale, and the stored/display mode — that is the complete input list, and the locale belongs in it because nothing restricts a validator to using it for message text alone. **Locality is structural and determinism is not.** The SPI hands the validator no other input, so no analysis need fear a hidden dependence on another cell; but a validator instance is host-constructed and may carry state, so the purity this clause assumes is a contract expectation rather than a guarantee, and it is exactly what an uninterpreted function symbol encodes. A validator that is not in fact pure breaks the uninterpreted model in the same way, and for the same reason, that it breaks the memoization described above. The codec resists the treatment regardless, since an uninterpreted string-to-string function blocks most reasoning about the value it returns — which now matters only for a consumer that opts conversion in, since the default path never reaches it.

a12-dmkits' [`CustomFieldTypeContextDiffTest`](../../a12-rulekit/adapter/src/test/kotlin/io/github/mbackschat/a12/dm/adapter/laws/CustomFieldTypeContextDiffTest.kt), [`CustomFieldTypeRejectionCodeDiffTest`](../../a12-rulekit/adapter/src/test/kotlin/io/github/mbackschat/a12/dm/adapter/laws/CustomFieldTypeRejectionCodeDiffTest.kt), and [`CustomFieldTypeMessageDiffTest`](../../a12-rulekit/adapter/src/test/kotlin/io/github/mbackschat/a12/dm/adapter/laws/CustomFieldTypeMessageDiffTest.kt) lock the registered path against both kernel strategies, including the cardinality discriminator: one value occupying two in-cap cells of a repeatable group draws two observations at distinct pointers under dynamic Groovy, generated Java, and the peer interpreter alike (`CustomFieldTypeContextDiffTest.theSameValueInTwoCellsReachesTheValidatorOncePerCell`, whose control routes the peer cache through a value-shaped key and turns red at `expected: <2> but was: <1>`). [`CustomFieldTypeContextCacheTest`](../../a12-rulekit/interpreter/src/commonTest/kotlin/io/github/mbackschat/a12/dm/interpreter/CustomFieldTypeContextCacheTest.kt) checks the peer's one-observation consumer boundary for a single cell, which is why it could not establish the per-cell arm on its own.

## Part B — §8 Enumerations

### B.1 Comparison is by stored value, and direct-field comparability depends on effective display remapping

- Rule conditions compare the **stored enumeration value**, not the displayed text: write `[Country] == "F"`, not `[Country] == "France"`.
- An ordinary enumeration is **effectively display-bearing** only when at least one localized display differs from its stored value. No authored labels and labels that all repeat their stored values are both effectively textless for this rule.
- A direct plain-String field can be compared with an effectively textless enumeration field, but not with an effectively display-bearing one. Likewise, two enumeration fields are rejected when exactly one is effectively display-bearing.
- Two effectively display-bearing enumeration fields need not have identical declarations. For every locale common to both, a shared stored value must have the same display and a shared display must denote the same stored value. Disjoint mappings and non-overlapping locale sets are accepted.
- This direct-field gate is shared by `==` and `!=`. A String literal that is a valid stored or selected-category token and an already-checked category access follow their separate domain and projection rules rather than this field-to-field display gate.
- If either Enumeration operand is an already-checked category access, the display-remapping gate is bypassed. Its projected category token can be compared by `==`/`!=` with a direct String value, another category token, or a plain Enumeration's stored token.
- Operand shape matters on the String side: `{[S]}` and String-producing operations do not undergo the immediate String-field display gate. Grouping an Enumeration retains its domain and display policy, and grouping a String literal retains its constant-domain check. `FirstFilledValue` over text operands produces a String result, so its result does not carry an Enumeration literal domain. These shape distinctions, including first-filled over two Enumerations producing String, are corroborated by the [reviewed comparison matrix](../docs/sources/inbound-handbacks.md#inbound-2026-10-09-reconciliation) in both operand orders, with grouped valid/invalid literals and effective-display controls.

### B.2 Categories via `->`

Enumeration values can carry named **category** attributes, read with the `->` operator:

```
[Country -> AdministrationArea] != "EU"
```

The category mapping is **positional** (`values[i]` categorizes enum value *i*) and **many-to-one** — the comparison fires for *every* value sharing that category value. An empty enum rides the not-evaluated track, category hop or not.

That pairing is positional at **declaration** time too, and the kernel enforces it: a category's token list must have exactly as many entries as the enum has values. A shorter list draws `MVK_MISSING_CATEGORY_VALUE`, a longer one `MVK_MISSING_INTERNAL_VALUE`, and an empty one draws `MVK_MISSING_CATEGORY_VALUE` once per unclassified value rather than once for the declaration. **The per-element multiplicity holds on the surplus side as well as the shortfall side**, measured rather than transferred: two surplus tokens draw `MVK_MISSING_INTERNAL_VALUE` twice, so the count is one per misaligned *token* and not one per misaligned category ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-21-corrections)). **An enum declaring an empty `values` list never reaches this pairing at all**: the model is not buildable, with categories and without them alike, so a consumer pairing an empty left side against declared tokens reports classes the Kernel does not raise on that model. A second category is judged independently of the first, and a body carrying no `categories` member is admitted. Equal cardinality is the whole rule: same-length tokens **disjoint** from the enum's own values are admitted, which is what separates positional pairing from any set-membership reading, and a same-length reordering is admitted too. Every enum value therefore has exactly one category token, so a stored value the category does not map cannot arise.

**The declaration check collects its notifications rather than stopping at the first, so order and multiplicity are observable** ([checkpoint](../docs/sources/model-structure-and-declaration-probes.md#src-enumeration-declaration-notifications)). Every notification is an ERROR, and they arrive in six blocks. (1) Only under a restricted `supportedCharacters` list: one `MVK_ENUM_VALUE_WITH_INVALID_CHARACTER` per rejected UTF-16 code unit of each stored value, one notification per rejected index. A supplementary-plane scalar's high surrogate is rejected even under a range numerically covering it, and its low surrogate is judged alone, rejected unless a declared range numerically covers it; the one model measured declaring a supplementary range does not build: under `A-Z` the scalar counts as two, under `U+0020–U+FFFD` as one, and two scalars sharing a high surrogate under that range count once ([supplement](../docs/sources/model-structure-and-declaration-probes.md#src-sort-list-capacity)). (2) One codeless supplementary-plane notification for the whole field when any stored value or display label holds a supplementary-plane scalar, under every charset; BMP non-ASCII text does not raise it. (3) The arity classes above, with every category's `MVK_MISSING_CATEGORY_VALUE` notifications ahead of every category's `MVK_MISSING_INTERNAL_VALUE` notifications, whatever the category order; a stored value holding a supplementary-plane scalar draws no shortfall notification, although its position still counts toward the arity. (4) One `MVK_CATEGORY_VALUE_DUPLICATE` per repeated stored value and category. (5) One `MVK_INTERNAL_VALUES_DUPLICATE` per repeated stored value. (6) One codeless repeated-value notification per repeated stored value. Blocks 4 and 5 skip a repeated value holding a supplementary-plane scalar; block 6 does not. Identical notifications collapse, so the same rejected unit twice in one value, or the same surplus token twice in one category, counts once, while equal notifications from different categories stay separate. Repeated category tokens are admitted. The order of categories or values inside blocks 3 and 4 is not observable through class codes and is not claimed.

> **Non-normative implementation note.** Keep static comparability separate from runtime projection. For a legal ordinary enum declaration, retain locale-tagged `(stored, display)` facts, derive effective display-bearing status from `stored ≠ display`, and check the common-locale relation in both directions. Runtime evaluation compares stored tokens; `->` is a positional lookup over parallel stored/category vectors, so many-to-one mapping falls out directly.

### B.3 The value-list quantifiers — per-cell three-way classification ⚠

`AtLeastOne` / `No` / `NotAll` `…FieldValue(s)IncludedInValueList(f1, f2 In v1, v2, …)` expand **both** sides per cell (a starred entry contributes one cell per instantiated row) and classify each cell by the three-way state (filled / empty / not-check-relevant = UNKNOWN, [§3](02-logic-and-formal-errors.md)):

- **A scope gate outranks this whole kind gate, so everything in this bullet holds only once the level is bound** — either a non-repeatable carrier, or a repeatable one written with its star. On an **unstarred repeatable** level the kind gate is never reached and `MVK_NO_WILDCARD` answers instead, whatever the slot's kind and whatever its shape: a group, its fields listed out, and a single field all draw it alike. Starring the level binds it, the scope gate falls silent, and the kind classes below apply unchanged. A checker that implements the kind denominator without this precondition reports the wrong code on every repeatable carrier.
- The multi-field family admits String, Enumeration, Number **and CUSTOM** fields — four kinds, not the three the diagnostic names. **Ahead of that kind gate the field list must share one base type**, and a list that does not draws `MVK_VARYING_TYPES_NOT_ALLOWED` whatever its kinds ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-25e-value-list-base-type), [checkpoint](../docs/sources/static-admission-and-class-probes.md#src-value-list-base-type-cross-pairs)). The four temporal kinds share one base type and a custom declaration shares String's, so a Date beside a date fragment and a Time beside a DateTime pass it and meet the kind gate, and a String beside a custom field is admitted. Each other kind is a base type of its own: String beside Number, Date ([checkpoint](../docs/sources/static-admission-and-class-probes.md#src-value-list-quantifier-kind-gate-partitions-three-ways)) or Enumeration, Boolean beside Confirm or Date, Number beside Date, and a date range beside String each draw the class, in either order where both were measured. **On a list of one base type, every other declared kind draws one class, `MVK_ONLY_STRING_ENUM_NUMBER_ALLOWED`, and that refused denominator is complete:** DATE, TIME, DATETIME, DATEFRAGMENT, DATERANGE, BOOLEAN and CONFIRM. **The code's own name is a misleading oracle for the admitted set** — it lists three kinds over a set of four, because the underlying string-likeness test admits a predefined custom type. A consumer that derives the admitted set by complementing the refused one is right; a consumer that reads it off the diagnostic's name refuses a legal CUSTOM slot. **The gate does not read the operand's shape** — a homogeneous group, a two-field list, and a sole field of the same kind draw the identical class, so a consumer must not classify a group's expansion by a rule of its own. A group operand's expansion joins the base-type gate, so a group holding a String and a Date draws `MVK_VARYING_TYPES_NOT_ALLOWED` as the field list or opposite a String, and so does a group holding a Number beside or opposite a String, and a category read counts as an Enumeration there, so one opposite a String draws it too ([checkpoint](../docs/sources/static-admission-and-class-probes.md#src-field-value-read-predictions)). **NUMBER is inside the admitted set and is what shows this is a kind gate rather than a literal-agreement one:** against a String literal list a Number slot clears this class and draws `MVK_INVALID_TYPES_FOR_COMPARISON` one step later, in every slot shape ([checkpoint](../docs/sources/static-admission-and-class-probes.md#src-value-list-slot-kind-set)). A literal right side is available for String and Enumeration fields: plain String literals are unrestricted decoded String tokens, while Enumeration literals follow the selected stored/category union rule below. A multi-field Number form has no literal-list shape and requires a nonempty field-valued right side, and the two refusals show how that surface is closed: after `In`, a bare `1` is read as a **path** and draws `MVK_INVALID_ENTITY`, while `1.00` does not survive the parser at all (`MVK_UNEXPECTED_TOKEN`). **The scalar twin does not share this limit** — `FieldValueIncludedInValueList(Assessed, 1, 2)` is admitted in the same model — so the two carriers' literal surfaces are not interchangeable. The asymmetry is invisible from either carrier alone, and it is why an admitted Number control on the quantifier has to be field-valued. Field-valued forms match the value list against the first field's base type: a Time value beside a String one opposite a String field, a Number or an Enumeration value opposite a String field, a String value opposite an Enumeration field and a String value opposite a Number field each draw `MVK_VARYING_TYPES_NOT_ALLOWED`, and so does the scalar `FieldValueIncludedInValueList(Carrier, [PickupTime])` over a String and a Time. **A field-valued form admits a sole field on each side**, so its arity rule is not the entity-list family's ([§9](07-repetition-and-iteration.md)): `AtLeastOne…(A In B)` over two plain String fields is admitted, against a live gate in the same model — repeating the reference draws `MVK_DUPLICATE_PARAM1` and crossing the base kind `MVK_VARYING_TYPES_NOT_ALLOWED` ([checkpoint](../docs/sources/static-admission-and-class-probes.md#src-entity-list-sole-operand-arity)). Measured on `AtLeastOne`; the two siblings state the same slot rules and are not separately measured here.
- When the values side is a literal String list and the fields side contains ordinary Enumerations or category accesses, static admission uses the **union** of the selected domains: every literal must be a stored token of at least one direct Enumeration operand or a category token of at least one category operand, but need not belong to every listed declaration. The fields side is nonempty, preserves authored order, and rejects an exact repeated reference; direct stored access and named category access on the same physical field are distinct references.
- When the values side is another field list, both sides are nonempty and preserve authored order, and no reference may occur twice across the combined lists, nor a group beside its own member. **The construct asks its gates in five positions** ([checkpoint](../docs/sources/static-admission-and-class-probes.md#src-value-list-cross-list-repeat-order), [inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-25g-value-list-order)):
  1. the field list refuses its own repeat as it is built;
  2. it then asks its root, base-type and kind gates and its **value validation**, so a raw String draws `MVK_INVALID_RAW_TYPE`;
  3. the value list asks its root gate and the first field's base type, a field value list refusing its own repeat first;
  4. a repeat across the two lists comes next, an exact one drawing `MVK_DUPLICATE_PARAM1` and a group beside its own member, `Recipient In Recipient/RecipientName`, `MVK_DUPLICATE_PARAM2`;
  5. a field value list's value validation comes last.

  Every operand of both lists is resolved as the text is parsed, so a name resolving to nothing on either side draws `MVK_INVALID_ENTITY` ahead of a raw String's refusal on the other side ([checkpoint](../docs/sources/static-admission-and-class-probes.md#src-field-value-read-predictions)). Over a String `Ref`, a Number `Amount` and a Date `Due`, `AtLeastOne…(Ref, Amount In Ref)` and `(Ref In Ref, Amount)` draw `MVK_VARYING_TYPES_NOT_ALLOWED` and `(Due In Due)` draws `MVK_ONLY_STRING_ENUM_NUMBER_ALLOWED`, while `(Ref, Ref, Amount In "x")` against a literal draws `MVK_DUPLICATE_PARAM1`. A checker that asks every repeat first reports the duplicate class for all four. Over a String `Reference` and a raw String `InternalMemo`, `(InternalMemo In InternalMemo)` draws `MVK_INVALID_RAW_TYPE` and `(Reference In Reference, InternalMemo)` draws `MVK_DUPLICATE_PARAM1`: the pair separates the field list's value validation, ahead of the repeat across the lists, from the value list's, behind it. Enumeration declarations need not share or contain each other's stored/category domains; runtime compares the selected projected tokens actually present in the two sides.
- A category projection inherits the underlying Enumeration cell's three-way classification before projecting its token: empty stays empty, a formally unavailable or invalid stored value stays UNKNOWN, and only a filled valid stored value contributes its possibly many-to-one category token. Consequently, an empty Enumeration reached through a category hop makes a fired `No` OMISSION and leaves `NotAll` non-firing; the hop never turns the empty cell into a present literal-like value. An index cell the document makes unavailable, a duplicated key or a row above capacity, stays UNKNOWN through the hop as it does for the value read ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-25h-category-index-relevance)).
- In partial validation, a starred entry has two relevance facts. Its instantiated cells are classified individually **and filtered by concrete relevance** (a non-relevant cell contributes no available concrete value to the scan; the two facts are independent, and `AtLeastOne` consults only this one), while its complete extent is established as soon as **one** relevant identifier covering the entry wildcards every repeatable level reopened from the first star downward, asked per iteration row. Listing every row concretely remains insufficient, but a concrete identifier sitting beside a qualifying wildcard does **not** take the extent away. This gate is weaker than the all-rows aggregates' gate in [§12](10-validation-and-polarity.md#5-full-vs-partial-validation), deliberately and measurably. An extent-unknown star is consumed like an UNKNOWN on that side: `AtLeastOne` ignores it on either side, `No` is suppressed on either side, and `NotAll` ignores it on the fields side but is suppressed on the values side.
- **`AtLeastOne`** consumes the complete values side first, skipping empty and UNKNOWN member cells, then scans fields in authored encounter order until a present match. Empty and UNKNOWN fields-cells are skipped; an empty value set does not fire. A fire is **OMISSION** when the matching fields operand was filtered or any filtered values operand contributed a present member, otherwise **VALUE**. A filtered values operand that contributes only empty/UNKNOWN cells does not change polarity.
- **`No`** consumes the complete values side before fields. An UNKNOWN values member suppresses the result, while an empty member, omitted tail, or reached values-side filter contributes sticky omission potential. It then scans fields in authored cell order: a match terminates as non-firing before every later field cell or operand, while a reached UNKNOWN before any match suppresses the result. If the scan exhausts without a match, it fires **OMISSION** when any reached empty field, omitted tail, filter, or values-side omission potential occurred, otherwise **VALUE**. It is the sole member that can fire when nothing is filled.
- **`NotAll`** consumes the complete values side with the same UNKNOWN/omission classification as `No`, then scans fields and fires at the first present value outside the set. Empty and UNKNOWN fields-cells are skipped. The fire is **OMISSION** when the outside-witness operand was filtered or the values side has omission potential, otherwise **VALUE**.
  - **The ordinary field-valued route first searches for a present subject, then collects members, then restarts the subject scan.** With no present subject it leaves the values side unread. That order is observable when a values-side `Having` filter can fail: a failure on an unread side is suppressed, while a reached filter failure remains observable. Each filtered scan preserves kept-successor lookahead before consuming its pending payload; an early match or outside witness can therefore hide later failures beyond that successor.
  - **The optimized emission route has narrower prerequisites.** It is selected when a fields operand has at least ten iterations and the values side has no filter, no iteration, and at least twenty operands. It hoists those member values and omits the presence prepass. With no present subject, both routes remain non-firing even when a member is formally unavailable. This equivalence of the pure member classification does not justify eagerly executing filtered values in the ordinary route. An evaluator that turns a formally unavailable member into UNKNOWN at collection time must retain the presence guard to preserve the ordinary result distinction ([source and measured boundary](../docs/sources/group-and-iteration-probes.md#src-sparse-filter-traversal)).
- **Membership chooses its own traversal policy for each pass.** `AtLeastOne` opts both member collection and subject search into the sparse-capable traversal of [§7](07-repetition-and-iteration.md#3-the-filter-having-the--correlation-and-aggregation); an empty collected set avoids the subject scan. `No` and `NotAll` use dense traversal, including `NotAll`'s presence prepass. A formally unavailable member terminates their collection before later filters or authored operands; `AtLeastOne` skips that member and continues. These distinctions apply to full validation and computation, with computation retaining its poison behavior for reached unavailable cells.
- **Table-backed (dynamic) Enumerations are deliberately outside this part.** The code generator rejects table-enum fields for the Groovy and JavaScript targets by declared, diagnosed policy — but that restriction can never fire, because **no producer supplies a table at all**: the accessor is abstract on the kernel's internal type, its sole implementor returns empty, and the public model API has no table concept. Table-backed Enumerations are therefore outside the observable language on every target rather than a Java-only capability, so the silence here is a scope boundary and not a conceded gap. One mechanism is worth knowing even so: dependent columns would drive a domain filtered by sibling field values, with omission polarity for a not-given subject — genuine evaluation semantics, and unreachable for a **second, independent** reason. That same sole implementor also returns an empty dependent-column list, so the cascade dies even on a hypothetical model that did supply a table name. Cite the empty column list rather than only the absent table: it is the tighter reason and does not depend on the table-name argument holding. **One gate sits *inside* that boundary and is live on every model, because its predicate runs the other way** ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-21-corrections)). The `ValueNotConsistent(<subject> To <values>)` family checks its subject first, and that check demands a **table** enum — so the absence of one is not what makes the class unreachable, it is exactly what fires it: an ordinary Enumeration, a String and a Number subject all draw `MVK_TABLE_ENUM_EXPECTED`, a group draws `MVK_NO_GROUPS_ALLOWED`, a starred selector `MVK_NO_WILDCARDS_ALLOWED`, and an undeclared path `MVK_INVALID_ENTITY`, against another operator on the same subject as the admitted control. The demand answers before the family's arity and member-kind gates, so neither a wrong member count nor a non-Enumeration member is ever visible, and the subject's own kind never matters. The scope boundary above is therefore about the table-backed *evaluation* semantics; this one static class belongs to the observable language and a consumer that skips the whole family reports nothing where A12 refuses.
- A `Having` filter is accepted on either side and drops rows before per-cell classification, but its polarity effect is encounter- and witness-sensitive as stated above; it is not one unconditional side-wide flag ([§12](10-validation-and-polarity.md)).

> **Non-normative implementation note.** Preserve authored operand boundaries and encounter order rather than flattening each side into one aggregate classification. The three quantifiers have distinct pass structure: values then fields for `AtLeastOne`/`No`, and for `NotAll` values then fields behind a fields-presence guard. Do **not** read the size-selected emission routes as permission to drop that guard: this encoding poisons the values side at collection time, so the guard is what produces the required non-firing result when no fields cell is present, and removing it would yield UNKNOWN instead. Preserve observable filter execution as well as the materialized outcome. Return `Verdict`, retain UNKNOWN explicitly, and prove the order separators; the operators are not Boolean duals. The public rule/message projection emits no finding for either `notFired` or `unknown`, so a fields-side `No` match-before-later-UNKNOWN separator is source-grounded and internally executable but is not independently message-observable without a negation consumer.

### B.4 Scalar membership is a singleton specialization, not Boolean negation ⚠

`FieldValueIncludedInValueList(subject, members…)` lowers to one-subject `AtLeastOne`; `FieldValueNotIncludedInValueList(subject, members…)` lowers to one-subject `NotAll`, never to empty-firing `No`. An empty or formally unavailable subject therefore makes **both** scalar forms non-firing. With a present subject, `Included` fires **VALUE** iff at least one present member equals it, while `NotIncluded` fires iff no present member equals it. An empty field-valued member contributes no atom; if `NotIncluded` otherwise fires, that missing member makes the fire **OMISSION**. A formally unavailable member is skipped by `Included` but poisons `NotIncluded`. A fire against an all-literal member list is **VALUE**.

The subject and member list admit only the String, Enumeration, and Number families, and the member list is nonempty. Literal members must match the subject family: String literals are unrestricted decoded strings, Enumeration literals must belong to the selected stored or category projection's domain, and Number literals are grammar-level integers with an optional leading minus. A field-valued member list is nonempty, has the same base type as the subject, and rejects an exact reference repeated anywhere across the subject plus members. **Each field-valued member is a field-value read ([§10](08-paths-and-references.md#3-the-asterisk-and-)), so its own gates run during the parse, ahead of the subject's kind gate and of the member list's duplicate and base-type gates** ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-25f-field-value-read), [checkpoint](../docs/sources/static-admission-and-class-probes.md#src-field-value-read-grid)). A raw member draws `MVK_INVALID_RAW_TYPE` beside a Number member, after a repeated member and against a Boolean subject. A group member draws `MVK_NO_GROUPS_ALLOWED` against a String or a Boolean subject, a starred member `MVK_NO_WILDCARDS_ALLOWED`, and a partially known Date member against a String subject `MVK_INVALID_DATE_TYPE`. **The subject is an entity, not a bracket** ([checkpoint](../docs/sources/static-admission-and-class-probes.md#src-field-value-read-remaining-sites)). Against field-valued members, a plain subject naming a fixed group is refused `MVK_NO_GROUPS_ALLOWED` only after the members' reads, so beside a raw member `FieldValueIncludedInValueList(Ledger, [Note])` draws `MVK_INVALID_RAW_TYPE`, while a category subject over a group, `(Ledger -> Band, [Note])`, draws `MVK_NO_GROUPS_ALLOWED` ahead of that member. The root waits for the members as a fixed group does, while an unstarred repeatable group draws `MVK_NO_WILDCARD`, a name resolving to nothing `MVK_INVALID_ENTITY` and a category subject over a String `MVK_NO_ENUMERATION` as the subject is read, ahead of them ([checkpoint](../docs/sources/static-admission-and-class-probes.md#src-field-value-read-predictions)). Against literal members nothing is read first, so the subject's group gate answers at once: a fixed group and the root draw `MVK_NO_GROUPS_ALLOWED` and an unstarred repeatable group `MVK_NO_WILDCARD`, on the String and the Number literal form, and so does a bare name naming a fixed group on the String form. Past the reads the subject's kind gate answers before its value validation ([`kf398`](../../a12-rulekit/docs/KERNEL-FINDINGS.md#kf398)): a partially known Date draws `MVK_ONLY_STRING_ENUM_NUMBER_ALLOWED` as a full Date does, against literals and against a field member, and a raw String `MVK_INVALID_RAW_TYPE`. Enumeration stored access and named category access on one physical field are distinct references; category identity is retained, and no cross-declaration domain-containment or display-remapping gate is added.

Runtime equality follows the family's ordinary value boundary: normalized evaluated text for String, the selected stored/category token for Enumeration, and numeric equality after the ordinary scale-19 normalization for Number. Empty numeric member fields contribute no zero atom.

> **Non-normative implementation note.** For validation, reuse the resolved value-list quantifiers: `Included → AtLeastOne`, `NotIncluded → NotAll`. Do not introduce Boolean negation or a second membership evaluator; those shortcuts lose the empty-subject and UNKNOWN-member asymmetries.

### B.5 Computation preconditions preserve reached errors and traversal order

Static field-list reading resolves and checks computation binding for each authored operand before advancing to the next. An unbound repeatable operand therefore preempts a later unresolved name; reversing those operands reverses the reported class. Whole-list checks, such as repeated-direct operands and mixed-kind checks, follow successful operand reading. Number-to-token overload fallback must preserve these read failures rather than replace the first one with a later fallback error. [The 13-case admission matrix](../docs/sources/domain-ingestion-probes.md#src-membership-read-order-k13) distinguishes missing names, unbound fields/groups, duplicate operands and mixed kinds, with admitted Number and String controls.

Computation preconditions use computation-phase reads: a reached formally invalid operand poisons the computation rather than becoming validation's skipped or unknown operand. For field-valued member lists, `AtLeastOneFieldValueIncludedInValueList` and `NoFieldValueIncludedInValueList` collect the members before scanning the subjects. The subject scan stops on its deciding match. `AtLeastOne` with no present members returns not-true without reading the subjects; `No` still scans them. `NotAllFieldValuesIncludedInValueList` first searches for a present subject, then collects the members, then restarts the subject scan and stops at the first present value outside the member set. If the presence search finds none, it returns not-true without reading the members.

Scalar `FieldValueIncludedInValueList` and `FieldValueNotIncludedInValueList` collect their members before reading the subject. Both return not-true for an empty subject, but neither inherits a plural prepass: an invalid member poisons even when the subject is empty, and an invalid subject poisons even when every member is empty. A present subject selects `Included` on a match and `NotIncluded` on no match. An empty Number member is absent, not zero.

Filtered computation streams retain the iterator's one-kept-successor lookahead: before consuming a selected subject, they search for its next selected successor. A failure in that search poisons before the pending subject can decide; after a deciding subject, filters beyond that prefetched successor remain unread. Member collection still exhausts its selected stream and reaches later invalid members. Excluded candidates do not contribute target reads.

The [computation membership grids](../docs/sources/computation-scheduling-probes.md#src-compositional-computation-guards) retain the separating controls across stored Number, String and Enumeration fields, scalar literals and field-valued members, and Number/String filtered stars. Category-projected runtime behavior, indexed/correlated compositions and generated-validation messages remain outside these runtime measurements.
