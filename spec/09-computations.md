# 09 — Computations (§11)

Computations write values into computed fields. They share the whole expression language with rules, so everything in §1–§10 applies — but computation adds its own hard parts:

1. **Every computation also generates a validation rule** over its complete alternative table; under overlapping guards this is deliberately not just “compare with the first selected result.”
2. Three outcomes per cell — **VALUE / CLEARED / ERRORED** — decided by operand states.
3. **Two kinds of "no value"**: a precondition-clear cascades as **EMPTY**; an invalidity-clear **POISONS** — and the poison is **read-driven and order-dependent**.
4. A computed value lands as a **string in the target's declared shape** (the *stored form*), which is what downstream sees.

This is the file to get exactly right if computed fields chain.

---

## 1. The ground rules

- **Every computation also generates a validation rule.** A filled computed field is checked against every holding alternative's guarded mismatch clause (exact shape in §6 below). With mutually exclusive preconditions this agrees with the first selected computation result; overlapping preconditions can make validation fire on a later alternative even when the stored value equals the first result. Assigning a time-dependent value like `Now` is legal but unstable: the generated validation rule can observe a later instant and report a mismatch immediately ([§6](05-dates-and-time.md)).
- **Scale must match, through the same comparison predicate as `==`/`!=`.** The generated validation rule compares the target against the operation, so the computed field's declared decimal scale is admitted exactly when that predicate admits it ([§5](04-numbers-and-decimals.md)): equal derived and declared scales always pass, and a **smaller** derived scale also passes when the whole operation retains multiplicative-constant capability, because the capable side is padded up to the declared scale. A derived scale **larger** than the declared scale is always rejected, and an unknown derived scale is rejected unless the model suppresses `MVK_INVALID_COMPARE_DEC_PLACES`. Wrap the calculation in a rounding construct to force a declared scale. Because a field is never capability-carrying, an operation containing any direct field reference outside a capable subexpression reduces to plain equality, which is why the equality reading holds for most authored computations without being the rule. The implicit scale comparison also precedes the target-reference gate: over an operation that reads its own target, a derived-scale mismatch reports only `MVK_INVALID_COMPARE_DEC_PLACES`, while suppressing that code exposes the target-reference refusal underneath it, so such a computation is a two-repair rejection reported one repair at a time. The order holds across expression shapes, and the authoring gate stands ahead of both ([checkpoint](../docs/sources/computation-scheduling-probes.md#src-join-operators-and-guards)). Measured: `+`, `-`, and `*` reading the target on either side against a literal or a Number field of matching or different derived scale, over targets of two scales ([`kf181`](../../a12-rulekit/docs/KERNEL-FINDINGS.md#kf181)); a bare copy, `Abs`, an operand-list `Max`, a power, a rounded division and a braced product, each of which draws the target-read class when its scale matches; a top-level division, a division under `Abs`, `Max` or a later product, a product under `Abs`, a braced product and a three-factor product, each of which draws the scale class when its scale does not; the same order when the self-read sits in a precondition rather than the operation; and the order ahead of the projected target-read class as well as the plain one. A second unbraced division draws `MVK_TOO_MANY_DIV_FOR_CALC` ahead of both, with or without a self-read and under a rounding wrapper, and so do a power over a power, `MVK_TOO_MANY_POW_FOR_CALC`, a wrapped literal, `MVK_NO_CONST`, a fractional exponent, `MVK_INVALID_NUMBER_FOR_EXP`, and a text operand's kind class. An aggregate, a `FirstFilledValue` and a group count over the target's group read the target in the same order. **The order holds across a computation's alternatives**: a self-read in one alternative beside a scale mismatch or a second unbraced division in another draws that class in either order, and beside an unresolved name in a later one that name's class, so a checker cannot settle the target-read class one alternative at a time. An operation reading the target twice reports the target-read class once per occurrence. Not measured: suppression over a division, aggregate or group-count self-read, and another computation family. Nothing here explains *why* the kernel orders the two gates that way; only the reported class per shape is measured.
- **The computed field may not appear in a precondition *nor* in an operation** (both directions draw the same rejection). The ban includes containing-group reads, with the exact exemptions in [§5](#5-where-a-computation-runs--scope-and-the-parallel-join): `GroupFilled` over a containing group is legal for fixed and repeatable targets, and `CurrentRepetition` reads a structural coordinate. `CurrentRepetition(group)` reads only the selected structural row coordinate: it contributes no contained-field dependency and must not be expanded into dependencies on every computed field below the group. Actual field reads remain ordinary dependency edges, so a `First := Base` computation under `CurrentRepetition(group) > 0` may precede `Second := First` without the structural guard manufacturing a cycle.
- **Computation execution is scoped to the computed field, not the declaration group.** An all-nonrepeatable target has exactly one implicit runtime instance even when its group has no document content, so a computation declared in another fixed subtree still computes that target. The retained [target-scope checkpoint](../docs/sources/computation-placement-and-constant-probes.md#src-fixed-computation-target-scope) separates this account from declaration-group iteration with a seeded Number target on both Kernel strategies, plus an empty document on dynamic Groovy and the independent interpreter.
- **The declaration group contributes no repetition of its own.** A constant computation declared in a *repeatable* group whose fixed target sits elsewhere produces exactly one value, both when that declaring group has no instantiated row and when it has three; it is neither silenced nor repeated. The same [declaring-group gate checkpoint](../docs/sources/computation-placement-and-constant-probes.md#src-computation-declaring-group-gate) measures that discriminator on both Kernel strategies together with cross-group Number, String, Boolean, and Confirm constants, which all execute to their constant at the target's own address. A Boolean or Confirm constant is authored with the catalog keyword `True`/`False` and stores lowercase `true`. Generated validation and public result/application behavior remain outside these rows. A **repeatable** cross-group target is measured separately and behaves as the general scope law predicts: a bare constant declared at the root computes once per instantiated target row and is indistinguishable from the same constant declared at the target's own group, on all four constant families ([checkpoint](../docs/sources/computation-placement-and-constant-probes.md#src-cross-group-repeatable-constant-target)). Because a constant carries no operand, that is the row on which only the target's own scope can supply iteration. **A Date constant need not match the target's exact format, but it is not unchecked.** Its static gate classifies the literal and target into compatible temporal component families, including the Base Year rule below, rather than requiring their spellings to match. At runtime the value is rendered into the target format, and the measured opt-in pre-1900 policy still applies. Two otherwise identical ISO targets receiving `"31.12.1899"` separate that policy: `rejectBefore1900: true` retains attempted `1899-12-31` as ERRORED, while the unguarded target accepts the same text, and neither clears ([checkpoint](../docs/sources/temporal-constant-and-base-year-probes.md#src-date-constant-pre-1900-target)). A double-quoted `"05.03.2024"` is admitted into targets declared `dd.MM.yyyy`, `yyyy-MM-dd`, **and** `yyyy` alike, while every other spelling — the ISO `"2024-03-05"` included — is refused `MVK_INVALID_COMPARE_TO_DATE` for having lexed as a String or Number constant. At runtime the same constant is **rendered into each target's declared format**: those three targets store `05.03.2024`, `2024-03-05`, and `2024`, on every instantiated row, with nothing cleared, nothing errored, and no message. So the constant is one temporal value and the declared format is a rendering of it, exactly as a Number constant's stored text is a rendering of its amount. A component-omitting target such as `yyyy` therefore **discards day and month silently** — not an error, not a clear, not a warning — which is the branch a carrier is most likely to get wrong ([checkpoint](../docs/sources/temporal-constant-and-base-year-probes.md#src-date-constant-target-formatting)). The ISO spelling a reimplementer reaches for first is the one that cannot be authored and the one an ISO target stores. **That admission rule is not Date-specific, and the deciding input is the target's declared *format string* rather than its kind.** A TIME field declared `HH:mm:ss` admits the clock literal `"12:30:00"` and refuses the date one; a TIME field declared `yyyy-MM-dd` does the exact opposite; a **DATE** field declared `HH:mm:ss` admits the clock and refuses the date. Each kind appears on both sides of both outcomes, so the kind is measured irrelevant and the literal's temporal family must match the format's, a mismatch drawing `MVK_INVALID_COMPARE_TO_DATE`. The two cross-kind cells **store** and not merely admit — a DATE-kind field declared `HH:mm:ss` stores `12:30:00`, a TIME-kind field declared `yyyy-MM-dd` stores `2024-03-05`, both unerrored — so the kind carries no part of the family rule at either stage. **The DATETIME carrier is governed by its format too**, measured separately rather than inherited from those two: a DATE-declared field carrying `yyyy-MM-dd'T'HH:mm:ss` stores `2024-03-05T12:30:00`, and a DATE_TIME-declared field carrying `yyyy-MM-dd` stores `2024-03-05`, each beside its aligned same-kind control ([checkpoint](../docs/sources/computation-placement-and-constant-probes.md#src-datetime-carrier-stores-by-its-format)). That third carrier matters because its format is the one carrying both component sets, so a store falling back to the declared kind would have shown up here and nowhere else. Within one family the format then renders, and may drop components silently: `"05.03.2024"` into a `yyyy-MM` DATE_FRAGMENT stores `2024-03`. **A date-shaped format is not one family, though: the year splits it.** Of the five component-omitting date formats, the year-leading `yyyy`, `yyyy-MM`, and `yyyyMM` admit a full-date constant while the yearless `MM` and `MM-dd` refuse it, identically on DATE and DATE_FRAGMENT declarations. A declared **Base Year** lifts that refusal for all four yearless targets, which is the same rule [§6](05-dates-and-time.md) states for a yearless date generally and [§8](07-repetition-and-iteration.md) for a yearless aggregate operand, here measured on the constant-assignment carrier rather than carried across to it. The store drops exactly the components the format omits, keeping the format's own separator: `yyyy` stores `2024`, `yyyy-MM` stores `2024-03`, `yyyyMM` stores `202403` ([checkpoint](../docs/sources/temporal-constant-and-base-year-probes.md#src-component-omitting-date-formats)). So two separate rules compose here — the family gates admission, the format renders the store — and neither is read off the declared kind. **TIME, ENUM, DATE_FRAGMENT, and DATETIME admit a bare constant; DATERANGE has no known witness.** The DATETIME spelling is the admitted German Date literal and clock literal joined by `T` ([checkpoint](../docs/sources/temporal-constant-and-base-year-probes.md#src-temporal-constant-literal-composition)). On a DATETIME target declared `yyyy-MM-dd'T'HH:mm:ss`, the ordinary literal stores `2024-03-05T12:30:00` on every instantiated row. **A DateTime constant has two separately observed zone-sensitive verdicts.** With the model zone fixed to `Europe/Berlin`, the exact same model carrying the spring-forward-gap literal `"31.03.2024T02:30:00"` passes static checking under a UTC JVM default and is refused `MVK_INVALID_COMPARE_TO_DATE` under a Berlin JVM default. When the UTC-admitted model runs against its declared Berlin zone, that gap supplies no value and one addressed `berechnungsWertFehler` value finding per in-capacity target row. The change projection reports no outcome for an empty target and a clear for a seeded target; neither has an errored attempted value ([seeded control and composed consumers](../docs/sources/temporal-runtime-fold-probes.md#src-compositional-temporal-disposition)). The observations establish a static host-zone dependency and a runtime model-zone dependency without identifying the Kernel's internal conversion step ([checkpoint](../docs/sources/temporal-constant-and-base-year-probes.md#src-datetime-constant-zone-split)). ENUM is the one whose target constrains the constant's *value* statically: a literal naming a declared value is admitted and one that does not is refused `MVK_INVALID_STRING_CONSTANT_FOR_ENUM_COMPARISON`, a static membership check distinct from String's runtime policy, Number's split policy, and Date's component-family admission plus measured runtime pre-1900 policy ([checkpoint](../docs/sources/temporal-constant-and-base-year-probes.md#src-constant-literal-family-gate)).
- **Boolean constants retain the Confirm asymmetry at a computation target.** A Boolean target admits both `True` and `False`. A Confirm target admits `True` but refuses `False` with `MVK_INVALID_COMPARE_TO_YES`; a computation may set a confirmation but cannot clear one with the false constant.

- **A wrong-kind constant's diagnostic is decided by an ordered ladder over the (constant family, target kind) pair, not by either side alone.** Rung 1: a **Boolean** target reports `MVK_INVALID_COMPARE_TO_YESNO` and a **Confirm** target `MVK_INVALID_COMPARE_TO_YES`, whatever the constant is. Rung 2: a **temporal** constant then reports `MVK_INVALID_COMPARE_TO_DATE` at every remaining target, including String, Enumeration, Number and DATE_RANGE, and all three temporal families share that one class. Rung 3: otherwise the target's declared kind decides — a temporal target `MVK_INVALID_COMPARE_TO_DATE`, a DATE_RANGE target `MVK_INVALID_COMPARE_TO_DATE_RANGE`, a String or Enumeration target `MVK_INVALID_COMPARE_TO_ENUM_OR_STRING`, and a **Number** target `MVK_INVALID_COMPARE_TO_ENUM_OR_STRING` for a string-like constant but `MVK_INCONSISTENT_TYPES_COMPARED` for a Boolean one. That Number cell and rung 2 are the only places the pair matters, and they are the two a consumer reading the table off one measured constant family gets wrong. A **CUSTOM** target is the String column exactly, with no rung of its own. The constant's family is a property of the literal's *content*, not of a distinct spelling — there is one string-literal syntax, so `"x"` and `"05.03.2024"` are the same authored form drawing different classes at the same String target ([checkpoint](../docs/sources/static-admission-and-class-probes.md#src-constant-assignment-diagnostic-ladder)).
- **A field source draws the class its kind pair draws in a comparison, and the ladder above is not that pair function** ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-26c-joined-comparison)). The generated validation compares the target with the operation (§6), so a field copied into a field of another kind is refused by that comparison, with no computation-specific class, and **its arms answer in the rule comparison walk's order, each claiming its kind on either side**, on every pair of the nine kinds measured ([checkpoint](../docs/sources/static-admission-and-class-probes.md#src-field-copy-comparison-grid)): a Confirm partner draws `MVK_INVALID_COMPARE_TO_YES`, a Confirm copied into a Boolean included; otherwise a Boolean partner `MVK_INVALID_COMPARE_TO_YESNO`; otherwise a temporal field against a non-temporal one `MVK_INVALID_COMPARE_TO_DATE`, a DateRange included; otherwise a DateRange partner `MVK_INVALID_COMPARE_TO_DATE_RANGE`; otherwise a Number against a String or an Enumeration `MVK_INVALID_COMPARE_TO_ENUM_OR_STRING`. That order is why a Boolean field into a String draws `MVK_INVALID_COMPARE_TO_YESNO` where a Boolean constant draws the text class, and one into a Confirm `MVK_INVALID_COMPARE_TO_YES` where `True` is admitted. Two temporal fields meet the date arm's format question rather than a kind test, so Date, Time and DateTime fields of different formats draw the date class against each other, while a TIME field declaring a complete-date format copies into a Date target. A String against an Enumeration, and two Enumerations, meet the display arm: a labelled side against a String or an unlabelled Enumeration draws `MVK_INVALID_COMPARE_ENUM_TO_STRING` in either direction and conflicting labels `MVK_INVALID_COMPARE_ENUM_TO_ENUM`, while **an unlabelled Enumeration copies into a String admitted**. At an Enumeration target the comparison answers first, and only a copy it admits reaches the calculation's own `MVK_ERROR_INVALID_ENUM_CALCULATION`, which a String into an unlabelled target and a wider unlabelled Enumeration draw ([checkpoint](../docs/sources/static-admission-and-class-probes.md#src-field-copy-comparison-grid)), as do a keyed String source and a stored or category read wider than the target's domain ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-26e-labelled-target), [inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-25i-enum-source)); a wider Enumeration whose labels also differ draws the display class alone. A keyed String source is measured into an unlabelled target only. A Number field of the other scale is refused `MVK_INVALID_COMPARE_DEC_PLACES` in either direction, by the scale rule above. A field of the target's own kind and scale is admitted on each of the eleven declarations measured, which separates the comparison from a computation-specific gate. The class is raised where the comparison closes: an arithmetic source `[Total] + 1` into a String draws the text class, and so does `[Total] [Note]`, rather than the unexpected-token class its stray read would draw. A tolerance band replaces the comparison's operator, so a String copied under one draws `MVK_INVALID_TYPE_FOR_TOLERANCE_OP` while a Number copy is admitted. How the target is spelled — relative below the declaring group, absolute outside it — leaves the class unchanged.
- A **non-repeatable computed field is calculated even when all its inputs are empty**. A Number calculation stores the real value `0`; a String expression runs, but a final empty text stores nothing. A literal-bearing result such as `" "` does store. Add an `AllFieldsFilled(...)` precondition to suppress the calculation entirely.
- `RangeAsString(field, start, end)` accepts one value-validating String-like field without a category or wildcard and requires `1 ≤ start ≤ end`. Its authored bounds are 1-based and inclusive over the field's evaluated String in UTF-16 code units. An empty source or an end beyond the evaluated length yields the empty String—never a partial prefix—while formal unavailability follows the ordinary computation poison path. The final result still passes through the normal String root-store and target checks.
- `RangeAsNumber(field, start, end)` uses the same checked field and UTF-16 range boundary, then accepts only a nonempty ASCII digit run. Every clean mismatch, empty source, or overshoot yields the real numeric value `0`; formal unavailability poisons. The result enters ordinary numeric arithmetic, generated validation, and Number target checking rather than a range-specific write path ([§5](04-numbers-and-decimals.md)).
- An operation-form `RoundDown`, `RoundUp`, `RoundAccounting`, or `Abs` may be the root or an ordinary operand inside larger arithmetic and consumes an already-checked number-like child, including another wrapper or an independently admitted operand-list `Min`/`Max`. The same boundary admits direct or grouped numeric `BaseYear`, a direct `FieldValueAsNumber(...)`, `RangeAsNumber(...)`, numeric field-list aggregate, temporal numeric component, Base-Year-derived component, or Date-only month/year-difference source. Only an immediate or grouped numeric literal is rejected at each wrapper boundary. Nested wrappers evaluate from the innermost outward; the child retains its own division, power, target-reference, and domain-failure checks. Enclosing division traversal crosses each reached value-function subtree, while each function node structurally separates an outer direct-left power. Rounding uses its authored scale and preserves the child's movement; absolute value preserves child scale, runs after the complete child, aggregate fold, or extremum selection, turns symmetric missing conversion/component/difference or bidirectionally fillable all-empty Sum/extremum zero into grow-only magnitude, and retains fixed Base-Year or already grow-only range/distinct-count values. Computation maps every clean missing or all-empty result to numeric zero and preserves arithmetic domain failure or formal unavailability through every wrapper ([§5](04-numbers-and-decimals.md), [§6](05-dates-and-time.md)).
- Indirect calculation **cycles** among computed fields are a **static refusal**, not a runtime hazard: A12 sorts the calculated fields topologically before it generates anything and reports `MVK_ERROR_CALC_CYCLE`, spelling the cycle out. The law reads declarations alone — each computed target and its required producers, with the group-specific rule in [§1.1](#11-group-derived-scheduling-dependencies) — so it is decidable without a document ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-21-corrections)). Three consequences a consumer reading only `operation` gets wrong: a read inside an **alternative's precondition** is an edge of that graph exactly as an operation's read is, although one is a condition spelled `FieldFilled(X)` and the other an operand spelled `[X]`; the graph is over **resolved fields**, so a circle closing through an aggregate over a repeatable group in one direction and an absolute read out of it in the other is refused like two sibling reads; and a **one-node** circle is a different code — a computation reading its own target draws `MVK_ERROR_REFERENCE_TO_CALCULATED_FIELD` (§6 below), so reporting the cycle class there names a verdict the Kernel never reached. A back edge through a field no computation writes is admitted. **A declaration a variant filter takes out is no node of that graph**: with `variantFilter` `ONLY` another variant on either computation of a two-computation circle, the model is admitted. Every other class measured beside the cycle withholds it — another computation's text defect or member class, a rule's text defect, a structural path class, a missing error text ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-25c-calculation-stages)).
- A computation may not write into the field a repeatable group declares as its **index**: that target draws `MVK_ERROR_INDEX_AS_CALCULATED_FIELD`, whether the computation is declared in the indexed group or at an ancestor of it. The refusal follows the resolved target and not the field or the operation. An ordinary sibling in the same group is computed into freely, and so is a field the group names as a **sort** field, although the group declares both kinds of member alike; a rule may still report on the index field. Like the cycle law it reads declarations alone ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-21-corrections), [checkpoint](../docs/sources/diagnostic-class-vocabulary-and-sweeps.md#src-index-iteration-and-constant-refusal-classes)). Confidence limit: measured with a Number index field under a constant and an aggregate operation.
- **The two prohibited predicates an English model can spell are refused in a computation's precondition and ordinary in a rule.** `CustomCondition` or `RepetitionNotUnique` in an alternative's precondition, and `CustomCondition` in the common precondition, draw `MVK_ERROR_INVALID_LANGUAGE_FEATURE`, while `RepetitionNotUnique` in the operation draws `MVK_UNEXPECTED_TOKEN`, an operation not being a condition ([`kf333`](../../a12-rulekit/docs/KERNEL-FINDINGS.md#kf333)). Inside a filter body neither reaches that class: the filter's own `MVK_DISALLOWED_CONSTRUCT_IN_FILTER_CONDITION` answers in the precondition, the operation and a rule alike ([§9](07-repetition-and-iteration.md), [inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-25b-computation-texts)).
- **A computation's own classes are asked in stages, and a failed stage ends the check** ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-25c-calculation-stages)). First comes a text the parser refuses or a name resolving to nothing, then the target, `MVK_ERROR_INDEX_AS_CALCULATED_FIELD`, then the normal form, `MVK_ERROR_INVALID_LANGUAGE_FEATURE`, then the alternatives, and last the rounding mode. The alternatives' classes stand together: `MVK_ERROR_EMPTY_PRECONDITION` for one unconditional alternative beside a preconditioned one stands beside `MVK_ERROR_INVALID_ENUM_CALCULATION` or `MVK_ERROR_REFERENCE_TO_CALCULATED_FIELD` in the other alternative. **On a Number computation the name stage is not computation-wide** ([checkpoint](../docs/sources/computation-scheduling-probes.md#src-join-operators-and-guards)): a name resolving to nothing is asked with its alternative's division-count, nested-power, kind and scale gates, one alternative at a time in authored order, and the first alternative failing one of them reports that class alone. So a scale-2 copy into a scale-0 target in the first alternative beside `[Nope]` in the second draws `MVK_INVALID_COMPARE_DEC_PLACES`, the reverse order `MVK_INVALID_ENTITY`, and a precondition naming nothing answers in its own alternative's place, ahead of an unconditional alternative in either order; within one alternative a name, a precondition's included, answers ahead of a scale mismatch or a second division. **From two alternatives on, an unconditional alternative's own reads of the target go unjudged**, whether or not another alternative is preconditioned ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-10-02a-alternative-walk)): `[T]; [B]`, `[T]; [T]` and an unconditional `[T]` beside a preconditioned `[B]` each draw `MVK_ERROR_EMPTY_PRECONDITION` alone, while a sole unconditional alternative reading its target draws the target-read class. The empty class is reported once however many alternatives are unconditional, at the first one's place, and every judged read draws the target-read class once, alternative by alternative in authored order. Within one alternative a self-reading precondition and operation draw the same class, so their relative order is not observable. **A common precondition guards no alternative; its target-read findings appear at the first alternative the walk judges, once per written read** ([checkpoint](../docs/sources/computation-scheduling-probes.md#src-self-read-alternative-walk)): a common `FieldFilled(T)` over `[B]; FieldFilled(G) => [C]` draws the empty class and then the target-read class, over `FieldFilled(G) => [B]; [C]` the reverse, over two or three preconditioned alternatives the target-read class once, and over two unconditional alternatives the empty class alone. **The projected class answers alone and once per computation**, from an alternative's operation, guarded or not, and from the common precondition, and withholds both the empty class and the plain class: `[T For "a"]` beside an unconditional `[B]` draws it alone in either order, as `[T -> Category]` does beside an unconditional projection or a guarded plain read. A projection in an alternative's own precondition is not measured. The unconditional-alternative walk holds alike on a repeatable target and on a fixed one nested below its root, and the common-precondition report placement and multiplicity hold on fixed root, fixed nested and indexed repeatable Number targets ([peer checkpoint](../docs/sources/computation-scheduling-probes.md#src-self-read-alternative-walk)). These observations specify the reported findings, not how often the common check executes. So a text defect in a computation's own precondition or operation withholds that computation's rounding, target and mixed-alternatives classes, while an arity or bad-name defect in another computation stands beside them. The error-text classes are not withheld by any stage measured: each of the six member classes stands beside `MVK_ERROR_MESSAGE_MISSING` and `RULE_HAS_NO_ERRORTEXT`, and the rounding class beside `INVALID_CHARACTERS` for a TAB in its message, while a text the parser refuses withholds `RULE_HAS_NO_ERRORTEXT` and leaves `MVK_ERROR_MESSAGE_MISSING` ([§12](11-messages-and-custom.md)). Where `MVK_ERROR_SEMANTIC_INDEX_OR_CATEGORY_FOR_ERRORFIELD` stands against the stages before the alternatives is measured only for the parse-time classes of the self-reference bullet below.

### 1.1 Group-derived scheduling dependencies

**Operand membership, forbidden target reads and required producer order are distinct.** For an expanded A12 model, a referenced group contributes every contained field to the operand inventory, including the consumer's own target and fields below deeper repeatable levels. That inventory feeds [the formal-input selection](#33-what-compute-reports); it is neither the runtime presence scan nor the scheduling graph. `CurrentRepetition` contributes a structural coordinate, not contained-field reads. The target-reference gate remains [§5](#5-where-a-computation-runs--scope-and-the-parallel-join)'s containment test with its named exemptions.

**Non-normative implementation note — content is a smaller input than membership.** For an already-resolved group and a valid enclosing-row binding, keep two content constituents: descendant fields whose repetition scope equals the group's own scope, including fields reached through fixed subgroups; and physical row witnesses for the group itself when repeatable and for its repeatable descendants, restricted to the bound address prefix. Fields below another repeatable level stay in the complete operand inventory, but their values need not be fetched to establish group presence: their instantiated row already supplies content. Thus a fixed root containing repeatable descendants retains its local and fixed-descendant fields as cell inputs, and its repeated descendants as row witnesses. Apply the pending/completed overlay of [§3.1](#31-a-precondition-clear-cascades-as-empty) to the cell inputs. This representation describes sufficient content constituents, not the Kernel's physical scan order or extra scheduling edges. A missing required row binding prevents constructing this input; it is not an empty-group answer. The representation does not extend the nested/keyed correspondence limits below.

For plain, unindexed group guards, an ordinary field read or a group read other than the positive containing-group forms named below retains its ordinary producer dependency. This includes `GroupNotFilled`, a positive group outside the consumer's ancestry, and reads in a later alternative that can never execute. The admitted singular `GroupFilled(G)` and positive fixed-root `AtLeastOneGroupFilled(Root)` forms use the conditional rule when the group contains the consumer: among computed fields in `G`, omit the consumer itself and producers whose syntactic profile protects `G`; retain every other producer. An ordinary read of that same producer still requires it. Ordinary input fields remain operands but are not computed-target nodes in the graph.

Ordinary group-list expansion does not grant that exemption. For a target inside non-root G, `AtLeastOneGroupFilled(G)`, `AtLeastOneGroupFilled(G,H)` and `AllGroupsFilled(G,H)` report `MVK_ERROR_REFERENCE_TO_CALCULATED_FIELD`; starred AtLeastOne/No operands containing the target do too. The [group-list admission controls](../docs/sources/computation-scheduling-probes.md#src-compositional-computation-guards) separate these from singular GroupFilled and the positive fixed-root form.
For a **nonrepeatable producer**, its syntactic profile is queried for a group `G`. A positive singular `GroupFilled(H)` leaf (or the admitted positive fixed-root AtLeastOneGroupFilled form) contributes protection exactly when `H` contains the producer and is `G` or a descendant of `G`. Other leaves contribute none. `And` needs protection from at least one operand; `Or` needs it from every operand. First distribute each computation's common precondition into its alternatives, then gather the **present** conditions across every computation of that target. At least one present condition must exist and all present conditions must protect `G`. An absent condition is omitted, not treated as an unprotected branch.

For a **repeatable producer**, implicit row guards are supplied to each computation before collecting the target's conditions. A computation whose profile does not already require its innermost repeatable group or a narrower containing group receives `GroupFilled` of that repeatable group as an additional common precondition. Queries at the repeatable group or an ancestor therefore remain protected. Below that group, an absent authored condition now contributes a present condition that does not protect the narrower group; it must not be omitted.

The [repeatable-profile grid](../docs/sources/computation-scheduling-probes.md#src-repeatable-group-profiles) separates the two stages. Put X and Y in fixed `Box` beneath unindexed repeatable `Rows`, with `X: GroupFilled(Box) => 1` and separate `Y: GroupFilled(Box) => [X]` and unconditional `Y:=2`. Both authored orders are refused with `MVK_ERROR_CALC_CYCLE`: Y's implicit row guard prevents protection of Box, retaining the reverse group-derived dependency. Changing X's group query to Rows, adding a common `GroupFilled(Box)` to Y's constant computation, or making Rows nonrepeatable admits both orders. These are static observations, not runtime results.

This profile is **not a guarantee about when the target computes**. With fixed `Gate`, `X` and `Y` in `Form`, let `X` be `GroupFilled(Form) => 1` and give `Y` two separate computations: `GroupFilled(Form) => [X]` and unconditional `2`. Both authored orders are admitted. With only stored target seeds, `X` clears and `Y` computes `2` in either order. With `Gate` filled, `X` computes `1` and `Y` selects `1` for guarded-first order or `2` for unconditional-first order. The absent guard does not remove `Y`'s profile, and runtime selection still preserves every alternative's authored position.

The [dependency grid](../docs/sources/computation-scheduling-probes.md#src-group-presence-conditional-dependencies) separates protected pairs from unconditional producers, `And` from bypassing `Or`, and group exemptions from ordinary field cycles. The [profile grid](../docs/sources/computation-scheduling-probes.md#src-group-conditional-profiles) adds common conditions, ancestor depth, both split-target orders, unselectable ordinary reads and one unindexed repeatable level. The recursive mechanism is source-read at the revision those checkpoints pin; retained runtime correspondence covers their Number targets and documents, not arbitrary nested/keyed groups or other target kinds. This scheduling rule does not change computation's [pending/completed read policy](#31-a-precondition-clear-cascades-as-empty), validation presence, or the generated validation rule.

## 2. Separate operations, and the three outcomes

**Validation and computation are separate operations.** `validateFull` never computes first; the consumer composes the form-engine flow **compute → apply → validate**, where *apply* follows the placement-sensitive per-cell contract in [`01-data-model.md §4.3`](01-data-model.md#43-the-compute--apply--validate-flow).

Per computed cell the outcome is one of:

- **VALUE** — a value is produced;
- **CLEARED** — *no* value; any stale stored value is wiped (never left standing);
- **ERRORED** — an attempted value returned with a target-check finding (e.g. digit overflow, a below-floor date or a reserved custom report). Application clears it; same-call availability follows target admission.

Which outcome an operand's state produces follows the per-kind split of [§2](03-empty-and-required.md), with compute's own twists:

| an operand that is… | NUMBER | DATE | STRING in a concatenation |
|---|---|---|---|
| **empty** | reads `0` → **VALUE** | operation not evaluated → **CLEARED** | contributes `""` inside the expression; the final result still passes through the root-store gate |
| **required and empty** | still `0` (the mandatory error is *validation's* concern, not compute's) | as empty → CLEARED | still `""` |
| **filled but formally invalid** | **CLEARED + poisons** the target for dependents (below) | CLEARED + poison (type-agnostic) | CLEARED + poison |

A **Number comparison in a computation precondition** also substitutes zero for a clean empty field. The measured `==`, `!=`, `<`, `<=`, `>` and `>=` guards select exactly as on explicit zero; `[N] + 1 > 0` and `0 < [N] + 1` therefore select when `N` is empty. A reached division-by-zero comparison does not hold, leaving a clean empty target, but still reads its other operand: a formally invalid right operand poisons that target and its dependent computation. A false left condition under `And` or a true one under `Or` skips that invalid suffix ([guard grid](../docs/sources/computation-scheduling-probes.md#src-numeric-computation-guards)). This is a computation-precondition observation; it does not change validation's omission polarity or establish another field kind's empty rule.

⚠ The guard consequence cuts both ways: over **DATE** operands an `AllFieldsFilled` precondition is *redundant* (a false precondition clears exactly as the unevaluated operation does), while over a **NUMBER** operand the same guard *changes behaviour* (guarded → CLEARED, where unguarded → computes `0`).

For String computations, replacing an empty operand by `""` is only the **per-operand expression rule**. The root store makes a second decision on the final result: a final empty String stores no value, regardless of whether it came from a bare copy, a literal, or an all-empty concatenation. It therefore yields CLEARED when a stale filled target exists and is otherwise silent; it is never a stored `""` VALUE. This empty-result gate runs **before** the target format check, so an empty final result aimed at a `minLength` target clears rather than becoming ERRORED. A no-value Date result similarly means that no operation produced a value, while Number has no empty result arm because empty-as-zero produces the real number `0`.

A final empty outcome stores nothing and dependents read the target as EMPTY, but it does not undo selection. Once an alternative has selected its operation, later alternatives are not tried, including alternatives contributed by another computation targeting the same field. A later computation's alternatives can win only when every earlier alternative falls through without selection. Delta reporting is decided afterward from the prior target state. ERRORED and poison are decided before the empty gate and are not swallowed by it.

The root-store decision and its precedence over target format checking are source- and dual-strategy-differential-locked in a12-dmkits' [`EmptyConcatStoreDiffTest`](../../a12-rulekit/adapter/src/test/kotlin/io/github/mbackschat/a12/dm/adapter/laws/EmptyConcatStoreDiffTest.kt) (IF123).

The STRING column above is the *concatenation* position. A **bare string copy** (`X = [S]`, one operand, no `+`) of an empty operand computes **nothing — CLEARED**, never a stored `""`. The `FieldValueAsString` coercion of a not-given read follows the same per-context split — a standalone copy CLEARS (the store path treats an empty string value as "no calculation was done"), a concatenation gets `""`; the coercion's operand must be a NUMBER/AMOUNT field (a string copies bare). For a filled Number, the coercion returns the same regime-selected formal-read text described in [§5](04-numbers-and-decimals.md#stored-decimal-identity-and-runtime-read-text-depend-on-the-storage-regime): a decimal-valued placement is re-rendered by the strip-and-minimum-scale projection, while a String-valued placement is read verbatim. It is not a separate raw-storage channel.

## 3. Two kinds of "no value" — the empty cascade vs the poison ⚠⚠

A CLEARED cell is not one thing; *why* it cleared decides what a downstream computation sees.

### 3.1 A precondition-clear cascades as EMPTY

A field whose own computation was cleanly unselected — because its `commonPrecondition` was false or no alternative matched — reads as **plainly empty** in a dependent: `FieldFilled(dep)` is false, a number operand reads empty-as-`0`.

The mechanism: a calculation run **strips every calculated field's *input* value from the working data**, so an un-computed calculated field reads **empty regardless of what the document stored**.

**The strip reaches every content read, not only a field read** ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-23c-computation-cascade-reads)). Inside one compute call a calculated field's stored value fills no group, is not counted by `NumberOfFilledFields`, has no category, and is never formal-checked as an operand: a malformed stored value raises nothing once the field is computed, because the read sees the computed value. What those reads see instead is the value a computation produced earlier in the same call. It fills the group holding it and, through non-repeatable groups, that group's parent too, in each row it was computed into, a keyed row included, and it counts. A poisoned result fills nothing, and a group read over it does not poison. A target's own stored value does not answer its own precondition, while a stored non-computed field beside it does. Confidence limit: every measured row runs a full `compute`, so the strip's reach over calculated fields a call does not run rests on a source reading, and the fill is measured to depth two through non-repeatable groups only ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-23d-grandparent-fill-and-malformed-key)).

Do not put every domain-undefined numeric operation in this clean-empty class. Division by zero and runtime-invalid integral power belong to the poison class in §3.2 when the result remains in the numeric family: the shared invalid numeric result survives legal `Abs`, `Min`, `Max`, and `RoundAccounting` wrappers, marks a Number target invalid, emits `berechnungsWertFehler`, and makes a dependent read poison. A Date-valued consumer projects the same missing numeric amount differently: `AddDays(StartDate, RoundAccounting(div, 2))` produces no Date value, clears a stale Date target, and does not attach `berechnungsWertFehler` to that Date target. These are consuming-operation rules, not contradictory global classifications. Maintained a12-dmkits [`DivisionDomainFailureComputationDiffTest`](../../a12-rulekit/adapter/src/test/kotlin/io/github/mbackschat/a12/dm/adapter/laws/DivisionDomainFailureComputationDiffTest.kt) and [`PowerDomainFailureComputationDiffTest`](../../a12-rulekit/adapter/src/test/kotlin/io/github/mbackschat/a12/dm/adapter/laws/PowerDomainFailureComputationDiffTest.kt) cover both domain-failure families, numeric-wrapper preservation, target formal error, and dependent poison through both kernel routes plus the peer interpreter. Fresh no-value-output versus stale CLEARED remain only delta projections and do not imply a clean-empty Number target.

### 3.2 An invalidity-clear POISONS

Reading a **formally-invalid cell** (an invalid operand's target, a domain-invalid computed Number such as division by zero or runtime-invalid integral power, an unavailable ERRORED computed value, [§3](02-logic-and-formal-errors.md)'s third state generally) **throws** inside the computing instance: it **aborts**, skips its remaining alternatives, produces no value, and **is itself marked invalid** — so its dependents' reads poison in turn.

**A category read is a read of that cell.** `[Plan -> Tier]` over a `Plan` holding a token outside its value list poisons exactly like the value read: the instance aborts and its target is reported CLEARED, whether a comparison, `FirstFilledValue`, or a value-list quantifier reaches the read ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-24b-category-read-poison)). An index cell the document makes unavailable, a key two rows carry or a row carrying none, poisons the category read as it does the value read ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-25h-category-index-relevance)).

Once a computed target is marked invalid, the cascade is **cause-blind**. The computation cache retains only invalid-target membership; a later value or presence read throws for that target without carrying the producer's attempted value, target-error subclass, originating formal cause, or message, and the generated catch marks the dependent invalid without adding a cascade message. Those producer details may remain in the producer's own rich outcome, but they do not pass through the dependency read.

The poison is **read-driven, therefore order-dependent**:

- compute's `And`/`Or` collapse each clean condition result to whether it is known true and evaluate left-to-right. `And` skips its right side when the clean left is false or unknown; `Or` skips its right side when the clean left is true. A poison already encountered on the left aborts either connective. A bare-group field-fill quantifier consumes the canonical field-major, repetition-major stream defined by [the fill-quantifier clause](02-logic-and-formal-errors.md#a4-fill-quantifiers-group-scopes-and-the-two-iteration-ranges) and **stops at its deciding cell**. A reached invalid cell poisons; one *beyond* a connective or scan stop is **never read and never poisons**.
- **A filtered aggregate whose candidate set is empty produces no value for that target row, and a dependent reads it as EMPTY. What the reporting channel *shows* for that row follows the target cell's prior state, not the ground of the no-value.** A target row whose cell held a value is reported *present and cleared*; a target row whose cell was already absent is *absent from the reported outcomes altogether*. Both grounds of no-value — an empty candidate set and an unmet precondition — behave identically once the seed is held fixed, so the split is a property of the cell rather than of the reason ([seed axis](../docs/sources/having-filter-probes.md#src-correlated-filter-string-computed-target), [clear-kinds account](../docs/sources/computation-scheduling-probes.md#src-diamond-dependency-clear-kinds)). Downstream the split is invisible: a dependent is present on every row and reads either shape as EMPTY, and neither poisons it. So the distinction is a **reporting** fact that a result-rendering consumer must carry and an evaluating consumer must not. So the reported result has **two** absence shapes while the **cascade has one** — a `Length` dependent of the absent row computes `0`, exactly as it would over a precondition-cleared producer. The distinction is therefore visible to a consumer reading the *result*, not to one evaluating a dependent, and neither kind may be treated as poison. The row identity is separately controlled: reordering the keys so the empty-candidate row moves to the front moves the absence with it ([checkpoint](../docs/sources/having-filter-probes.md#src-correlated-filter-string-computed-target)).
- `FirstFilledValue` is the one **stop-at-first** value combiner: it consumes target cells only until the first filled cell, so an invalid *target-cell tail* is invisible, while an invalid target cell before the first given one clears the computation. A reached filtered star retains [§7.3](07-repetition-and-iteration.md#3-the-filter-having-the--correlation-and-aggregation)'s separate one-kept-successor lookahead: filter poison while finding that successor can precede the current target, but a terminal current target hides filters after the prefetched successor and every later authored operand.
- A numeric arithmetic expression evaluates its **one-pass lowered tree**, not necessarily the authored tree, from left to right. At a binary node the left subtree is evaluated first and the right subtree is evaluated before the arithmetic method is applied. A domain-invalid numeric result such as division by zero or runtime-invalid integral power is a value-level invalid result rather than a thrown read, so it does not hide a later poisoned read; a poison already thrown by the left subtree aborts before the right subtree. A lowering rewrite can therefore change which of two poisoned field reads is encountered first.

Both cascade read-rules reach **inside** a downstream computation's `Having` filter and its preconditions' quantifiers — a silently-cleared upstream target reads EMPTY there; a poisoned one poisons the reading computation.

**That split governs a plain operand read too, and it is the whole difference between the two clear-kinds.** Measured on a four-deep dependency diamond — one producer, two independent dependents, one join — a producer cleared by an **unmet precondition** is read as EMPTY by its dependent, which answers `0`, and the join answers over it normally; a producer cleared because its own source was **malformed** poisons its dependent, which clears, and the join clears with it. Same topology and same operands: only the kind of the producer's clearing differs. **Poison therefore crosses a join** rather than being substituted away — a join reading one poisoned and one clean operand clears, while the same join over an *absent* source substitutes empty-zero and computes, which is the control that keeps the two accounts apart. **A consumer cannot read the kind off the target's own reported state:** both kinds surface as cleared-and-not-errored with no formal-operand entry for the precondition case, so the distinction is observable only in what the dependents do. **A clear is visible to a dependent inside the same call.** With a stale value stored in the cleared producer's target, the join answers over an *empty* read rather than over that stored value — measured as `7` where reading the stale `99` would give `106`. So clearing takes effect before the dependent's read, not at application time. **A bare constant operation honours a precondition** exactly as a computed one does, writing when met and clearing when not, and its clear is read as empty by the same rule. Ordering is correct through the join at that depth — evaluating the join before its branches, or the branches before the producer, each predicts a different value for the joined target and both are refuted by the clean row. One failing branch does not abort the plan: the independent branch computes its value in every failing row.

> **Non-normative implementation note.** Thread compute reads through an error effect, e.g. `Except Poison Value`, with **short-circuiting `And`/`Or`** that do *not* evaluate the right operand once the left decides (so an unread invalid cell never surfaces its `Poison`). This makes order-dependence a *consequence* of the evaluation order, exactly as in the engine — do **not** eagerly evaluate all operands and then combine, or you will poison on cells the engine never reads. Model the empty-cascade separately: **before** computing, replace every computed field's stored input with `empty` in the working document, so a not-yet-computed dependency reads empty (§3.1) rather than its stale stored value. These two mechanisms — pre-strip-inputs (empty cascade) and throw-on-read (poison) — are distinct and must both be present.

Temporal operand-list extrema evaluate reached operands in order. A malformed field before an unresolvable DateTime literal aborts without a target-local `berechnungsWertFehler`; reversing those operands reaches the literal failure first and emits that code. Both invalidate the target and poison its dependents. An ordinary literal is the control that distinguishes failure order from an unconditional literal error ([measurement](../docs/sources/temporal-runtime-fold-probes.md#src-compositional-temporal-disposition)).

In validation, a reached unresolvable DateTime label in a comparison produces the authored rule’s `VALUE_ERROR`; it does not become an ordinary unknown operand or truth-valued leaf. The [Boolean truth pass](10-validation-and-polarity.md#31-truth-testing-and-message-classification) can skip the comparison after a false or unknown prefix, but a later false `And` operand cannot suppress a runtime failure already reached. A true whole condition can reach a previously skipped comparison during its separate message-classification pass. This is measured with absent, malformed and valid fields in a nonempty Berlin document; it does not change validation’s enclosing content or relevance gates ([same measurement](../docs/sources/temporal-runtime-fold-probes.md#src-compositional-temporal-disposition)). In an ordinary full-validation row loop, that failure terminates the rule rather than continuing to later rows. Its error message uses the iterator’s first address, even when the failing comparison was reached in a later row. Ordinary fired verdicts continue iteration, and a failed rule does not stop independent rules ([iteration controls](../docs/sources/temporal-runtime-fold-probes.md#src-compositional-temporal-disposition)).
### 3.3 What compute *reports*

The full V2 computation result is richer than a three-way change delta. It exposes all successful non-clearing computed instances, including successes unchanged from the computation source; the source-relative changed subset of those successes; erroneous computed instances; cleared instances that were filled in the source; and eagerly collected formal operand errors as a separate channel. `noErrorOccurred` is true exactly when both error channels—the erroneous computed instances and formal operand errors—are empty. The eager formal-error inventory does not replace dependency-sensitive execution: whether an invalid producer poisons a dependent remains determined by scheduling and whether that dependent actually reads it.

**Result assembly can fail after computation has finished.** The V2 result requires one diagnostic per full error pointer before separating computed-instance errors from residual operand errors. Two findings at the same complete pointer cause a whole-call duplicate-key failure, regardless of their codes or payloads; findings at distinct physical row pointers do not collide. A reserved Custom report together with a selected index-uniqueness finding can trigger this failure. Independent computations, including their target callbacks, still run before assembly fails. No computation result or applied snapshot is returned, and the original document remains unchanged. An ordinary rejected operand or a duplicate index with only one finding per row instead permits result assembly; an unused custom index contributes no selected preliminary finding. [The committed assembly controls](../docs/sources/inbound-handbacks.md#src-computation-diagnostic-assembly) distinguish execution, report construction and application.

**Formal input scope includes preprocessed group operands.** It remains narrower than full validation's document-wide findings. Before collecting operands, each authored computation below a repeatable group receives an implicit positive guard on its innermost repeatable ancestor, unless its explicit conditional-group profile already protects that group or a narrower group containing the target. Expanding that implicit guard includes every uncomputed descendant, including fixed and repeatable descendants. An explicit narrower containing-group guard can therefore exclude outer siblings that the default row guard would include. An inner repeatable target adds no outer-parent subtree, and a root-only target adds no implicit subtree. Computed fields remain excluded. Declaring the computation elsewhere does not change this target-based preprocessing. Operand-derived over-limit controls retain their ancestor/descendant relation ([operand controls](../docs/sources/over-repetition-probes.md#src-over-limit-finding-multiplicity), [target-subtree controls](../docs/sources/inbound-handbacks.md#src-inbound-2026-10-09a), [guard qualification](../docs/sources/computation-scheduling-probes.md#src-computation-guard-operand-scope)).

**A cleared instance carries no informative value of its own, so clearedness is a channel-membership fact and never a value reading.** Its value accessor reports **present and empty** for every clear, not the stale input it erased, measured on both codegen strategies. A consumer that reads that accessor instead of the channel therefore aliases a clear with a computed empty string, and one that treats the accessor's optional as a has-value flag reads a clear as a value. Whether a *computed* empty value is reachable at all is a separate per-target-family question and is not settled here, so the separation is a guarantee about the shape of the report rather than a claim that both states occur for every family.

The two public error channels partition one computation message stream by exact pointer matching. A message is associated with an erroneous computed instance only when a nonempty computed value exists at that pointer; otherwise it remains in the API-named `formalErrorsInOperands` residual channel regardless of what the message points at. A value-less Number target failure can therefore be both source-relative `CLEARED` and represented by a target-pointed residual message, with no erroneous computed instance, and still makes `noErrorOccurred` false. Cascade poison and clean no-value emit no such message.

Before ordinary computation processing, the V2 operation formally validates every non-computed field in the source-defined operand set. In an expanded A12 model, that set is the union across every checked computation of directly referenced fields; every field contained by an ordinary referenced group; every field contained by a conditionally referenced ancestor group; each index field needed by a semantic-index or parallel-iteration group; and fields contributed by the implicit guards above. The collection traverses operations, alternative and common preconditions, filters, and semantic-index key expressions; computed fields are then excluded from formal input checking. This is a checked-plan inventory, not a runtime read trace or dependency schedule.

The same full-call index-default staging used by full validation runs after computation's formal ingestion and before its selected index preliminary rules. An eligible absent or present-empty Enumeration index can therefore receive its declaration-owned S-value during computation. Mandatory and uniqueness preliminary rules run only for index fields retained by the expanded operand inventory; an unused bad index does not enter this prepass. Selected invalid filled values are reported, an ordinary required-empty omission is not, and a selected empty or non-unique index is reported unless full-call default staging supplies its value. Computation processing continues after these errors are collected. The resulting `formalErrorsInOperands` inventory is eager and independent of runtime reachability; it must not become a global abort or an eager poison injected into every computation. The legacy unique-entity/H-model path has a different all-noncomputed input profile and early-abort behavior and is outside this expanded-A12-model contract.

A computation reached through a **parallel-iteration** operand does not use that read-time index gate at all, and its failure blast radius is wider than the malformed row. On this route the iteration-values lookup yields nothing, so the loop body never executes and no read-time throw can occur; affected instances are instead marked **after** the loop. The marking keys on each existing instance's coordinates **truncated to the shared prefix** — the level of the common ancestor of the computed field and the malformed index group's parent, plus one — and every instance whose truncated prefix matches is marked. The consequence is that **which index group carries the malformed key decides how far the damage spreads**:

- a malformed key in an **off-path** iterated index group truncates *above* the sibling level, so sibling parent rows are marked too and a clean sibling's computed target is **cleared** even though its own key still matches a clean row;
- a malformed key in the computed field's **own on-path** index group truncates *below* the sibling level, so siblings stay distinguished and a clean sibling's target **survives with its value**.

The over-marking in the first case is deliberate rather than incidental. Both code-generation strategies agree on both outcomes and on the all-distinct control, so this is engine behaviour and not a strategy split. Two authoring preconditions gate the route and explain why ordinary corpora never reach it: the iterated group's index field must carry the **same name** as the index field on the computed field's path, and the operand must be a bracketed **non-starred** reference. A starred reference is a wildcard rather than an iteration and takes the ordinary route instead.

The change projection remains exact: **VALUE only on a typed change** (the computed value differs, by typed equality, from what was stored in the computation source), **CLEARED only when the source cell was filled**, and **ERRORED unconditionally**. A report-all evaluator must project to this change boundary before differential comparison, but that projection must not erase successful unchanged instances from the full result. The public computed-instance collections are extensional by pointer and payload; no schedule-order promise follows from their collection iteration order.

Application preserves that source-relative classification when the retained result is applied to another compatible destination. CLEARED places a present-empty target and its directly addressed missing ancestry even when the destination target was absent; ERRORED clears only a destination target that already exists; changed VALUE places the exact computed value and directly addressed missing ancestry. A no-value outcome over an absent source target mints no CLEARED action and therefore remains a no-op on the destination. At one repeatable level, a direct Number or String placed action also materializes every predecessor row through its exact coordinate, retains existing predecessor content, and preserves numeric row addresses independently of CLEARED-before-VALUE action-category order. At exactly two finite direct Number or String levels, the outer predecessor prefix is complete while each inner prefix is materialized only beneath the action's addressed outer row; synthetic outer predecessors gain no inner rows. Later validation reads the returned applied document directly, with no implicit validation during computation and no recomputation before the explicit validation call. The measured one- and two-level Number and String topologies, later-validation address sets, and remaining depth and family limits are owned by [`01-data-model.md` §4.3](01-data-model.md#43-the-compute--apply--validate-flow).

For a Number target, “typed equality” is specifically equality of the source and computed V2 objects, not equality of parsed amounts or internal strings. Computed Number output is a `BigDecimal`; an original `BigDecimal` is equal only when value and scale agree, while an original V2 `String` or a negative-scale `BigDecimal` is unequal to every computed Number form even when its plain text and numeric amount agree. Thus computed `7.00` is unchanged only against a source decimal with coefficient `700` and scale `2`; source text `"7.00"` is still a change.

Time change classification is not operation- or placement-specific. It compares the stored and computed V2 objects, so the ingress route determines source identity. Typed V2 ingress converts non-String kinds to their typed objects: nonrepeatable and repeatable `Time(...)`, `TimeFromDateTime`, and Time `FirstFilledValue` therefore use ordinary stored-clock equality, and reapplying a computation over its own output produces no VALUE action for an identical clock. V1 String ingress instead leaves a typed cell holding unconverted text, so every measured non-String kind is changed even when its seed text denotes the computed value; Number, Date, DateTime, Time, DateRange, Boolean, and Confirm all show this behavior, while String is unchanged on both routes. A source-identical discriminator must therefore use typed ingress or reapplication rather than a V1 text seed.

## 4. The stored form — a computed value lands as a string in the target's shape

A computed value is ordinarily stored in the **target field's own declared format**. The bounded unconfigured interpreted DateRange declaration-order divergence is stated below.

A dependent temporal operation reads that stored representation under the target's runtime policy; it does not inherit components discarded by rendering. With Base Year 2024, adding one day to a `dd.MM.` value `31.12.` stores `01.01.` and a dependent Year extraction reads 2024, not the expression's 2025. Similarly, a wrapping FROM range copied to an admitted TO target is re-anchored as TO on dependent read: without Base Year, the observed start/end years are 1999/2000. Static component compatibility still applies: a full-Date field cannot be copied into a yearless Date target, and a range first-filled list of unlike declared formats is refused ([stored-read controls](../docs/sources/inbound-handbacks.md#src-inbound-2026-10-09a)).

A component-omitting date target keeps only the components its format names, and a declared **Base Year contributes nothing to the stored text**. One `"05.03.2024"` constant written to targets declared `MM`, `MM-dd`, `yyyy-MM`, `yyyy`, and a complete date stores `03`, `03-05`, `2024-03`, `2024`, and `2024-03-05` respectively, unerrored and uncleared, in a model that declares a Base Year. The Base Year belongs to the **authoring** gate only, and that gate is symmetric: **a Base Year is required exactly when the constant and the target disagree about carrying a year, in either direction, and never otherwise.** A complete constant is admitted into any year-bearing format — `dd.MM.yyyy`, `yyyy-MM-dd`, `yyyy`, `yyyy-MM`, `yyyyMM` — with no Base Year, and refused into `MM` or `MM-dd` without one; a **yearless** constant such as `"05.03."` is the mirror image, admitted into `MM` and `MM-dd` with no Base Year and refused into every year-bearing format without one ([§6](05-dates-and-time.md), [checkpoint](../docs/sources/temporal-constant-and-base-year-probes.md#src-temporal-constant-literal-composition)). The `yyyy` target is what identifies the year as the deciding component rather than component agreement generally: it differs from a complete constant in two components of three and needs no Base Year, while `MM-dd` differs in one and does. Read instead as *a yearless format needs a Base Year*, the rule gets both yearless-constant rows wrong. Having admitted the constant the store still writes no year.

**The gate reads the literal's temporal family and the year agreement, and nothing else — in particular it does not compare component sets.** The separating target is `MM`, which names the month alone: the yearless literals `"05.03."` and `"13.07."` are both admitted into it with no Base Year declared, and the store writes `03` for the first, uncleared and unerrored, silently dropping the day. A component-set reading refuses both, since each literal carries a component the format does not name. The controls on that same target keep this from being a claim that `MM` is unguarded — a clock literal into `MM` is refused, and so is a complete date without a Base Year. **Both refusals report the same `MVK_INVALID_COMPARE_TO_DATE`,** so the wrong-family ground and the year-disagreement ground are indistinguishable by code and a consumer must re-derive which rule fired from the pair rather than read it off the diagnostic. **The year-agreement half is conditional on the model having no Base Year**, which the sentence above states only for the rows it measured: a declared Base Year makes year agreement vacuous, so the very `"05.03.2024"`-into-`MM` row that is refused here is admitted once the flag is set, and clearing it restores the refusal on byte-identical model bytes ([checkpoint](../docs/sources/temporal-constant-and-base-year-probes.md#src-base-year-yearless-store)). A third ground rides beneath both and belongs to the literal rather than to the pair: the constant must classify as a real calendar date at all, so `"29.02."` and `"31.04."` are refused against an admitted `"30.04."` under the same code, and that check consults no Base Year ([§1](05-dates-and-time.md#1-constant-format-and-the-stringdate-literal-ambiguity-)). **This whole gate is the target carrier's, and a temporal *operation* operand is governed by three different ones** — operand granularity (`MVK_WRONG_DATE_FORMAT_FOR_OP`, refusing a `MM` field in `DifferenceInDays` while admitting a `MM-dd` one), year agreement under its own code (`MVK_DATE_WITH_AND_WITHOUT_YEAR`), and calendar validity reported at the literal (`MVK_INVALID_DATE_STRING`) ([checkpoint](../docs/sources/temporal-constant-and-base-year-probes.md#src-yearless-anchor-is-the-base-year)). A consumer implementing one temporal-constant gate for both carriers is wrong in both directions. The mirror separator on the time side does not exist: an hour-only `HH` format is refused at field declaration, so no target can name a proper subset of a clock literal's components. So a consumer must not complete a yearless store from the Base Year, and must not infer from an admitted constant that the target retains the year the constant supplied.

For the closed direct single-level starred temporal `FirstFilledValue` profile, selection happens in the typed value domain before target rendering. A full Date contributes its exact instant to this target path; its underlying scalar value also carries decoded date parts and calendar basis, but this computation does not retain those two components after selection. A Time retains only its decoded `TimeOfDay`, not the runtime transport date or instant, and a DateTime retains its exact instant rather than source text or a cached wall label.

A DateRange retains an exact ordered endpoint pair for the two full-Date policies, `yyyy`, `yyyy-MM`, and Base-Year-completed `MM` or `MM-dd`. Without Base Year, interpretation-free `MM` with slash or an empty separator, `MM-dd` with slash, and `dd.MM` with dash retain only their component pairs and never acquire a synthetic year or instant. Direct single-level starred `FirstFilledValue` is independently measured for static admission and runtime under all eight declaration pairs. Source and target need only expose the same declared component set, so every interpretation-free crossing within a set is admitted in both directions: the two full-Date policies cross, `MM` crosses between slash and the empty separator, and `MM-dd` crosses with `dd.MM`. A different component set is refused, and the target policy decides the stored spelling. An unconfigured interpretation-bearing route is separately declaration-order dependent in the Kernel. In the measured two-block control, placing interpreted `dd.MM` declarations first makes an interpreted `MM` source `11/02` valid and stores `01.11-01.02`, while a standard `MM` source `03/10` stores `01.03-31.10`; placing the same `MM` declarations first rejects the wrap and stores `03/10` for the ordered source. Both Kernel strategies agree within each order. This falsifies both the former universal dotted-carrier rule and a universal declaration-local rule. No broader account is stated until the generated shared-format equivalence classes and their consumers are measured.

The checked direct-field DateRange account separately scans a finite list of at least two nonrepeatable sources under one common lexical profile, the declared `(format, separator)` pair, from all eight admitted pairs. `interpretationOfYear` is not part of that source-uniformity profile, so otherwise matching `FROM` and `TO` sources may appear in one list. It scans them in authored order: empty sources continue, while the first present value or reached formal source terminates selection and hides every later source. The eager formal-input inventory still reports every malformed selected source independently of that lazy computation scan. The common ordered scan returns no value on exhaustion.

Kernel calibration covers full-Date dotted/dash lists at lengths two and three, three-source lists for all four slash-separated fragment profiles, an empty-separator `MM` source list crossing to a slash-separated `MM` target, and a two-source dotted `dd.MM` list mixing `FROM` and `TO`. It also covers ISO/slash list execution, an empty-separator `MM` target rendering the halved form, a fragment list's formal suffix reported by the eager inventory while an earlier value is kept, and a length-four list selecting its fourth source. Arities above four, the remaining five declaration pairs as list carriers, and a seeded target on those profiles remain external evidence pending. Format and separator remain declaration policy. This is a semantic typed-value account, not a claim that the externally observed implementation necessarily decodes and re-renders rather than copying text.

- a **TIME** produced by `Time(...)` or `TimeFromDateTime(...)` as exact zero-padded `HH:mm:ss`. This bounded computation target admits the clock format and requires complete hour/minute/second components, so every admitted real clock passes the basic target check. Other legal formats on a TIME declaration are outside this target profile. The runtime temporarily carries the clock as 1970-01-01 in the model zone, but neither that date nor an instant is part of Time identity or stored output. Rules evaluated after application observe the stored wall clock rather than a UTC decoding of that carrier. Missing, fully present impossible, and non-relevant constructions store no value; formal unavailability remains poison rather than becoming a clock;
- a **DATE** in that field's `format`, not ISO ([§6](05-dates-and-time.md)). Computation authoring admits only a `FULL` Date target. `FirstFilledValue` selects a Date before the target renders it: the source list retains its exact-format gate, but the target need not share that spelling or component precision. Target compatibility follows the temporal comparison rule, including year presence and Base Year. The [fixed/repeated target matrix](../docs/sources/repeatable-temporal-computation-probes.md#src-temporal-target-profiles-k11) admits dotted full-Date sources into ISO targets and full-Date or year-month sources into year-only targets, storing `2024-05-06` or `2024` from the same selected value as appropriate. An empty first source falls through; a reached malformed source clears instead of using the later valid source, without affecting another physical row. DateTime-to-Date remains refused. The repeatable sibling-star route separately admits an ISO target with the pre-1900 check enabled when the ISO source does not carry that check. `DAY_OPTIONAL`, `MONTH_OPTIONAL`, and `YEAR_OPTIONAL` targets are rejected with `MVK_INVALID_DATE_TYPE` because the generated implicit validation comparison reads the computed target, and suppressing that error is itself rejected with `MVK_INVALID_SUPPRESSED_WARNING`. For an admitted `FULL` target, the runtime renders the concrete Date first and then runs the basic target check; an enabled pre-1900 check therefore reports the exact attempted Date as ERRORED rather than erasing it;
- a **DATETIME** selected by the closed direct `FirstFilledValue` profile by rendering the exact selected instant in the model zone. The currently calibrated profile stores whole seconds as `yyyy-MM-dd'T'HH:mm:ss`; source text and a cached source wall label do not determine the result;
- a **DATE_RANGE** selected by the closed direct single-level starred `FirstFilledValue` profile under all eight statically admitted and runtime-measured policies: `yyyy-MM-dd` with `/`, `dd.MM.yyyy` with `-`, slash-separated `yyyy`, `yyyy-MM`, `MM`, and `MM-dd`, `MM` with an empty separator, and `dd.MM` with `-`.

  Assignment and direct-star target admission compare date-component sets, not lexical profiles, so a dotted full-Date range may be stored into an ISO full-Date target and the target renders `yyyy-MM-dd` endpoints. Different component sets are refused with `MVK_INVALID_COMPARE_TO_DATE_RANGE`; the direct-field-list shape separately requires one common lexical `(format, separator)` pair, excluding `interpretationOfYear`, and its measured lexical mismatch yields `MVK_VARYING_TYPES_NOT_ALLOWED`. The list's two gates are **ordered**: the common-profile requirement decides first, so a three-source list whose odd member matches the target still reports the varying-types code rather than a component refusal. Both spellings of each set participate on either side of every interpretation-free shape: an empty-separator month source list feeds a slash-separated month target, and a `MM` or `MM-dd` construction reaches a `MM`-with-empty-separator or `dd.MM` target. The target's own spelling renders those list and construction results. The unconfigured interpretation-bearing direct-star route has only the declaration-order discriminator above, not a field-local target rule.

  Exact or Base-Year-completed cells render their resolved endpoints through the target profile. Without Base Year, `MM`/slash and `MM-dd`/slash constructions, plus selected cells under all four yearless runtime profiles, render their retained ordered components without manufacturing a year. An inverted construction retains the attempted target text as ERRORED, empty construction input clears, and formal input poisons before empty.

  Direct-construction runtime calibration now covers every admitted constructor target: full-Date input to the dotted/dash and the ISO target, no-Base-Year `MM` and `MM-dd` under both spellings of each, the `yyyy` and `yyyy-MM` targets including their equal-endpoint rows, and the Base-Year-completed `MM` and `MM-dd` targets, which render back to their declared components even where the completion reaches a leap-aware month end. Every profile retains an inverted attempt as ERRORED under its own spelling. Direct-star static admission covers all eight declaration pairs and every crossing within a component set, while runtime calibration covers all eight pairs, both full-Date crossing directions, the yearless `MM` and `MM-dd` crossings, and configured and no-Base-Year fragment results.

  The direct-field-list external denominator and remaining limits are stated above. Failure to resolve an exact cell's endpoint remains an explicit unsupported/fault boundary rather than a copied or guessed target value;
- a **NUMBER** first receives a **scale-19 `HALF_UP` pre-round**, then follows one of two scale branches. On the ordinary **fit** branch, where the stripped natural scale does not exceed the target's `maxFractionalDigits`, it renders at `max(naturalScale, minFractionalDigits)` (`10` into a two-decimal field stores `10.00`) with **no length cap**. An over-15-digit fit result is therefore retained **in full** and is ERRORED by the ordinary target check, never re-rounded to pass it. On the **no-fit** branch, reachable in a legal model only when the computation suppresses `MVK_INVALID_COMPARE_DEC_PLACES`, the value renders with at most 16 significant digits when its integer part permits that bound and is marked ERRORED unconditionally; the shared total-digit/signedness prefix still supplies a more specific target cause when it fires. On both branches and at every magnitude, the stored text is plain dot-decimal notation and never exponent/scientific notation. The no-fit branch is an explicit warning-suppressed compatibility surface, not permission for an ordinary implementation to round every result to the target's maximum scale.

The computed Number's canonical rendering makes invalid characters, plus, signed zero, and leading zeroes unreachable, and fit rendering already guarantees the declared fractional interval. The remaining fit-path first-error order is: more than 15 total digits; forbidden negative sign; effective integer-digit cap (explicit `maxIntegerDigits`, otherwise the amount trait's `15 − maxFractionalDigits`); forbidden zero; rendered minimum length; rendered maximum length; value below the inclusive minimum; value above the inclusive maximum. Length counts the sign and decimal separator. On the warning-suppressed no-fit path, only total-digit overflow and forbidden negative sign precede the inevitable decimal-place mismatch; the fitting-only suffix is not reached.

The stored form is **what downstream sees**: a dependent computation reads the padded string back, and the change-equality of §3.3 is **scale-sensitive** — a computed `7.00` over a stored `7` counts as a change. Target rejection retains its attempted stored form and reports ERRORED unconditionally. A domain-invalid expression such as legal rounded division by zero or runtime-invalid integral power is different: it produces no attempted stored value, marks the target invalid with `berechnungsWertFehler`, has no delta for a fresh target and CLEARED for a stale filled target, and poisons a dependent read.

A computed result is formal-checked with the **basic** format check only — type format plus declared constraints, **without** the charset / leading-blank / trailing-blank baseline that stored *input* values get — so a computed string starting or ending with a blank stores as a plain **VALUE**.

For an ordinary **STRING** target, the final-empty root decision happens before that basic check, so no value clears rather than violating a positive minimum. A nonempty attempted value is checked in declaration order: forbidden CR/LF first; then, when line breaks are permitted, CRLF→LF normalization in a temporary checking view; then the declared pattern, positive minimum length, and positive maximum length. Length is the normalized UTF-16 code-unit count, an explicit zero bound is inactive, and both authored bounds remain active when combined. The normalization does not rewrite the computed attempt: an accepted value and an ERRORED value both retain the exact attempted internal String, while the first failing clause supplies the error cause.

For an ordinary closed **ENUMERATION** target, the authoring gates below refuse an out-of-domain computed token before runtime. A constant must belong to the target's stored-token domain. A direct Enumeration source must have its complete stored-token domain contained in the target domain and must satisfy the ordinary direct-Enumeration display-remapping compatibility gate. A category source is checked by its complete projected category-token domain and bypasses that direct-display gate. A source reached by up-steps from a fixed group inside a repeatable one is judged as a local one: `[../Banded -> Band]` is admitted where `Band`'s tokens lie in the target domain, and the wider category and the wider field draw `MVK_ERROR_INVALID_ENUM_CALCULATION`, as does a keyed String source such as `[Claims/Memo For "X"]` ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-25i-enum-source)). `FirstFilledValue` is admitted only when every selected Enumeration/category source satisfies the same target compatibility. Arbitrary String fields and expressions are not Enumeration-producing operations merely because both families store text. A Number source is refused `MVK_INVALID_COMPARE_TO_ENUM_OR_STRING`, measured on a root computation and on one reading its declaring group's Number ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-26b-dispositions)). At runtime, an empty selected source remains no-value, a formally invalid reached source poisons the computation, and an admitted present source stores its exact selected token through the common String-shaped target result.

A computed **CUSTOM** target invokes its registered validator on the attempted text, with the declaration bounds, effective locale and stored-value mode. An empty root or inherited poison bypasses the target callback. Acceptance produces the usual value result; any callback finding produces `ERRORED` with the exact attempted text and project payload, even if it equals the old target. An ordinary rejection makes the target unavailable to later computations. The exact reserved `testIDNummer` report instead leaves the attempted value readable in the same call, while application still clears that errored target. Neither the old target's stored value nor source acceptance can replace target checking; the same rule applies after `FirstFilledValue` selection. [Custom ingestion and continuation](06-strings-and-enumerations.md#a3-custom-field-type-validation) distinguish this target check from the source's single normalization pass.

> **Non-normative implementation note.** Keep a Number target's exact decimal representation as `{unscaled, scale}` through target checking and typed change comparison: kernel V2 uses scale-sensitive decimal equality, so `7` and `7.00` differ even though their rational amounts agree. Render the normalized stored representation only at the document boundary in plain dot-decimal form, and parse that stored representation on downstream reads; any locale-specific decimal separator belongs to a separate display/materialization layer and does not alter stored text. Keep the computed-result formal check a *reduced* variant (no charset/blank baseline) distinct from the input formal check of [§3](02-logic-and-formal-errors.md).

## 5. Where a computation runs — scope and the parallel join

- A computation iterates over its **computed field's** repetition scope — where it *writes*, not where its node is declared — and an all-non-repeatable target computes exactly one instance even on an empty document (a non-repeatable group is implicitly present). That instance's precondition is decided like any other, because **a computation precondition has no row gate**: `[Quantity] < 5` selects on `{}`, on an empty `Order`, and on an `Order` holding only the computed target's own stored value, which the strip above removes. A guard over a group below a repeatable row selects whether that group is empty, absent, or holds only another field ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-23c-computation-cascade-reads)). Validation's [row gate](03-empty-and-required.md#a4-the-row-gate--where-the-substitutions-stop) is validation's alone. For the distinct rule-iteration account, see [§9](07-repetition-and-iteration.md).
- **Which operands that scope admits on the ordinary bound-scope route** is decided per operand by the target's own scope, not by placement equality: an operand is admitted exactly when the computed target's repetition scope binds every repeatable level the operand crosses. A nonrepeatable operand feeding a repeatable target is therefore ordinary, as is an operand one level up feeding a target two levels down. An operand crossing an additional repeatable level **below the target's scope** is refused `MVK_NO_WILDCARD`, and the `*` wildcard under an aggregate is the flattening route for that shape rather than a variant of this one. A sibling repeatable group instead selects the separate parallel-iteration route below: matching index-field names admit it, different names draw `MVK_ERROR_FIELD_INVALID_INDEX`, no index field draws `MVK_NO_WILDCARD`, and a starred aggregate remains admitted. At runtime an ordinary operand is read at its **own** path inside the current target row, which decides exactly which target instances it reaches. A form-level operand reaches every target instance; an operand **one level up** from a two-level target reaches only the instances under its own enclosing row, and two enclosing rows with different values give their own leaves different results. Emptiness and formal invalidity travel the same way: an invalid operand clears exactly the target instances beneath it and leaves its siblings' instances computing normally.
- The computed target field itself is statically forbidden anywhere in the computation's common precondition, alternative preconditions, or operations, including nested condition/filter syntax. Which class is reported follows the **reading mode** of the self-read rather than the slot it sits in. A plain direct target-field occurrence reports `MVK_ERROR_REFERENCE_TO_CALCULATED_FIELD`. An occurrence read through a **projection**, an Enumeration category `[target -> Category]` or a semantic index `[target For key]`, instead reports `MVK_ERROR_SEMANTIC_INDEX_OR_CATEGORY_FOR_ERRORFIELD`, whose repair is to drop the projection rather than the reference. The projected class **pre-empts** the plain one wherever both readings occur: in one operation, in either operand order of a two-entry `FirstFilledValue`, and across slots, so the two classes cannot be decided slot by slot. Naming the computed field as a semantic index's **key** rather than as the indexed field reports the projected class too, measured for one key position. Projecting any other field is an ordinary computation source. This is authoring rejection, not a runtime dependency cycle or an empty read. Incompatible categories, category or mixed lists longer than two, stars, a projection living only inside a `Having` filter, a category projection on a repeatable computation, and scheduling interactions remain unmeasured; a semantic-index self-read on a repeatable target draws the projected class ([checkpoint](../docs/sources/computation-scheduling-probes.md#src-self-read-alternative-walk)). References to other computed fields remain ordinary scheduling dependencies. **The self-read predicate is *containment*, not equality, with the following shape-specific exemptions** ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-21-corrections)): a reference to any **ancestor** of the computed field is a read of it, so a computation writing `Legs/Distance` draws `MVK_ERROR_REFERENCE_TO_CALCULATED_FIELD` from `GroupNotFilled(/Routing/Legs)`, from `NumberOfFilledGroups(/Routing/Legs*) > 0`, and from `GroupNotFilled(/Routing)` over the **root** — which in an ordinary rule is admitted, so no entity-list root class competes there. The exemptions are singular `GroupFilled` over such a group, the admitted positive fixed-root `AtLeastOneGroupFilled(Root)` form, and a `CurrentRepetition` operand, and they are carve-outs rather than a rule about group predicates, which is exactly what the refused `GroupNotFilled` over that same group establishes. A checker keyed on equality admits the group rows; one keyed on containment alone refuses the two the Kernel admits. The law reaches a target with no declared scale unchanged, in the operation and in the precondition alike. **The parse-time classes measured beside them answer ahead of both classes of this bullet** ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-25b-computation-texts)): beside a plain self-read in the operation, a text in a rounding slot of the same operation draws `MVK_NO_NUMBER`, an argument too many in the precondition `MVK_PARAMSIZE_INVALID1`, and an unresolved name `MVK_INVALID_ENTITY`, each alone. The projected class yields to a precondition's `MVK_NO_NUMBER` or `MVK_INVALID_ENTITY` the same way, and so does the enumeration-compatibility class `MVK_ERROR_INVALID_ENUM_CALCULATION`, a text computed into an Enumeration, to a precondition's arity gate or unresolved name.
- **Alternatives** evaluate top-to-bottom. Only a known-true precondition selects; a clean false or unknown precondition falls through; a poisoned read aborts the computation and skips the remaining alternatives. The **first selected alternative** supplies the operation and ends the scan—even if that operation later produces no value—while no selected alternative yields **CLEARED**. A missing precondition is legal only on the sole alternative; a multi-alternative table must guard every row. Mutual exclusivity is authoring discipline rather than a consistency gate: overlapping preconditions resolve at compute time to the **first declared**. Model composition handing one field several separate computations does not introduce a second selection mechanism: code generation distributes each computation's common precondition into its alternatives and concatenates all of those alternatives, in the order supplied by the model, into one first-match table for the field. A non-holding guard falls through across computation boundaries, but the first selected alternative ends the scan even when its operation stores nothing; reached poison and runtime failure also end it. Exhausting the combined table without a selection and selecting an operation that stores nothing both yield no stored value, but only the former permits every later row to be considered.
- Operands reaching into **sibling indexed groups** run [§9](07-repetition-and-iteration.md)'s **parallel iteration**: rows join by the shared **index-field value**, never physical position; an unmatched side reads empty; the calculation never *creates* a repetition (a key present only on the side group computes nothing); and an **invalid index cell in *any* joined group clears *every* instance** of the computation (deliberately broader than strictly necessary).
- A **starred operand** read from an iterating row binds the enclosing row only for levels *strictly above* the first star — a same-group star spans **all** rows, which is also how one **poisoned sibling cell aborts every row's** dependent.
- **Every repeatable level a starred operand leaves unstarred is read per row, and containment is asked of it first.** Into a target outside the declaring group, every such level draws `MVK_ERROR_FIELD_NOT_IN_RULEGROUP`, on either side of the first star, whatever binds it and whatever its index declaration, while the fully starred operand is admitted into a fixed target; a declaring group beside the target's own that binds nothing refuses exactly as one that binds the level does. With the target inside the declaring group the walk decides, and the outermost unstarred level the target does not bind names the class. A level below the first star, or below the target's own group, draws `MVK_NO_WILDCARD` whatever its index declaration, a target inside that level included; a `For` key on a level below the first star is judged by the index gate instead. A level beside the target's group draws `MVK_ERROR_FIELD_NO_INDEX` when it declares an index field and the target's own path declares none, and `MVK_NO_WILDCARD` when it declares none; with the target's path keyed as well, the parallel-iteration route of the second bullet decides. A level the target lies in is bound by the target's repetition scope like any operand's. A plain read and a fixed group operand follow the same table, into a String target as into a Number one and whatever leaf reads the field, a repeatable group named without its star included, whose own level counts. The token and Boolean value counts, `SumOfProducts` and the Number, DateRange and Enumeration `FirstFilledValue` place the class by the target too ([checkpoint](../docs/sources/group-list-and-capacity-probes.md#src-walk-batch-reading-scope)). A `Having` filter's own leaf and a semantic index's value half are not per-row reads: from a fixed declaring group the target lies outside, `Sum(../Shipments*/ShipWeight Having [../Shipments/ShipKey] == "X")` and, with `Shipments` keyed, `[../Shipments/ShipWeight For "A"] + 1` are admitted, as they are from the target's own group and on the rule arm ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-24e-filter-leaf)). Containment answers ahead of arity, the scale comparison and target self-reference, whichever operand reads the target, and an operand list is judged whole: a star's unbound level answers ahead of a duplicate elsewhere in the list, in either order ([checkpoint](../docs/sources/group-list-and-capacity-probes.md#src-computation-star-binding-gate), [inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-24d-star-containment)).
- A **semantic-index read is column-strict in compute**: any invalid cell in the index column (malformed, duplicated, or empty) clears *every* computation reading that parent-scoped column ([column boundary](08-paths-and-references.md#42-per-lookup-validation-vs-per-column-compute)) — even one whose key matches a clean row (broader than the validation side's per-lookup rule, [§10](08-paths-and-references.md)). Over a clean column the compute read equals the validation read (a no-match or matched-but-empty cell reads empty-as-`0`). A matched **formally-invalid** cell poisons per *read cell*: a sibling computation reading a clean cell of the same row stays a VALUE.

## 6. The implicit validation rule, precisely

The "also acts as a validation rule" ground rule has one exact generated shape, shown with every optional member present, `⏎` marking a line break and spacing insignificant:

```
one alternative:  FieldFilled(F) And (commonPrecondition⏎) And (precond₁⏎) And mismatch₁([F], operation₁)
two or more:      FieldFilled(F) And (commonPrecondition⏎) And (⏎
                    ((precond₁⏎) And mismatch₁([F], operation₁)⏎) Or⏎
                    ((precond₂⏎) And mismatch₂([F], operation₂)⏎) Or … ⏎)
```

Confidence limit: the list's opening `(⏎` and its `Or⏎` separators rest on a read of the Kernel's alternatives joiner alone, which no row separates from a spelling without those line breaks ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-25f-generated-text)).

**Every member is parsed inside that one text, so each is followed by a `)` it did not write, except a lone alternative's operation, which ends the text** ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-25f-generated-text)). A member that stops short therefore draws `MVK_UNEXPECTED_TOKEN` wherever an added `)` follows it: a blank, `null` or whitespace operation beside a sibling, an operation ending on `+` or with `{` or `[` open beside a sibling, a precondition ending on `And`, `Or` or a comma or with `[` open, and a common precondition ending on `And` or with `[` open. Only where it ends the text does it keep its own class: a lone blank operation or one ending on `+` draws `MVK_INCOMPLETE_INPUT`, and a lone operation with `{` open `MVK_EXPECTED_TOKEN_NOT_FOUND`. A lone alternative's precondition with `(` open draws `MVK_EXPECTED_TOKEN_NOT_FOUND` too, because the added `)` closes its call and leaves its own group open. The codeless `problem.document.basic.computationOperationEmpty` line accompanies an empty or `null` operation and not a whitespace one.

**The members are one text for class precedence too: among the classes raised while the joined text is parsed, on every pair measured, A12 names only the one first in the joined order** ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-26c-target-read)). A precondition's class stands ahead of its own operation's, an unresolved name in that operation included, and the common precondition's ahead of an alternative precondition's. The first alternative's operation's class stands ahead of the second alternative's precondition's, so the preconditions are not all judged first. The alternatives stage and the error-text classes of §1's stages bullet are not parse classes, and there several stand together. The `[F]` the shape writes is read like any bracket: a `DAY_OPTIONAL` Date target draws `MVK_INVALID_DATE_TYPE` and a raw String target `MVK_INVALID_RAW_TYPE`, each with no comparison class beside it, on the rows measured with a source of the target's own kind. A partially known Date or raw String *source* into a Number draws the same read class, where a full Date or an ordinary String source draws a comparison class (§1).

- It fires **only when the field is *filled*** and at least one alternative whose precondition holds **disagrees** with the stored value — with the **computation's own name** as the fired error code.
- Each alternative's mismatch is ordinary strict `!=` unless that alternative declares a `toleranceRangeOp`; in that case the generated rule preserves the named fixed `DiffersWithToleranceRange1 / 2 / 5 / 10` operator. Stored and computed values inside or exactly on that normalized tolerance band do not produce a mismatch firing.
- **The computation's `roundingMode` is judged against each alternative's comparison** ([`kf297`](../../a12-rulekit/docs/KERNEL-FINDINGS.md#kf297), [inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-25c-calculation-stages)). It is declared once, as `Exact`, `RoundUp` or `RoundDown`, an absent mode meaning `Exact`, and any other spelling, a different letter case included, leaves the model unbuildable with no class. `RoundUp` beside an alternative declaring no `toleranceRangeOp`, whose mismatch is therefore the strict `!=`, draws `MVK_ERROR_WRONG_ROUNDING_MODE`, while `RoundUp` against a band and `Exact` against either are admitted, and so is `RoundDown` against a band. The gate is owed by every alternative, so one band-less alternative among banded ones refuses a `RoundUp` computation in either position. `RoundDown` beside a band-less alternative draws the class too ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-25g-rounding-mode)).
- **An admitted banded mode rounds the written value to zero places, and the generated validation compares the operation as authored** ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-25g-banded-rounding)). Beside a tolerance band `RoundUp` rounds toward +∞ and `RoundDown` toward −∞, at zero places, as measured into a two-digit target: `RoundUp` writes 1.25 as 2 and −1.25 as −1, and `RoundDown` writes 1.75 as 1 and −1.25 as −2. `Exact` beside a band floors a finer operation to the target's declared digits, 1.255 as 1.25 and −1.255 as −1.26, where the same model without its band errors. An empty operand writes 0 under `Exact` and `RoundUp`. Under `DiffersWithToleranceRange1` the validation stays silent on 0.30 and on 2.20 beside an operation of 1.25 and fires on 0.25 beside a finer 1.259, under every mode, which comparing with the rounded or floored value would not reproduce. Confidence limit: one model and one band, both Kernel strategies agreeing.
- A **cleared-vs-stored** mismatch is deliberately **not** flagged (no tier's comparison holds).
- When the alternative preconditions are mutually exclusive, the one holding comparison describes the same operation that computation selects. If alternatives overlap, the paths deliberately differ: computation executes only the first holding operation, while the generated validation rule retains every holding alternative's mismatch disjunct and may therefore fire even when the stored field equals the first operation. This validation behavior is why authors must make tier preconditions mutually exclusive even though model consistency checking does not reject overlap.

The generated rule **anchors at the computed field**: its error entity is the target's absolute location (the `computedFieldRelPath` resolved from the computation node, even across sibling subtrees or roots), independent of the declaring container's instance content (an empty declaring container does *not* silence it). A cross-group computation into a *repeatable* target is not categorically rejected. `MVK_ERROR_FIELD_NOT_IN_RULEGROUP` is a **containment gate that fires only under derived iteration**, and iteration is derived from *either* of two independent sources: the computed field's own repeatable scope, which reaches the gate through the generated rule anchored at that field, or a per-row read, whatever binds its level ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-24d-star-containment)). The gate then fires exactly when the computed field does not lie at or below the declaring group. So a pure constant with no operand at all is still refused into a repeatable target declared in an unrelated group, while the same constant is admitted at the target's own group *and* at any ancestor of it, including the root — containment, not parenthood. Symmetrically, a repeatable declaring group derives no iteration by itself: a constant into a fixed target is admitted from one, and only adding a per-row operand refuses it. **An aggregate over a star is not a per-row operand** while it leaves no repeatable level unstarred ([checkpoint](../docs/sources/computation-placement-and-constant-probes.md#src-fixed-target-star-placement)); one that leaves a level unstarred, above its first star or below it, reads that level per row and is refused like any per-row read ([§5](#5-where-a-computation-runs--scope-and-the-parallel-join), [inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-24d-star-containment)). A sibling-star `FirstFilledValue` into a *fixed* target is admitted from the target's own group, from an ancestor, from an unrelated sibling group, and from the starred source's own repeatable group, matching a bare constant at all four placements; only an unstarred per-row read refuses, with containment wherever the target lies outside the declaring group, and its diagnostic names iteration explicitly. **The operand side is free too.** In a direct nonrepeatable `FirstFilledValue` list, a source need not lie in the declaring group, and two sources of one list need not share a group with each other; both spellings are admitted at every declaring-group placement, with a two-format list in that same cross-group shape refused `MVK_VARYING_TYPES_NOT_ALLOWED` as the live control ([checkpoint](../docs/sources/computation-placement-and-constant-probes.md#src-date-range-direct-list-cross-group-sources)). Containment therefore constrains neither side of a shape that cannot iterate. **A different root group is admitted too**: with two root groups declared, a bare constant and a star aggregate reading the other root's repeatable group both compute a fixed target across the root boundary, while the same constant into a *repeatable* target from the other root is refused exactly as a same-root non-containing sibling is, so containment is path containment and nothing root-relative. So for a fixed target there is no placement restriction at all until an operand derives iteration — neither equality nor containment describes it, and an unstarred read of a repeatable field **from a declaring group that contains the target** is refused on the walk instead — `MVK_NO_WILDCARD` when the extent declares no index field, and `MVK_ERROR_FIELD_NO_INDEX` when it declares one, two extents differing in nothing else moving the code by the declaration alone. From a declaring group the target lies outside, repeatable or not, the same read reaches the placement gate instead, which is the refusal above, and that half is uniform across both extents. Neither reading alone is right: placement alone can refuse when the target repeats, and the operand alone can refuse when the target lies outside the declaring group. **Only a computation can separate the two sources.** A rule's error field must be referenced by its own condition, so a repeatable error field is necessarily a per-row operand too and the two sources collapse into one; the gate itself is shared, but the constant-into-a-repeating-target shape exists only on the computation side. That asymmetry is measured by a12-dmkits rather than here, because this project's `rule check` route refuses an error field outside the declaring group client-side before the Kernel sees it. The [declaring-group gate checkpoint](../docs/sources/computation-placement-and-constant-probes.md#src-computation-declaring-group-gate) owns the seven-row matrix and that provenance. **Containment governs the operand-bearing routes too, and a relative operand is what makes it look otherwise.** A sibling-star `FirstFilledValue` into a repeatable target is admitted from the target's own parent and from every ancestor, refused only from a sibling that the target does not lie below, and a constant control at the same four placements gives the identical pattern. Moving such a declaration to an ancestor while leaving the operand spelled relative to the old base refuses on an operand-resolution failure carrying a *different* code, so a placement rule read off that refusal is reading the operand's error. The code depends on where the stale walk lands: `MVK_INVALID_ENTITY` while it stays inside the tree, and `MVK_TOO_MANY_PARENT_GROUPS` once the new declaring group is a **root**, where the `..` walks off the top and arity refuses first. Re-spell the relative operand for the new base, or write it absolute, and the ancestor declaration is admitted. A target in one sibling repeatable group may read a starred field in another sibling group under the same enclosing repeatable parent: `FirstFilledValue(../Choices*/Window)` into `Tasks/SelectedWindow` is admitted, runs once per physical task row, and scans only that task's enclosing parent's choices. Two tasks under one parent therefore receive the same first choice while tasks under another parent receive that parent's distinct value. The generated rule reports at the exact repeated target instance; in the retained matrix a stale second task whose stored target differs from the selected value reports the computation's message at `Projects[1]/Tasks[2]/SelectedWindow`. An enclosing parent with a task but no choices clears the stale target, and the cleared-versus-stored mismatch remains unreported as stated above.

The same bounded sibling-star route is measured for complete ISO DateTime. `FirstFilledValue(../Choices*/Stamp)` into `Tasks/SelectedStamp` binds selection to each enclosing parent, retains every physical task address separately, and anchors the generated mismatch message at the exact repeated DateTime target. Malformed source text before a later valid source remains formal poison and clears the dependent target. This same-format, single-zone sibling capture does not independently distinguish the direct DateTime account's exact-instant selection plus target rendering from source-text copying.

The executable Number sibling-star route accepts a nonempty authored list of same-scale, unfiltered, single-axis sibling-star operands; the Kernel-calibrated subset contains one or two operands. `FirstFilledValue(../Primary*/Candidate, ../Secondary*/Fallback)` into a repeatable sibling `Targets/Result` survives persisted structured read-back and whole-model checking; the earlier one-source control remains admitted, while removing its only star is refused with `MVK_NO_WILDCARD`.
