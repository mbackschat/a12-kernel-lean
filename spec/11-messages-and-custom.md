# 11 — Error-message interpolation and CustomCondition (§13 + §14)

Two small areas. Interpolation is a pure render step over an already-fired message; `CustomCondition` is the rule language's host-code predicate hook. The separate registered [custom field-type validator](06-strings-and-enumerations.md#a3-custom-field-type-validation) classifies stored cells during formal observation and is not a `CustomCondition`.

---

## Part A — §13 Error-message interpolation

The authored error text carries producer-specific tokens that are resolved against the evaluated document to produce the end-user message. Rule-owned and field-owned templates do not share one grammar.

- In a **rule-owned** error text, **`$Field$`** interpolates the referenced field's **name/label**, **`$Field.value$`** interpolates its **value**, and **`$$`** denotes one literal `$` — **but only *outside* a parameter** ([inbound](../docs/SOURCES.md#inbound-2026-09-21-corrections)). Inside one the first `$` closes the parameter and the second opens the next, so `see $Premium$$Adjuster$` is **two** parameters, not one parameter beside a literal dollar, and A12 answers it with two diagnostics rather than one; `see $Prem$$ium$` is likewise two names rather than the single name `Prem$ium`. A consumer treating every `$$` as an escape stays silent on a text A12 refuses twice. `Field` is a rule-relative field path rather than a fixed word.
- A rule-owned `$Field.value$` may be used **only if** the field is referenced in the condition at least once **without an asterisk**, and error-text paths **may not contain asterisks**. This field-membership requirement belongs to the **unkeyed** parameter form; a parameter carrying a semantic-index key is gated on the index instead (below).
- **The value suffix carries two independent static gates, each with its own class, and the second is a field-declaration property.** The star rule's refusal is `PARAM_VALUE_WITH_STARREFERENCE`, measured where the condition reaches the field only through a starred aggregate operand; the same field's bare `$Field$` is admitted in the same message, so the gate belongs to the suffix and not to the reference. Independently, a String field declared with **no value validation** refuses `$Field.value$` with `INVALID_NO_VALUE_VALIDATION`, whose text states the rule, while `$Field$` on that field and `$Field.value$` on an ordinary String field are both admitted. So a consumer must read the referenced field's declaration and not only the condition. A suffix written **after** a suffix is neither an alternative nor a composition: `$Field.value.value$` draws `MVK_INCOMPLETE_INPUT` ([checkpoint](../docs/SOURCES.md#src-message-parameter-surface-and-iteration-gates)).
- **`$Entity.Vordruckzeile$` and `$Entity.Vordruckname$` are live name-position forms, and they are the one field form that skips the condition-membership gate.** Both are admitted on a field the rule's condition never references, on a Number field as on a String one, on a field inside a repeatable group, and under the bare, group-relative, and absolute spellings of the entity — where every other name-position form on an unreferenced field draws `INVALID_FIELD`. Their only measured gate is that the entity resolves to a **field**: an undeclared name and a group each draw `INVALID_ENTITY`. Neither composes with a further suffix — `.value` after one draws `MVK_INCOMPLETE_INPUT` and `->Category` draws `MVK_UNEXPECTED_TOKEN` — and the bare terminal without an entity, `$Vordruckzeile$`, is an entity lookup drawing `INVALID_ENTITY`. What either form renders is unmeasured ([checkpoint](../docs/SOURCES.md#src-message-parameter-surface-and-iteration-gates)).
- **The rule-context terminal is a group, so every field-shaped spelling of it is refused — and one spelling escapes as an internal error.** `$RuleGroup$`, `$RuleGroup.value$`, and `$RuleGroup->Category$` all draw `INVALID_PARAMETER`, and `$RuleGroup/Field$` draws `MVK_UNEXPECTED_TOKEN` because the terminal is a complete entity spec that no path may extend. But `$RuleGroup.Vordruckzeile$` and `$RuleGroup.Vordruckname$` draw **`MVK_INTERNAL_ERROR`**, whose text reports a missing referenced entity for the `RuleGroup` context, reproduced from a root-group rule and from one two levels down. That is a Kernel defect surfacing through a static rule check rather than a semantic class, so a consumer must treat the code as an internal fault and not as a diagnosis of the authored text ([checkpoint](../docs/SOURCES.md#src-message-parameter-surface-and-iteration-gates)).
- A rule-owned field reference may instead carry an Enumeration **category** suffix, **`$Field->Category$`**, which is an alternative to the value suffix rather than a further decoration of it. Three static gates apply after entity resolution and the ordinary condition-membership gate: the arrow must be followed by a category name; the referenced field must be an **Enumeration** declaration; and the name must be one of that declaration's declared categories. An empty category name is therefore a semantic refusal, not an early syntax refusal: an unknown field reports `INVALID_ENTITY`, an unreferenced field reports `INVALID_FIELD`, and a referenced field reports `NO_CATEGORY` even when it is not an Enumeration. The same prerequisite ordering holds when another arrow follows the empty first category. Unlike the value suffix it requires neither a non-starred reference nor value validation. A doubled arrow has no single diagnostic class because the first suffix is checked before trailing syntax: a declared first category reaches `MVK_UNEXPECTED_TOKEN`, an undeclared first category draws `INVALID_CATEGORY`, and a non-Enumeration field draws `FIELD_NO_ENUM`. The suffix interpolates the **category token the field's current stored value maps to**, not the category's name or stored value. The value suffix instead interpolates the Enumeration value's declared label, falling back to the stored token when that value is unlabelled. An **empty** Enumeration renders the empty string under both suffixes, while its `$Field$` label still renders.
- A rule-owned field reference may finally carry a **semantic-index key**, `$Field For "k"$` or `$Field For KeyField$`, which looks the field up in a repeatable group by that key. The key comes **last**: it follows any value or category suffix, and a suffix written after the key is a parse failure (`MVK_UNEXPECTED_TOKEN`) rather than an alternative spelling. A key is either a **quoted literal token** or a **path to the keying field**; an unquoted bare word is therefore read as a field reference and refused `INVALID_ENTITY` when no such entity exists, not as an unlexable token. A key that is itself keyed is refused `ILLEGAL_SEMANTIC_INDEX`, quoting the **inner** index.
- A keyed field's prerequisite gates also precede an empty category name. With a literal key absent from the condition, `$Field-> For "k"$` reports `MVK_INDEX_FOR_ERROR_TEXT_INVALID` for a resolved field whether or not the condition references it plainly; an unknown field reports `INVALID_ENTITY` first ([category-gate checkpoint](../docs/SOURCES.md#src-message-category-gate-order)).
- That parameter's static gate is on the **semantic index, not on the field**: the rule condition must use the same index the same way. A keyed parameter may name a field the condition **never references**, but only one such field: **the group's declared index field**. The admitted set is exactly the field the condition keys together with that index field — a third field of the same group, keyed identically, is refused `MVK_INDEX_FOR_ERROR_TEXT_INVALID`. So what must match is the keyed group and key *plus* the displayed field being one of those two, not the group's fields at large ([checkpoint](../docs/SOURCES.md#src-keyed-parameter-admits-the-index-field-only)). **The key literal must also be a valid value for the index field's declared kind:** a Number index field keyed `"k1"` refuses the *condition* with `MVK_INDEX_VALUE_INVALID`, before any parameter question arises, so the two gates report apart. The pairing is exact in both directions: a condition that reads the group plainly, or keys it by a *different* key, refuses the keyed parameter `MVK_INDEX_FOR_ERROR_TEXT_INVALID`, and a keyed condition operand does **not** license the unkeyed spelling of that field, which is refused `INVALID_FIELD` by the ordinary membership gate. A field-valued key and the value suffix both compose with this gate, and a category suffix composes too: a valid category on a plainly-read Enumeration still draws the index class.

- A rule-owned parameter may instead be the **Base Year** terminal — `BaseYear` in English, `Referenzjahr` in German — optionally followed by a signed integer offset, `$BaseYear+3$` or `$BaseYear-1$`. Its only static gate is that the model declares a Base Year; there is no bound on the offset. The interpolated text is the declared Base Year with that offset applied, rendered as a plain decimal: against a Base Year of 2020, `$BaseYear$`, `$BaseYear+3$`, and `$BaseYear-1$` render `2020`, `2023`, and `2019`. It depends on the model alone rather than on the document.
- A rule-owned parameter may instead occupy the **group position**, written `$#…$`, which is distinct from the name position and resolves the same words differently. Its argument is an **absolute group path**, and the admitted set is the rule's own group together with its ancestors, at any depth: for a rule at `/Probe/Rows`, `$#/Probe/Rows$` and `$#/Probe$` are admitted while a declared descendant `$#/Probe/Rows/Deeper$` and a sibling `$#/Probe/Store$` both draw `INVALID_GROUP`. Containment therefore runs the opposite way from the computation declaring-group gate: the *named* group must contain the rule's group. A relative spelling is refused even when it names a real group, since `$#Rows$` draws `INVALID_GROUP`, so the leading slash is required rather than conventional.

- **`RuleGroup` carries a placement condition the other shorthand does not.** A declaration sitting directly in the root group may not use it: `$#RuleGroup$` there is refused `RULEGROUP_IMMEDIATELY_BELOW_ROOT`, whose text states the rule, while the same message one level down is admitted. The gate belongs to that word alone — from the same root-declared locus, `$#RootGroup$` and the **absolute** spelling of that very group are both admitted — so the group is nameable and the position works; what is refused is the shorthand whose meaning would there coincide with `RootGroup` ([checkpoint](../docs/SOURCES.md#src-rulegroup-shorthand-root-gate)). **Both carriers share the gate**, measured separately rather than carried across: a validation rule whose error field sits directly in the root group draws the same refusal, with the same three-spelling contrast from that one locus, and the kernel's text names rules outright ([checkpoint](../docs/SOURCES.md#src-rulegroup-root-gate-on-the-rule-carrier)). So a clause admitting the shorthand wherever the group position is legal — "the rule's own group plus its ancestors, at any depth" — is over-general in exactly the place no ordinary fixture reaches, because at that locus the rule's own group *is* in the admitted set.

- The two keyword shorthands belong to the **condition language**, in both directions, while the retired terminals do not. On a model whose condition language is German, `$#LfdNr$` is admitted and `$#RuleGroup$` and `$#RootGroup$` both draw `INVALID_GROUP`; on an English one the verdicts are exactly reversed. The absolute-path spelling is admitted under either language, so only the keyword set is selected. A **retired** terminal is language-independent: `$#Zeile$` draws `PARAM_INVALID_IN_NEW_WORLD` under German exactly as under English, so the Kernel recognizes it in both bundles and refuses it on the modern route in both. A model's condition language also cannot be switched once its rules are authored in the other language: the change is refused with one `MVK_UNEXPECTED_TOKEN` per rule naming the keyword that no longer parses, so the setting is chosen before authoring rather than migrated ([checkpoint](../docs/SOURCES.md#src-german-condition-language-terminals)).
- An admitted group parameter renders the **1-based repetition index of that group in the firing row**, and a nonrepeatable group renders the constant `1`. The index is the row's own coordinate rather than a firing ordinal: over a three-row document whose rule fires on rows 2 and 3, `$#/Msg/Rows$` renders `2` and `3`, not `1` and `2`. The two keyword shorthands render exactly as the paths they abbreviate, so `$#RuleGroup$` follows the rule's own group and `$#RootGroup$` its chain root — which is `1` whenever that root is nonrepeatable. This is a **number**, not a label or a path, and a declared label does not change it: with labels on both the repeatable group and the root, every group parameter renders exactly as before, while labelling the *field* changes what the name position renders in the same message. So the name position renders a field's label or name, the group position a coordinate, and that is what makes them two positions rather than one with two spellings ([checkpoint](../docs/SOURCES.md#src-message-group-parameter-rendered-index)).

- **Each parameter renders the coordinate of the level it names, not the firing row's innermost one**, and it takes a doubly nested topology to see the difference. Under a **repeatable** root with two stacked repeatable levels below it, one message firing at consignment 2, box 3, item 4 renders `item=4`, `box=3`, `cons=2`, `$#RuleGroup$` as `4` and `$#RootGroup$` as `2` — four distinct integers in one message, which no single-level document can separate. That also settles `$#RootGroup$` on a repeatable root: it renders **that root's own index**, where a nonrepeatable root's constant `1` leaves the two readings indistinguishable. And the per-segment quote escape renders exactly as the bare spelling does, so quoting is transparent at runtime as well as at admission ([provenance](../docs/SOURCES.md#src-2026-09-05-group-parameter-render-reconciliation)). **The German shorthands render the same coordinates as their English twins**, so the condition language selects the keyword set and nothing about what a keyword denotes: on a `de_DE` model with a repeatable root, `$#RegelKontext$` advances with the firing item while `$#LfdNr$` holds at the root's own index ([provenance](../docs/SOURCES.md#src-2026-09-05-german-shorthand-render-reconciliation)).
- An absolute argument resolves in **two gates the Kernel reports apart**. Its first segment must name a declared root group; when it does not, the refusal is `INVALID_ROOT_GROUP` whatever follows the root, so `$#/Nope$` and `$#/Nope/Rows$` draw the same code, and the match is case-sensitive. Only under a declared root does containment decide, and an unknown group below one, such as `$#/Probe/Nope$`, draws the ordinary `INVALID_GROUP`. Each segment may take the name grammar's single-quote escape: `$#/'Probe'/'Rows'$` is admitted. Admission alone does not establish that it resolves to the *same* group as the bare spelling, since only the containment gate narrows which group it could be, so this states the admission and not the identity. A malformed spelling is refused earlier still, on its own lexical codes: an unbalanced quote and an empty quoted segment draw `MVK_LEXER_STANDARD_ERROR`, a trailing separator `MVK_INCOMPLETE_INPUT`, and a doubled separator `MVK_UNEXPECTED_TOKEN`.

- Two keyword shorthands occupy that position for the endpoints of that chain: `$#RootGroup$` and `$#RuleGroup$` are both admitted. `$#RootGroup$` names the root of the **rule's own** ancestor chain rather than a model-wide root, which a model with two root groups separates: a rule under the second root admits the shorthand while the other root draws `INVALID_GROUP`. This does not contradict the name-position measurement below, where bare `$RootGroup$` draws `INVALID_ENTITY`; the same word is an entity lookup there and a group terminal here. `$#Zeile$` and `$#Usb$` draw `PARAM_INVALID_IN_NEW_WORLD`, a code distinct from `INVALID_GROUP`, so the Kernel recognizes both and refuses them on the modern route. `$#Vordruckzeile$`, `$#Vordruckname$`, and `$#index(...)$` draw plain `INVALID_GROUP` on this carrier, so they are not terminals in this position.

- **The root gate is shared by both positions; only the gate below it is position-specific.** A bad first segment draws `INVALID_ROOT_GROUP` in the name position exactly as in the group position, so the root check is one mechanism serving both. Below the root the name position answers `INVALID_ENTITY` — it resolves a group *or* a field — where the group position answers `INVALID_GROUP`, and neither localizes the failure further: a bad middle segment and a bad leaf draw the same code as each other ([checkpoint](../docs/SOURCES.md#src-two-positions-share-the-root-gate)).

- The group position has **no explicit index syntax**: `$#/Msg/Rows[1]$` is refused `MVK_LEXER_STANDARD_ERROR`, brackets not being in that grammar at all. The position therefore renders the firing row's own coordinate and cannot be pinned to another row. `index(...)` is by contrast a **live terminal in the name position**, so the two positions carry different terminal sets. It is lowercase with arity one — a capitalised `Index(` or an empty `index()` draws `MVK_UNEXPECTED_TOKEN` — and **it is admissible**: `$index(Key).value$` renders where the rule's error field sits inside a repeatable group whose declared index field is `Key`. Three conditions each carry their own refusal. The argument must be that index field's **bare short name**, so an absolute path, a group-relative path, a nonexistent name, and a non-index field of the same group all draw `INVALID_INDEX_FIELD`, whose text names its own three disjuncts: the argument *is either no index-field, is referenced wrongly, or is not used in the rule condition*. The index field must lie on the **error field's own path**, so the same parameter under a root-group error field draws that class too. And the suffix is **mandatory**: omitting it draws `INVALID_INDEX_FIELD_PARAMETER`, on an Enumeration index field as on a String one. The alternative `->Category` form is **admitted** on an Enumeration index field carrying that category, so the two suffixes are live alternatives on one declaration rather than one form with a dead sibling; they do not compose, and `.value->Cat` is `MVK_UNEXPECTED_TOKEN`. Its own two refusals are the field's kind and the category's existence: a non-Enumeration index field draws `FIELD_NO_ENUM` and an undeclared category name draws `INVALID_CATEGORY`, whose text reports it as an incorrect error text for the language rather than as an entity fault. Both the keyword and the suffix are case-sensitive, and the suffix is locale-keyed: under an English condition language it is lowercase `value`, while a capitalised `Value` and the German `Wert` each draw `MVK_UNEXPECTED_TOKEN` there. The Kernel's own terminal tables give `Wert` as that suffix's German spelling and `index` as the keyword in both languages, which is read from the tables rather than measured on a German model. Bare `$index$` without parentheses is not a terminal and draws `INVALID_ENTITY` ([checkpoint](../docs/SOURCES.md#src-index-terminal-admitting-spelling)). **Two further gates run before the suffix, and one of them reads the rule's own condition.** The short-name lookup refuses on multiplicity as well as absence: two nested repeatable groups whose index fields share a short name draw `INVALID_INDEX_FIELD_AMBIGUOUS`, where the identical parameter is admitted from an error field on the level carrying only one of them. Then the checker filters the **condition's** referenced index fields by that same short name and cross-checks their repeatability against the error path's, so what the condition does with that field decides the parameter: a plain unstarred reference is admitted, while a `For "k"`-keyed one and a **starred** one each draw `INVALID_INDEX_FIELD_REP_ITER` under either suffix, and a condition naming a differently named index field leaves the set empty and skips the gate entirely. That last case is why a parameter can be admitted beside a condition that never mentions the index field at all. **A non-repeatable indexed group arms its own gate, and that gate admits exactly one declaration shape rather than refusing the whole shape.** Where the index field a parameter names sits on a group that does not repeat, the parameter draws `INVALID_INDEX_FIELD_NONREP_ENUM` unless that index field is an Enumeration whose declared value set holds a single value and whose S-value is set; on that one declaration the parameter is admitted. Two of those conjuncts are separated by measurement — an Enumeration declaring two values and an Enumeration declaring one value with no S-value each refuse — while the same String index field on a *repeatable* group admits the identical parameter, so the trigger is the group's repeatability and not the field's kind. The Enumeration requirement itself is **read from the checker rather than measured**, because the model format lets only an Enumeration declare a value set or an S-value at all, so a non-Enumeration index field fails the other two conjuncts automatically and no observation separates the three. The S-value conjunct is the Kernel's weaker test of non-emptiness and not a comparison against the declared value; that distinction is unreachable, because a non-member S-value is refused `MVK_S_VALUE_INVALID` by the model gate before any parameter is examined, so the two readings agree on every legal model. Both suffixes draw the class alike, placing this gate before the suffix branch. Every refusing declaration is itself legal — the model passes consistency checking on its own, and the refusal appears only once a message names the index field ([checkpoint](../docs/SOURCES.md#src-nonrepeatable-index-field-gate)). The remaining declaration shape carries its own class and no route reaches it: a group declaring several index field names is `INVALID_INDEX_FIELD_COMPOSED_INDEX` ([checkpoint](../docs/SOURCES.md#src-index-terminal-refusal-classes)). **Past the repeatability gate the checker compares the two index fields' declarations against each other, and each mismatch has its own class.** The witness shape is a condition that iterates a repeatable group off the error field's own path, which puts two same-short-named index fields in the filtered set; on two Enumeration index fields, differing stored value sets draw `INVALID_INDEX_FIELD_ENUM_XML_VALUES` under both suffixes, and identical value sets with a differing value-to-category mapping draw `INVALID_INDEX_FIELD_ENUM_XML_TO_CAT` under `->Category` while `.value` stays admitted. So the two suffixes read different parts of the same pair of declarations. Three further mismatches carry their own classes and no route reaches them: a differing value-to-display mapping is `INVALID_INDEX_FIELD_ENUM_XML_TO_DISPLAY`, one Enumeration index field against one of another kind is `INVALID_INDEX_FIELD_INCONSISTENT_TYPES`, and a repeatability disagreement outside iteration is `INVALID_INDEX_FIELD_REP` ([checkpoint](../docs/SOURCES.md#src-message-parameter-surface-and-iteration-gates)). What an admitted `index(...)` of either suffix renders is not measured.

- **The group position takes the semantic-index key, and the key must match the condition's exactly.** `$#/Probe/Cases2 For "X"$` is admitted where the condition references a field of that group keyed `For "X"`; from the same condition the unkeyed `$#/Probe/Cases2$` and the differently keyed `$#/Probe/Cases2 For "Y"$` both draw `INVALID_GROUP`, the same class an off-path group draws. So the keyed and unkeyed spellings are not alternatives at one locus: whichever the condition established is the one the parameter must use. The key literal must also be a declared value of the group's index field, or the **condition** is refused `MVK_INDEX_VALUE_INVALID` before any parameter question arises ([checkpoint](../docs/SOURCES.md#src-message-parameter-surface-and-iteration-gates)).
- **`$#RootGroup$` has one gate of its own, and it reads the condition rather than the model: parallel iteration.** Where the condition iterates a repeatable group off the error field's own path — reachable when that group's index field shares its short name with the error path's — `$#RootGroup$` draws `INVALID_HASH_LFDNR_FOR_PARALLEL_ITERATION`, whose text states the rule and directs the author to a parallel-iteration parameter instead. The identical parameter from the identical error field is admitted once the condition is not parallel, so the gate is the condition's shape and not the locus. The absolute spelling of that same root, and the absolute spelling of the iterated group, both stay admitted under parallel iteration ([checkpoint](../docs/SOURCES.md#src-message-parameter-surface-and-iteration-gates)).
- **A rule-message template has three character tiers, and only the innermost is ASCII.** The whole template's repertoire is the **BMP** — Latin-1, Latin Extended-A, currency, Greek, Cyrillic, CJK, punctuation, NBSP, and `U+FFFD` are all admitted, while both supplementary-plane scalars measured are refused. That repertoire refusal is codeless and conveys the runtime formal charset class. The named template gates select linebreak (`INVALID_LINEBREAK`: exactly LF, CR, `U+2028` and `U+2029`) before control characters (`INVALID_CHARACTERS`: every code point Java's `\p{C}` matches — control, format, private use, unassigned and a lone surrogate, measured on C0, tab, DELETE, the C1 block with `NEL`, soft hyphen, zero-width space, `U+FEFF`, `U+200E`, `U+E000` and the unassigned `U+0378`), before dollar parity. The control gate is asked of a code point, so a supplementary character inside `\p{C}` (`U+F0000`, `U+E0001`) draws the repertoire refusal and `INVALID_CHARACTERS`, one outside it (`U+1F600`) the repertoire refusal alone, and a lone surrogate both; which code points are unassigned is the running JDK's Unicode version's, and the rows were measured on JDK 21. Either gate withholds the parameter classes after it, as the tab does: beside a zero-width space or a line separator an unknown name draws no `INVALID_ENTITY`, and beside a zero-width space an unclosed parameter draws no `WRONG_NUMBER_OF_DOLLARS`. A computation's message draws the same classes on the four rows measured there, LF and `U+2029` `INVALID_LINEBREAK`, a tab and `U+FEFF` `INVALID_CHARACTERS`. So does a String field's pattern message, measured with both separators, tab, `NEL`, soft hyphen, zero-width space, `U+FEFF`, `U+200E`, `U+E000`, `U+0378` and both supplementary rows, behind an encoding gate that answers a lone surrogate there with `WRONG_ENCODING` in place of `INVALID_CHARACTERS` ([inbound](../docs/SOURCES.md#inbound-2026-09-26m-message-characters)). Inside a **parameter body** the bound narrows to printable ASCII together with `ÄÜÖäüöß`: `é`, `€`, and a CJK letter each draw `MVK_LEXER_STANDARD_ERROR` naming the character and its 1-based parameter offset. The same characters in surrounding text are admitted; unknown names using the seven German letters reach entity lookup and draw `INVALID_ENTITY` ([character checkpoint](../docs/SOURCES.md#src-message-template-character-repertoire)).
- **The repertoire finding coexists with named failures.** On the measured validation-rule carrier, a supplementary-plane scalar accompanies a separate linebreak, control-character, odd-dollar, unknown-entity, or parameter-lexer diagnostic. The retained envelopes list the codeless finding first and the named finding second; that reporting order does not establish internal check execution order. A valid parameter does not suppress the repertoire refusal, and two offending scalars still produce one codeless finding. A projection containing only named `codes` loses this distinction and cannot establish an exclusive failure priority. This corrects the former claim that charset checking runs last ([co-reporting checkpoint](../docs/SOURCES.md#src-message-repertoire-co-reporting)). A String field's pattern message reports the refusal on the field, measured beside a named class with `U+F0000`, which draws `INVALID_CHARACTERS` and the refusal, and a lone surrogate, which draws `WRONG_ENCODING` and the refusal, while `U+1F600` draws the refusal alone; beside the line, parity and parameter classes no row reads it ([inbound](../docs/SOURCES.md#inbound-2026-09-26m-message-characters)). An Enumeration's invalid-value message reports it on the field too. A String pattern message for a locale the model does not declare is not asked, a tab for `fr_FR` and `U+1F600` for `de_DE` both admitted; no row reads an Enumeration's message in such a locale ([inbound](../docs/SOURCES.md#inbound-2026-09-26n-field-message-gates)). A rule's message written for a locale the model does not declare draws no refusal, and [01 §1.1](01-data-model.md#11-the-two-special-model-level-configurations) owns the model's other texts ([inbound](../docs/SOURCES.md#inbound-2026-09-26m-model-texts)).
- **A refused DSL member withholds the error-text checker's classes, and the message's presence classes stand.** When the owning declaration's condition or operation draws a class of its own, the classes the rule error-text checker draws are withheld: a control character's `INVALID_CHARACTERS`, an unread parameter's `INVALID_FIELD`, an odd count's `WRONG_NUMBER_OF_DOLLARS`, a descendant group parameter's `INVALID_GROUP`, a Base-Year parameter's `NO_BASE_YEAR` in a model without one, a parameter's parse class `MVK_UNEXPECTED_TOKEN`, a key on an unindexed field's `MVK_INDEX_FOR_ERROR_TEXT_INVALID`, and `RULE_HAS_NO_ERRORTEXT`. `MVK_ERROR_MESSAGE_MISSING` and `MVK_ERROR_MESSAGE_FOR_LANGUAGE_MISSING` are reported beside the member's class. So the split follows the checker rather than the spelling: an account that withholds the unprefixed classes and keeps the `MVK_` ones misplaces the parse and index-key rows.
- **The member classes measured to withhold them.** On a rule: a text that does not parse, `MVK_INVALID_ENTITY` for a name that does not resolve, `MVK_LEXER_STANDARD_ERROR`, `MVK_EXPECTED_TOKEN_NOT_FOUND`, `MVK_FIELDNAME_NOT_UNIQUE`, `MVK_TOO_MANY_PARENT_GROUPS`, `MVK_UNEXPECTED_TOKEN`, `MVK_INVALID_ROOT_GROUP`, `MVK_PARAMSIZE_INVALID1`, `MVK_DUPLICATE_PARAM1`, `MVK_INVALID_COMPARE_TO_ENUM_OR_STRING`, `MVK_INVALID_WILDCARD`, `MVK_NO_WILDCARD`, `MVK_NO_WILDCARDS_ALLOWED` and `MVK_ERROR_FIELD_NOT_REFERENCED`, which is post-parse and withholds the same set: a control character, an odd dollar count, a parameter's parse class, a key on an unindexed field, and `RULE_HAS_NO_ERRORTEXT` beside the presence classes, which stand ([inbound](../docs/SOURCES.md#inbound-2026-09-25b-message)). On a computation: `MVK_INVALID_WILDCARD`, with both template classes, and `MVK_NO_WILDCARD`, with the control character only; a messageless computation keeps `MVK_ERROR_MESSAGE_MISSING` and loses `RULE_HAS_NO_ERRORTEXT` beside a refused operation or precondition. Not every checker class is measured beside every member class, and a class outside these sets is predicted to behave alike, not measured; the inbound records own the pairs. A condition naming `BaseYear` in a model without one draws `MVK_NO_BASE_YEAR` alone, that class being the member's own. A class about another member does not withhold the message: a rule-name refusal `MVK_RULE_NAME_INVALID` or a blank error code `MVK_ERROR_CODE_MISSING` is reported together with the message's class. So the gate is the DSL member's own verdict: the name and error-code rows rule out whether the declaration drew anything, and `MVK_ERROR_FIELD_NOT_REFERENCED` on a condition that parses and resolves rules out whether it parsed and resolved ([inbound](../docs/SOURCES.md#inbound-2026-09-24e-message-withheld), [inbound](../docs/SOURCES.md#inbound-2026-09-25-message-withheld)).
- The terminal bundle is **owned by the message, not by the rule**, and `RuleGroup` names the *owning declaration's* group rather than a validation rule's. On a **computation** message the absolute path, both keyword shorthands, and a name-position field are admitted, and the retired `$#Zeile$` draws the same `PARAM_INVALID_IN_NEW_WORLD` it draws on a rule — the Kernel's own refusal text names the computation `Rule with path '…Comp'`, which is why the terminal resolves. So "rule" in the terminal's spelling is internal vocabulary, and a consumer reading it as validation-only refuses admitted computation messages. Static admission is what is measured here; what the shorthand renders on that carrier is not ([checkpoint](../docs/SOURCES.md#src-terminal-bundle-on-the-computation-carrier)).

- The **terminal match is on the raw argument**, so quoting a word removes its terminal reading rather than merely being stripped first. `$#'RootGroup'$` and `$#'RuleGroup'$` draw `INVALID_GROUP` naming a group of that name, and `$#'Zeile'$` draws `INVALID_GROUP` rather than the retired code its bare spelling draws. What an admitted group parameter renders is not covered by this static account. The [group-parameter checkpoint](../docs/SOURCES.md#src-message-group-parameter) owns the admission matrix and the [resolution checkpoint](../docs/SOURCES.md#src-message-group-parameter-resolution) owns the two gates, the quoting rule, and their limits.

- The parameter grammar's terminals are **bilingual, and exactly five of them differ**: value/`Wert`, `For`/`Fuer`, `RuleGroup`/`RegelKontext`, `RootGroup`/`LfdNr`, and `BaseYear`/`Referenzjahr`. `index`, `Zeile`, `Usb`, `Vordruckzeile`, and `Vordruckname` are spelled the same in both, and `Zeile` and `Usb` are not permitted in an A12 model at all. In name position, the wrong-language value, Base-Year, or rule-group terminal is looked up as an entity and draws `INVALID_ENTITY`; the own-language rule-group terminal is recognized but invalid at that position and draws `INVALID_PARAMETER`. In keyword position, the wrong-language `For`/`Fuer` spelling is a parse failure, `MVK_UNEXPECTED_TOKEN`. `RootGroup`/`LfdNr` draws `INVALID_ENTITY` in both languages on the rule-owned carrier, but that measured absence is not a claim about other parameter owners that share the terminal bundle.
- A name that collides with one of the selected condition language's terminals is written in the parameter grammar's **single-quote** escape, and the quotes are erased before any lookup, so an unnecessary quote is transparent. The rule-message producer's requirement is **narrower** than the condition language's: the terminals for value, root-group index, line, USB, form-line, form-name, and `index` are accepted **unquoted** inside an entity name for historic reasons, so only the remaining terminals need the escape. A trailing value terminal is therefore never ambiguous with a name — that terminal is not one of the four a name may end with.
- `$Field.value$` applies a presentation profile selected by the message locale's **exact tag**, not by a locale cascade or the field's declared storage format. The complete measured lookup is: `en`, `en_US`, and `us` use `MM/dd/yyyy`, decimal `.`, grouping `,`; `de` and `de_DE` use `dd.MM.yyyy`, decimal `,`, grouping `.`; `ch` uses `dd.MM.yyyy`, decimal `.`, grouping `'`; `fr` uses `dd/MM/yyyy`, decimal `,`, grouping space; `gb` uses `dd/MM/yyyy`, decimal `.`, grouping `,`; and `nl` uses `dd-MM-yyyy`, decimal `,`, grouping `.`. An unmapped tag, including `fr_FR`, performs no presentation and leaves the stored value unchanged. The mapped profile reaches Date, Number, DateTime, and DateRange values; Time remains unchanged. DateTime's `T` and DateRange's declared separator become a space when presented. Numeric sign and the stored fractional-digit count are preserved, so presentation neither pads `1234.5` nor drops its sign.
- A **partially known** Date interpolates its **stored spelling, zero markers and all**, rather than either of the interval boundaries it denotes. Stored `2024-06-00` renders `06/00/2024`, `2024-00-00` renders `00/00/2024`, and `0000-00-00` renders `00/00/0000`. So a renderer reads the value's stored components and must not complete it for display: completing the first of those would print `06/01/2024`, which is its earliest boundary and a date the document never stated. The marker belongs to its **component** rather than to a text position, and travels with it: the same omitted-day value renders `06/00/2024` under `en_US` and `00.06.2024` under `de_DE`.

- For a missing or empty rule-owned display value, interpolation uses the referenced field format's exact default supplied by the actual presentation route; it is not inferred from or transformed by the message locale. On the current modern `DocumentV2` route, a Number's **minimum** fractional digits determine **`0`**, **`0.00`**, and so on, and that default keeps `.` even under `de_DE`; String supplies **`""`**. A distinct legacy or presentation-information route remains unclaimed until separately characterized.

- The rule error-text checker examines only locales declared by the model. A parameter error in a declared locale is rejected, while the identical invalid text under an undeclared locale is silently accepted and stored because that locale is not examined. A well-formed undeclared-locale text is observationally identical at this gate. Authoring tools may deliberately reject undeclared locale keys before calling the Kernel, but that stricter instrument policy is not Kernel semantics. The same holds for every checker class measured: a control character, an odd dollar count and `$BaseYear$` without a Base Year are each admitted under an undeclared `fr_FR`. Of two entries for one declared locale only the last is examined, so an unknown parameter in the first entry is admitted and in the second draws `INVALID_ENTITY` ([inbound](../docs/SOURCES.md#inbound-2026-09-25-message-withheld)). **`RULE_HAS_NO_ERRORTEXT` asks after every declared locale, an answered one beside it included**, on a rule and on a computation alike: with `en_US` answered, an empty `de_DE` text or no `de_DE` entry draws `MVK_ERROR_MESSAGE_FOR_LANGUAGE_MISSING` and `RULE_HAS_NO_ERRORTEXT`, a whitespace-only `de_DE` text the first alone, and an answered `en_US` followed by an empty `en_US` entry both, the last entry again being the one judged ([inbound](../docs/SOURCES.md#inbound-2026-09-25b-message)).
- A String pattern's own invalid-value text instead accepts exactly two fixed tokens, spelled in the model's **condition language** whatever locale the text is written for: **`$field$`** and **`$field.value$`** in English, **`$Feld$`** and **`$Feld.Wert$`** in German. The stylized `$Field$`, an actual field name such as `$Code$`, the other language's token, and a token with one non-ASCII letter, `$fïeld$`, are invalid parameters, `INVALID_PARAMETER`; the rule message's parameter-body bound, whose lexer refuses that letter, does not apply here ([checkpoint](../docs/SOURCES.md#src-count-placement-overlap-list-grid)). The parameters are the pieces a split at each `$` returns once **trailing empty pieces are dropped**: an empty pair inside the text (`cost $$ in capitals`) or at its start (`$$ capitals only`) is an empty parameter and invalid, while an empty pair at the very end (`capitals only $$`) or alone (`$$`) names no parameter and is admitted, and two parameters back to back (`$field$$field.value$`) are admitted. An empty pair in a refused position is not a literal-dollar escape at this producer; whether an admitted trailing pair renders as literal dollars is unmeasured. The character gates come before dollar parity and parity before the parameters, each withholding what follows: a tab beside an odd count draws `INVALID_CHARACTERS` alone, and a wrong name beside an odd count `WRONG_NUMBER_OF_DOLLARS` alone. **An empty text is not a message**: it draws `MVK_ERROR_MESSAGE_AND_PATTERN_INVALID`, the pattern-message pairing's class, and no character class ([inbound](../docs/SOURCES.md#inbound-2026-09-26n-field-message-gates)).
- **The field-message check reports one class per field, from the first locale in declared order whose text fails.** With a tab in the `en_US` text and a line feed in the `de_DE` one, declaring `en_US` first draws `INVALID_CHARACTERS` and declaring `de_DE` first `INVALID_LINEBREAK`, whichever entry the model writes first. Of two entries for one locale the later is asked, and a pattern message for a locale the model does not declare is never asked. An Enumeration's invalid-value message meets the same gates, a tab drawing `INVALID_CHARACTERS` and `$Status$` `INVALID_PARAMETER` while `$field$` is admitted; a String message with no pattern meets them too, a tab drawing `INVALID_CHARACTERS` beside `MVK_ERROR_MESSAGE_AND_NO_PATTERN`; a required field's own message does not, a tab there being admitted. A field its own `ONLY` variant filter deletes is never asked, as the filter deletes a rule ([inbound](../docs/SOURCES.md#inbound-2026-09-26n-field-message-gates)).
- **A field whose path, or an ancestor group's, draws a path class draws nothing about its message.** A tab in the pattern message of a field named `Codeé`, `1Code` or `Co.1de`, or beneath a group named `Parté` or `1Part`, draws `MVK_PATH_INVALID` and no `INVALID_CHARACTERS`, and a `/` in either name `MVK_PATHS_INCONSISTENT` and no `INVALID_CHARACTERS`. A name class that is not a path class does not have that effect: a field named `Co.de`, `Co:de` or `_Code`, a group named `Teilä`, and a root group named `1Claim` each keep the message's `INVALID_CHARACTERS` beside whatever name class they draw. The discriminating pair is `Co.de` against `Co.1de`, both dotted. A rule's refusal elsewhere in the group withholds nothing on the field: a rule condition's parse error or a missing error target is reported beside the field's `INVALID_CHARACTERS` ([inbound](../docs/SOURCES.md#inbound-2026-09-26n-field-message-gates)).
- String-pattern field replacement is one-pass. With template `Value [$field.value$]` and stored invalid value `$field$`, the resolved text is exactly `Value [$field$]`; inserted bytes never become template syntax.
- Requiredness is a distinct field-owned producer. The measured `en_US` template `Cost $$ $field$` is valid and resolves to `Cost $$ Code` under the tested label-or-name profile, preserving the doubled dollar pair. This witness separates requiredness from String-pattern and rule-owned parsing; it does not establish the complete requiredness grammar.

What a fired message actually carries:

- The message's error text is the **interpolated end-user text** — tokens already resolved against the evaluated document (the authored template stays in the model). Only the runtime can produce it, because it depends on the data.
- A rule-owned **`$Field$` delegates to the runtime identifier-display policy.** On the public service route, an available label-provider result wins exactly, including `""`; otherwise a nonempty localized model label wins; otherwise the resolved identifier's path/index debug representation is used. On the kernel's own `validateFull`, which configures no provider, that last branch renders the field's **short name** — `Amount`, not a path — so a consumer must not expect a path there; a declared label still wins. A configured provider may itself choose label-or-name, but that is caller policy rather than the kernel's built-in fallback.
- A number's **unit trait** (amount / percent / permille) does **not** render into a rule-owned `$Field.value$` — the interpolation yields the bare number; the unit is a UI concern.

> **Non-normative implementation note.** Keep a producer-specific checked parser in front of one shared left-to-right renderer. For a rule-owned template, field-name input is `{ providerResult?, modelLabel?, debugDisplay }` and field-value input is `{ displayValue?, exactFormatDefault }`; a present provider result, including empty output, wins, only a nonempty model label beats the debug display, and a missing or empty display value selects the exact format default. For the measured String-pattern field producer, lower the already-selected owning-field name and value directly to opaque text; do not apply the rule path's lookup or empty-display default and do not admit its `$$` escape. Keep rendering entirely separate from firing or formal classification—the decision and cause are established first, and interpolation shapes only the text of that already-decided result.

## Part B — §14 CustomCondition — the escape hatch

When the language cannot express a check, **`CustomCondition <Name>`** delegates the decision to **host code that the consuming system registers**. The engine parses and places the rule like any other, but calls out to that implementation to decide whether it fires.

```
FieldFilled(id) And CustomCondition NotReverse
```

`<Name>` uses the `nameOhnePunkt` token grammar: one or more ASCII letters or digits, `_`, `:`, or `ÄÜÖäüöß`. An unquoted name may begin with a digit, `_`, or `:` and may consist only of digits. A reserved token such as `Today` must be single-quoted as `'Today'`; the quoted form begins with a non-digit name character and otherwise uses the same alphabet. Hyphen, dot, slash, and whitespace are not name characters.

**A dot is not a name character, but an entity name may be *composed* of dotted parts, and each part after the first is narrower than a whole name.** A part following a dot must begin with a non-digit name character, so `$Anchor.Nope$` reaches entity lookup and draws `INVALID_ENTITY` while `$Anchor.2$` never becomes a name and draws `MVK_UNEXPECTED_TOKEN`. A slash-separated numeric segment is by contrast an ordinary path element, so `$Anchor/2$` also draws `INVALID_ENTITY`. Those two spellings are the old-world running-number and line specifiers, whose grammar production is gated on the model being an H-model, so neither reaches its own `INVALID_FIELD_L` or `INVALID_FIELD_Z` class from an A12 document model; no witness for either is known as of the measured revision ([checkpoint](../docs/SOURCES.md#src-message-parameter-surface-and-iteration-gates)).

**A quoted segment is lexed as a unit, so an illegal character inside it is refused a layer earlier than the same character bare.** `'Ro-ws'`, `'Ro ws'`, and `'1Rows'` in the group position each draw `MVK_LEXER_STANDARD_ERROR`, while their bare spellings reach the group lookup and draw `INVALID_GROUP` — the same code an undeclared but well-formed name draws. A consumer must therefore not merge the two codes: they report different layers, and only the lexer one says the text was never a name.

**The parameter's name token is wider than any group may be named, so some legal tokens can never resolve.** The Kernel refuses to declare a group named `1Rows` or `Ro-ws` with `MVK_PATH_INVALID`, and a digit-initial or `:`-bearing name is refused on every declaring carrier, so the token grammar's digit-initial and `:`-bearing names are well formed and permanently unresolvable, and their `INVALID_GROUP` is the only answer the Kernel can give ([checkpoint](../docs/SOURCES.md#src-parameter-token-versus-group-declaration-alphabet)).

**That conclusion survives, but the rule an earlier version of it stated does not: the declared-name alphabet is the *carrier's*, and it is not one law.** "A name may contain only letters, digits and underscores, and must begin with a letter or an underscore" was read off two group refusals and is wrong on both halves once a second carrier is asked, in the one direction a consumer may not take ([inbound](../docs/SOURCES.md#inbound-2026-09-21-corrections)). Five of thirteen name shapes answer differently on a **field** than on a **group**, and neither carrier is simply the stricter one: a **nested** group refuses a leading underscore as `NAME_STARTS_WITH_UNDERSCORE_AND_WRONG_PATTERN`, reserving it for `__meta` and `__attachment_meta*`, where the **root** group admits `_Orders` and a **field** admits `_Slots`; a group name admits `ä` and `ö` (`Teilä`, `Slöts`), a root group `Ö` as well (`Ördner`), and refuses `é` (`Parté` draws `MVK_PATH_INVALID`), while a field name refuses `ö` and `é` (`Slöts`, `Codeé`), so the group's non-ASCII allowance is not "any non-ASCII letter"; that it is exactly the German umlauts and `ß` its name pattern names is source-read, with `ß`, `ü`, `Ä` and `Ü` unmeasured ([inbound](../docs/SOURCES.md#inbound-2026-09-26n-field-message-gates)); and a 61-character name is refused codeless as a group and admitted as a field, the 60-character limit being the group's alone. The **code** moves with the carrier too. A field answers a second validator the group's name never reaches, so its classes carry the `_A12_DV` suffix — `MVK_NAME_INVALID_DOT_COLON_A12_DV` for `.` and `:` except a dot followed by a digit (`Co.1de`), which draws `MVK_PATH_INVALID` alone ([inbound](../docs/SOURCES.md#inbound-2026-09-26n-field-message-gates)), `MVK_NAME_STARTS_WITH_DIGIT_A12_DV` beside the ordinary `MVK_PATH_INVALID` for a digit-initial name, `MVK_NAME_STARTS_WITH_XML_A12_DV` for an `xml`/`XML`/`Xml` prefix — where both group carriers answer with the unsuffixed spellings; and whether a *name* class fires at all splits root from nested, a digit-initial name drawing `MVK_NAME_STARTS_WITH_DIGIT` and no path class on the root, the path class and no name class on a nested group, and both on a field. A `/` inside a name is the one shape that answers alike everywhere, as `MVK_PATHS_INCONSISTENT`, because it makes the element's own path disagree with the tree rather than being a bad name. A **rule's** name is not judged: a digit-initial or dotted rule name leaves A12 unable to build the model, so no consistency verdict exists and there is no class to reproduce, and an `xml` prefix on a rule is simply admitted. A consumer applying one carrier's measured law to another therefore refuses legal models — which is what happened on the peer's own portable checker, to a model whose root group was named `_Orders`.

Constraints and runtime behaviour:

- **Forbidden in computation rules** and **inside filter (`Having`) conditions**.
- Like any predicate it does **not** exempt the rule from the error-field rule ([§9](07-repetition-and-iteration.md)) — here the `FieldFilled(id)` conjunct references the error field. A **bare** `CustomCondition X` referencing no field is rejected (`MVK_ERROR_FIELD_NOT_REFERENCED`).
- When ordinary rule evaluation reaches `CustomCondition X`, the kernel invokes the registered callback with four inputs: the document/data view, the partial-validation relevant-entity set (or an all-relevant marker during full validation), the complete set of formally incorrect field instances, and the current rule error-field `PartiallyKnownDocumentMultiPointer` ([§2.1](01-data-model.md#21-repetition-contexts-the-iteration-environment)). Under parallel iteration it may carry `UNKNOWN` and then has no exact-pointer counterpart.
- Formal errors do **not** automatically suppress that invocation. Only the callback knows its hidden dependencies, so the callback contract requires it to inspect relevance and formal-invalid inputs and return `false` when one of its own necessary fields cannot be used. Unrelated formal errors need not decide it. A callback that returns `true` contributes a **VALUE** firing leaf; `false` contributes the kernel's collapsed non-firing/unknown leaf, after which normal `And`/`Or` composition and rule emission apply.
- Empty-row eligibility belongs to the complete condition, not to a callback-internal read set that the kernel cannot see. A `CustomCondition` leaf is structurally classified as able to fire on empty; the common `FieldFilled(id) And CustomCondition X` form is blocked on an empty row by its `FieldFilled` conjunct, while `CustomCondition X Or FieldFilled(id)` may reach the callback on that row.
- A missing registration is a validation integration error. A callback may also throw through the documented host failure route; neither case is silently converted into "did not fire".

**The extensibility surface is closed.** Custom **conditions** and [custom **field types**](06-strings-and-enumerations.md#a3-custom-field-type-validation) are the engine's *only* custom hooks — there is **no** custom *computation* or function. A custom field validator contributes a formal cell observation; `CustomCondition` contributes a rule-predicate result. A computation's operation vocabulary is closed, and `CustomCondition` (the one predicate hook that could otherwise reach a computation) is barred there.

> **Non-normative implementation note.** Introduce an explicit `CustomConditionInvocation` carrying the document/data view, full-versus-partial relevance, the formal-invalid address set, and the current error-field pointer, then parameterise the successful-result fragment by `customConditions : Name → CustomConditionInvocation → Bool`, separate from the custom-field-validator map in `World`. The row gate and surrounding condition decide whether the oracle is invoked; do not derive an `unknown` result merely from a nonempty formal-invalid set. Oracle `true` yields `.fired .value`, and `false` yields the non-firing leaf. Purity and totality are deliberate reproducibility restrictions of the Lean account, not properties enforced by the kernel's host runtime; a missing name is an elaboration/well-formedness error and a thrown host exception is an explicit out-of-theory integration failure. Purity alone does not imply locality or monotonicity, so whole-rule theorems must exclude custom conditions or require an explicit oracle contract. The operation vocabulary on the computation side remains closed.

## Checklist for §13 + §14

- [ ] Rule-owned interpolation is a **pure render step** after firing; field names use provider result → nonempty model label → debug priority, with a present empty provider result still winning.
- [ ] A missing or empty rule-owned field display uses the exact format-supplied default; display bytes are opaque, and message rendering neither reads nor renormalizes the evaluation cache. The current `DocumentV2` Number default follows minimum fractional digits and uses `.` in the tested locale/model-config cases; String supplies empty. A number's unit trait is not rendered.
- [ ] Rule-owned `$Field.value$` requires a non-starred reference; error-text paths are asterisk-free. A **keyed** parameter is gated on the semantic index instead of on the field, exactly and in both directions, so field membership is the unkeyed form's requirement alone.
- [ ] Producer-specific field templates remain distinct: the measured String-pattern grammar accepts only the condition language's two tokens (`$field$`/`$field.value$`, `$Feld$`/`$Feld.Wert$`), rejects an empty `$$` inside the text or at its start and admits one at its end or alone, reports one class per field from the first failing locale in declared order, and inserts opaque bytes once; the measured requiredness witness preserves `$$` and is not generalized to a complete grammar.
- [ ] A reached `CustomCondition` receives document, relevance, formal-invalid addresses, and the current error pointer; its callback—not an evaluator pre-gate—decides its hidden dependencies. `true` is VALUE; whole-condition structure decides empty-row reach; the rule must reference the error field; the construct is **barred** in computations and filters. Lean deliberately admits a pure, total successful-result oracle and treats missing/throwing host callbacks as integration failures.
- [ ] A `CustomCondition` result is distinct from the declaration-driven custom-field formal observation owned by §7.
- [ ] Extensibility surface is **closed**: custom conditions + custom field types only; no custom computation/function.
