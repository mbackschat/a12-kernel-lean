# 07 — Repetition, iteration, and cross-array evaluation (§9)

This is the kernel's most distinctive semantics, and the largest single reimplementation risk. A flat rule fires zero or once. Repeatable data creates **per-row rule messages only through an iteration-bearing condition reference**: a star consumed operand-locally by an aggregate reopens that operand's row stream without itself producing one rule evaluation per reopened row. Several constructs turn a rule into what is effectively a small **query language over arrays** — joins, correlated subqueries, aggregates, uniqueness.

The mental model to hold: **iteration produces a set of repetition contexts** (the `Env` of [`01-data-model.md §2.1`](01-data-model.md#21-repetition-contexts-the-iteration-environment)), the rule is evaluated once per context, and each construct is *about how the environment is built and extended*.

---

## 1. When a rule iterates, and where its error lands

A rule **iterates when its condition contains an iteration-bearing repeatable reference.** Its **iteration scope is derived from the condition's references — never from the rule node's placement or from the error entity by itself.** An ordinary unstarred reference contributes its repeatable path. A starred operand contributes only the already-bound repeatable prefix strictly above its first `*`; the starred level and every level below it are reopened by that operand rather than added to the surrounding rule iteration. Candidate-local references inside `Having` likewise belong to the operand-local traversal rather than to the surrounding rule scope.

**Runtime evaluation uses the V2-effective repetition structure.** A mutable V1 document may contain only a placement at repetition `n`, but validation and computation first convert it to immutable V2. That conversion creates missing ancestors and pads repetitions `1..n-1` with empty group instances, scoped independently under each concrete parent. Those padded repeatable rows are instantiated content and participate in per-row iteration exactly like explicitly created empty rows. This is not an alternative sparse JSON encoding: every position in a canonical Document JSON array is explicit, including `{}`.

- At an outermost repeatable level, the rule is evaluated once per concrete V2 repetition, preserving full parent coordinates and document order; no outer row means no evaluation. **Nested validation iteration has a distinct implicit-child rule:** under every existing repeatable parent iteration row, a nested repeatable validation scope with no concrete child contributes one implicit child at repetition 1, recursively. The implicit child is an evaluation context, not a stored group instance: `GroupFilled`, starred group/index operands, mandatory and `uniqueIndex` auto-checks, parallel identity, and computation continue to use concrete V2 rows only. `RepetitionNotUnique` uses the validation iteration domain and can therefore report an optional-empty duplicate on implicit child pointers. A positive child guard remains false on an implicit empty row and cannot prove the row was not evaluated; an empty-as-zero comparison separates the two readings. Each emitted message attaches to the exact concrete or implicit validation context.
- Compatible nested references select the deepest ordinary nonparallel path. Incompatible sibling/cross-branch paths require the separate parallel-iteration construction; they are not merged positionally.
- The **error field must inhabit a scope compatible with** the derived iteration — a genuine cross-cardinality split is rejected (`MVK_ERROR_FIELD_NOT_IN_RULEGROUP`).
- The **error field must be *referenced* by the condition** — directly, or indirectly (an enclosing `GroupFilled(Group)` counts) — or the model is rejected (`MVK_ERROR_FIELD_NOT_REFERENCED`). This is an admission and error-targeting constraint, not another source of iteration levels. A `RepetitionNotUnique` **authored `@From` clause contributes its whole group subtree as a reference**, admitting fields inside the group and descendant groups but not parent fields. The keys' own group is *not* an implicit reference: dropping `@From` rejects the same inside/descendant error fields even when default scope resolution selects the same group, so an implementation must retain whether `@From` was authored rather than reconstructing it from the resolved scope. **This gate runs after the operand-locus gate, so it never reports first for a condition that offends both.** A condition holding an unstarred repeatable operand read from a non-iterating locus is rejected `MVK_NO_WILDCARD` even when the error field is absent from that condition, while the same unreferenced error field draws `MVK_ERROR_FIELD_NOT_REFERENCED` once the repeatable operand is removed. The locus gate also runs before whole-list arity: a sole bare overlap operand draws `MVK_NO_WILDCARD` from a non-iterating locus but reaches `MVK_PARAMSIZE_INVALIDFN` from an iterating locus. So a consumer that checks error-field reference or arity before operand loci will report a class the Kernel does not.

Example: a rule with error field `Round` inside a repeatable `Poker` group, condition `FieldFilled(Poker/Round) And [Poker/Win_Loss] >= 0`, evaluates once per existing round and reports on the offending round.

Two boundary rules sharpen this:

- **The error entity alone is not an anchor.** A rule whose error field sits *deeper-repeatable* than its condition references keeps the *references'* scope (the error field does not deepen iteration on its own).
- **A rule with no repeatable (non-starred) reference evaluates exactly once**, anchored at its error entity, regardless of its declaring container's instance content. The declaring group matters only for resolving relative references. When that empty derived scope fires and the error field descends through repeatable levels the scope does not bind, the message pointer **pins those levels to concrete repetition 1**. This may identify a physically present first row or, when the whole-condition content gate permits, a phantom first-row anchor. Omitting `[1]` in a rendered projection does not turn the address into a declaration pointer — the exact/message-pointer distinction is [`01-data-model.md §2.1`](01-data-model.md#21-repetition-contexts-the-iteration-environment). Rule placement remains irrelevant.

> **Non-normative implementation note.** `iterationScope : Rule → Except ScopeError (Option (List RepeatableLevel))` is computed from the checked condition references. Compatible scopes merge by prefix and retain the deepest path; sibling paths fail into the separately specified parallel boundary. Rule assembly then proves that the checked error declaration is compatible with the derived scope and is referenced by the condition. `evalRule` enumerates the validation contexts (`Env`s) that assign a row to each level in scope, preserving complete parent coordinates and document order. The outermost level uses concrete V2 rows; each deeper level uses concrete children when present and otherwise contributes the implicit validation child at row 1. Do **not** derive scope from where the rule node or error entity is declared, and do not reuse this validation-only projection for stored-content, star, auto-check, parallel-identity, or computation consumers. A rule with empty scope evaluates once at the root `Env`.

Static negative-condition admission is checked **separately at every ordinary iteration level** selected above. At one level, an `And` is admitted when at least one child both references that level and is itself admitted; an `Or` is admitted only when every child references that level and is admitted. Leaf admission is operator- and operand-sensitive rather than one global “negative operator” flag. For the direct iterating Number-field-versus-immediate-number-literal shape, the kernel treats ordinary `==`, `>=`, and `<=` as unguarded exactly when its host-converted integer form of the literal is zero; strict `<`/`>`, ordinary `!=`, tolerance-not-equal, and a converted nonzero literal are admitted. The host conversion parses the finite decimal to nearest-even binary64, applies Java `Math.round` — half-up toward positive infinity, with long saturation — and then narrows to signed 32-bit by two's-complement wrap before testing zero or positivity. Exact rational value plus the authored fractional-digit count determines this conversion because number literals have no exponent and the parser removes only redundant leading zeros; signed zero is the sole lost spelling and has the same converted integer. Consequently the classifier is not exact-decimal sign or zero, and **two distinct mechanisms produce that gap; they must not be conflated.**

For a group-list leaf containing a starred group, a queried level is referenced only by operands whose captured prefix contains that level. `AtLeastOneGroupFilled` is guarded there exactly when **every** operand references the level; mixing a fixed operand with an iterating starred operand makes the leaf unguarded. `NoGroupFilled` is unguarded whenever any operand references the level. A level outside every operand's captured prefix is not referenced by that leaf. These leaf results then compose through the same `And`/`Or` rules above: an independently guarded conjunct can admit a negative starred list, while a guarded sibling of an `Or` cannot.

- **At narrowing time**, the signed 32-bit truncation is reachable and is the sharpest separator of all. On a **scale-0** field a bare integer literal satisfies the comparison's decimal-places gate and reaches the classifier, where it is judged on its *narrowed* value: `== 4294967296` (`2^32`) is **rejected** because it narrows to zero, while `== 4294967297` is admitted because it narrows to one. Two literals differing by one, both astronomically far from zero, land on opposite sides of the partition — a widening or saturating conversion admits both, so this pair pins 32-bit truncation specifically. `2^63` is likewise admitted: rounding saturates at the maximum long, which narrows to minus one. **At the long boundary the two signs disagree, and the cause is the range's own asymmetry rather than the parse step.** Neither `+(2^63 − 1)` nor `−(2^63 − 1)` is representable in binary64; both parse onto `±2^63`, so the parse step is symmetric here and decides nothing. The saturation is not symmetric: `+2^63` exceeds `Long.MAX_VALUE` and saturates down to `2^63 − 1`, whose low 32 bits are all set, narrowing to minus one; `−2^63` **is** `Long.MIN_VALUE` exactly, passes through unsaturated, and has its low 32 bits clear, narrowing to zero. So `== 9223372036854775807` is admitted while `== -9223372036854775807` is **rejected** — equal magnitude, opposite classification, produced by the two's-complement long range being asymmetric rather than by `Math.round`'s half-up direction. This is the sharpest separator against an implementation using exact 64-bit integer arithmetic in place of the binary64-and-saturate chain: exact arithmetic narrows `−(2^63 − 1)` to one and admits it, while agreeing with this account on the positive side. It is not a blanket negative-boundary rejection — one representable step away, `== -9223372036854773760` is admitted again, since doubles just below `2^63` are spaced 1024 apart and only the low-32-bit residue decides. `== 9223372036854775808` behaves as its neighbour `2^63 - 1` does and is likewise admitted, since both parse onto the same double. **Measured through the kernel at a12-dmkits `ee2f5d84`**, which confirmed all three admission rows and the intermediate conversion values that separate saturation from binary64 granularity as the cause.
- **At rounding time**, `Math.round` does **not** lift a double strictly below one half. Its half-up direction is instead asymmetric about zero: `0.50` converts to one while `−0.50` converts to zero, so two literals of equal magnitude and opposite sign classify differently. Half-even would give zero for both and half-away-from-zero would give one for both; only half-up toward positive infinity matches.
- **At parse time**, binary64 round-to-nearest-**even** lifts every decimal in `[½ − 2⁻⁵⁵, ½)` onto exactly one half, because that interval's values are ties between `0.5` (even significand) and `0.5 − 2⁻⁵⁴` (odd). Rounding then yields one. The lift is **positive-side only**: a lifted `−0.5` still converts to zero, so the asymmetry above survives the parse step rather than being softened by it.

**The parse-time lift is authorable, behind the one waivable diagnostic.** Its shortest witness needs **17** fractional digits — at sixteen or fewer the interval holds no decimal strictly below one half — while a Number field's maximum fractional digits caps at **14** ([§5](04-numbers-and-decimals.md)) and a comparison literal may carry at most the field's scale. That literal gate is `MVK_INVALID_COMPARE_DEC_PLACES`, the kernel's **only** suppressible code, so `14 < 17` raises the authoring cost of the witness rather than forbidding it. Against a scale-14 field with the gate suppressed, `== 0.49999999999999998` is **admitted** and `== 0.49999999999999990` is **rejected**: two literals of equal length differing only in the final digit, both strictly below one half, straddling the whole partition. Two related traps are worth stating because both come from reading a diagnostic instead of measuring: that gate is **at most**, not equality — its message says the digit counts "are different", but a *shorter* literal is admitted and reaches the partition normally; and the historical `floor(x + 0.5)` implementation of `Math.round` did lift a double just below one half, but that is confined to host JDKs before 7, is a property of the platform rather than of the kernel, and must not be reproduced. The same classification applies with the literal on either comparison side. Direct evaluated-String `Length(field)`, direct `RangeAsNumber(field, start, end)`, direct `FieldValueAsNumber(field)`, and direct numeric Day/Month/Quarter/Year or Hour/Minute/Second extraction from a temporal field are also field operations in this zero-sensitive family: each target reference supplies ordinary scope. Addressed `Length` runtime reads that exact checked String cell and uses the ordinary evaluated UTF-16 length; addressed `RangeAsNumber` retains its checked interval and grow-only missing/fixed fallback-zero distinction; addressed `FieldValueAsNumber` retains the checked String or stored/category Enumeration projection and domain-derived scale before applying the established conversion; addressed temporal extraction retains the checked Date/Time/DateTime kind and available-component certificate before projecting the decoded row value. An empty temporal source produces symmetric fillable zero, a filled source produces a fixed component, and formal unavailability remains UNKNOWN. Fixed `BaseYear`-derived extraction contributes no field scope. Date-only `DifferenceInMonths` and `DifferenceInYears` instead retain two ordered operands under their own zero-sensitive operation branch: every field operand contributes its declaration-owned ordinary scope, compatible prefixes merge to the deeper scope, and a direct or range-selected `BaseYear` operand contributes none. `DifferenceInDays` shares that scope, zero-admission, and addressed-order account but separately admits DateTime and retains the checked concrete model-zone profile, each decoded local label, and each already-resolved exact instant. `DifferenceInHours`, `DifferenceInMinutes`, and `DifferenceInSeconds` share the same two-field scope and zero-admission branch but accept DateTime fields only, require the selected time component and compatible year presence, retain the exact selected unit, and evaluate signed elapsed epoch milliseconds with truncation toward zero; `BaseYear`, Date, and Time operands are rejected. Runtime reads every difference operand in authored order from one complete environment, maps either missing operand to symmetric fillable zero, preserves formal UNKNOWN, and keeps structural addressing failure outside UNKNOWN. Top-level operation-list `Abs`, rounding, and operand-list Min/Max whose direct Number references all iterate at the queried level retain that zero-sensitive partition. When an operation-list or entity-list reference set is **mixed** at that level—at least one reference iterates there and at least one does not—every immediate numeric-literal comparison is unguarded, independent of operator, operand direction, or literal conversion; the family-specific zero/positive tests apply only to the all-iterating case. A filtered entity-list slot contributes its selected target reference to this classifier, not the references inside its `Having`; those filter references retain their separate authoring and runtime roles. For a plain or filtered-star Number entity list at one ordinary scope, `FirstFilledValue`, `Sum`, `MinValue`, and `MaxValue` are zero-sensitive; `NumberOfDifferentValues` is instead sensitive to a positive threshold under `<`, `<=`, `!=`, or tolerance when the count is on the left and the reversed directions when it is on the right; `NumberOfValueInFields` has both sensitivities. The String/Enumeration overload of `NumberOfValueInFields` uses the same zero and positive-threshold branches over its selected target references. A row-aligned plain-star `SumOfProducts` is zero-sensitive but has no positive-count sensitivity. A top-level ordinary arithmetic or power expression is instead represented as a composite operation and is not reclassified by the visitor's direct field/list-versus-constant branches: wrapping the same iterating field in such an expression can therefore make this static gate admit a condition whose syntactically direct counterpart it rejects. This paragraph describes static model admission only; runtime still evaluates the original decimal comparison.

## 2. Parallel iteration — joining two repeatable groups by key

When a rule references **two repeatable groups where neither is nested in the other**, they are iterated **jointly, keyed by an Index Field** that must exist on each group and **share the same name and type**. This is an **outer join** over the index values:

```
FieldsNotCollectivelyFilled(Demand/Units, Capacity/Units)   -- iterated per shared Warehouse index value
```

**Constraints:** at most **one** index field on the error field's path and on each parallel-iterated group; parallel iteration is **not allowed over rules using `RepetitionNotUnique`**; and **negative conditions are not allowed in a parallel iteration** except alongside a positive condition.

**Mechanics (verified):**

- The iteration value-set is the **union** of the joined groups' index values.
- An **unmatched side reads "not specified"**, its message `PartiallyKnownDocumentMultiPointer` carrying the fixed sentinel repetition index **`-5`** (`IIdentifier.UNKNOWN`); that address has no exact-pointer counterpart ([§2.1](01-data-model.md#21-repetition-contexts-the-iteration-environment)).
- An **invalid** index value (duplicated or empty) marks that group's index invalid for the parent, so references into it read three-valued **UNKNOWN** for unmatched values — which *suppresses* a negative operator like `FieldsNotCollectivelyFilled`.
- Non-repeatable intermediate groups are **transparent** to the join; a repeatable **non-indexed frame** is legal above exactly one joined group.

> **Non-normative implementation note.** This is a genuine outer join. Model it as: collect each group's `Map IndexValue Row`; the iteration keys are `keysOf(a) ∪ keysOf(b)`; for each key build an `Env` where a present side binds its row and an absent side binds the `-5` sentinel (read as "not specified"). Keep the sentinel explicit because several downstream reads (a negative predicate going UNKNOWN on the unmatched side) depend on distinguishing "absent" from "empty".
>
> Under partial validation, build each `Map IndexValue Row` from the **relevant** index cells only, then take the union as above. Three consequences are measured. First, a relevant set that names a payload field but not the index field yields an empty key set and therefore no iteration. Second, a group whose index cell is absent from the relevant set while the other side still supplies the key binds the `-5` sentinel exactly as a group with no row does, so relevance can make the sentinel reachable; rule gating treats that unmatched side's own repetition level as unbound because no row was chosen there. Third, a non-relevant index cell also **invalidates the column for that parent**, exactly as an empty cell does, so unmatched references into that group read UNKNOWN rather than definite empty. One such cell is enough on either side. Only a negative operator separates this third rule from the weaker account.
>
> Independently of relevance, a **duplicated** index value is not a selectable entry. Every colliding row leaves the map, so row order never resolves the value. The value keys the join only if another group carries it cleanly, and references to it from the compromised group are unmatched and therefore UNKNOWN. A clean value in the same compromised group still joins normally.
>
> Also independently of relevance, the map is keyed by the index field's **normalized value**, not its stored text, using the same declared-kind projection as the semantic index. On a Number index field, `5` and `5.00` are one key within and across groups; on a String index field, the same tokens remain distinct.
>
> **Cache membership/relevance and formal admission precede every index-identity relation.** An over-limit row is outside the cache and contributes no key, collision participant, selectable row, or column compromise. An in-cache stored cell that is non-relevant for the partial call, empty, built-in-invalid, or rejected by a registered custom type contributes no key, collision participant, or selectable row and compromises an unresolved column to UNKNOWN. Relevance is checked first, so excluding a custom cell does not invoke its validator. With Number rows `05 -> 10` then `5 -> 20`, lookup `5` selects row 2 while row 1 retains its leading-zero formal error; reversing them selects admitted row 1. With `05`, `5`, and `5.00`, the invalid row stays outside the relation while the admitted peers collide, so key `5` is unavailable. Presence uses the resolved identity: an unavailable matching key makes both `FieldFilled` and `FieldNotFilled` UNKNOWN. A target below the indexed group inherits its nearest indexed ancestor; the key selects that outer row, authored target-group coordinates remain independently iterated, and lower levels default to row 1 for message attachment. Message-pointer target identity is authored syntax rather than canonical runtime-key identity. An ordinary message reference to the repeated error field, directly or through a containing group operand, keeps physical iteration authoritative. Otherwise only semantic references targeting the repeated error field or an ancestor group containing it count: one exact authored key target carries its selected repetition or clean-no-match `[-5]`, using the deepest error-containing selector independently of operand order, while two distinct key expressions retain ordinary error-row iteration even when they normalize to one Number key or currently select one row. Sibling payload references add no pointer target. On the compute path, the current cascade overlay supplies both a field-valued query key and the selected scalar/group payload below an indexed ancestor.

## 3. The filter `Having`, the `$` correlation, and aggregation

`Having` filters a repetition list (a `*`-path) down to the rows where a condition holds, **before an aggregate consumes it**:

```
Sum(Products*/Quantity Having [Products/ProductName] == "N33") > 100
```

**The filter's condition is the ordinary condition production, and the ordinary refusals apply inside it.** Measured admitted in a field-list filter: a String equality against a literal or another String field, `FieldFilled` and `FieldNotFilled` with no iteration-negativity refusal, a Number `!=`, `And`, `Or`, parentheses, a bare outer scalar reference with no `$`, and a group-presence leaf. Measured refused, by the general rules rather than by a filter-specific gate: mixing `And` with `Or` unbracketed draws `MVK_BRACKET_MISSING` here exactly as it does at a rule's top level ([§2](02-logic-and-formal-errors.md#a1-connectives-are-two-valued-parentheses-are-mandatory)), and a String field in a numeric ordering comparison draws `MVK_INVALID_TYPE_FOR_COMPARISON` from a single-leaf filter carrying neither connective nor parentheses ([checkpoint](../docs/SOURCES.md#src-having-filter-condition-grammar)). So a reimplementation must reach the filter through its full condition evaluator; a Number-comparison-only filter fragment is narrower than the kernel, and the `$` machinery below is an *addition* to that grammar rather than the shape of it.

**An admitted reference to a level the star does not reopen is a constant, so the filter keeps every candidate or none of them.** The reopened level is the one the operand stars; a reference naming any other repeatable level on the operand's path, or a nonrepeatable field, resolves to the same row for every candidate and therefore cannot select a subset. What differs between those two carriers is only how far the constancy reaches: an unstarred repeatable **ancestor** is constant wherever the enclosing iteration binds that ancestor to the same row — so two host rows disagree only when they differ in *that* coordinate, not merely in being different rows — while a **nonrepeatable** leaf is constant across the whole document. Measured with the ancestor two levels above the star: the two host rows under one ancestor row agree, and the pair under the other answers the ancestor's own gate. Measured on `Sum` over a two-level operand: three host rows gating `1, 0, 1` yield `30, 0, 50` under the ancestor filter and `30, 70, 50` under the leaf one, and the leaf filter collapses to zeroes on a document differing only in that cell. **A domain the filter empties yields the aggregate's zero, not a cleared target** — the gated-off row reports a value of `0`, which is the same empty-domain zero a never-instantiated domain and a capacity-emptied one produce. The rule holds on **both arms and in both spellings**: a validation rule over such a filter fires on exactly the host row whose selection emptied, and the `$` marker computes identically at a level the star did not reopen. Neither gate reads **depth**: a reference two repeatable levels above the star is admitted exactly as an immediate ancestor is, and one whose path crosses two repeatable levels *off* the operand's path is refused exactly as a single off-path level is, so the gates are decided by path membership alone. A reference the star *does* reopen is the candidate-varying case and none of this applies to it — such a reference drops its own row and leaves the aggregate at its ordinary value ([checkpoint](../docs/SOURCES.md#src-filter-reference-level-runtime)).

**Which class a refused filter reports is a property of the filter, not of the operator that wraps it** — identical across a temporal extremum, a distinct count, and a filled-field count on every refusal tested. The comparison gate has **two columns keyed on the literal's family and they agree on only the two temporal kinds.** Against a *numeric* literal, a String, Boolean, Confirm, Enumeration or DATE_RANGE field side all collapse into `MVK_INVALID_TYPE_FOR_COMPARISON` (singular — not the plural constant the value-list quantifiers draw), while both temporal families draw `MVK_INVALID_COMPARE_TO_DATE`. Against a *String* literal the same kinds spread across four classes exactly as [§11](09-computations.md)'s constant-assignment ladder does at its string-like row, String being admitted and Enumeration gated on its stored-token domain. Three scope classes separate what one description would merge: a root-level field the filter's star cannot bind reports `MVK_NO_ITERATION_FOR_WILDCARD`, a *different* repeatable group's field read without a star reports `MVK_INVALID_ITERATION_IN_FILTER_CONDITION`, and a star written inside the filter reports `MVK_NO_WILDCARDS_ALLOWED`. The equality scale gate applies inside the filter too, admitting the same literal against a declaration whose scale fits ([checkpoint](../docs/SOURCES.md#src-having-filter-comparison-and-scope-classes)).

The keep rule is exact: retain a candidate only when the filter condition is **known true**. A false or three-valued unknown result drops that row **before the aggregate or quantifier reads the selected consumer cell**. The filter otherwise uses the ordinary condition tables, so a dominating true `Or` may still decide despite an unknown sibling. In a standalone comparison, an invalid row-local operand drops only that candidate; an invalid captured-outer operand makes that comparison unknown for every candidate that reads it, so each such standalone filter drops.

**A dropped row leaves the aggregate available, and that is the opposite of what an unavailable *target* does.** A non-true conjunct removes its own candidate and the aggregate then answers over the survivors — zero of them included, which is an ordinary `0` for a count or a `Sum` and not an unavailable operand. One malformed filter cell among several selected rows therefore costs exactly that row: a two-row selection whose first row is well-formed and whose second carries a malformed filter operand answers from the first row alone. Contrast the target position in the paragraph below, where the first selected formally unavailable cell makes the **whole** aggregate unavailable; carrying that rule onto the filter reports unavailability where the kernel excludes one row. ⚠ **The empty-operand-as-zero rule ([§2](03-empty-and-required.md)) reaches an *absent* filter operand and not a *formally invalid* one.** An absent Number operand participates as `0` and the comparison decides normally, so `[Amt] < 5` is true on an absent `Amt` and keeps the row; a malformed `Amt` instead makes the conjunct non-true in **both** comparison directions and keeps no row under either. So a filter's three-valued drop is not reducible to a substituted value that then compares false ([checkpoint](../docs/SOURCES.md#src-having-filter-nontrue-row)).

Computation uses the same condition tree but not validation's unknown-as-drop projection: a formally invalid filter operand actually reached during computation poisons the reading computation. Filter and target reads are interleaved by one **kept-successor lookahead**. After a candidate is kept, the iterator searches through later false candidates until it finds the next kept candidate or exhausts the stream before the consumer reads the current candidate's target. A poison encountered during that search therefore wins over a filled current target. Once one successor has been kept, a terminal current target leaves every filter after that successor unread. This is neither eager filtering of the complete selection nor target-first row evaluation, and an earlier terminal authored operand still hides every later operand and its filter.

The **`$` operator** — usable **only inside a filter condition** — switches a reference from the candidate environment to the **complete captured outer repetition environment** of the iterating rule *or repeatable computation instance*, turning the filter into a **correlated subquery** (e.g. "holidays whose date equals the current stop's ETA"). **The capture source is whatever instance the filter's enclosing evaluation iterates, not specifically a rule:** a computation whose target is a repeatable field is evaluated once per target row, and `$` binds that row, measured at exact per-row values on both codegen strategies. Read as rule-only, a reimplementation either refuses a legal per-row computed target or leaves its capture unbound. The reference's resolved repeatable level then selects its own coordinate from that environment: a parent-level `$` reference and a nested-descendant `$` reference may denote different repetition indices in the same rule instance. At least one unmarked reference must reach a repeatable level reopened by the filtered operand; an all-`$` filter or one whose unmarked references are confined to bound ancestor levels does not establish the filtered iteration and is rejected. Every other unmarked reference must be available from the candidate environment, while every `$` reference must be available from the captured rule environment. **`$` is not optional sugar, but it is not the only way to reach an outer field either, and the distinction is by level rather than by scope.** For a level the star **reopens**, the marker is the sole way to read the captured coordinate, because the unmarked reference reads the candidate's — that difference is the whole correlation. For an unstarred repeatable **ancestor on the operand's own path** that the enclosing iteration binds, the candidate environment inherits that coordinate from the captured prefix unchanged, so *both spellings are admitted and read the same row*: measured on a two-level model with a one-star operand, where the marked and unmarked filters fire on identical rows over a document whose outer field varies across those rows. **That redundancy does not extend past the operand's path, and off it the marker is load-bearing rather than optional.** For a repeatable level the operand's path does not contain, the unmarked spelling is refused `MVK_INVALID_ITERATION_IN_FILTER_CONDITION` as the sole condition *and* beside an in-scope conjunct, and it stays refused even when the enclosing rule iterates that very level, while the `$`-marked spelling is admitted beside an in-scope conjunct. So a consumer must not strip `$` as redundant on the strength of the ancestor rows: on a sibling that turns a legal model illegal ([reconciliation](../docs/SOURCES.md#src-2026-09-05-second-reconciliation)). Neither spelling satisfies the in-scope requirement above — a bare outer reference as a filter's **whole** condition is refused `MVK_NO_ITERATION_FOR_WILDCARD` exactly as a marked one is — so the requirement and the reachability question are separate. A consumer may therefore drop or add the marker on a non-reopened level without changing behaviour, and must never do so on a reopened one.

A same-group starred candidate set includes the current outer coordinate unless explicitly excluded; correlation does **not** imply self-exclusion. `CurrentRepetition(G) != CurrentRepetition($G)` compares the resolved repetition coordinate at level `G`, not an opaque physical-row identity. In a multi-star `A*/B*` candidate set, comparing only `B` can therefore exclude every candidate that shares the outer row's `B` leaf index across different `A` rows.

**Aggregation consumes an ordered resolved stream, not a mathematical set.** Authored entity-list entries retain their authored order, a group entry expands its fields in stable model order, and repetition coordinates advance in ascending order with the lowest nested repeat level changing fastest. `Having` selection occurs before the selected target is read, as above; the first selected formally unavailable or non-relevant target makes the aggregate unavailable immediately, so the suffix is not read. The internal kept-successor order still determines which reached filter or target failure occurs first, but the public computation result erases that source identity; a draining aggregate that reaches the same failure set therefore cannot expose filter-versus-target precedence, while a prefix consumer such as `FirstFilledValue` can expose which suffix was never reached. `Sum` performs no arithmetic step for an unspecified cell—the same numeric contribution as zero—but records that cell's own declaration for polarity. `MaxValue` / `MinValue` ignore unspecified fields; a Number list with none specified yields `0`, while a Date list yields no value ([§2](03-empty-and-required.md)). `Sum`'s per-step arithmetic is specified in [§5](04-numbers-and-decimals.md#5-internal-precision--the-constants-that-must-match-exactly).

**⚠ A filter's own connectives are commutative on the validation arm and order-sensitive on the computation arm.** The filter condition is the ordinary condition production, so validation evaluates it as a strong-Kleene tree: a true disjunct dominates an unavailable one from either side, and reordering conjuncts or disjuncts cannot change which rows are selected. The computation arm reads left to right and the first **reached** poison aborts, so authored order is observable. **Both connectives short-circuit, each on its own dominating polarity.** The disjunction's witness is one document whose cells never change: with a malformed `Amt` and a present `Sku`, `Having (FieldFilled(Amt) Or FieldFilled(Sku))` produces **no computed outcome** while `Having (FieldFilled(Sku) Or FieldFilled(Amt))` computes its value, because the clean true decides before the malformed cell is read. The conjunction is the mirror image with the dominating operand *false* instead of true: on the same malformed `Amt` with `Sku` **absent**, `Having (FieldFilled(Sku) And FieldFilled(Amt))` computes its value while the reverse spelling produces no outcome. Filling that `Sku` removes the false operand, and then **both** conjunction spellings abort — which is what separates the short-circuit from a conjunction that merely ignores its poison. Each document's validation count is available under every spelling. So a consumer that normalizes, sorts, or otherwise reorders a filter's operands preserves the **validation arm's own reading of that filter** and silently changes the computation's. That is narrower than preserving the form's validation outcome: once compute has run, a rule reading the computed field sees the changed value, so a rewrite that is order-safe for one filter is not thereby order-safe for the document. The eager `formalErrorsInOperands` inventory reports the malformed cell in **every** one of those cases and therefore cannot be used to predict the abort ([§9](09-computations.md)).

**`NumberOfDifferentValues` admits a bounded operand-kind domain and reports homogeneity from the first operand's family.** The admitted kinds are string, enumeration, number, and date/time; a Boolean or Confirm operand is refused `MVK_ONLY_STRING_ENUM_NUMBER_CMP_DATE_ALLOWED`, whose text names that set. A **Custom**-declared field is admitted here and classed with the **string** family — mixing it with a Number draws `MVK_STRING_ENUM_AND_NON_STRING_ENUM` — which is the opposite of the custom-type validity predicate in [§5](05-dates-and-time.md), where a Custom operand is refused outright. One field kind, two operators, two answers, so neither may be read off the other. Homogeneity itself is two rules selected by the **first** operand: number-first then string draws `MVK_NUMBER_AND_NON_NUMBER`, string-family-first then number draws `MVK_STRING_ENUM_AND_NON_STRING_ENUM` — the same illegal pair under two codes ([checkpoint](../docs/SOURCES.md#src-distinct-count-operand-domain)).

The direct plain-field form of `Sum` / `MaxValue` / `MinValue` / `FirstFilledValue` / `NumberOfDifferentValues` requires at least two distinct resolved field references. A single group or flattened (`*`) operand is legal through the separate expansion route because it denotes a field scope rather than a singleton direct list. In an ordinary document model, duplicate checking rejects repeated direct non-wildcard field references, repeated fixed group paths, and indirect group/field overlap, while wildcarded occurrences are treated differently rather than symmetrically. Repeating either a direct field or a fixed group reports `MVK_DUPLICATE_PARAM1`; repeating the same starred group is admitted. **All exact non-wildcard identities share one authored encounter scan, independent of field/group class:** the duplicate whose second occurrence arrives first supplies the repair witness, and only after no exact duplicate exists does strict ancestor overlap run. Thus `(group, field, field, group)` names the field while `(group, group, field, field)` names the group. The indirect ancestor/descendant arm (`MVK_DUPLICATE_PARAM2`) still fires *between* two wildcarded references: `Sum(/Invoice/Lines*, /Invoice/Lines*/Fees*)`, a starred group beside its own starred descendant, is rejected while the same starred group twice is accepted. The singleton direct-field cardinality fault is structurally separate because it contains no operand pair. Inside `Having`, the `$` marker participates in this exact direct-operand identity rather than being erased before the duplicate scan: the authored pair `($P, P)` is admitted under `Sum`, `NumberOfFilledFields`, and `NumberOfDifferentValues`, while `(P, P)` in the same filter reports `MVK_DUPLICATE_PARAM1`. Only that authored order is Kernel-locked here; the reverse pair and `($P, $P)` are not inferred from typed-surface tests. Evaluation preserves repeated wildcard streams; it never silently deduplicates them. The field/star and starred-overlap boundaries are measured under `Sum`; fixed-group equality and the two mixed-fault orders are measured under `FirstFilledValue`. HModel wildcard checking is a separate profile whose indirect arm has no witness here.

**A group-scope operand carries its own admission gates on this carrier, and they are measured on it rather than generalized from the group-list quantifiers or the filled-group count.** A single starred group is a complete operand list by itself, measured for `Sum`, `MaxValue`, `MinValue`, and `NumberOfDifferentValues` over one repeatable group and for `NumberOfFilledFields` over another. A **repeatable** group operand written without its `*` is rejected `MVK_NO_WILDCARD` (measured under `Sum` and `NumberOfFilledFields`), while the starred form of that same operand is admitted; a **non-repeatable** group operand is admitted unstarred, and a star written on one is rejected `MVK_INVALID_WILDCARD` (both measured under `NumberOfDifferentValues`, on conditions character-identical apart from the `*`). The same code is measured for a starred nonrepeatable **root** under `NumberOfFilledGroups` ([§1](02-logic-and-formal-errors.md)); one row is a root and the other is not, so this star refusal is not root-specific. A group operand mixes with ordinary field operands, and nested stars both survive: `Sum(/Invoice/Lines*/Fees*)` is admitted. The **kind gate reads the group's expansion, not the group**, and each carrier keeps its own class: an expansion containing a String field draws `MVK_NO_NUMBER` under `Sum` and `MVK_NOT_SORTABLE` under `MaxValue`. **The extrema's class is positional too, measured on explicit field lists:** the *first* operand selects the family and every later operand must join it, so a temporal leader with a non-temporal member after it draws `MVK_DATE_AND_NONDATE` while a non-temporal leader draws `MVK_NOT_SORTABLE` for any member that is not a Number. The same two operands in the other order therefore draw different codes with the verdict unchanged — `MaxValue(Amount, DueOn)` against `MaxValue(DueOn, Amount)` — and every temporal kind counts as a date for the leading test. **All four extrema follow it**, the field-list `MinValue`/`MaxValue` and the value-expression `Min`/`Max` alike, each with a family-homogeneous control admitted in both forms so the refusal attaches to the mix rather than to operand count; the value-expression pair is a different operator from the field-list pair, so that is measured coverage rather than a generalization ([inbound](../docs/SOURCES.md#inbound-2026-09-05b)). A leading String is classified by that same rule rather than by being unsortable. **The sortable leader set is `{NUMBER}` together with every temporal kind — DATE, TIME, DATE_TIME and DATE_FRAGMENT all lead successfully.** ENUM, BOOLEAN, CONFIRM, DATE_RANGE, CUSTOM and STRING each draw `MVK_NOT_SORTABLE` leading the list, so none of them leads an overload of its own, and each draws that same code after a Number leader. **A later position admits the leader's own class**, so DATE follows DATE and TIME follows TIME; only after a *Number* leader is NUMBER the sole survivor. An earlier version of this clause gave the leader set as `{NUMBER, DATE}` and generalized the Number row's later-position rule to every list; both were wrong, and a `MaxValue(Frag, FragB)` admitted control already sitting in this project's own evidence refuted the first ([provenance](../docs/SOURCES.md#reviewed-2026-09-07-handback--the-extremum-leader-set-and-the-powers-derived-scale)). A **typedef** field resolves to its base kind here, so a NUMBER-based typedef leads and follows exactly as a NUMBER does while a STRING-based one draws `MVK_NOT_SORTABLE`. A starred single-field operand takes the same verdict and the same code as the plain field of that kind in both positions, so this gate reads the declaration rather than the operand form — a starred *group* slot and a filtered star are still untested. **The extrema's kind domain is strictly narrower than the distinct count's, and CUSTOM is the witness:** it is refused at the extrema yet admitted by both `NumberOfDifferentValues` and `FieldValuesNotUnique`, where DATE_RANGE is refused by all four — so neither gate's domain may be read off the other. DATE_RANGE is refused as an operand of both distinct-count members too, and their codes differ: `NumberOfDifferentValues` reports `MVK_ONLY_STRING_ENUM_NUMBER_CMP_DATE_ALLOWED` where `FieldValuesNotUnique` reports the `CMP_`-less `MVK_ONLY_STRING_ENUM_NUMBER_DATE_ALLOWED`, each against an admitted DATE control ([checkpoint](../docs/SOURCES.md#src-extrema-operand-family-is-positional)). Only after the family gate passes does the component-set gate below run, so a temporal-led list has two refusals under it. **A group operand's expansion supplies that leading kind at the extrema too**, on the same reorder discriminator the distinct count uses: an expansion declaring ENUM then NUMBER then DATE draws `MVK_NOT_SORTABLE`, one declaring DATE then NUMBER draws `MVK_DATE_AND_NONDATE`, and an all-NUMBER expansion is admitted as the liveness control — a reading under which a group expansion is simply not a sortable list predicts one constant class per family and cannot produce that spread. Under `NumberOfDifferentValues` the class is **positional** in the same way, and there the group form is what exposes it: the code names the class of the *first* expanded field, so a group declaring a NUMBER then a STRING draws `MVK_NUMBER_AND_NON_NUMBER` while one declaring a STRING then a NUMBER draws `MVK_STRING_ENUM_AND_NON_STRING_ENUM` — two models differing in nothing but declaration order. The expansion therefore has an order as well as an extent. A group declares no kind of its own, so this gate cannot be decided from the operand's own declaration: a checker must own the expansion's extent, including its recursion into nested subgroups. **The two halves generalize differently, and the asymmetry is structural rather than incidental.** The star, arity, and both duplicate gates are the shared entity-list checker's, which every carrier in this family routes through, so they do not vary by carrier even where a row measured only one; the kind gate is each operator's own question about the expansion's values, which is exactly why one carrier's class never transfers to a sibling. `FirstFilledValue` routes through that same shared checker, admits a group operand in both repetition shapes, and reads its expansion at the kind gate like the other carriers: a heterogeneous expansion draws `MVK_VARYING_TYPES_NOT_ALLOWED`, and the written-out expansion draws the same code, so the group form and its explicit form agree *here* even though the wildcard gate separates them. Its compatible families are `{String, Enumeration, Custom}` pairwise; `STRING` beside `NUMBER` and `DATE` beside `STRING` are refused `MVK_VARYING_TYPES_NOT_ALLOWED`, and `CONFIRM` beside String is `MVK_NO_BOOLY_ALLOWED`. Among **temporal** operands this gate reads the format's **component set** and not the kind: a DATE declared `yyyy` beside a DATE_FRAGMENT declared `yyyy` is admitted across two kinds. **It is not a format-spelling rule, and the distinction is measured on the pair where the two readings disagree:** two DATE fields declared `yyyy-MM-dd` and `dd.MM.yyyy` carry identical component sets under different spellings, and `MaxValue`, `MinValue`, and `NumberOfDifferentValues` all **admit** them — at an explicit field list, at explicit starred fields, and at a group operand's expansion alike, each against a same-format control. So does `yyyy-MM` beside `yyyyMM`. Component sets that genuinely differ are refused `MVK_DATEFORMATS_NOT_COMPATIBLE`, which names both formats, and a declared **Base Year** lifts that refusal for a yearless operand exactly when the remaining components already agree: a yearless `MM` aggregates with `yyyy-MM` and `MM-dd` with a complete date, while both stay refused against a year-only operand. `FieldValuesNotUnique` is the carrier whose gate really is the declared **format string** — it refuses both equal-set pairs above against its own same-format control, with its own code `MVK_ONLY_STRING_ENUM_NUMBER_DATE_ALLOWED` whose text names "the same dateformat". Reading that rule onto the extrema, as an earlier version of this paragraph did, rejects legal models. The two carriers are measured to agree here, which is agreement between two measurements rather than a shared mechanism, so neither clause rests on the other's rows. **The format rule holds across all five temporal kinds, on witnesses that do not depend on the closest pair.** `DATE` beside `DATE_FRAGMENT` invites the objection that a fragment simply *is* a partial date; `TIME` beside `DATE_TIME` does not, and the two can share a declared format exactly, because a DateTime may be declared with the degenerate time-only `HH:mm:ss`. That pair is admitted at one shared format, while two `DATE_TIME` fields at differing formats are refused, each against its own same-kind control. `DATE_RANGE` behaves identically once its allowlisted **(format, separator)** pair is treated as the format: one shared pair admitted, two legal pairs refused. `BOOLEAN` remains unmeasured against this gate.

**Whether a group-scope operand is admitted at all is a property of the individual operator rather than of its family, so no verdict here transfers by analogy.** One sweep across every carrier admits it under the seven field-fill quantifiers, the three plural value-list quantifiers in both their literal and entity value forms and in either slot, `FirstFilledValue`, `NumberOfFilledFields`, and the `MinValue`/`MaxValue` extrema over a date group, in both repetition shapes wherever both are legal. It is rejected `MVK_NO_GROUPS_ALLOWED` by the operand-list `Min` and `Max` in either shape, by `DateRangesOverlap`, by the custom-type `Valid`/`Invalid` overload, and by `FieldValueAsString`, `ValueAsDate`, and `RangeAsString`; `ValueAsDate` also refuses a **starred field** operand, `MVK_NO_WILDCARDS_ALLOWED` reported at the operator itself, so its two refusals are separable exactly as `Min`'s are, while an operand inside a repeatable group is admitted when the reading rule's iteration scope binds that group (see [§5](05-dates-and-time.md)); the plural `AtLeastOneDateRangeOverlaps` nevertheless admits one in its `In` slot. **Two of those pairs disagree inside one family**, which is why the list is enumerated rather than summarized: `Min`/`Max` refuse where their `MinValue`/`MaxValue` siblings accept, and the singular overlap predicate refuses where its plural sibling accepts, so neither the operator's name nor its family predicts the gate. `Min`'s two refusals are separable, and only a starred *field* operand shows it: that draws `MVK_NO_WILDCARDS_ALLOWED` while a group draws the group code, so the group refusal is its own gate rather than a wildcard refusal in disguise. The `Min`/`Max` refusal also holds on the **computation** carrier, in both the common-precondition and alternative-operation positions and in both repetition shapes, with the same starred-field separator; that was measured rather than carried over, because this paragraph's own finding is what forbids transferring a verdict between carriers.

**An admitted group operand is expanded and the result type-checked, not waved past the kind gates.** A homogeneous group cannot separate those two readings; a heterogeneous one does, and a DATE group against a String value list is rejected `MVK_ONLY_STRING_ENUM_NUMBER_ALLOWED` where the same carrier over a String group is admitted. An evaluator may therefore rely on the expansion having been checked. A group uniformly of one unsortable kind is a separate question from a mixed one and is also refused: `MVK_NOT_SORTABLE` under the extrema in both repetition shapes, with the equivalent explicit field list drawing the same code, which places that gate on the operand's kind rather than on its groupness.

**Semantic-index admission is carrier-specific even within these group and entity-list operators.** An indexed field is one operand and is admitted by `NumberOfFilledFields`; an indexed group is admitted by `AllFieldsFilled` and `NoFieldFilled`, while the otherwise identical unindexed repeatable group reports `MVK_NO_WILDCARD`. `NumberOfFilledGroups` refuses an indexed group with `MVK_SEMANTIC_INDEX_NOT_ALLOWED`, `RepetitionNotUnique` refuses an indexed operand with the same code, and a semantic index written below `*` reports `MVK_SEMANTIC_INDEX_AND_WILDCARD`. These measured cells do not establish admission for any unlisted operator; [§10](08-paths-and-references.md#4-rows-are-addressed-by-semantic-key-never-by-position-) owns the selection form and its other restrictions.

**The three gates read three different things, and the wildcard gate reads the authored path**, which is what makes a group operand and its own written-out expansion two different models rather than two spellings of one. Arity reads the authored slots, so a group slot is already-many, measured under `FieldValuesNotUnique` and again under `MoreThanOneFieldFilled`, where a single-field group is admitted while that same field authored alone is rejected `MVK_PARAMSIZE_INVALIDN`. The kind and category gates read the expansion. The wildcard gate reads the **authored path** and checks the operand at its own level only: `FieldsNotCollectivelyFilled(Sections*, Note)` is admitted, while `FieldsNotCollectivelyFilled(Sections*/Title, Sections*/Answers/Text, Note)` — that same expansion written out — is rejected `MVK_NO_WILDCARD` for the nested repeatable level's missing star, and starring that level admits it again. Neither neighbouring gate predicts this: reasoning from the category gate would expect the group form to be refused, and reasoning from arity gives no view of the explicit form at all. **So a consumer that normalizes a group operand into its expansion can emit a model the kernel rejects**, and its own fixtures will not reveal that while every group in them is flat.


**A `Having` filter site refuses a group path outright, and no spelling attaches a filter to a group operand.** `NumberOfFilledGroups(G/Sub* Having (…), G2)` is rejected `MVK_NO_GROUPS_ALLOWED` naming the filter as the site, in either operand position and on both the validation and the computation arm, while the same filter over a field list and the same group operand unfiltered are both admitted. The refusal is reached at **static arbitration**, not only at code generation, so a consumer authoring against the static checker sees it. Six carriers are measured, each against its own unfiltered control: the four field-fill quantifiers, `FieldValuesNotUnique`, `FirstFilledValue`, the value aggregates, `NumberOfFilledGroups`, and `NumberOfFilledFields`. The operator-level fallback an author would reach for next — a `Having` written after the operand list — is a **parse error**, not a second refused site, which is what closes the question rather than merely widening it. Each measured filter reads its own group's field. **The different-group case is one gate rather than a refusal of its own, and it is about scope rather than about groups:** a filter whose condition carries no reference into the filtered list's own iterated level draws `MVK_NO_ITERATION_FOR_WILDCARD`, whether the out-of-scope reference is a plain field predicate on a **nonrepeatable** other group's field, a group-presence leaf, or two such conjuncts together. Supply one in-scope reference and the same condition is admitted, in either conjunct order. **That satisfiability is what distinguishes this gate from the one below, and it is why the two must not be read as one refusal with two spellings.** **A group-presence leaf is therefore admitted inside a field-list filter** — as one conjunct beside an in-scope reference, and as the *sole* condition when the group it names is the filtered list's own, which also shows a group reference binds the iteration exactly as a field reference does. Measured on both the validation and the computation arm ([checkpoint](../docs/SOURCES.md#src-having-filter-condition-scope)). Keep this apart from the operand-site rule above: `MVK_NO_GROUPS_ALLOWED` refuses attaching a filter **to a group operand**, and says nothing about what a legally sited filter's condition may name. **A `$`-marked reference does not satisfy that requirement.** A filter whose only reference is `$`-marked draws the same `MVK_NO_ITERATION_FOR_WILDCARD`, measured on a field-presence leaf and on a String equality against a literal; one in-scope conjunct beside the identical `$`-marked leaf admits the whole condition, which isolates the missing in-scope reference as the cause rather than the marked leaf. So `$` pins a reference to the captured outer repetition and thereby moves it *out* of the filtered level — it cannot be the reference that binds it. **The requirement is a syntactic occurrence check, and it accepts any reopened level.** One ordinary reference at *any* level the operand reopens satisfies it — a two-star operand whose filter references only the outer starred level is admitted even though the inner one is also starred, so the lowest reopened level is not privileged. Connective position is irrelevant: an in-scope reference under `Or`, where the filter can be satisfied without ever consulting it, is admitted, while a condition whose every reference is `$`-marked is refused whatever the connective. **The check counts unmarked *references*, not field pointers, so a `CurrentRepetition` operand satisfies it alone** — `CurrentRepetition(Rows) != CurrentRepetition($Rows)` is admitted as a filter's whole condition, and the same comparison with both sides marked is refused. **What such a reference contributes to the gate is the repeatable scope of its path, exactly as a field reference declared in that group would contribute:** a **nonrepeatable** group whose path carries no repeatable level is refused `MVK_NO_ITERATION_FOR_WILDCARD` as the sole condition and admitted beside one in-scope conjunct, while a **nonrepeatable** group nested under the starred level is admitted **as the sole condition** — the two differing only in whether a reopened level lies on the path. So the same path account governs this gate and the binding one above, and neither reads the named group's own repeatability ([checkpoint](../docs/SOURCES.md#src-filter-repetition-reference-reads-its-path)). That admission carries the self-exclusion **topology** as a precondition and is not general: the level `Rows` names must be at once reopened by the operand's star *and* bound by the enclosing iteration. **"Enclosing iteration" is the right word here rather than "rule", for `CurrentRepetition` exactly as for `$`:** a computation whose computed target is repeatable binds it, and the identical calculation with the target moved to the root is refused `MVK_NO_WILDCARD` — the two spellings differ only in where the target sits ([reconciliation](../docs/SOURCES.md#src-2026-09-04-reconciliation)). **The rule host obeys the same law, and the gate is the binding rather than repeatability:** `CurrentRepetition(G)` is admitted exactly when the host's iteration binds `G`, so it is admitted in a rule whose error field lies inside `G` and refused `MVK_NO_WILDCARD` from a rule placed above `G`, each placement's plain-condition control being admitted. A **nonrepeatable** group is admitted at its own locus with a constant index, which is what shows the requirement is binding and not repeatability. **The requirement runs over the named group's whole path rather than over the group itself: every repeatable level on that path must be bound, and the refusal names the unbound *ancestor*.** A **nonrepeatable** group nested under a repeatable one is admitted from a host that binds the ancestor and refused `MVK_NO_WILDCARD` from a host above it — *"Missing specification of an asterisk for 'Rows' in '/Rep/Rows/Fixed'"*, pointing at `Rows` and not at the group named. The separating control is a nonrepeatable group with **no** repeatable ancestor, admitted from that same non-binding host: the two differ only in whether an unbound repeatable level lies on the path. So a nonrepeatable group is not bound everywhere; it inherits its ancestors' requirement, and it is only a group whose path is repeatable-free that needs no iteration at all. Naming a **repeatable** sibling from a host that does not bind it is the same refusal for the same reason, with the named group supplying the unbound level itself. **Within a condition or a computation operation the operand is then an ordinary Number expression, and the binding law is the only gate it answers to:** it is admitted bare, inside arithmetic, on either side of a comparison, against a field operand, and as a comparison operand inside a `Having` filter, on the validation arm and as a computation's whole operation alike, each against its own plain control. The one position that refuses it is an **aggregate's operand list** — `Sum(CurrentRepetition(G))` is a parse refusal, `MVK_UNEXPECTED_TOKEN` naming the operator. That is not a fact about this operand: the same position refuses an arithmetic wrapper identically, so it takes field paths and no expression of any kind ([§4](04-numbers-and-decimals.md)) ([checkpoint](../docs/SOURCES.md#src-currentrepetition-operand-carriers)). **The two spellings then draw on different binding sources, and this is what the marker selects:** an *unmarked* `CurrentRepetition(G)` is satisfied by the enclosing iteration **or** by an operand's own star that reopens `G`, so inside a filter it is admitted even from a non-iterating host, while a *marked* `CurrentRepetition($G)` reads the captured environment and is satisfied only by the enclosing iteration — refused `MVK_NO_WILDCARD` in that same shape. **That contrast governs only what is legal inside a filter, because `$` is filter-only by site.** Outside a filter the marker is refused `MVK_INVALID_OUTER_ITERATION` — a code of its own, whose text states the rule outright — **even where the enclosing iteration does bind the level named**, so the site is checked before any binding question and the marked spelling is not a generally available variant of the unmarked one. Measured on both arms: a validation condition at a host that binds `G`, and a computation operation whose target is repeatable, each refused while the identical marker inside a `Having` filter in the same model is admitted and the unmarked spelling at the same host is admitted. A marked **nonrepeatable** group draws the same refusal, which shows the check is indifferent to what the marker names. [§5](05-dates-and-time.md) carries the same rule from the `DateRange` endpoint carrier ([checkpoint](../docs/SOURCES.md#src-currentrepetition-operand-carriers)). So the self-exclusion pair's requirement that its level be both star-reopened and host-bound is a consequence of these two rules rather than a third rule: the comparison carries one reference of each kind ([checkpoint](../docs/SOURCES.md#src-currentrepetition-host-iteration)). Hold everything fixed but the level and the verdict flips — a rule iterating `Lines` whose operand stars only `Items` draws `MVK_NO_WILDCARD` for `CurrentRepetition(Items) != CurrentRepetition($Items)`, which is the marker rule below governing a pointer-free operand exactly as it governs a field one. This is the one place the distinction is observable, because [§1](01-data-model.md)'s reference expansion gives a `CurrentRepetition` operand no field pointer at all, so a gate implemented over that expansion refuses both spellings. The reflexive unmarked `CurrentRepetition(Rows) == CurrentRepetition(Rows)` is admitted too, so the gate turns on the marker rather than on the comparison being non-trivial. **And `$` may only name a level the enclosing rule iteration actually binds:** a marked reference to a level the operand's own star reopens is refused `MVK_NO_WILDCARD`, because the captured environment has no coordinate there, while the same marker on a level the rule does bind is admitted. The **group** carrier is measured and behaves exactly like the field one, including the split between the two gates: a **nonrepeatable** out-of-scope group leaf as the filter's sole condition is refused `MVK_NO_ITERATION_FOR_WILDCARD` whether or not it carries the marker, and one in-scope conjunct admits either spelling, while `GroupFilled` naming a repeatable **sibling** is refused `MVK_INVALID_ITERATION_IN_FILTER_CONDITION` as the sole condition and beside an in-scope conjunct alike. So `GroupFilled` reads the captured environment as a field reference does and obeys **both** gates rather than one out-of-scope rule, and the marker is redundant only where a field reference's is ([reconciliation](../docs/SOURCES.md#src-2026-09-05-second-reconciliation)). So a consumer that pushes a row filter down onto a group operand emits a model the kernel rejects even though both halves are separately legal.
**A filter condition may not reference a level that would need its own iteration, and no conjunct rescues it.** A reference to a field inside a **repeatable group the filtered operand's path does not contain** is refused `MVK_INVALID_ITERATION_IN_FILTER_CONDITION`, and — unlike the scope gate above — adding an in-scope reference beside it changes nothing: the identical conjunct that admits a nonrepeatable out-of-scope leaf leaves this one refused. So these are two gates, not two spellings of one, and the satisfiability column is what separates them. **Path membership is the whole predicate, and the direction along the path is irrelevant:** a level *above* the star that still lies on the operand's path — bound by the host, not reopened — draws the **satisfiable** scope-gate code and is admitted beside one in-scope conjunct, in both the plain and the marked spelling, rather than the prohibition a level off the path draws ([checkpoint](../docs/SOURCES.md#src-filter-reference-above-the-star)). Three further rows fix the account. The same reference **outside** any filter draws the ordinary `MVK_NO_WILDCARD` instead, so the code is filter-specific rather than a general unbound-reference code. The filtered operand's **own** starred group may be referenced in its own filter, so the prohibition is about *another* level and not about the group. And the condition cannot supply the missing iteration itself: a star written inside a filter condition is refused `MVK_NO_WILDCARDS_ALLOWED`. **The predicate is path membership and not reopening, and the two come apart in both directions.** An unstarred repeatable *ancestor* on the operand's path is not reopened and is nonetheless on the satisfiable side, while a repeatable level nested **under** a level the operand's star does reopen — but off its path — is refused as the sole condition and beside an in-scope conjunct alike. So being reachable from a reopened level is not being in reach, and the reopened level's own field, admitted alone, is the contrast that shows the two gates read different things. **The remedy an author needs, once told that no conjunct clears the second gate, is the marker.** `$` moves the reference into the captured environment, which clears the iteration gate and leaves only the satisfiable scope gate: a `$`-marked reference to an off-path repeatable level the enclosing iteration binds is refused as the sole condition and **admitted** beside an in-scope conjunct. It is not a general escape — with no enclosing iteration to capture, the same marked reference draws `MVK_NO_WILDCARD` instead, so the marker needs an outer coordinate before it needs a conjunct. The gate also does not yield to the host: hosting the rule *inside* the off-path repeatable level leaves the unmarked reference refused exactly as from a non-iterating locus ([checkpoint](../docs/SOURCES.md#src-filter-scope-versus-iteration-gates), [reconciliation](../docs/SOURCES.md#src-2026-09-05-second-reconciliation)).

**Which of two coincident properties the second gate reads is not established, and no legal model separates them.** Every refused reference names a level that is at once off the operand's path *and* unbound by the operand's star; every admitted out-of-scope one names a level at once on that path *and* bound by an enclosing iteration. The discriminating model — an unstarred repeatable ancestor on the operand's path that nothing binds — is unauthorable, because that shape makes the **operand** illegal (`MVK_NO_WILDCARD`, with the unfiltered control confirming the refusal is the operand's rather than the filter's). So the two readings are extensionally equal over every legal model, and this clause deliberately states the gate by its observable rather than by a mechanism ([reconciliation](../docs/SOURCES.md#src-2026-09-05-second-reconciliation)).

**An operand's star binds its own filter and not its host rule, so the rule still reports once.** A rule at a non-iterating locus whose aggregate stars a repeatable level and filters on that level's coordinate fires **one** message, attached to its own error field, even when the filter admits several rows. The star's iteration is confined to the aggregate's candidate list, which is the runtime counterpart of the static rule that an aggregate over a star derives no iteration for placement. A message count alone cannot establish this — a rule that fires once and one that fires per surviving row and is then deduplicated give the same number — so the discriminating observation is the error pointer of each fired message ([reconciliation](../docs/SOURCES.md#src-2026-09-05-reconciliation)).

**The filter's scope gate reaches a multi-operand group quantifier exactly as it reaches a scalar leaf.** `AllGroupsFilled`, `NoGroupFilled`, `NumberOfFilledGroups` and `NumberOfFilledFields` inside a filter condition behave as the scalar group-presence leaf does: admitted beside an in-scope reference in either spelling, refused `MVK_NO_ITERATION_FOR_WILDCARD` as the sole condition in either spelling, so the marker moves no verdict there either ([reconciliation](../docs/SOURCES.md#src-2026-09-05-reconciliation)).

**At evaluation the expansion's extent belongs to the expansion rather than to any one operator**, and the account the `FieldValuesNotUnique` clause states below is measured on further carriers. The same recursive reach across a nested repeatable level holds for all seven field-fill quantifiers. A group-scope fill quantifier evaluated from a rule authored on a repeatable level strictly *below* the operand still answers from the operand's extent, so `AllFieldsFilled(<group>)` is false from every row whenever any cell below the operand is empty. A starred operand `G*` read from a rule authored on `G` iterates `G`'s own level, and a doubly-starred operand iterates both starred levels whatever the consuming computation's own row is. `FirstFilledValue` adds the one clause here that is not that contract restated: it selects the operand's first filled cell in the expansion's stable model declaration order. Among two direct fields and among two fixed nested subgroups, the earlier declaration wins even when the later path sorts first; a filled direct field precedes the nested rows. For a terminal single-level starred group, traversal is declaration-major: every instantiated row of the earlier declaration precedes every row of the later declaration, so row 2 of `First` wins over row 1 of `Second`.

**A group operand follows [the consuming operator's directional-fill rule](10-validation-and-polarity.md#4-the-directional-fill-machinery-behind-the-typing), not one complete-versus-incomplete flag for its whole expansion.** The fixed-group `FirstFilledValue` matrix makes that local consequence observable: direct-both is VALUE despite later empty nested declarations, while selecting the second direct field or either nested field after an empty direct prefix is OMISSION. The starred-group matrix agrees: an immediate first-row value is VALUE, the declaration-major cross-row selection is OMISSION after an empty earlier cell, and a no-row group star before a direct fallback makes that fallback OMISSION. The declaration-ordered expansion must therefore enter the prefix scan without first collapsing whole-group missingness. ⚠ This is a **different mechanism** from the filter-reached escalation the `FieldValuesNotUnique` clause states below, which keys on a reached `Having` and not on fill state. Neither account measures the other's axis, and merging them would assert an equivalence nothing here establishes.

`NumberOfDifferentValues` accepts one homogeneous value-comparable family: Number; String together with ordinary stored Enumeration and Custom; or mutually comparable date-like declarations. Date, DateFragment, Time, and DateTime are each legal operand kinds, but **sharing a kind is not sufficient** — two date-like operands whose declared component sets differ are rejected with `MVK_DATEFORMATS_NOT_COMPATIBLE`. **The count then compares the decoded value at the list's shared component set after Base Year supplementation, not at full calendar precision.** Two `yyyy-MM`-declared operands holding `2024-03` count as one value and `2024-03` beside `2024-04` as two, on a `DateType` whose declared format omits the day and on a `DateFragmentType` alike, both codegen strategies agreeing. A component-omitting *format* is a different declaration from a **partially known** date, which carries a `datePrecision` and is refused as an operand of this operator outright ([§5](05-dates-and-time.md)); the refusal of the second must not be read as a restriction on the first. Every omitting format reaches the count, **yearless ones included** — `MM` beside `MM` and `MM-dd` beside `MM-dd` are admitted and compared as yearless calendar positions — and under a declared Base Year a supplemented yearless operand compares at the supplemented precision: `MM` holding `03` and `yyyy-MM` holding `2024-03` are **one** value at Base Year 2024, and `03` beside `2024-04` are two. So the compared identity is keyed to the supplemented set, and a consumer requiring a complete calendar date before counting refuses legal models. **A time-bearing operand folds on the same rule**: two TIME fields at `HH:mm:ss` separate on the clock, two DATETIME fields at the instant format separate on the instant, and a TIME beside a **DATETIME declared the degenerate `HH:mm:ss`** counts one value for one clock reading — so the identity follows the declared component set across the kind boundary exactly as the admission gate does, and must not be keyed on the declared kind. Whether a DATETIME's identity is the exact instant or the decoded local label is not separable by stored text within one model zone, since a wall label resolves to a single instant there. **A group operand's count uses that same expansion extent at runtime, not only at the kind gate**: a nonrepeatable group declaring two equal dates plus a nested subgroup holding a differing one counts two, and three when all three differ, so the nested subgroup's field contributes. A declared-but-uninstantiated repeatable row contributes no value of its own. **The extrema fold a component-omitting operand too, and order it at the shared set's own precision**: a `yyyy-MM` pair and a yearless `MM` pair are each admitted and ordered by `MinValue`/`MaxValue`, the yearless one even with no Base Year declared, so no interval domain is involved. A **partially known** declaration is the separate case those operators refuse outright, and that refusal must not be read as reaching a component-omitting format.

  **This operator's admission is decided by its FIRST operand, which is what distinguishes it from every sibling gate in the family.** The first operand fixes the required family and each later one must join it, so the refusal code names the *first* operand's class rather than the offending one: Number-first draws `MVK_NUMBER_AND_NON_NUMBER`, String-, Enumeration-, or Custom-first `MVK_STRING_ENUM_AND_NON_STRING_ENUM`, and date-like-first `MVK_DATE_AND_NONDATE`. Both orders of each pair are measured and each flips the code, `(Number, Number, String)` and `(String, String, Number)` report their leading class rather than the offender's, and `(Number, Date, String)` — two different offenders behind an admissible lead — still reports the Number class. A first operand outside all three families is refused earlier, by a class-admission gate naming the admitted set: a BOOLEAN first draws `MVK_ONLY_STRING_ENUM_NUMBER_CMP_DATE_ALLOWED` whatever follows it, while the same BOOLEAN behind an **admitted lead** is merely a homogeneity violation and draws that lead's class code — the Number code behind a Number, the String/Enumeration/Custom code behind a String. **So the class-admission code is reachable only from the leading slot**, and reading it as "a Boolean operand is present" is wrong in both directions. The Kernel states the rule in the message text itself and **names the offender there while the code names the class the list was judged against** (*"If the first parameter is a string or enumeration then all parameters have to be of type string or enumeration. Corrupt: 'Discontinued'."*), so a consumer locating the bad operand reads the text and never switches on the code. Contrast `FieldValuesNotUnique`, whose gate is order-independent over the whole list and whose class-admission code is `MVK_ONLY_STRING_ENUM_NUMBER_DATE_ALLOWED` — the same name **without** the `CMP` token, so the two are separate mechanisms rather than one shared check ([checkpoint](../docs/SOURCES.md#src-distinct-count-first-operand-class)). An implementation that reports the offending operand's class, or that shares one homogeneity check across the two operators, is wrong on the orders that separate them. The Number overload identifies filled values by the same scale-19 equality as ordinary Number comparison and uniqueness. The String/Enumeration overload compares the evaluated String value or ordinary stored Enumeration token exactly after declaration-owned checking; String and stored-Enumeration fields may mix, the same token from either kind counts once, and category projection is not admitted. Custom's membership in this family is locked only at static admission here; its runtime identity remains unmeasured. Every overload has integral result scale 0. Empty cells and declared-but-uninstantiated rows do not enter the set but leave its size growable; a reached filter makes the available count both-directionally fillable because later filling can alter membership; the first reached formally unavailable or non-relevant selected cell makes the aggregate unavailable. Repeating a wildcard slot still consumes its stream again, but equal repeated values do not increase the distinct count.

`SumOfProducts(A*, B*)` is a specialized pair aggregate rather than an ordinary flattened entity list. It accepts exactly two Number fields whose immediate **owning group is the same**; that group need not itself be repeatable, but each operand path must cross a repeatable level at one model-instance/root-sequence coordinate. Only the path's lowest repeatable level may carry an unrestricted `*`, and `Having` is rejected. The refusal class is pair-dependent: different owning groups report `MVK_DIFFERENT_GROUPS`, including two operands that share one starred ancestor but whose fields sit at different depths; an operand below a repeatable level it leaves unstarred reports `MVK_NO_WILDCARD`, including a plain descendant of the other's starred group and a star above the lowest repeatable level; a multi-star operand reports `MVK_WILDCARD_ONLY_AT_LOWEST_LEVEL_ALLOWED`; a filtered operand reports `MVK_WILDCARD_AT_LOWEST_LEVEL_REQUIRED`; and only a pair with no repeatable level reports `MVK_REPEATABLE_LEVEL_REQUIRED`.

The result scale is the sum of the two field scales. Evaluation constructs one common row environment stream and, in canonical row order, multiplies the two values from each environment and adds that product to the running total; every multiplication and addition uses the precision-50 boundary. An empty cell supplies numeric zero with its own declaration's directional missingness. A formal failure in **either** zipped list makes validation unavailable and computation poison; the offending cell's position does not change that verdict, and the formal pass emits every invalid cell regardless of the rule, so validation output carries no witness for an ordering here. An omitted row at either path makes a successful validation result both-directionally fillable.

Partial validation gates this operator by **complete extent, per iteration row**, rather than by the normalized wildcard-only gate: an iteration row whose starred extent is enumerated in full evaluates, but the enumeration must cover the complete cross-product of row coordinates rather than merely every coordinate at each level independently, and a partial enumeration leaves the row UNKNOWN. The cover is taken over the union of the relevant entities addressing that row, so coverage spread across entities of different wildcard shapes counts. The retained observations do not distinguish declared capacity from rows present in the document when deciding that extent. Covering only one of the two fields likewise remains insufficient.

**The filter condition may not contain**: `CustomCondition`, `RepetitionNotUnique`, a semantic index, a parallel iteration, or a nested filter — refused as `MVK_DISALLOWED_CONSTRUCT_IN_FILTER_CONDITION`, whose message names the offending language feature. Two further constraints bound the filter's operands rather than its constructs. It **must reference the iterated level**, or the wildcard has nothing to iterate and the model is rejected with `MVK_NO_ITERATION_FOR_WILDCARD`; and its operands must be **unstarred**, so a filter referencing `Items*/Sku` is rejected with `MVK_NO_WILDCARDS_ALLOWED` while the unstarred `Items/Sku` inside the same filter is admitted. The filter therefore names the candidate row it tests, never a second flattened stream. A filter can offend the construct rule and the iterated-level rule at once, and then the **iterated-level class is the one reported**: a filter consisting *only* of a `CustomCondition` leaf draws `MVK_NO_ITERATION_FOR_WILDCARD`, not the disallowed-construct class, which surfaces once the filter also carries a term that does reference the iterated level.

> **Non-normative implementation note.** A filtered star is `filter (fun candidateEnv => evalFilter cond candidateEnv outerEnv doc) candidates` — where `evalFilter` resolves a `$`-marked reference against the complete captured `outerEnv` and an unmarked reference against `candidateEnv`. Each resolved reference still names the repeatable level whose coordinate it reads. That two-environment split *is* correlation; collapsing `outerEnv` to one scalar “outer row” is incorrect. The filter-content restrictions are a well-formedness check on the AST.

## 4. Where a star binds — the anchor rules ⚠

This is the subtlest part. A `*` in an operand path controls which enclosing indices are *fixed* (inherited from the current row) versus *re-opened* (iterated over).

- A starred operand read from an iterating row binds the enclosing indices **only for the repeatable levels strictly above the (first) `*`** — the starred level itself **always iterates its full extent**. So a **same-group star spans *all* rows, not the current one** (only `$` correlates; a bare star never does). A multi-star operand `A*/B*/F` binds at the levels **above `A`**.
- Declared-tail completeness follows that same first-star boundary **hierarchically**. For `A*/B*/C*/F`, missing declared capacity at `A`, beneath any actual in-scope `A` row at `B`, or beneath any actual in-scope `A/B` row at `C` leaves an open tail; so does an instantiated selected leaf whose `F` cell is empty. The unfiltered star is structurally complete only when every reopened repeatable level is exhausted under every actual parent and no selected leaf is empty. A reopened level with no finite `repeatability` is always open. A repeatable level strictly above the first star remains bound, so unused capacity outside that bound row does not taint the operand. Comparing the flattened leaf-row count only with the deepest cap is invalid: a dense branch can numerically hide a missing outer or middle branch.
- An instantiated row beyond its level's declared `repeatability` remains in the physical topology and still supplies structural group content, but it is **outside the evaluation domain** of the operands that expand rows. Measured on starred `Sum`, starred-field `NumberOfFilledFields`, and starred-group `NumberOfFilledGroups` at one repetition level, and on a **group operand** for `NumberOfFilledFields`, `NoFieldFilled`, `AtLeastOneFieldFilled`, both `NumberOfValueInFields` overloads, `Sum`, `MinValue`, `MaxValue`, and `NumberOfDifferentValues`. A **starred field operand** carries the same four value consumers — `MinValue`, `MaxValue`, `NumberOfDifferentValues`, and `NumberOfValueInFields` — each against its own in-capacity control, and `MinValue` additionally against a reversed document in which the over-limit row holds the smaller value, since a document whose in-capacity rows already contain the minimum cannot discriminate ([checkpoint](../docs/SOURCES.md#src-starred-field-operand-extent)). The internally selected full-validation account applies that extent to a **filtered Number star** too, for `Sum`, both extrema, `NumberOfDifferentValues`, and `NumberOfValueInFields`; this branch has no retained Kernel observation and establishes no filter/capacity order. **The star makes no difference to a group operand**: the count and `Sum` answer identically over `G/Sub*` and over the unstarred `G`, each against its own control ([checkpoint](../docs/SOURCES.md#src-starred-group-operand-extent)). Its descendant cell contributes neither a value nor a formal poison, and the row does not increase a group count. This exclusion is separate from declared-tail completeness and does not erase the row from `GroupFilled`-style presence. **Nesting does not change it for a fixed group operand**: the excluded row may sit at an outer or an inner repetition level and the answer is the same either way ([checkpoint](../docs/SOURCES.md#src-group-operand-over-limit-extent)). Whether the same exclusion applies when an outer or inner axis of a nested *star* exceeds capacity remains externally unverified.
- **The row is removed from the domain rather than admitted and classified unavailable**, and that distinction is invisible on every document whose over-limit cell is well formed, because both accounts predict the same definite answer there. A **malformed** cell separates them: in capacity it makes `Sum` non-evaluable, while the identical cell one index above capacity leaves `Sum` answering its in-capacity total ([checkpoint](../docs/SOURCES.md#src-group-operand-capacity-consumer-sweep)). An implementation that filters over-limit cells *after* classifying them therefore agrees everywhere except on the documents that mix a bad cell with a good one, which is the shape a conformance suite built from clean fixtures never reaches. The split is measured on the unstarred group operand and on the starred one, and it holds identically, on `Sum` and on the count alike. **The exclusion never makes the aggregate non-evaluable**: over an in-capacity domain that the projection has emptied, every operator answers a definite `0` — `Sum`, both extrema, `NumberOfDifferentValues`, and `NumberOfValueInFields` alike — both where no repeatable row exists at all and where every present cell sits above capacity, so an emptied domain and an unavailable one stay distinct. The extrema remain free to move in either direction while empty in-capacity rows survive, which is what keeps their zero identity separate from the counts'.
- **The exclusion reaches every consumer of the operand stream, on every operand form it admits — with one place the two accounts are indistinguishable.** `FieldValuesNotUnique` on the Number and token carriers, `NumberOfDifferentValues`, and `FirstFilledValue` all answer from the declared-capacity extent, measured on a starred field, a starred group, and a fixed group alike: a duplicate pair spanning an in-capacity row and an over-limit one stays silent, `A, A, B` over a `max 2` group answers a distinct count of `1` rather than `2`, and a document whose only filled cell sits above capacity produces **no computed first-filled outcome at all** rather than that cell's value. The distinct count and `FirstFilledValue` are what the observation settles, because an admitted-and-unavailable row would make each of them unavailable where the Kernel answers definitely. **Uniqueness is not settled by it and cannot be**: that operator already skips a formally unavailable operand exactly as it skips an empty, so removing an over-limit cell from the extent and keeping it as an unavailable one produce the same verdict on every document. A reimplementation may take either route there, and neither is evidence about the other consumers ([checkpoint](../docs/SOURCES.md#src-capacity-consumer-sweep)).
- **The exclusion is a property of the operand, not of the validation arm.** An operand evaluated inside a *computation* answers from the same declared-capacity extent: over one starred field and one group carrier, `Sum`, `MinValue`, `MaxValue`, `NumberOfDifferentValues`, and `NumberOfValueInFields` produce the identical table under `compute` that they produce under full validation, on both codegen strategies. The mechanism is visible here in a way full validation cannot show it — the engine reports `zuGrosseKontextnummer` for the over-limit cell among the computation's operand errors and *still* yields an uncleared, definite computed value, so a formal error is present in the operand and does not reach the result. An implementation that shares one enumeration across the two arms is therefore right about this exclusion and must not special-case it per arm ([checkpoint](../docs/SOURCES.md#src-capacity-projection-computation-arm)). **An unavailable computation is absent rather than zero**: an in-capacity malformed operand yields no computed outcome at all, where the identical cell one index above capacity leaves every computed value intact — which is how the two exclusions are told apart on the compute path.
- **The same row produces no computed value, and its target is then cleared.** A repeatable target's computation runs once per **in-capacity** instantiated row: a group declared `max 3` carrying constant computations produces exactly three rows of computed values whether the document instantiates three, four, or five. The excess row is not simply skipped, though — a target cell holding a stored value in such a row is **cleared**, in the same run where its in-capacity siblings compute a value from a source present for both. So an over-limit row leaves the value-producing domain and stays in the clearing one, exactly as an in-capacity row whose computation yields no value does; an implementation that drops the row leaves a stale value the Kernel removes. They report `zuGrosseZeile` on the row and `zuGrosseKontextnummer` on each of the row's declared cells in the same run, so the row is demonstrably present and simply not computed into ([checkpoint](../docs/SOURCES.md#src-over-limit-computation-target)). Two **sibling** over-limit rows each draw their own `zuGrosseZeile`; absorption applies to nesting, not to disjoint rows. **The exclusion reaches through an ancestor**: a row beyond an *outer* level's capacity contributes no target either, although its own coordinate at the target level is in range, so the excluded set is decided by the whole environment rather than by the target level's coordinate. **Which level the excess row sits at does not matter**: over three repetition axes, documents differing only in whether the outer, middle, or inner level overflows produce identical computed results. Measured on three carriers and three topologies — a bare constant at one repetition level, a sibling-star `FirstFilledValue` under a repeatable ancestor, and a `DateFromDateTime` conversion across three axes. The physical row list and the target inventory therefore differ by exactly these rows, and an implementation sharing one enumeration between validation and computation will compute into rows the Kernel leaves untouched.

- A **cross-subtree** star binds only along the **shared named ancestry** — an enclosing row's index is never applied *positionally* to an unrelated chain, so a cross-subtree count or presence reads **identically from every iterating row**.
- A bare (unstarred) reference to a repeatable group in a group-scope quantifier is an **iteration anchor of its own** — ancestor-or-self, per row, judging the *current* row's cells. **Its admission is decided by the error field's locus, and index-keying is not a gate:** the bare form is admitted exactly when the error field sits inside the operand, and is otherwise rejected `MVK_NO_WILDCARD`. The starred form is admitted from any locus. Measured within one model built twice and differing in a single builder call, the whole matrix over four quantifiers, both spellings, and three error-field loci is identical with and without a declared `indexFieldName`, and identical whether or not the error field *is* that index field, so none of those three co-varying candidates beyond locus survives.
- **Where the operand names a chain of repeatable levels, the unstarred levels must form a prefix of that chain, and the error field must sit inside the innermost unstarred level.** A star does not cover the levels beneath it: an operand starring an outer level while leaving an inner repeatable level bare is rejected `MVK_NO_WILDCARD` at every polarity and every error-field placement. **This is the row that composing the two gates separately gets wrong**, because the wildcard gate on its own sees the outer level starred and the iteration gate on its own sees an error field that could make the inner level iterable. A fully starred chain has no unstarred level, hence no iteration, hence neither a locus requirement nor the polarity-adjacent refusal below. A **filter belongs to a field operand and is refused on a group operand** (`MVK_NO_GROUPS_ALLOWED`), measured on three unrelated carriers — the fill quantifiers, `FieldValuesNotUnique`, and `FirstFilledValue` — each against its own unfiltered control, and with the same filter admitted on the field form. So a filter cannot move either gate, and no filtered group-operand state exists to have a behaviour.

> **Non-normative implementation note.** Encode the rule literally: given the current `Env` and an operand path, keep the `Env` bindings for levels **strictly above the first starred segment**, and *re-open* (iterate all rows of) the starred level and everything below it. "Same-group star spans all rows" is then not a special case — it is what "re-open the starred level" *means* when the star is at the current level. The cross-subtree rule = only shared-ancestry prefixes carry a binding; unrelated chains start from a fresh iteration. Define tail completeness recursively over that reopened repetition tree: compare each actual parent's child coordinates with that level's finite cap, recurse through actual children, treat an absent cap as unbounded/open, and inspect selected leaf emptiness. Do not materialize the declared Cartesian product, and do not replace the recursive predicate with one flattened count. Property-test the environment and completeness functions against hand-computed small cases (1–2 rows, 1–2 levels).

## 5. `GroupFilled` and the other repetition rules

Validation presence for one concrete group instance is a product of three independent dimensions: `content` records formally admitted content, `erroneous` records whether a formally rejected descendant marked the group erroneous, and `relevance` is `NONE`, `PARTIAL`, or `FULL`. Do not collapse that state to one Boolean.

- Formally admitted content comes from a formally valid valued descendant, a duplicate index value admitted before uniqueness reports its error, or an instantiated repeatable descendant row. A created-but-empty repeat row is therefore content for itself and its ancestors. An over-limit row still supplies that structural content even though it receives `zuGrosseZeile` / `zuGrosseKontextnummer` and its ordinary row checks are suppressed.
- A malformed, custom-invalid, or constraint-invalid value rejected by formal conversion is not content. It independently marks every ancestor group erroneous.
- For a **repeatable** `G`, an instantiated row itself establishes content. For a **non-repeatable** `G`, the group's own structural node is not content; only the admitted descendant sources above count.
- When a non-repeatable group is the written terminal below one or more starred ancestors, the first star still reopens the canonical ancestor topology, but the terminal remains non-repeatable. Evaluate the same group product once in each selected complete environment; do not reinterpret an instantiated ancestor row as terminal content and do not replace the product with a topology-row count.

Under full relevance, the scalar predicates are exactly:

| admitted content | erroneous | `GroupFilled` | `GroupNotFilled` |
|---|---|---|---|
| no | no | false | true |
| no | yes | false | unknown/non-firing |
| yes | no | true | false |
| yes | yes | true | false |

Admitted content decides `GroupNotFilled` false before an independent error is considered; a content-free erroneous group remains unknown. This leaf distinction is the project's selected internally coherent account rather than a Kernel observation: within this theory, final condition evaluation collapses both unknown and false leaves to non-firing, so its rule/document message projection does not separate the two accounts. `GroupNotFilled` is therefore not Boolean negation of `GroupFilled`. Group-list tally and plain numeric group-count consumption are specified in [§1](02-logic-and-formal-errors.md#a4-fill-quantifiers-group-scopes-and-the-two-iteration-ranges).

Under partial validation, any relevant descendant gives each ancestor group at least `PARTIAL` relevance. Admitted content observed in that relevant slice is enough to establish `GroupFilled`; absence requires `FULL` relevance plus no content and no error. `FULL` relevance comes from an explicitly relevant group or ancestor, or complete relevant coverage of all declared descendant fields across deeper repeatable axes. One relevant empty descendant cannot prove absence.

- Some conditions are **refused inside a per-row iteration** (`MVK_NEG_CONDITION_IN_ITERATION`), and the refusal is lifted by a positive guard, e.g. `GroupFilled(K) And AtLeastOneFieldFilled(K/F)`. **The gate is syntactic and is not a predicate over the condition's meaning; specifying it semantically is measurably wrong in both directions.** `FieldsNotCollectivelyFilled` is grammatically negative and admitted, while `NumberOfFilledFields(G) < 1` carries no negation at all and is refused. And because that count cannot fall below zero, `< 1`, `<= 0`, and `== 0` denote one predicate, yet `< 1`, `< 2`, `<= 1`, and `!= 1` are refused where `<= 0`, `== 0`, `>= 0`, `> 0`, and `>= 1` are admitted; the tautologous `>= 0` passes. So the analysis does not normalize the comparison and does not decide the condition's truth set, whatever the diagnostic's own wording suggests. The refusal is **kernel-owned**: a consumer must ask rather than predict it, and the useful response to an author is to require the positive guard rather than to reason about which conditions qualify. It tracks the **iterated** level, not the operand, so one spelling at one polarity can be admitted or refused according to where the error field sits. **Value comparisons on a repeatable operand are outside the gate at every polarity.** A stored DateRange equality and an extracted-endpoint comparison are each admitted from inside the repeated group under `==`, `!=`, and an order operator, measured against a live control on the same model where `FieldNotFilled` on that same operand is refused and its `FieldFilled`-guarded form is admitted. So the gate's reach is presence-shaped rather than polarity-shaped, which is one more reason a consumer cannot derive it from a condition's truth set. It is also **read-shaped**: a negative presence operand read through a **semantic index** escapes the gate entirely. `FieldNotFilled(Rows/F For "k")` with the error field inside `Rows` and no positive guard is accepted, because a keyed lookup is not an iterated read. Such a clean no-match rule fires **once** with row coordinate `-5`, the Kernel's `IIdentifier.UNKNOWN` reanchoring sentinel. A consumer should preserve that message-pointer state as **no matching row**, not reject the rule or reinterpret it as wildcard coordinate `0`. Once a positive guard makes the rule iterate, the error field must be referenced through an iterating operand; the keyed lookup itself does not satisfy that requirement and draws `MVK_ERROR_FIELD_AND_ITERATION_INVALID`.
- **List predicates over a repeatable group with `*` consider all *possible* repetitions**, including unspecified ones, not only those holding data (the "declared range" of [§1](02-logic-and-formal-errors.md#a4-fill-quantifiers-group-scopes-and-the-two-iteration-ranges)).
- An instance **beyond the group's declared `repeatability`** draws the structural errors `zuGrosseZeile` / `zuGrosseKontextnummer` (**VALUE**) at the address-formal gate before scalar conversion, and the over-limit rows' ordinary checks are **suppressed** ([§3](02-logic-and-formal-errors.md)); creating that row still supplies structural content to its non-repeatable ancestors.
- **"At least N rows"** is expressible via the starred single-group count: `NumberOfFilledGroups(G*)` counts one repeatable group's in-capacity instantiated rows *including zero*, so `NumberOfFilledGroups(Items*) < N` fires at 0…N−1 rows (the aggregate-consumed star does **not** put the rule into per-row iteration). An over-limit physical row remains structural content but does not increase this numeric count. **"At most N"** stays structural (`repeatability`).
- **`FieldValuesNotUnique(f1, f2, …)`** — or the starred `FieldValuesNotUnique(G*/f)` over a repetition's rows — fires when two of the operands' **compared** values are equal, and it answers at the first duplicate it finds while scanning operands in authored order: empties are skipped (two empties are not a duplicate), equality is the **typed** comparison (a scale-0 `5` equals a scale-2 `5.00`), and a formally-invalid operand is **skipped exactly like an empty** — it does *not* suppress. So a duplicate on either side of an invalid cell still fires, while two *equal* invalid values are not a duplicate at all because neither enters the comparison. This is a deliberate exception to the general rule that a formal error suppresses a referencing rule ([§3](02-logic-and-formal-errors.md)), and it is the pair of observations that separates skipping from suppressing: both accounts predict silence for the equal-invalid case alone. It needs **more than one operand, unless the sole operand is a starred or a group slot** — a single direct operand is rejected `MVK_PARAMSIZE_INVALIDN`, while a single *starred* slot is admitted, and so is a single **group** slot even where its expansion is one cell (below), which refutes the row stream a starred slot expands to as the general rationale for admitting one slot — and every operand must share **one comparability category**, detailed below: mixing categories is rejected `MVK_VARYING_TYPES_NOT_ALLOWED`, and unlike `NumberOfDifferentValues` this is stricter than token comparability, so even String beside stored Enumeration is refused. Arity is the earlier gate: a single BOOLEAN or CONFIRM operand also reports `MVK_PARAMSIZE_INVALIDN`, not the kind code described below. It is *not* a declared-kind rule, however: Custom beside String is accepted. Differing Number *scales* remain admitted, which is what makes the typed cross-scale equality above reachable. The type name of a list is not otherwise constrained, and a mixed direct-plus-starred list of one category is admitted.

    Two independent gates decide admission, and **the kind gate runs first**: a Boolean or Confirm beside another category reports the kind code with the mixing code *absent*. Each gate applies to the **whole operand list**, so authored position does not select the class: an inadmissible operand authored last still reports the kind code, not the mixing code that an earlier operand would have produced. An implementation that refuses at the first offending operand it walks past gets this wrong whenever the inadmissible operand is not the first offender. Both separating operand orders have been measured. **BOOLEAN, CONFIRM, and DATE_RANGE** are refused outright, reported `MVK_ONLY_STRING_ENUM_NUMBER_DATE_ALLOWED`; DATE_RANGE is excluded by kind even though it carries a declared format. Every other category is admissible, CUSTOM included, and a Custom operand's registered type name is not part of the gate.

    Among **temporal** operands the same code additionally requires **one identical declared `format` string**, and that rule keys on the format rather than on the kind. The discriminator is decisive in both directions: a DATE declared `yyyy` beside a DATE_FRAGMENT declared `yyyy` is **accepted** across two kinds, while two DATE fields differing only in declared format are **refused**. A kind-equality reading gets both cases wrong. String, Enumeration, and Number operands carry no format constraint, which is what keeps this temporal-local rather than a general same-declaration rule — differing Number scales stay admitted.

    The separate mixing gate reads a comparability **category**, not a declared kind: the categories are `{String, Custom}`, `{Enumeration}`, `{Number}`, and `{Date, Time, DateTime, DateFragment}`. Custom beside String is therefore accepted, while Date beside String or Number is refused `MVK_VARYING_TYPES_NOT_ALLOWED`. A cross-temporal list such as Date beside Time is refused by the *format* rule and reports that code with the mixing code absent, which is what places Time and DateTime inside the temporal category rather than outside it. Every operand must additionally be a **value** validation, and an Enumeration **category** projection is refused for this operator as for every field-list predicate, so only stored values are compared.

    A **group-scope operand** is likewise admitted, and the two gates read it differently. Arity is satisfied by the group *slot*: a group whose expansion is a single field is admitted, while that same field authored directly is rejected `MVK_PARAMSIZE_INVALIDN`. The category gate instead reads the **expansion**, so a group expanding to a Number beside a String is rejected `MVK_VARYING_TYPES_NOT_ALLOWED` exactly as the equivalent explicit list is. Both non-repeatable and starred repeatable groups are admitted.

    At evaluation the group operand's expansion is compared as a **single value set** over every `(row × field)` cell reachable below it, descending through nested subgroups and iterating every row of any repeatable one. It is neither per-row nor per-field: a duplicate lying within one row across two fields, or between two rows of a nested subgroup, fires exactly as one across the operand's own rows does. The recursion needs no authored `*`, because the iteration comes from the *model's* repeatability rather than from the star; the same extent holds when the operand does carry one. Empty cells are skipped rather than counting as duplicates of each other, as in an explicit list. No depth limit is measured: with two stacked repeatable levels below the operand, a duplicate at neither level's first row still fires, while an all-distinct control over that fixture stays silent. **The compared set is bounded by the operand, not by the rule's own row**, and that cuts both ways from the operand's own depth. A rule authored on a repeatable group whose operand names an ancestor compares that ancestor's whole extent; conversely a repeatable level *above* the operand stays fixed at the rule's binding, so an operand starring an inner level under a bound outer one compares only the rows the star reopened. Reading the depth off the rule pins the first case wrongly, and reading no depth at all widens the second.

    ⚠ That scope rule is an observed contract rather than a derived one. An implementation that reuses its star machinery for the group expansion, and reads the compared extent off the rule's own iterating group or binding depth, gets it wrong; reading a binding implementation is exactly what produces that wrong derivation, so the extent is to be measured rather than inferred. The **same depth** governs the `referenced` set ([§3](01-data-model.md)), and the two channels disagreeing about one operand's own extent is the cheapest available signal that one of them is wrong.

    A firing over a group operand emits exactly **one** message, anchored at the error field's concrete **first row**, and neither the count nor the address depends on where the duplicate lies: a duplicate spanning two of the operand's rows and one lying wholly inside its second row report identically. That holds with the rule authored on the root and on the repeatable group itself, and with the error field resolving above the operand's level and per row inside it. The per-row error field is what separates one evaluation over the operand from a per-row evaluation whose two messages collapse onto a single shared address, because only the per-row locus gives the second account two distinct addresses to report at. Every measured firing is VALUE. Both operand forms are measured and they agree, the unstarred one including with the error field placed inside a nested repeatable subgroup and the duplicate lying wholly in that subgroup's later rows. The firing's `referenced` set carries the expansion at **wildcarded** coordinates for every repeatable level at or below the operand, while levels above it stay concrete. There is no reached-`Having` contrast to state for the group form, because a filter cannot attach to a group operand at all (below); that is not an open measurement but an absent question, and it holds at every fill state at once.

    Among admitted temporal operands the compared identity is the operand's **exact stored text**. That is what the *dynamic* runtime reads for this operator, and it is a different reading from the decoded date that `NumberOfDifferentValues` uses over the same entity lists, so the two neighbouring operators must not be assumed to share a value identity. The generated-Java strategy is unread for this operator's temporal comparison, so this is one runtime class's account rather than a cross-strategy observation; both strategies were measured to agree on the surrounding skip and polarity rules. Under the mandatory single declared format the stored-text and decoded-value accounts agree, **assuming one declared format admits one text per value**. That assumption is not measured: a pair such as a leniently parsed `1.2.2020` stored beside `01.02.2020` under `dd.MM.yyyy` would separate the two accounts, because stored text makes them distinct while the decoded date makes them a duplicate. No such storable pair is known as of kernel 30.8.1 probing at a12-dmkits `ddaf2e13`. Compare the stored text; if such a pair turns out to be storable, this sentence is the clause that changes and nothing above it does.

    ⚠ A source-level reading of the engine additionally suggests the comparison *domain* is selected by whether the **first** operand is a Number field. That selection is measured **absent**: cross-scale Number equality holds in both operand orders, so no order-dependent comparison mode surfaces. The stored-text reading above stands on its own as the temporal identity, not as a consequence of operand order.
  - **The starred form is aggregate-style: it evaluates once per surrounding bound prefix, not once per duplicate row.** For values `[7,5,5]` the kernel emits **one** message, at the error field's concrete *first-row* address, even though the duplicated values occur in rows 2 and 3. Moving the rule between the repeating group and its parent does not change that result. An unfiltered firing is **VALUE**; a **reached `Having` makes a firing OMISSION even when every retained value is filled** ([§12](10-validation-and-polarity.md)). The `referenced` set contains the starred value field with its reopened group coordinate **wildcarded** plus any field operands used by `Having`; `CurrentRepetition` contributes no field pointer. `RepetitionNotUnique` ([§6](#6-repetitionnotunique-precisely-)) is the per-row alternative and attributes each duplicate row instead.

## 6. `RepetitionNotUnique`, precisely ⚠

`RepetitionNotUnique(… @From Group)` checks uniqueness within a chosen reference group; the `@From` directive selects the scope (unique per order vs. unique across all orders). The verified mechanics:

**Key-admission diagnostics mostly reuse the group-list classes rather than adding their own.** A repeated key draws `MVK_DUPLICATE_PARAM1`; an unresolvable key path draws `MVK_INVALID_ENTITY`; a starred key path draws `MVK_NO_WILDCARDS_ALLOWED`, because the operator *forbids* a star rather than requiring one; and a non-repeatable error field draws `MVK_NO_WILDCARD`. One class is specific: `MVK_REPEATABLE_GROUP_MISSING`, and **three structurally different shapes collapse into it** — a second key in a non-repeatable group, a sole key whose group is not repeatable at all, and the rule authored at the repeated group instead of its parent. The last holds for both absolute and relative key spellings. A second key in a parallel repeatable group instead draws `MVK_NO_WILDCARD` on the measured index-free fixture and is not part of this collapse. A Number key is admitted, so the unsupported-kind refusal is not about Number.

- **Fires per row whose (composite) key duplicates another row's** within the scope — a composite key compares as the **tuple**. An **all-empty** key row is **skipped**, but among participants (≥ 1 key field filled) **empties match empties**. Polarity: all-filled duplicates are **VALUE**; a duplicate with an empty (fillable) key component is **OMISSION**.
- It is an ordinary per-row **3VL predicate leaf** in every model-legal `And`/`Or` tree. The duplicate relation is built over the full selected scope independently of every surrounding branch, then its per-row result composes through the ordinary verdict/polarity tables of [§12](10-validation-and-polarity.md#3-every-fired-message-is-typed--value-vs-omission-). A guard-false duplicate does not fire yet still makes its partner a duplicate; an RNU OMISSION under `Or` with a false sibling remains OMISSION, while an independently firing VALUE sibling wins. A negative-presence sibling that would let the iterating rule fire on a not-filled repetition is not model-legal (`MVK_NEG_CONDITION_IN_ITERATION`).
- A **formally-invalid key cell drops its row from the duplicate relation**, per key cell: malformed, duplicate-index, over-repetition, and **required-empty** cells all count as unknown — the distinguishing property is **requiredness, not emptiness** (an *optional*-empty cell is a valid null participant). A formal error on a **non-key** field of the same row does *not* drop it.
- Under **partial validation**, a row participates in duplicate construction only when every instance of every composite-key field in that row is relevant. If any key component is nonrelevant, that row is excluded; a duplicate cluster therefore exists only among rows whose complete keys are relevant. An independently decisive relevant branch in the surrounding Boolean tree may still fire.
- When RNU supplies the firing, `referenced` contains every key field in the current row and every duplicate peer row. A VALUE RNU firing has no `fillToFix` pointers; an OMISSION RNU firing projects that same complete duplicate-cluster key set into `fillToFix`. References owned by independent composed branches remain resolved at the current evaluated row rather than expanding over the duplicate peers. These are pointer sets, not ordered sequences.
- The **default reference group** (no `@From`) is the **first repeatable group below the rule group** on the key path, and uniqueness is checked per that group's **parent row** — a key two repeatable levels deep is checked across all inner rows of the whole outer scope, not per intermediate group. `@From` overrides.

The key list contains one or more direct plain field references. Groups, categories, wildcards, semantic-index accesses, and String fields configured without value validation are rejected, but there is no Number/String-only kind gate: every otherwise value-validating field kind is admitted. Runtime equality has exactly two branches. Number keys compare as the normalized numeric values of [§5](04-numbers-and-decimals.md); every non-Number key compares the exact internally stored text. A direct Enumeration key therefore uses its stored token—not display text or a category projection—and temporal keys do not acquire instant-based comparison merely because ordinary temporal comparisons do.

**Composite-key order does not select the repetition domain.** Key components may occur at different depths when their parent groups all lie on one hierarchy path. The deepest key parent supplies the row coordinates; shallower components resolve against that row's own ancestor coordinates. Reversing the authored key-component order therefore preserves the duplicate rows and VALUE/OMISSION polarity, including when an ancestor `@From` explicitly scopes the relation. Parallel branches are not one established class: the measured index-free fixture draws `MVK_NO_WILDCARD`, while the indexed fixture draws `MVK_NOT_IN_SAME_PATH`; what selects between them is unknown.

A model-legal condition contains at most one `RepetitionNotUnique` leaf. A second occurrence is rejected during consistency checking with `MVK_INVALID_COMBINATION_OF_REPETITON_NOT_UNIQUE`. This is an operator-specific model-legality constraint, not an evaluation rule and not an EBNF restriction.

> **Non-normative implementation note.** Two-phase, and the phases must be separate: **(1)** derive the duplicate multiset over the whole scope from eligible rows (under partial validation require every key component to be relevant; drop rows with any invalid/required-empty key cell; skip all-empty-key rows), computing which keys occur ≥ 2× and retaining their complete peer clusters; **(2)** expose the per-row RNU verdict as an ordinary leaf inside the complete Boolean tree, then project peer pointers only when that leaf contributes to the firing. The trap is folding a surrounding guard into phase (1) — the duplicate relation is branch-independent, so a guarded-away row still makes its partner a duplicate. Composite key = tuple with "empty matches empty" among participants; equality is the typed comparison of [§5](04-numbers-and-decimals.md)/[§8](06-strings-and-enumerations.md).
