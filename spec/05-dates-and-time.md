# 05 — Dates and time (§6)

Dates carry more surprises than any other scalar type. The recurring theme: a date is **not** a canonical instant — it is a value in a *declared format*, with a *precision*, sometimes deliberately imprecise (fragments), and its arithmetic is **asymmetric** (add ≠ inverse of difference) and **calendar-corrected**. And a string literal that *looks* like a date silently *is* one.

Empty-date behaviour (not-evaluated in comparisons; `0` in the extractors/differences; dropped/`no value` in aggregates) is in [§2](03-empty-and-required.md).

Stored Date, Time, DateTime, and DateRange text is converted non-leniently against the field's declared format. A noncanonical spelling such as `2024-3-5` or `20240305` for a `yyyy-MM-dd` declaration, `14:5:0` for `HH:mm:ss`, or `1.1.2024-31.12.2024` for a fixed-width range does not normalize to a temporal value: conversion fails, the physical placement and exact text remain, and formal checking makes the cell not-check-relevant. Conversely, text that converts already has the model format, so stored temporal input has no Number-like canonicalization stage.

The temporal field-format gate is kind-independent over the measured denominator. Across a derived universe of 135 candidate strings, the kernel admits `yyyy-MM-dd`, `dd.MM.yyyy`, `yyyyMMdd`, `yyyy`, `yyyy-MM`, `yyyyMM`, `MM`, `MM-dd`, `MMdd`, `ddMM`, `HH:mm:ss`, and `yyyy-MM-dd'T'HH:mm:ss` on DATE, TIME, and DATE_TIME alike, with no kind-split candidate; the other 123 candidates are refused. This is not a closed-vocabulary claim outside that printed universe. Admission is not derived compositionally from component presence: `ddMM` is admitted where `dd.MM` is refused, and `yyyyMMdd` is admitted where `ddMMyyyy` is refused. The DateRange `(format, separator)` allowlist is a separate domain and is stated in [§8](#8-date-ranges-and-overlap).

Stored DateRange formal checking has four ordered failures. A token that does not contain the declared separator yields `datumBereichTrennerFehlt`; once the separator is present, a split other than two nonempty endpoints or a lexically or calendrically invalid endpoint yields `datumBereichFormatFalsch`; two valid endpoints with start after finish yield `datumBereichNichtGueltig`; an otherwise ordered range whose start precedes `1583-10-16` yields `datumBereichDatumFalsch`. Equal endpoints are valid. Every failure keeps the physical placement and exact text while making a reached validation read UNKNOWN and a reached computation read poison.

An empty declared DateRange separator is a real admitted policy, not the absence of a delimiter. Under the legal `MM` plus empty-separator declaration, the stored token is split at its midpoint, so `0609` has endpoints `06` and `09`; it is not split into characters and does not yield `datumBereichTrennerFehlt`.

## 1. Constant format and the string/date literal ambiguity ⚠

Date constants are written **`DD.MM.YYYY`** (day first) regardless of locale; the decimal separator is always `.`. A **string literal that matches the date format is interpreted as a date constant**, which is why it cannot be used in string concatenation:

```
"30.11." + [YearString]        -- invalid: "30.11." is read as a date
"30." + "11." + [YearString]   -- valid: the pieces don't match the date format
```

The literal is typed **by its own syntax, not by context**:

- `[StringField] == "15.06.2024"` is **rejected** (string field vs a date constant).
- a `dd.MM.yyyy` literal compares **chronologically** to a DATE field *whatever the field's stored format*, and rides in argument position: `DifferenceInDays(OrderDate, "01.01.2022")`.
- **inside a value list**, a date-looking entry stays a plain **string**.
- an **ISO-format literal** `"2022-01-01"` is lexed as a **string**, never a date.
- the **omitted-year form** `"13.07."` (trailing dot) injects the model's **Base Year** (a reference year, *not* a floor); a model without a Base Year **rejects** it.

A Time constant is likewise typed by its own syntax and is locale-independent: exactly eight ASCII characters in `HH:mm:ss` form, with two digits per component and a real `00:00:00`–`23:59:59` clock. Short widths, different separators, non-ASCII digits, hour 24, and minute or second 60 are rejected statically as invalid date strings rather than reaching evaluation as ordinary Strings. Generated evaluation represents an admitted Time constant on 1970-01-01 in the model zone, but Time comparison and `DateTime(date, time)` observe only its decoded hour, minute, and second.

> **Non-normative implementation note.** Resolve the ambiguity in the **lexer/typer**, not the evaluator: a literal token is classified as `dateConst` iff it matches `DD.MM.YYYY` (or the omitted-year shape), as `timeConst` iff it matches the exact real `HH:mm:ss` shape, and otherwise as `strConst`, with ISO date shapes always remaining `strConst`. Downstream evaluation then never has to "guess" a literal's kind. This mirrors the engine: the literal is typed by syntax.

## 2. Addition and difference are asymmetric and calendar-corrected

`DifferenceInMonths` / `DifferenceInYears` first order their endpoints, compute the **largest nonnegative whole number of months/years that can be added from the earlier date without passing the later date**, and then apply the sign of `second − first`. A reverse fractional result therefore truncates toward zero; it is not mathematical floor or a signed calendar-component count:

```
DifferenceInMonths("31.01.2010", "30.03.2010")   -- returns 1, not 2
```

Direct Day/Month/Quarter/Year and Hour/Minute/Second extraction, plus Date-only `DifferenceInMonths`/`DifferenceInYears`, each produces a non-expandable scale-0 Number operation. Operation-form `RoundDown`/`RoundUp`/`RoundAccounting` and `Abs` accept those results directly, including a component extracted from direct or range-selected `BaseYear`. Direct numeric `BaseYear` is likewise admitted because it is a number-like reference operation rather than an authored numeric literal. An empty temporal field or empty difference operand yields symmetric fillable zero in validation: rounding preserves both movement directions, while `Abs(0)` retains only possible magnitude growth. Direct and derived Base-Year values are fixed, and formal unavailability remains UNKNOWN in validation or poison in computation through either wrapper.

And addition is not the inverse of difference:

- **`AddYears`** maps the last day of February to the last day of February: `AddYears("28.02.2023", 1) = 29.02.2024`. More precisely it *corrects into* a leap year: `28.02.1999 + 1 year = 29.02.2000` (not the plain `28.02.2000`).
- **`AddMonths`** preserves the *day number* and **clamps** end-of-month overflow to the shorter month's last day, never carrying into the next month: `AddMonths("28.02.2011", 12) = 28.02.2012`; `31.01.2008 + 1 month = 29.02.2008`.
- The two therefore **disagree across a leap-year boundary** — a naive age check built on them is wrong around leap days. **Fractional offsets are truncated toward zero, not rounded, and the truncated decimal is then narrowed to the low signed 32 bits like Java `BigDecimal.intValue()`**; it is neither range-rejected nor saturated.

The same amount conversion applies to all six shifts: `AddDays`, `AddMonths`, `AddYears`, `AddHours`, `AddMinutes`, and `AddSeconds` admit an ordinary signed Number operation, truncate its reached decimal toward zero, and retain the low signed 32 bits. Overflow wraps rather than rejecting or saturating, so `4294967303` (`2^32 + 7`) shifts by `7` and `4294967296` shifts by `0`. Sub-day shifts narrow before multiplying by their unit. An empty direct Number amount contributes ordinary numeric zero; a domain-invalid amount produces no temporal value.

The calendar basis of the operand is observable, and no one calendar implementation applies to every temporal consumer. A real value produced by `Date(...)` retains the constructor's model-zone legacy hybrid-calendar identity through legal `AddDays`/`AddMonths`/`AddYears` and `DifferenceInDays`/`DifferenceInMonths`/`DifferenceInYears` consumers. Stored values, fragments, ranges, and each other operation remain governed by their separately stated clauses; this constructed-value rule does not classify them globally. A constructed-Date month/year shift whose nominal field-preserving landing lies in the missing `1582-10-05..14` cutover labels normalizes forward by ten civil labels. Thus `1582-09-10 + 1 month = 1582-10-20`, `1581-10-10 + 1 year = 1582-10-20`, and from `1582-09-10` the constructed dates 15 October and 20 October are respectively zero and one whole month away. From `1581-10-10`, 15 October 1582 is zero whole years/11 whole months away, while 20 October is one year/12 months away. The `AddYears` February-28 correction itself uses Gregorian leap status even on the Julian side: `1499-02-28 + 1 year = 1500-02-28`, although `Date("29", "2", "1500")` is constructible there.

Constructed-Date calendar shifts also retain the exact model-zone instant selected by their particular `GregorianCalendar` mutation; equal decoded labels do not imply equal results. Direct Date comparison resolves both operands to exact instants: a constructed or shifted Date supplies its retained instant, while an ordinary stored Date derives one through the ordinary model-zone parse. `Calendar.DAY_OF_MONTH` carries the source instant's offset into the nominal target and re-fits to the offset actually in force there only when the re-fit preserves the target civil date. Travel direction is not the discriminator: under `Europe/Berlin`, `AddDays(Date("30", "9", "1916"), 1)` carries CEST and lands at `1916-09-30T22:00:00Z`, while `AddDays(Date("1", "3", "1916"), 214)` carries CET into the same target label and lands at `1916-09-30T23:00:00Z`, equal to freshly constructed `Date("1", "10", "1916")`. At the repeated midnight, `AddDays(Date("30", "9", "1916"), 1) == Date("1", "10", "1916")` is therefore false, while the corresponding one-month and one-year comparisons are true. `AddMonths` and `AddYears` use sign-independent compute-time resolution: both signed month routes from 1 September/November 1916 and both signed year routes from 1 October 1915/1917 into 1 October 1916 select the later CET instant. A nominal month/year gap normalizes to its post-gap label. Calendar field mutation preserves the source millisecond except when the leap-to-nonleap February-28 correction deliberately clears the entire clock.

A date shift evaluates an operation-valued amount through the ordinary numeric-expression semantics, including authored order and directional missing provenance. Thus an empty Number field plus `1` supplies the concrete amount `1` marked not-given, while a domain-invalid expression has no amount to apply. For example, `AddDays(StartDate, RoundAccounting([x] / 0, 2))` yields a valueless Date and clears a stale Date target; it does not attach the numeric `berechnungsWertFehler` to that Date target. This is a Date-consumer projection of the invalid numeric operand, distinct from assigning the same expression to a Number target.

An empty direct Number-field amount is different: the generated field read supplies numeric zero with missing provenance. When the Date/DateTime source has a value, the shift therefore retains the same concrete value but marks it not-given; a true downstream comparison fires with OMISSION rather than VALUE. The generated shift evaluates its Date/DateTime source before the numeric amount: a formal source stops before the amount, while a cause-free empty source still reaches it.

**Sub-day arithmetic** operates on exact integer **milliseconds since epoch**. Stored and constructed Date/Time/DateTime syntax has whole-second precision, but `Now` retains the injected validation clock's millisecond identity:

- `AddHours` / `AddMinutes` / `AddSeconds` require a date-bearing operand whose format exposes the selected time component, preserve that DateTime format, and carry across the day boundary. A Time-only operand is rejected; use `TimeFromDateTime(AddHours(dateTime, amount))` or its Minute/Second counterpart when a Time value is required.
- `DifferenceIn{Hours,Minutes,Seconds}(a, b) = (epochMillis(b) − epochMillis(a)) / unitMillis`, **truncated toward zero** — a reverse difference of −5 h 30 m is **`-5`**, not `-6`, and a `999 ms` residual is `0` seconds. Argument order is `b − a` (same as `DifferenceInDays`).

> **Non-normative implementation note.** Do not erase the operand's calendar basis. A proleptic-Gregorian total function is suitable only for a narrowed consumer/domain whose own clause or proof establishes that equivalence; a constructed-Date consumer needs a supplied legacy-calendar operation or a proof-backed supported profile. `AddMonths`/`AddYears` need the explicit end-of-month clamp and the Feb-into-leap-year correction as *code*, not as an assumed library default. The sub-day family is cleanest after resolution as `Int` epoch-milliseconds with truncating integer division (`Int.tdiv`, toward zero — **not** `Int.fdiv`).

## 3. Constructing dates, and checking validity

`Date(Day, Month, Year)` builds a date from numeric parts (also: a 2-argument form supplying the year from the Base Year, and a 4-argument `Date(Day, Month, Century, ShortYear)` form). Each explicit component may be a field, its matching direct Date extractor in the three-part form, or a quoted decimal string constant; the forms may be mixed. A bare numeric token is not a component literal: it is parsed as an entity name and rejected with `MVK_INVALID_ENTITY`. Day, Month, and complete Year admit only `DayFromDate`, `MonthFromDate`, and `YearFromDate` respectively. The extractor operand uses the ordinary nonliteral Date-expression grammar rather than only a direct field, must resolve to Date or DateTime with the selected component after optional Base-Year supplementation, and is evaluated before its component is passed to the constructor; a direct temporal literal inside the extractor is rejected. The rejection code depends on convertibility rather than extractor family or kind match: a literal that parses in the model's temporal format reaches the constant-position gate and is `MVK_NO_CONST`, while a literal that parses as no temporal value—such as ISO `"2019-01-01"` in the ordinary model format—fails first with `MVK_INVALID_DATE_STRING`. Thus even `HoursFromTime("01.01.2020")` is `MVK_NO_CONST`: it converted before the operand-position refusal. An empty extractor source therefore keeps the constructed Date incomplete, while formal unavailability remains exact. After quote removal, a constant is checked as a nonempty sequence of UTF-16 code units accepted by the host decimal-digit predicate, then parsed as an integer. Day and Month have no width restriction and accept respectively `1 ≤ value < 32` and `1 ≤ value < 13`, so leading zeroes of arbitrary length are legal. Complete Year requires exactly four code units and `1800 ≤ value < 2200`; Century requires exactly two and `18 ≤ value < 22`; Short-Year requires exactly two and `0 ≤ value < 100`. Supplementary-plane digits occupy surrogate code units and therefore fail this character-wise gate. A direct Number-field component must have effective maximum fractional digits zero—an omitted maximum passes—admit only nonnegative values by its sign policy or an explicit minimum, and have either the complete stored-length bound for its position or the positional maximum. Day accepts width 2 or maximum 31; Month accepts width 2 or maximum 12; complete Year accepts width 4 or any maximum from 1000 through 9999; Century accepts width 2 or any maximum from 10 through 99; Short-Year accepts width 2 or exactly 99. `maxIntegerDigits` is not the stored-length alternative. A direct String-field component must have maximum length equal to that positional width and either be an extensible enumeration or use exactly one of `[0-9]+`, `[0-9]*`, `\d+`, `\d*`, `[0-9]{width}`, or `\d{width}`; regex-equivalent spellings are rejected. The complete-Year position alone also accepts a Date field whose exact declared format is `yyyy`. An admitted String or `yyyy` Date field is converted from its stored text as a Number; empty keeps the construction incomplete, formal unavailability remains exact, and a present out-of-range component reaches the constructor's unreal-date check rather than being clamped. The four-part form rejects extractors in either split-year position, evaluates Day, Month, Century, then Short-Year, and forms the year as `Century × 100 + ShortYear`; a fixed Short-Year zero is present, while an unfilled field or extractor result keeps the construction incomplete. Quoted constants are fixed present inputs and never read document state. `Time(...)` and `DateTime(...)` construct the corresponding values. A constructed date is **invalid** if any referenced part is unfilled, or the parts don't form a real calendar date (`Date("31", "11", "2000")` — November has 30 days; or 30 February).

`Time()` through `Time(Hour, Minute, Second)` supply a leading prefix of zero to three components; every omitted trailing component is the fixed value zero, so `Time()` is midnight and `Time("10", "30")` is `10:30:00`. Each authored component is statically restricted to its matching field, extractor, or in-range decimal-digit string constant before runtime conversion, and those forms may be mixed across positions. A Number field must have effective maximum fractional digits zero (an omitted maximum passes), admit only nonnegative values by its sign policy or an explicit minimum, and have either maximum stored length 2 or the exact positional maximum (23 for Hour and 59 for Minute or Second); `maxIntegerDigits = 2` is not the stored-length alternative. Admission does not make every stored spelling usable: under the maximum-length-2 profile with no minimum, `5` produces the padded clock component `05`, while stored `"05"` is rejected as `zahlHatFuehrendeNullen` and clears the target. Adding minimum stored length 2 also rejects the unpadded single-digit value as too short, so that combined profile admits the declaration but cannot represent a valid single-digit component. A String field must have maximum length 2 and either be an extensible enumeration or use one of the checker-recognized digit-only patterns `[0-9]+`, `[0-9]*`, `\d+`, `\d*`, `[0-9]{2}`, or `\d{2}`; unlike Number, this carrier accepts and converts `"05"`. An extractor must be `HoursFromTime`, `MinutesFromTime`, or `SecondsFromTime` at the matching component position. Its operand is the ordinary nonliteral temporal-expression grammar, not only a direct field: the source may be any statically admitted Time- or DateTime-bearing expression that exposes the selected component, while a direct temporal literal inside the extractor is rejected. The nested temporal source is evaluated before the extractor call. An empty source therefore reaches the constructor as numeric zero with missing provenance and still makes the constructed Time incomplete; a present temporal expression that yields no value reaches the constructor as fixed numeric zero instead, while formal unavailability remains exact. At runtime a formally unavailable/non-relevant supplied component dominates missingness, a missing supplied component produces an incomplete/not-given no-value, and a fully present but impossible clock produces a distinct present/unreal no-value. `DateTime(date, time)` evaluates Date before Time, retains those Time-side reasons, gives non-relevance precedence over ordinary no-value after both operands are reached, and resolves a real combined wall label in the model zone.

`TimeFromDateTime(source)` requires a DateTime operand whose declared or derived format contains Year, Month, Day, Hour, Minute, and Second. A valueless source is returned with its not-given or non-relevant reason unchanged. For a present source, the operation reads Hour, Minute, and Second in the model zone and constructs a Time value anchored at 1970-01-01; downstream Time consumers therefore observe the retained wall clock, not the source Date or exact instant. When used as the Time argument of `DateTime(date, time)`, the outer constructor still evaluates its Date argument before evaluating this extraction.

`DateFromDateTime(source)` is its Date-valued sibling and requires the same **complete** DateTime operand. It reports the source label's **own** date components with the time dropped: a stored `2024-06-15T00:30:00` extracts to `2024-06-15`, and converting the retained instant to UTC first — which would give `2024-06-14` at a `+0200` model zone — is measured wrong. The result is a **Date**, not a DateTime: it compares against a Date field, against `Today`, and against another `DateFromDateTime`, and it is admitted as a Date-addition operand, while comparing it to `Now` or to a `TimeFromDateTime` result is rejected `MVK_INVALID_COMPARE_TO_DATE`. A valueless source is returned with its not-given or non-relevant reason unchanged. Both component extractors reject every other source at the operator with the single class `MVK_WRONG_DATE_FORMAT_FOR_OP`, including a plain Date field and the degenerate time-only DateTime of the paragraph below. Like `ValueAsDate`, the operand is written as a **bare** path; bracketing it is a parse failure, and the extraction is not admitted inside an ordinary Date extractor such as `Day(...)`. Neither component extractor has a sibling-parallel repeatable spelling in the measured `Projects/Choices` to `Projects/Tasks` topology: for both `DateFromDateTime` and `TimeFromDateTime`, relative and absolute `Choices*/Stamp` operands are refused at the extractor with `MVK_NO_WILDCARDS_ALLOWED`, while removing the star from the otherwise identical paths is refused with `MVK_NO_WILDCARD`. This is a static authoring boundary and does not transfer to the separately admitted sibling-star `FirstFilledValue` family.

**Within the measured 135-candidate denominator, a declaration's format string rather than its field kind determines admission and the retained stored-input outcomes.** Every one of the twelve formats in the measured candidate partition above is admitted on every temporal kind, including `HH:mm:ss` on DATE and DATETIME, `yyyy-MM-dd` and `dd.MM.yyyy` on TIME, the fragment format `MM` on TIME, and the ISO datetime format on DATE, each persisted exactly as declared. A refused candidate fails at the model level as an invalid date format however natural it looks for its kind; a TIME field is refused `HH:mm` while being admitted `yyyy-MM-dd`. Each kind does have a single *default* (`HH:mm:ss` for TIME, `yyyy-MM-dd'T'HH:mm:ss` for DATETIME), but a default is not a restriction. One string is a specific trap: the day-first **`dd.MM.yyyy'T'HH:mm:ss`** is refused on every kind, even though the kernel does define it for DateTime-valued **expressions** such as `Now`, the `DateTime(...)` constructor, and a DSL constant. The degenerate case below is one instance of the measured kind/format freedom, and a consumer must not infer a component set from a field's kind.

A DATE field may be declared with seven **component-omitting** formats beside the three complete ones: `yyyy`, `yyyy-MM`, `yyyyMM`, `MM`, `MM-dd`, `MMdd`, and `ddMM`; the complete formats are `yyyy-MM-dd`, `dd.MM.yyyy`, and `yyyyMMdd`. A component-omitting field's stored text is shorter than a complete date and its value denotes an **interval** or a yearless calendar position: a whole calendar year for `yyyy`, a whole month for the two year-month spellings, and a month/day position for the four yearless spellings. The semantic account has one rejection cause for this family: a parse or calendar failure reports the format finding, and there is no position-in-time branch because no complete date is present to compare with the floor. The retained Kernel rows establish this account for named width, extra-component, separator, range, and unreal month-day failures; other stored texts remain externally unverified. Separators and component order are exact: `yyyy-MM` rejects `202006`, `yyyyMM` rejects `2020-06`, `MMdd` rejects `06-15` and reads `0611` as month 6/day 11, while `ddMM` rejects `15-06` and reads `0611` as day 6/month 11. A yearless value has no completion until something supplies a year. Its day is bounded by the month's **greatest possible** day, February included at 29, because no year is available to decide leapness: `04-31` and compact `3104` are rejected, while `04-30`, `02-29`, compact `0229`, and day-first compact `2902` are accepted. This is the same yearless day bound the DateRange overlap rule uses. These formats compare through the **ordinary** direct-comparison gate with no special rule: component sets need not agree, so a `yyyy` operand compares with a `yyyy-MM` one and with a complete date, while a yearless operand is rejected `MVK_INVALID_COMPARE_TO_DATE` against any year-bearing one unless the model declares a Base Year to supply the year. The gate is year presence after that supplementation, not format identity. Empty stored text is present and value-free on every one of these formats.

A DateTime field may legally be declared with the degenerate **time-only** format `HH:mm:ss`, and such a field is fillable and comparable but is admitted as an operand almost nowhere. Every temporal operation that reads a component refuses it while the identical condition on an ISO-declared sibling is admitted, and the refusals are **three distinct classes** rather than one gate: the component extractors including `TimeFromDateTime` and `DateFromDateTime` draw `MVK_WRONG_DATE_FORMAT_FOR_OP`, `AddHours` and `DifferenceInHours` draw `MVK_INVALID_TIME`, and comparison against `Now` draws `MVK_INVALID_COMPARE_TO_DATE`. **The kernel wants a complete DateTime for all of them, including the time extractor**, which the format does carry; the natural reading that what the format retains is usable and only what it omits is refused is therefore wrong, and it is the same requirement that makes `TimeFromDateTime` refuse a plain Time field. `FieldFilled` and equality against a same-format sibling are admitted, which is what keeps the refusals from being satisfied equally by a field that is simply dead.

```
Invalid(Date(Day, Month, Year))   -- fires on 31.11, 30.02, an unfilled part, …
```

**The truth projections of `Valid` and `Invalid` are strong-Kleene complements, but one full verdict does not determine the other**, because the construction has reason-bearing non-values:

- An **unreal `Date(...)` carries no date value** — it does *not* roll over and does *not* keep an out-of-range label. Its direct numeric date/time extractors and date differences nevertheless produce the actual Number **`0`** with fixed/present provenance. An incomplete construction also produces `0`, but retains not-given/fillable provenance; a fired comparison can therefore be VALUE for unreal input and OMISSION for incomplete input even though the numeric amounts agree. A malformed/formally unavailable construction projects to UNKNOWN instead, never to zero.
- `Valid(Date(...))` = all parts present ∧ well-formed ∧ the date is real → fired **VALUE**.
- `Invalid(Date(...))` = parts well-formed ∧ (not real ∨ some part empty). Its polarity is **directional**: an empty fillable part → **OMISSION**, a present-but-unreal date → **VALUE**. It even fires on an **all-empty** row.
- A **malformed** part suppresses **both** predicates (each goes UNKNOWN; the formal error fires instead). This is the UNKNOWN/UNKNOWN arm of strong-Kleene complementation, not ordinary Boolean false.
- The decisive non-law is at the full verdict/polarity level: incomplete and unreal constructions both make `Valid` not fire, but `Invalid` must recover **OMISSION** for incomplete and **VALUE** for unreal.
- To fire `Invalid` **only** on a complete-but-impossible date, prefix `AllFieldsFilled(...)`.

The constructor's **calendar-reality test is model-zone-sensitive and uses the legacy hybrid calendar**, not an abstract proleptic-Gregorian `LocalDate`. Kernel 30.8.1 creates a non-lenient `GregorianCalendar` in `modelConfig.timeZone`; the default cutover uses Julian rules before the Gregorian transition, and a zone discontinuity can remove a complete local date. Consequently, UTC `Date("29", "2", "1500")` is real under the Julian side of that calendar, while `Date("30", "12", "2011")` is unreal in `Pacific/Apia` because that local date was skipped. This is separate from the later 1583-10-16 stored/computed-value floor. The zone database is a runtime input not identified by the kernel behavior version alone. A portable implementation must reproduce the pinned legacy calendar, zone, and zone-data behavior or fail closed outside its explicitly supported calendar domain; substituting a zone-free proleptic-Gregorian predicate is not equivalent.

The reason and calendar basis compose through legal temporal producers rather than being rediscovered at each leaf:

- A Date- or DateTime-valued operation carries either a concrete value with its calendar/instant identity or a no-value reason. Incomplete/not-given, present-but-unreal, and non-relevant/malformed provenance must remain distinguishable; non-relevant dominates when a `DateTime(date, time)` combines it with a check-relevant no-value.
- `DateFromDateTime`, `TimeFromDateTime`, and legal `Add*` descendants preserve the source no-value reason. Real `Date(...)` descendants preserve the legacy-calendar identity described in §2.
- Numeric component extractors and date differences map incomplete/not-given and present-but-unreal operands to the same amount `0`, but retain fillable versus fixed provenance respectively; they map a non-relevant operand to UNKNOWN.
- The direct date-component family is `DayFromDate`, `MonthFromDate`, `QuarterFromDate`, and `YearFromDate`. For a real source, the quarter is `((month - 1) / 3) + 1` with integer division; the numeric-zero projection of an incomplete or unreal source remains `0` for Quarter just as it does for the direct components.
- Direct component extraction is admitted only when the source kind exposes the selected half and its declared format contains the selected component: Day needs day, Month and Quarter need month, Year needs year unless model Base Year supplies it, and Hours/Minutes/Seconds need their matching time component. Date extractors accept Date or DateTime; time extractors accept Time or DateTime. The separate partially-known Date precision gate is stricter and runs before Base-Year supplementation: `DAY_OPTIONAL` rejects Day, `MONTH_OPTIONAL` rejects Day/Month/Quarter, and `YEAR_OPTIONAL` rejects every date-component extractor.
- Direct date `Min`/`Max` skips check-relevant valueless operands when another concrete value exists; a non-relevant operand propagates non-relevance. This consumer admission does not widen the grammar: a result such as `YearFromDate(Min(...))` remains authoring-rejected where the extractor requires a narrower source form.
- Operand-list `Min`/`Max` and field-list/star `MinValue`/`MaxValue` also admit homogeneous TIME operands or homogeneous full-component DATETIME operands whose declared formats expose comparable component sets. Time selection compares each decoded time-of-day coordinate; DateTime selection compares each resolved physical instant, not its rendered wall label. In both families, check-relevant valueless operands are skipped, an all-empty selection has no value, any reached non-relevant operand propagates non-relevance, and an empty, omitted-tail, or encountered-filter source retains symmetric missing provenance on a selected value. A seconds-level Time difference therefore remains ordered even when a shorter display omits it, and an exact selected DateTime instant remains distinct from an equal-looking stored value on the other side of a model-zone overlap.

Temporal format admission deliberately has two strengths. A direct comparison requires matching year presence unless the Base Year supplies `YEAR`, and requires both formats to contain some date component or neither; only `==` and `!=` additionally require both formats to agree on whether they contain any time component. It does not require identical component sets: ordering admits `yyyy-MM` against `yyyy-MM-dd`, Date against DateTime, and `HH:mm` against `HH:mm:ss`, while equality rejects only the Date/DateTime pair among those examples. Temporal operand-list and field-list extrema are stricter: after optional Base Year supplementation their complete six-component sets must be identical, and a DATETIME extremum requires all year/month/day/hour/minute/second components.

`Valid(Field, "CustomTypeName")` and `Invalid(Field, "CustomTypeName")` are the other forms. Static model checking requires a single non-wildcarded value-validation **field** operand whose declared type is String, Enumeration, or extensible Enumeration, and a nonempty type name; it does **not** require registry membership. With a registered validator the two predicates are complementary for a filled value and neither fires for an empty value. An unregistered name is degenerate rather than rejected: both predicates fire for a filled field, each as an ordinary rule message carrying VALUE polarity at the concrete error address, and neither fires for an empty field. The value-specified gate therefore decides before any registry contact, so registration state cannot influence an unspecified value, and the two states in which no usable validator exists — no factory supplied at all, and a factory present that returns nothing for the name — are indistinguishable.

> **Non-normative implementation note.** A bare `Option CalDate` is insufficient: its `none` would collapse incomplete, unreal, and non-relevant constructions even though validity, numeric polarity, and later temporal composition distinguish them. Use a reason-bearing result such as `real (calendarBasis, CalDate) | incomplete | unreal | unknown`, define the two validity verdict projections separately, and give each consuming operation an explicit projection. Their truth projections complement under strong Kleene; `Invalid` is not a unary function of the full `Valid` verdict.

## 4. The Gregorian floor

**Dates before 16 October 1583 are invalid — as stored or computed *values*.** The floor is always-on and exact:

- strict *before*: `1583-10-15` errors, `1583-10-16` is valid;
- a day-optional value completes its omitted day to `01` **before** the check;
- a **stored** value below it is the formal error `datumFalsch` (suppressing referencing rules, [§3](02-logic-and-formal-errors.md)); a **computed** one is **ERRORED**; a date **range** floors its *start* the same way.
- It is distinct from the *opt-in* "younger than 1900" additional check.

`DateType.youngerThan1900Check` is a separate opt-in, declaration-owned basic-format check, independent of Date precision and the always-on Gregorian floor. When enabled, a concrete Date strictly before `1900-01-01` is the formal error `datumFalsch`; `1900-01-01` is valid. Ordinary partial-Date completion and reason preservation happen before this check, so an unknown-year value remains non-relevant rather than being reclassified as an ancient concrete date. The same declared gate classifies an admitted computed FULL-Date target as described in [§11](09-computations.md); partial Date computation targets remain statically rejected and do not create another runtime case.

⚠ The floor is **not** a runtime criterion for the `Date(...)` **construction**: `Invalid(Date("1", "1", "1500"))` does **not** fire (in 30.8.1). The floor gates *values*, not the constructor's reality test.

Also: **a date value is stored and formal-checked in its field's declared `format`, not a canonical wire format** — the same calendar date is well-formed in one field and `datumFormatFalsch` in another. A consumer must read each field's `format` to parse its dates.

## 5. Time zones and the sub-day difference

`DifferenceInHours/Minutes/Seconds` is **absolute-instant subtraction** — `floor(|instant₂ − instant₁| / unit)`, sign from operand order — under the normative Groovy-dynamic behavioral anchor. Generated static-Java is required co-evidence and agrees on the exercised historical cases. No identical-behavior claim is made for the TypeScript/luxon target: a legal strategy split is recorded and never overrides Groovy-dynamic.

The model's configured **`timeZone`** is the DM-JSON key `content.modelConfig.timeZone`; the capitalized `TimeZone` is the *internal* metamodel key code generation copies it into. Absent means `UTC`. An explicit id is model-legal exactly when it is the literal `GMT` or `java.util.TimeZone.getTimeZone(id).getID() != "GMT"`. Known IANA ids, `GMT±HH:MM`, `UTC`, `Zulu`, and `Etc/UTC` are legal. An empty, unknown, or misspelled id that silently collapses to `GMT` is rejected with `MVK_INVALID_TIME_ZONE`.

The normative kernel path applies that id at parse time through legacy `java.util.TimeZone` plus non-lenient `SimpleDateFormat`, not `java.time`. A plain DATE is midnight in the model zone. Across a daylight-saving transition:

- Under **`UTC`**, the wall-clock gap equals the instant gap.
- Under **`Europe/Berlin`**, two datetimes straddling a transition differ by their *physical* elapsed time: `2024-03-31T01:30:00 → 03:30:00` is `DifferenceInHours = 1` (the skipped 02:00 hour), and `2024-10-27T01:30:00 → 03:30:00` is `3` (the repeated hour).

That non-lenient zone-set parse gives every historical transition the following laws:

- **Every gap is a FORMAL error.** A stored wall time that does not exist (`2024-03-31T02:30:00` under Berlin) draws `datumFormatFalsch` — the non-lenient round-trip rejects it — and suppresses a referencing rule exactly like any malformed value. It is **not** rolled forward.
- **Every overlap selects the smaller/after offset.** In an ordinary modern CEST→CET overlap that is CET: `01:30 → 02:30` on `2024-10-27` is `DifferenceInMinutes = 120`, and two stored `02:30` values are instant-equal. In a historical CEMT→CEST overlap the same general rule selects CEST, not CET.
- **Datetime comparison is instant-based too** (`==`/ordering compare the parsed instants), and a **chained `Add{Hours,Minutes,Seconds}` result keeps its exact instant**: `AddHours(01:30 CEST, 1)` lands on the *daylight* side of the ambiguous hour, so it is **not** equal to the equal-looking stored `"02:30:00"` (which re-parses standard) — the pair is 60 real minutes apart. A rendering-based re-parse loses this; the arithmetic is instant-in, instant-out.
- **A `Calendar.DAY_OF_MONTH` landing assumes the source instant's own offset**, not an offset chosen from the signed amount. The nominal target advances the source wall label by whole days while retaining its clock and millisecond. If the offset actually in force at that candidate differs, the target is re-fitted to the actual offset and that re-fit is kept only when it preserves the target civil date; otherwise the first candidate stands. The spring-gap separator is a pair, not a generic roll-forward rule: `2024-03-30T02:30 + 1 day` starts from CET and renders `2024-03-31T01:30`, while `2023-08-31T02:30 + 213 days` starts from CEST, reaches the same gap, and renders `2024-03-31T03:30`. Adjacent transition probes can therefore resemble a direction or gap-normalization rule only because their source already carries the offset that account would choose. A backward landing onto the 1916 `23:00–24:00` gap supplies the historical control: `1916-05-01T23:30 - 1 day` preserves 30 April and renders `1916-04-30T22:30` CET instead of changing the civil date to 1 May.

## 6. Date fragments and fragment ranges

A **DateFragment** is a deliberately imprecise date (format `MM`, `yyyy`, `yyyy-MM`, `MM-dd`).

- Fragments are **comparable only if both formats include the year or both omit it** (or globally via the Base Year). A missing component defaults to `01`.
- When an operation requires a concrete Date and the model declares a Base Year, a fragment **completes to the earliest concrete date**: missing month becomes `01`, missing day becomes `01`, and missing year becomes the declared Base Year. It then compares, shifts, or extracts **as a plain date**. The fragment format decides which `Add*` apply.

A **fragment-format date range** completes its two endpoints **asymmetrically**:

- the **start** to the interval's *earliest* date, the **end** to its *latest* (missing month → `12`, missing day → the month's last day, leap-aware).
- So a `yyyy` range `2024/2025` denotes `2024-01-01 .. 2025-12-31`.
- With a declared Base Year, an `MM` range uses day `01` and the leap-aware month end in that year, while an `MM-dd` range uses its stated month and day for both endpoint positions. Without a Base Year, same-profile `MM` and `MM-dd` construction equality, inequality, and construction-versus-stored comparison remain authorable and distinguish a change to either ordered endpoint; these observations do not supply a year-bearing instant. Overlap applies [§8](#8-date-ranges-and-overlap)'s uniform-year gate to the whole operand list rather than to a distinguished pair, so without a Base Year any year-bearing operand beside any yearless stored profile is refused with `MVK_DATE_WITH_AND_WITHOUT_YEAR`, and a declared Base Year completes every yearless operand and admits the same list.

**Stored temporal failures use the Date formal codes, and the retained Kernel matrix is bounded by the twelve measured formats and their discriminating values.** There is no Time-specific or DateTime-specific formal code. For every retained value, DATE, TIME, and DATE_TIME agree cell for cell, so field kind does not select among those observed classifiers. The semantic account for an `HH:mm:ss` declaration maps width and component-range failures to the format error and has no date-error branch; the retained rows cover each component and the 24-hour boundary. Hour **24 is not an end-of-day spelling**: `24:00:00` is refused exactly as `25:00:00` is, while `00:00:00` and `23:59:59` are admitted, so the hour's range is 0 through 23 inclusive. At a complete Date or DateTime format, a real value before `1583-10-16` reports the date error, while an unreal component reports the format error before the floor can speak; `yyyyMMdd` therefore admits `15831016`, reports the date error on `15831015`, and reports the format error on `00000615` and `20240231`. The ISO DateTime literal `'T'` is mandatory. These observations do not establish classifier behavior for a format outside the 135-candidate declaration denominator or for an unmeasured stored text inside a measured format.

**Partially known Date values** use literal zero components in a monotone suffix governed by `DateType.datePrecision`. `DAY_OPTIONAL` admits a full Date or an omitted day such as `00.06.2024`. `MONTH_OPTIONAL` additionally admits an omitted month only when the day is also omitted, such as `00.00.2024`. `YEAR_OPTIONAL` additionally admits an omitted year only when month and day are both omitted, namely `00.00.0000`. A lone `0` is never an omission marker, an omitted month with a present day is invalid, and an omitted year with a present month or day is invalid.

**Which formal cause a rejected partial value carries is decided by the declaration first, then by reality.** A **full-precision** declaration reports *any* omission marker as the format error `datumFormatFalsch`, because an omission is not a legal spelling for it at all. A declaration that admits omissions instead splits its rejections in two. The **format** error covers a wrong component width or separator count and an unreal calendar date among the value's **present** components — including an impossible month standing beside a legally omitted day, where the omission is admitted and the month is not. The **date** error `datumFalsch` covers a zero pattern that is not a monotone suffix, a suffix deeper than the declared precision admits, and an admitted value whose **earliest completion** falls below the universal Gregorian floor or the enabled pre-1900 boundary. So an implementation must test the present components' reality *before* their position in time, and both before the precision gate: `1583-10-00` on a `DAY_OPTIONAL` declaration is the date error while `1583-11-00` is admitted, and `2024-13-00` on that same declaration is the format error rather than either omission failure. The two thresholds are indistinguishable from the cause alone and separable only from the declaration.

`ValueAsDate(field, FirstDay|LastDay)` resolves a known-year partial value to the earliest or latest matching concrete Date: an omitted day becomes `01` or the leap-aware month end, an omitted month-and-day becomes January 1 or December 31, and a full value resolves to itself. An omitted year becomes non-relevant before month/day completion, so an enclosing direct comparison evaluates to UNKNOWN rather than ordinary non-firing emptiness; it is not completed with the formal checker's temporary year 2000. `ValueAsDate` is a Date-valued operation. In addition to direct comparisons, the grammar explicitly admits it in the special Date-operand positions of Date addition, Date difference, and the Date argument of `DateTime(...)`; an ordinary Date extractor such as `Day(ValueAsDate(...))` does not admit that operation in its narrower operand grammar. A partial-Date field is **not** readable as a plain Date operand at all: a bare reference to one in an ordinary comparison is rejected `MVK_INVALID_DATE_TYPE` ("it is not allowed to use a partly known date"), which is what `ValueAsDate` exists to bridge.

**The operand's reading locus.** A partial-Date operand may lie **inside a repeatable group**, and it is admitted exactly when the reading rule's own iteration scope binds that group: the same absolute operand path is accepted by a rule whose group is the repeatable one and rejected by a rule at the parent, where the Kernel demands an asterisk (`MVK_NO_WILDCARD`) instead. A **starred** operand is rejected outright, `MVK_NO_WILDCARDS_ALLOWED` reported at `ValueAsDate` itself rather than at the enclosing comparison, so no iteration scope admits one; a group-scope operand is likewise rejected, under [§7](07-repetition-and-iteration.md). Measured on the direct-comparison carrier; a locus verdict does not transfer to the Date-addition, difference, or `DateTime(...)` carriers, which remain unmeasured for this question.

> **Non-normative implementation note.** Model a fragment as `(present-components, format)` and give it a single `completeEarliest : Fragment → CalDate` plus, for ranges, a `completeLatest`. Keep completion a *pure* function separate from comparison, so a fragment "becomes a date" at exactly one place. The start/end asymmetry for ranges is the subtle bit — two different completion functions, chosen by endpoint position.

## 7. The point-in-time and reference sources

- `Today` ignores the time of day — more precisely, it truncates the validation instant to midnight **in the model zone** (a zone-set calendar), so under `Europe/Berlin` the day boundary is Berlin midnight, not UTC midnight. `Now` is the raw validation instant, including any millisecond remainder supplied through `currentDateForTest` or sampled from the wall clock; it is not rounded to authored DateTime precision before comparison or difference. `Now` is a DATETIME. Ordering (`<`, `<=`, `>`, `>=`) against either DATE or DATETIME is legal and compares both operands on the common model-zone timeline, with a DATE interpreted at model-zone midnight. Equality and inequality require the other operand to carry a time component, so `Now == PlainDate` and `Now != PlainDate` are rejected with `MVK_INVALID_COMPARE_TO_DATE`. `Now` remains unsuitable for stable equality: it is legal as a computation result but generated validation may sample a later instant and immediately disagree ([§11](09-computations.md)).
- **`BaseYear` is polymorphic by its typed use:** an explicitly date-typed source receives the base-year *start* (`2020-01-01`); a numeric comparison, ordinary arithmetic expression, or Number computation receives the fixed scale-0 year number (`2020`); and `StartOfDateRange(BaseYear)` / `EndOfDateRange(BaseYear)` are `01.01` / `31.12` of the reference year. It is *model config*, not the clock; **VALUE** polarity.

> **Non-normative implementation note.** Inject the clock (`Today`/`Now`) as an explicit parameter — a `PointInTime` in the evaluation environment — never a global read. This keeps `eval`/`compute` pure and deterministic (essential for reproducible property tests and for the "compute is a function" stance of [`01-data-model.md`](01-data-model.md)). `BaseYear` is model config, resolved by the typed consumer — a small dispatch, not a clock read.

## 8. Date ranges and overlap

Date ranges support only `==` / `!=` (**no ordering**). A stored DATE_RANGE or `DateRange(start, end)` construction may appear on either equality side, against another construction, or as a DATE_RANGE computation result. A construction is not admitted as a date-range overlap or bound-extraction argument and **cannot be nested** inside other constructs.

A DATE_RANGE declaration is statically admitted for exactly eight `(format, separator)` pairs: `dd.MM.yyyy` with `-`, `yyyy-MM-dd` with `/`, `yyyy` with `/`, `yyyy-MM` with `/`, `MM` with `/`, `MM-dd` with `/`, `MM` with the empty separator, and `dd.MM` with `-`.

Every other pair in the complete candidate grid is refused, including separator swaps, every dot separator, every other empty separator, and every `yyyyMM` pair. This declaration allowlist does not by itself establish that every DateRange operation admits every pair.

For the retained yearless profiles, `interpretationOfYear` may be omitted or set to `FROM` or `TO`. An omitted key **is** the standard interpretation; a present but empty token is **not** an omission and makes the model illegal at deserialization rather than defaulting, so empty and absent stay distinct here exactly as they do for a cell value. The key is accepted on every admitted declaration pair, including year-bearing ones where it cannot apply, so declaration admission never gates it. With a declared Base Year, a wrapping range with no interpretation is `datumBereichNichtGueltig`, while `FROM` or `TO` admits the identical text and completes it across two adjacent years; an ordered range stays in the Base Year under every reading. Without a Base Year, the Kernel result is not a field-local function of this declaration. In the measured order-only control, declaring interpreted `dd.MM` fields before interpreted `MM` fields makes both Kernel strategies admit `11/02`, while moving the otherwise identical `MM` declaration block first makes them report `datumBereichNichtGueltig`. The broader generated-format equivalence classes and consumers remain unmeasured, so no universal unconfigured validity rule is inferred from either order. The tempting binder mechanism also points the wrong way, because the host JSON binder coerces an empty token to null for enums by default; this family does not follow it.

In a configured model, `FROM` keeps a wrapping range's start in the Base Year and moves the finish into the following year, while `TO` keeps the finish in the Base Year and moves the start into the preceding year. Each endpoint's calendar reality is checked in the year it is placed in, so `01.11-29.02` under Base Year 2020 is valid with `TO`, whose finish lands in leap year 2020, and `datumBereichFormatFalsch` with `FROM`, whose finish would land on a February 29 that 2021 does not have. The unconfigured branch remains limited to the declaration-order observations above.

Both overlap operators **refuse** an operand whose declaration carries an `interpretationOfYear`, reporting `MVK_INVALID_DATE_RANGE_FORMAT` against the composite declared format. The refusal applies on either operand side of either operator, under a yearless or a year-bearing exact profile, and with or without a declared Base Year, so it is a property of the declaration rather than of the value or its completion. Bound extraction and equality comparison admit the same declaration, so the gate belongs to the two overlap operators alone.

`StartOfDateRange(field)` and `EndOfDateRange(field)` select the stored range's first and second endpoint respectively and expose it as a Date. Extraction is admitted on **every** admitted declaration, including a yearless profile in a model with no Base Year; what is gated is each consumer, because the selected endpoint carries exactly the date components its declaration retains. A numeric extractor is therefore admitted exactly where that set exposes its component, with the model's declared Base Year supplementing the **year** and nothing else, which is the same admission rule a direct Date field uses and *not* the exact-value gate the comparison consumers below apply: `MonthFromDate` and `QuarterFromDate` on `MM`, `MM-dd`, `dd.MM`, `yyyy-MM`, or a full-Date profile; `DayFromDate` on `MM-dd`, `dd.MM`, or a full-Date profile; `YearFromDate` on `yyyy`, `yyyy-MM`, or a full-Date profile in any model, and additionally on every yearless profile once the model declares a Base Year. Every other pairing is refused `MVK_WRONG_DATE_FORMAT_FOR_OP` at the extractor, and a declared Base Year never widens the month or day halves, so `DayFromDate` on `MM` stays refused in a configured model. The selection and its component are one authored operand rather than two, because the endpoint alone is not a numeric value; that operand is admitted in a Number **computation** operation on the same terms as in a validation condition, with the ordinary locus rule deciding the target — a row endpoint computes a field inside its own repeated group, while a scalar endpoint computes either. Like a direct temporal component, an endpoint component is a **non-expandable scale-0** Number operation, so assigning it to a fractional Number target is refused `MVK_INVALID_COMPARE_DEC_PLACES`, the one waivable code. At runtime the computed value is the selected endpoint's component under the ordinary rules of this family, including from an unconfigured yearless range, whose retained labels are read directly: an unplaced range computes the real number `0` rather than clearing, and a formally invalid range clears the reading computation's target while a sibling computation over a clean operand in the same row still computes its own value. Comparing a selected endpoint with a full Date, whether a literal or `Today`, follows the ordinary direct temporal admission rule, so only a **yearless** profile with no Base Year is refused `MVK_INVALID_COMPARE_TO_DATE`; every year-bearing profile is admitted, including the incomplete year-only `yyyy` profile. Comparing two selected endpoints follows the same rule, which admits `MM` against `MM-dd` and refuses `MM` against `yyyy`; at runtime each fragment is first completed by its endpoint position, so a month-only start equals a month-and-day start exactly when that day is the month's first. An empty range stays empty. Ordinary formal invalidity makes validation UNKNOWN and poisons computation with the same cause before either endpoint is selected. The validation-scoped required-empty finding remains the existing exception: it is UNKNOWN in validation and stays empty in computation. The ordinary operand is a non-wildcard, non-category DATE_RANGE field, either direct or selected by a **semantic index** — `StartOfDateRange(Rows/Window For "k")` and its field-keyed form are admitted, as are a keyed operand of the overlap predicate and of stored range equality, at a nonrepeatable locus, at an iterating one, and even when the keyed group is the group being iterated. A **starred** operand is refused `MVK_NO_WILDCARDS_ALLOWED` at either locus, so no wildcard form of this operand exists, and a **group** operand is refused `MVK_NO_WILDCARD`. `BaseYear` is the separately typed source described above, while a `DateRange(start, end)` construction is not admitted here.

At this carrier the shared wildcard gate is measured rather than carried over: a **starred** endpoint draws `MVK_NO_WILDCARDS_ALLOWED`, while an **unstarred repeatable** field or a group operand draws `MVK_NO_WILDCARD`, and an arity other than two is a parse refusal, `MVK_UNEXPECTED_TOKEN`.

Each `DateRange` endpoint is a bare A12 `entitySpec` reference, including a literal- or field-keyed semantic-index selection; a bracketed calculation is illegal there. `Today`, `BaseYear`, an `Add*` operation, and a date literal in either endpoint position are refused with `MVK_UNEXPECTED_TOKEN`.

A starred field is refused with `MVK_NO_WILDCARDS_ALLOWED`; an unstarred group with `MVK_NO_WILDCARD`; and a starred group or the rule-context group with `MVK_NO_GROUPS_ALLOWED`. A top-level outer-iteration marker is refused with `MVK_INVALID_OUTER_ITERATION`, while the same marker is admitted inside a `Having` filter that supplies its iteration.

After the entity-reference gate, each endpoint must be a complete DATE or DATE_FRAGMENT whose declared format has at least one date component and no time component. A Number, String, DateTime, or DateRange field, a partial DATE, or endpoint formats with different component sets are refused with `MVK_WRONG_DATE_FORMAT_FOR_OP`.

DATE and DATE_FRAGMENT may mix, and different lexical format spellings are legal when their component sets agree. Literal- and field-keyed semantic-index endpoints are admitted, but semantic indexing is not the only way to read a field below a repeatable group.

An ordinary unstarred endpoint that crosses a repeatable group is governed by the enclosing rule's iteration scope. With the error field outside that repeated group it is refused with `MVK_NO_WILDCARD`; moving the error field inside the repeated group admits it. This is a rule-locus condition shared with other operators, not a DateRange-construction restriction. **The claim is measured across the DateRange carriers rather than transferred between them:** the overlap predicate, stored range equality, an extracted endpoint compared against a fixed Date, a pair of extracted endpoints, a numeric component of an extracted endpoint, and the two-endpoint construction all admit the same repeatable operand from inside the repeated group and all refuse it `MVK_NO_WILDCARD` from outside, on one model differing only in the error field's placement. Each refusal names the offending operand rather than a neighbouring one, which is what isolates the carrier under test. The six agree, and that is agreement between independent measurements rather than an inference from a shared mechanism, so a carrier absent from this list is not covered by it — neighbouring gates in this family do vary by carrier. At the numeric-component carrier the locus gate also reports **before** the component gate: a row operand whose profile withholds the requested component still draws `MVK_NO_WILDCARD` from a non-iterating locus rather than the format class. The retained filter control instead admits an explicit outer-iteration marker and does not establish ordinary crossed-repeatable endpoint admission from filter context alone. Overlap tests treat endpoints as **inclusive (closed intervals)**.

Equality or inequality additionally requires the two resulting DateRange operands to expose the same declared date-component set. A component mismatch between otherwise valid constructions is refused with `MVK_INVALID_COMPARE_TO_DATE_RANGE`; it is not evaluated by completing the coarser range into the finer one. With a Base Year, this admits matching `MM` or matching `MM-dd` constructions but still refuses `MM` beside `yyyy-MM` and `MM-dd` beside full Date. Mixing those component profiles inside one construction instead yields `MVK_WRONG_DATE_FORMAT_FOR_OP`.

The same gate governs two **stored** DATE_RANGE fields compared with each other, and it reads only the component set: the declaration's lexical spelling never enters it. Over the eight admitted declarations that leaves five component classes, and each class's spellings cross freely — `yyyy-MM-dd` against `dd.MM.yyyy`, `MM` with slash against `MM` with the empty separator, and `MM-dd` against `dd.MM`. Every pair drawn from two classes is refused, including `dd.MM.yyyy` against `dd.MM`, which shares a separator and differs only in components. The refusal is symmetric in the authored order and identical for `==` and `!=`. Where the pair is admitted, the comparison decides on retained identity rather than stored text, so the two spellings of one class agree exactly when their resolved endpoints or their retained yearless labels agree.

DateFragment endpoints use [§6's asymmetric fragment-range completion](#6-date-fragments-and-fragment-ranges): a start completes to its earliest local date and a finish to its latest, so `yyyy` endpoints become January 1 and December 31 respectively, `yyyy-MM` or Base-Year-resolved `MM` endpoints span the selected month, and Base-Year-resolved `MM-dd` endpoints retain their stated day. The completed local labels are resolved under the model's accepted zone profile, and DateRange equality or inequality compares both ordered resolved endpoints. The [`yyyy` checkpoint](../docs/SOURCES.md#src-date-range-year-fragment-construction), [`yyyy-MM` checkpoint](../docs/SOURCES.md#src-date-range-year-month-fragment-construction), and [Base-Year checkpoint](../docs/SOURCES.md#src-date-range-base-year-fragment-construction) establish calendar labels and comparison outcomes, not externally exposed exact endpoint instants.

**Both overlap operators admit their operands by year class, and apply no component-set gate.** Every compared operand must include the year or none may; a mix is refused `MVK_DATE_WITH_AND_WITHOUT_YEAR`. The gate reads the whole operand list rather than a distinguished pair, so a list of three or more is refused on any mix, and every declared spelling of one yearless component set behaves alike. For `AtLeastOneDateRangeOverlaps` the list is the scalar together with its `In` list, so the gate spans both sides and a completed fragment is admitted as scalar or as list member. A declared Base Year completes each yearless operand and therefore admits every list, including `yyyy-MM-dd` beside `MM`; within one year class the operator admits differing component sets outright, unlike the equality gate above. A completed yearless operand occupies the Base Year alone, so an exact operand naming another year is disjoint from it, while an exact range spanning into the Base Year still meets the completion.

Without a Base Year an all-yearless list is admitted as well, and compares month/day labels directly with no completion: a month-only endpoint spans day `01` through that month's yearless maximum last day, February reaching `29` because no year decides leapness, and both ends stay closed. A configured Base Year instead makes the stored value itself completable and therefore falsifiable, so `02-29` under Base Year 2023 is `datumBereichFormatFalsch` rather than any overlap verdict. The [mixed-year checkpoint](../docs/SOURCES.md#src-date-range-mixed-year-overlap) and [yearless-overlap checkpoint](../docs/SOURCES.md#src-date-range-yearless-overlap) establish both accounts on either codegen strategy.

The two overlap predicates differ in **shape** ⚠:

- **`DateRangesOverlap(op0, op1, …)`** is **any-pair** among *all* operands' kept, filled ranges (one growing set): a list-internal pair fires even when a scalar operand is disjoint, and a same-cell self-pair via scalar + star fires on every filled row.
- **`AtLeastOneDateRangeOverlaps(scalar In list…)`** is genuinely **scalar-vs-list**: two list cells overlapping *each other* do **not** fire.

Checked `AtLeastOneDateRangeOverlaps` authoring retains one direct, stored, non-wildcard scalar separately from a nonempty list of direct, plain-starred, filter-starred, fixed-group, or starred-group operands. An admitted group operand contributes every DateRange declaration in its recursive subtree at every instantiated row below the operand's own repetition depth. The current checked fragment admits that group shape only when its complete expansion is nonempty and every declaration is a supported DateRange; mixed and empty expansions remain outside the represented fragment rather than carrying an inferred Kernel refusal.

For both: intervals are **closed** (back-to-back periods sharing a boundary day overlap); an **inverted** range (start after end) **never** overlaps; empty or formally unavailable cells are **skipped**.

Their firing polarity is scan- and operand-shape-sensitive:

- `DateRangesOverlap` fires **OMISSION** exactly when the scan has processed a kept, filled range from a filter-bearing operand at or before the first overlapping pair; otherwise it fires **VALUE**. A filtered operand with no kept, filled range does not taint a later firing.
- `AtLeastOneDateRangeOverlaps` resolves the scalar first and does not read the list when that scalar is unusable. Otherwise it visits list operands in authored order, visits each operand's cells in its canonical address order, and stops at the first overlap. It fires **OMISSION** exactly when that first matching list operand carries a filter; otherwise it fires **VALUE**. An earlier filtered but disjoint list operand does not taint a later unfiltered match, and a later filtered match cannot change an earlier unfiltered result.

For a group operand's rich Analyze/Explain trace, this specification normalizes canonical address order as declaration-major recursive model order with each declaration's rows in canonical row order. Current external observations establish the complete group extent, including the second field of the second row, but not a Kernel-visible witness order inside one unfiltered group; the normalized intra-group order is therefore project-defined and does not strengthen the external correspondence claim. Group operands carry no filter, so this choice cannot change the predicate verdict or polarity.

For `AtLeastOneDateRangeOverlaps`, an empty, malformed, or formally unavailable scalar collapses directly to no fire; overlaps internal to the list cannot rescue it. Stored inverted ranges are normally rejected by their field's formal check and therefore skipped, while the resolved interval relation independently returns false if an inverted pair reaches it.

## 9. DateTime rides the date-format definition — but the operand gates are PER-OPERATOR ⚠

The date **extractors** (`DayFromDate`, …) accept a DateTime operand and see its **DATE part** (times ignored). The time extractors (`HoursFromTime`, `MinutesFromTime`, `SecondsFromTime`) likewise accept either Time or DateTime and see only the **TIME part** (the DateTime date is ignored). Beyond the extractors, the earlier blanket claims ("differences see the date part; arithmetic is rejected") are **wrong per-operator** — probe-corrected (kernel 30.8.1, 2026-07-18):

- **`DifferenceInDays` accepts DateTime operands and is TIME-OF-DAY AWARE**, but its general rule is a signed **model-zone calendar-step count**, not unconditional subtraction on zone-free wall labels. The kernel orders the resolved legacy `Calendar` values, qualifies its whole-year candidate through the same corrected `Calendar.YEAR` mutation used by `AddYears`, makes a `yearDifference × 365` lower-bound jump with `Calendar.DAY_OF_MONTH`, advances by single calendar days until the next landing passes the later operand, and then restores authored argument order (`b − a`). The year qualification therefore uses the sign-independent later/post-gap `YEAR` landing described above, while every lower-bound or residual `DAY_OF_MONTH` landing assumes the offset of the instant from which that particular step starts and preserves milliseconds. The familiar wall-seconds quotient happens to agree with the maintained controls: `23:00 → 01:00` next day is **0**, not the date-part 1, while the equal-wall-time Berlin `2024-03-30T12:00 → 2024-03-31T12:00` is **1** despite only 23 elapsed instant hours. It is not a generally equivalent formula, even within Berlin: `2024-03-30T02:30 → 2024-03-31T01:45` counts **1** because one calendar-day addition lands at `01:30` before the second operand, whereas Δ wall-label seconds is only 23 h 15 m and would truncate to 0; the long-range source-offset separator `2023-04-01T02:30 → 2024-04-05T02:30` counts **369**, not the **370** produced by a direction-selected landing. A short overlap qualifier can self-correct through the residual loop, but the long spring-gap span `2003-03-31T02:30 → 2024-03-31T03:00` separates the year resolver: compute-time qualification counts **7670**, while direction-selected gap qualification counts **7671**. Across a whole-date discontinuity the distinction is sharper: in `Pacific/Apia`, `2011-12-29T12:00 → 2011-12-31T12:00` is one zone-calendar day because a single `DAY_OF_MONTH` step skips 30 December, whereas a proleptic wall-label coordinate would incorrectly return two. **Mixed `(datetime, date)` pairs are legal** — the date reads as midnight in the model zone.
- **`DifferenceIn{Months,Years}` REJECT a DateTime operand** at code generation (`MVK_WRONG_DATE_FORMAT_FOR_OP`) — date-only.
- **`AddDays` accepts a DateTime operand and is TIME-PRESERVING** (`15T22:00 + 1 = 16T22:00`); a special-hour landing follows the source-offset/refit rule (§5). **`AddMonths` / `AddYears` REJECT a DateTime operand** at code generation.
- **`DifferenceIn{Hours,Minutes,Seconds}` REJECT a plain DATE operand** — DateTime-only, mirror-image of the months/years gate.
