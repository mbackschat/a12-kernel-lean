# 05 — Dates and time (§6)

Dates carry more surprises than any other scalar type. The recurring theme: a date is **not** a canonical instant — it is a value in a *declared format*, with a *precision*, sometimes deliberately imprecise (fragments), and its arithmetic is **asymmetric** (add ≠ inverse of difference) and **calendar-corrected**. And a string literal that *looks* like a date silently *is* one.

Empty-date behaviour (not-evaluated in comparisons; `0` in the extractors/differences; dropped/`no value` in aggregates) is in [§2](03-empty-and-required.md).

**A temporal field need not declare a format, and the Kernel then resolves the default from its declared kind.** A DATE, TIME, or DATE_TIME declaration carrying an empty type payload is legal, and the field behaves throughout as if it declared its kind's default format: the format-less DATE carries the complete-date component set, admitted beside `yyyy-MM-dd` and refused beside `yyyy-MM` with `MVK_DATEFORMATS_NOT_COMPATIBLE`, while the format-less TIME and DATE_TIME carry the full clock and full stamp sets respectively. The resolution reads the **kind**: a format-less DATE beside a format-less DATE_TIME is refused incompatible, so the three do not share one default. What is resolved is a format *string*, not an absence — the format-string gate that `FieldValuesNotUnique` applies **admits** a format-less DATE beside a declared `yyyy-MM-dd` field while refusing that field beside a `dd.MM.yyyy` one, so the resolved default compares equal to the default spelling rather than being exempted ([checkpoint](../docs/sources/static-admission-and-class-probes.md#src-temporal-declaration-without-a-format)). The exact literal the Kernel holds is not exhibited by these rows; what they pin is its component set and its equality class at every gate measured.

Stored Date, Time, DateTime, and DateRange text is converted non-leniently against the field's declared format. A noncanonical spelling such as `2024-3-5` or `20240305` for a `yyyy-MM-dd` declaration, `14:5:0` for `HH:mm:ss`, or `1.1.2024-31.12.2024` for a fixed-width range does not normalize to a temporal value: conversion fails, the physical placement and exact text remain, and formal checking makes the cell not-check-relevant. Conversely, text that converts already has the model format, so stored temporal input has no Number-like canonicalization stage.

The temporal field-format gate is kind-independent over the measured denominator. Across a derived universe of 135 candidate strings, the kernel admits `yyyy-MM-dd`, `dd.MM.yyyy`, `yyyyMMdd`, `yyyy`, `yyyy-MM`, `yyyyMM`, `MM`, `MM-dd`, `MMdd`, `ddMM`, `HH:mm:ss`, and `yyyy-MM-dd'T'HH:mm:ss` on DATE, TIME, and DATE_TIME alike, with no kind-split candidate; the other 123 candidates are refused. This is not a closed-vocabulary claim outside that printed universe, and a wider sweep has since found one more member: over a 1,223-candidate universe that also varies a **trailing separator**, exactly one further string is admitted — `dd.MM.` — bringing the admitted vocabulary to thirteen ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-21-corrections)). The 135-candidate universe could not contain it, every candidate there having joined components and stopped. Admission is not derived compositionally from component presence: `ddMM` is admitted where `dd.MM` is refused, and `yyyyMMdd` is admitted where `ddMMyyyy` is refused. The DateRange `(format, separator)` allowlist is a separate domain and is stated in [§8](#8-date-ranges-and-overlap).

**Kind-independence reaches the computed target too, and there the format is the *whole* gate.** A computed `Time(…)` is admitted into a **DATE**-declared field whose format is `HH:mm:ss` and refused into a DATE-declared `dd.MM.yyyy` one; a computed `Date(…)` mirrors it, admitted into a **TIME**-declared `dd.MM.yyyy` field and refused into both clock-formatted targets; and a computed `DateTime(…)` is admitted into DATE- and TIME-declared fields alike whenever they carry the DateTime format, refused otherwise. All three computed temporal families obey the one rule, none carrying a kind gate of its own. **The runtime text parser follows that same declared format, and the declared kind supplies no fallback**: a DATE declared `HH:mm:ss` holding `12:30:00` is a clock reading — it counts as one value with a TIME holding the same reading — while a valid *date* text stored in that field draws `datumFormatFalsch` and leaves the cell formally invalid rather than parsing as the kind would allow. **The rule is symmetric across all three kinds**: a TIME and a DATETIME each declared `yyyy-MM-dd` count as one value with a DATE declared the same, and a clock text in the TIME-declared date field draws that same date-format cause — so the finding code names the **format** the parser applied and not the field's kind. Both arms read the same way, and a formally invalid cross-kind operand **suppresses a computation's outcome** rather than producing a cleared or errored value for it. Holding the kind fixed and varying the format flips the verdict, while holding the format fixed and varying the kind does not change it, so the declared kind does not participate in the decision at all. Every refusal is `MVK_INVALID_COMPARE_TO_DATE`. The comparison is against the declared format **as a whole** rather than any fragment of it: a `DATETIME` target declared `yyyy-MM-dd'T'HH:mm:ss` contains the clock pattern and still refuses a computed Time ([checkpoint](../docs/sources/computation-placement-and-constant-probes.md#src-computed-temporal-target-reads-the-format-not-the-kind)). **An admitted cross-kind target stores by that same declared format**, so a DATE declared `HH:mm:ss` stores `12:30:00` and a TIME declared `yyyy-MM-dd` stores `2024-03-05`, each beside its aligned same-kind control; the DATE_TIME carrier, whose format holds both component sets, was measured rather than inherited ([inbound](../docs/sources/computation-placement-and-constant-probes.md#src-datetime-carrier-stores-by-its-format)). **Neither decision can distinguish the carrier that produced the value.** Admission is the ordinary comparison gate, because a computation *is* a comparison condition whose first operand is the target's own value, and that gate reads the two operands' result formats with no access to the target's declared kind; the store is one runtime entry point shared by every computed temporal, reached from a single emitted call site with the producing expression interpolated, and it renders through the target's declared format. So the constant carrier's measured store rows and every constructed, shifted, first-filled, or addressed carrier reach the same rendering, and no carrier owes a separate row ([checkpoint](../docs/sources/computation-placement-and-constant-probes.md#src-computed-target-gate-is-carrier-invariant)).

Stored DateRange formal checking has four ordered failures. A token that does not contain the declared separator yields `datumBereichTrennerFehlt`; once the separator is present, a split other than two nonempty endpoints or a lexically or calendrically invalid endpoint yields `datumBereichFormatFalsch`; two valid endpoints with start after finish yield `datumBereichNichtGueltig`; an otherwise ordered range whose formally completed start precedes `1583-10-16` yields `datumBereichDatumFalsch` (see §8 for the distinction from endpoint completion). Equal endpoints are valid. Every failure keeps the physical placement and exact text while making a reached validation read UNKNOWN and a reached computation read poison.

An empty declared DateRange separator is a real admitted policy, not the absence of a delimiter. Under the legal `MM` plus empty-separator declaration, the stored token is split at its midpoint, so `0609` has endpoints `06` and `09`; it is not split into characters and does not yield `datumBereichTrennerFehlt`.

## 1. Constant format and the string/date literal ambiguity ⚠

Date constants are written **`DD.MM.YYYY`** (day first) regardless of locale; the decimal separator is always `.`. A **string literal that matches the date format and names a real calendar date is interpreted as a date constant**, which is why it cannot be used in string concatenation. The calendar is the legacy hybrid one, Julian before the October 1582 cutover: `"29.02.1500"` and `"04.10.1582"` are date constants, while `"05.10.1582"` through `"14.10.1582"` and `"29.02.1700"` are Strings, and a constant before the cutover is a Julian instant, so `DifferenceInDays("04.10.1582", Inception)` counts no skipped label ([inbound](../docs/sources/inbound-handbacks.md#src-inbound-2026-10-21)). Its digits are ASCII: an Arabic-Indic digit makes the shape a String. The calendar is part of the test: `"29.02.2023"` has the shape but no date, so it is a String, admitted opposite a text field and refused opposite a Date as a text is, `MVK_INVALID_COMPARE_TO_DATE` under `==` and `MVK_INVALID_TYPE_FOR_COMPARISON` under `>` ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-26d-constant-typing)):

```
"30.11." + [YearString]        -- invalid: "30.11." is read as a date
"30." + "11." + [YearString]   -- valid: the pieces don't match the date format
```

The literal is typed **by its own syntax, not by context**:

- `[StringField] == "15.06.2024"` is **rejected** (string field vs a date constant).
- a `dd.MM.yyyy` literal compares **chronologically** to a DATE field *whatever the field's stored format*, and rides in argument position: `DifferenceInDays(OrderDate, "01.01.2022")`.
- **inside a value list**, a date-looking entry stays a plain **string**.
- an **ISO-format literal** `"2022-01-01"` is lexed as a **string**, never a date.
- the constant is typed **before the comparison walk**, and the walk's arms then read it as they read a field ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-26d-constant-typing)). The boolean arm answers before the date arm, and the date arm before an Enumeration's domain is asked: `[Paid] == "05.03.2024"` draws `MVK_INVALID_COMPARE_TO_YESNO`, while `[Tier] == "05.03.2024"` and `[Tier] == Now` draw `MVK_INVALID_COMPARE_TO_DATE`. A valid date or `HH:mm:ss` literal opposite a text draws `MVK_INVALID_COMPARE_TO_DATE`, and so does a date constant ordered against a Number, both sides being orderable. Opposite a DATE_RANGE a date constant lands on the date arm, `MVK_INVALID_COMPARE_TO_DATE`, and a Number, Boolean or text constant on the range arm, `MVK_INVALID_COMPARE_TO_DATE_RANGE`. A date fragment meets the same component test as a Date: `[FiscalYear] == "05.03.2024"` and `[Season] == "05.03."` are admitted, while `[FiscalYear] == 2024` draws `MVK_INVALID_COMPARE_TO_DATE`, a number being no date constant.
- Under `==`, **`BaseYear` meets the walk's arms as a Number opposite every kind but a Date**, which takes it as the date-typed source [§7](#7-the-point-in-time-and-reference-sources) gives it, and its range endpoints meet them as a date, in either position ([checkpoint](../docs/sources/diagnostic-class-vocabulary-and-sweeps.md#src-condition-class-projection)). Opposite a String `[Note] == BaseYear` draws `MVK_INVALID_COMPARE_TO_ENUM_OR_STRING`, as an Enumeration does, labelled or not, opposite a DATE_RANGE `MVK_INVALID_COMPARE_TO_DATE_RANGE`, opposite a Time or a DateTime `MVK_INVALID_COMPARE_TO_DATE` and opposite a scale-2 Number `MVK_INVALID_COMPARE_DEC_PLACES`, while a Date and a scale-0 Number are admitted. `StartOfDateRange(BaseYear)` and `EndOfDateRange(BaseYear)` instead draw `MVK_INVALID_COMPARE_TO_DATE` opposite a String, a Number, a DATE_RANGE, a Time or an Enumeration.
- `Today` is a date of `dd.MM.yyyy` and `Now` a date-time, and a stamp literal such as `"05.03.2024T12:30:00"` is a date-time too, so the clock matters under `==` only: opposite a Date, `== Now` and `==` the stamp draw `MVK_INVALID_COMPARE_TO_DATE` while `>` the stamp is admitted, and `[Stamped] == Today` and a Time `== Now` draw the date class ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-26d-constant-typing)). A computation's constant is typed the same way (§11).
- the **omitted-year form** `"13.07."` (trailing dot) injects the model's **Base Year** (a reference year, *not* a floor). A model without a Base Year does **not** reject it outright: what a missing Base Year costs is *year agreement*, so the literal is refused only where it meets a year-bearing counterpart — a year-bearing target or comparison operand (`MVK_INVALID_COMPARE_TO_DATE`), or a year-bearing operand in a temporal operation (`MVK_DATE_WITH_AND_WITHOUT_YEAR`). An all-yearless temporal operation is admitted with no Base Year declared and resolved against a **default anchor that is a leap year**, so `DifferenceInDays("28.02.", "01.03.")` is 2 there. The anchor is otherwise exactly the declared Base Year, in both directions: the same difference is 2 under Base Year 2024 and 1 under 2023, and the rule reaches a stored yearless `MM-dd` field identically ([checkpoint](../docs/sources/temporal-constant-and-base-year-probes.md#src-yearless-anchor-is-the-base-year)). The **exact** default year is not pinned — only its leap-ness is measured, with no witness known for the year itself at a12-dmkits `c4864f70e`.
- the omitted-year form must also be a real calendar date **in a common year**, and that check never consults the Base Year: `"30.04."` is admitted where `"31.04."`, `"00.01."`, `"13.13."`, and `"29.02."` are refused, the last of these even under Base Year 2024. A model may therefore compute across a February 29 that no literal can name. Keep this apart from the **stored** yearless day bound in [§3](#3-constructing-dates-and-checking-validity) below: the literal's check consults no Base Year at all, while the stored value's does, so the two differ under a *leap* Base Year — where `"29.02."` is still refused as a literal and `02-29` is admitted as a stored value — and coincide in refusing it under a common one. The source literal and the stored value do not share a bound, and now differ in which inputs they read rather than only in the number they compare against.

A Time constant is likewise typed by its own syntax and is locale-independent: exactly eight ASCII characters in `HH:mm:ss` form, with two digits per component and a real `00:00:00`–`23:59:59` clock. A literal of any other shape is no Time constant. Opposite a Time field, short widths, other separators, non-ASCII digits, a trailing space, hour 24, and minute or second 60 all draw the one class `MVK_INVALID_COMPARE_TO_DATE` statically rather than reaching evaluation ([`kf78`](../../a12-rulekit/docs/KERNEL-FINDINGS.md#kf78), ledger (`SPEC-2026-07-27-06`)). In the pattern slot `"12:30"` is an ordinary String and admitted ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-26d-constant-typing)), and assigned to a Time target it is refused, a class the [checkpoint](../docs/sources/temporal-constant-and-base-year-probes.md#src-constant-literal-family-gate) does not record. Generated evaluation represents an admitted Time constant on 1970-01-01 in the model zone, but Time comparison and `DateTime(date, time)` observe only its decoded hour, minute, and second.

> **Non-normative implementation note.** Resolve the ambiguity in the **lexer/typer**, not the evaluator: a literal token is classified as `dateConst` iff it matches `DD.MM.YYYY` (or the omitted-year shape) and names a real calendar date, as a date-time iff it joins such a date, `T`, and a real `HH:mm:ss` clock, as `timeConst` iff it matches the exact real `HH:mm:ss` shape, and otherwise as `strConst`, with ISO date shapes always remaining `strConst`. Downstream evaluation then never has to "guess" a literal's kind. This mirrors the engine: the literal is typed by syntax.

### Comparison entry and grouping

A comparison first checks whether both operands are constants; braces preserve constantness. Such a pair is refused with `MVK_INVALID_COMPARE_TO_CONST` unless the left operand has a temporal result type and exactly one operand is an **ungrouped** `Today` or `Now`. Passing this entry gate still requires the comparison operator's remaining checks. It precedes the pattern-slot and tolerance-kind gates as well as ordinary comparison checks ([checkpoint](../docs/sources/static-admission-and-class-probes.md#src-comparison-entry-gates)).

Grouping is therefore observable at authoring: `Today == Today` is refused, `{Today} == Today` and `Today == {Today}` are admitted, and `{Today} == {Today}` is refused again. `Now` has the same grouping distinction. A bare `Today` against `"05.03.2024"` is admitted in either order, but grouping that `Today` makes the pair fail the constant gate; grouping the literal leaves its admission unchanged. Depth beyond the first brace changes nothing, because the gate counts **ungrouped** clocks rather than reading a nesting level: `{{Today}} == Today` is admitted exactly as `{Today} == Today` is, and `{{Today}} < 1` is refused exactly as `{Today} < 1` is. Which direction a group moves the verdict therefore turns on the *partner*, not on the brace: against a Number constant a group never admits — it converts the date-kind refusal into the constant one — while against another clock it always admits, at either depth.

The left temporal-type requirement makes the constant gate directional: `Today < 1` clears it and is refused later with `MVK_INVALID_COMPARE_TO_DATE`, while `1 < Today` is refused with `MVK_INVALID_COMPARE_TO_CONST`. That later refusal is **not** about clock-ness, and it is **not** directional: a date *field* on either side of a Number reaches the same gate and the same class, so `[Due] < 1`, `1 < [Due]`, `[Due] < [Amount]` and `[Amount] < [Due]` are each refused `MVK_INVALID_COMPARE_TO_DATE`, although a field operand never meets the constant gate at all ([checkpoint](../docs/sources/static-admission-and-class-probes.md#src-ordering-date-class-reads-the-pair)). The two are separable and should be implemented separately — the constant gate asks about immediacy, grouping and the left operand's result type, the date-kind gate about the pair's declared kinds. Removing braces or swapping operands before static checking is therefore not generally a legality- or diagnostic-preserving transformation, because the constant gate reads the order.

**An equality between two fields asks its kind arms in a fixed order, and only the first to refuse draws a class** ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-25e-comparison-arm-order)). The two boolean kinds' arms answer before the date's, the date's before the date range's, and the date range's before the text, Enumeration and Number arms. So a Confirm against a Date, a date range or an Enumeration draws `MVK_INVALID_COMPARE_TO_YES`, and a Boolean against a Date, a String or a Number `MVK_INVALID_COMPARE_TO_YESNO`. A Date against a date range, an Enumeration or a Number draws `MVK_INVALID_COMPARE_TO_DATE`, and a date range against a String, an Enumeration or a Number `MVK_INVALID_COMPARE_TO_DATE_RANGE`. A checker that judges each arm on its own reports two classes where the Kernel reports one.

The other temporal kinds and a custom declaration are measured at these gates too ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-25e-value-list-base-type)). A date fragment, a Time and a DateTime each order against their own kind. A fragment, a Time and a Date ordered against text, and a custom field ordered against a number, draw `MVK_INVALID_TYPE_FOR_COMPARISON`, and under a tolerance operator a DateTime against a Number and a custom field against a number draw `MVK_INVALID_TYPE_FOR_TOLERANCE_OP`. A Confirm against a fragment, a Time or a custom field draws `MVK_INVALID_COMPARE_TO_YES`, and a Boolean against a Time or a custom field `MVK_INVALID_COMPARE_TO_YESNO`.

## 2. Addition and difference are asymmetric and calendar-corrected

`DifferenceInMonths` / `DifferenceInYears` first order their endpoints, compute the **largest nonnegative whole number of months/years that can be added from the earlier date without passing the later date**, and then apply the sign of `second − first`. A reverse fractional result therefore truncates toward zero; it is not mathematical floor or a signed calendar-component count:

```
DifferenceInMonths("31.01.2010", "30.03.2010")   -- returns 1, not 2
```

Direct Day/Month/Quarter/Year and Hour/Minute/Second extraction, plus date-formatted `DifferenceInMonths`/`DifferenceInYears`, each produces a non-expandable scale-0 Number operation. **After the operand's earlier admission gates, including direct partial-Date precision for numeric extraction, the declared format's component set decides this gate, and the declared kind takes no part** — the same rule the store and the comparison gate follow. So `HoursFromTime` admits a **DATE**-declared field whose format is `HH:mm:ss` and refuses a **TIME**-declared field whose format is `yyyy-MM-dd` with `MVK_WRONG_DATE_FORMAT_FOR_OP`, `YearFromDate` does the exact opposite, and `DifferenceInYears` takes that TIME-declared date-formatted field beside an ordinary DATE field; each kind therefore appears on both sides of both outcomes, which is what rules out reading the gate off the kind ([checkpoint](../docs/sources/computation-placement-and-constant-probes.md#src-temporal-operand-family-is-the-formats-not-the-kinds)). The year position is the one component a declaration need not carry: a **declared Base Year supplies it**, so `YearFromDate` is admitted even on a pure `HH:mm:ss` field, which has no date component at all. The Base Year widens no other position. Operation-form `RoundDown`/`RoundUp`/`RoundAccounting` and `Abs` accept those results directly, including a component extracted from direct or range-selected `BaseYear`. Direct numeric `BaseYear` is likewise admitted because it is a number-like reference operation rather than an authored numeric literal. An empty temporal field or empty difference operand yields symmetric fillable zero in validation: rounding preserves both movement directions, while `Abs(0)` retains only possible magnitude growth. Direct and derived Base-Year values are fixed, and formal unavailability remains UNKNOWN in validation or poison in computation through either wrapper.

**The Base-Year supplementation reaches the completed-period difference as well as the extractor, and where it removes a gate the refusal class moves.** `DifferenceInYears` admits a yearless `dd.MM.` operand when the model declares a Base Year and refuses it `MVK_WRONG_DATE_FORMAT_FOR_OP` when it does not, while `DifferenceInMonths` over that identical operand is admitted either way **when both endpoints are yearless** — so the axis is the supplied year position, not the operand. **The partner is a second axis, and without a Base Year it answers first.** A yearless operand against a *dated* one draws `MVK_DATE_WITH_AND_WITHOUT_YEAR` at `DifferenceInMonths` when no Base Year is declared: that is the year-**mixture** gate, asked of the pair, not the unit's own operand gate. Declaring the Base Year supplies the missing year position and so removes the mixture, which is why the same mixed pair is admitted there. A grid that varies the unit and the partner together therefore reports the mixture's class as though it were the unit's, and the homogeneous rows are what separate them. The consequence a consumer must not read past is that the class is conditioned too: with a Base Year declared, a pure `HH:mm:ss` operand at `DifferenceInYears` draws `MVK_INVALID_TIME`, because the component gate that would have answered is exactly the one the Base Year disabled and the has-any-calendar-component question answers in its place; without a Base Year the same operand draws `MVK_WRONG_DATE_FORMAT_FOR_OP`, and `DifferenceInMonths` draws that class in both models. Two units of one family can therefore agree on every admitted operand and still answer different codes on a refused one, so the class is read per unit and per model and never carried across the pair. A time half refuses both completed-period units however complete the date half is — a `yyyy-MM-dd'T'HH:mm:ss` declaration is refused `MVK_WRONG_DATE_FORMAT_FOR_OP` at both — while `DifferenceInDays` admits that same instant and refuses the pure clock, each family's own missing half drawing its own code.

And addition is not the inverse of difference:

- **`AddYears`** maps the last day of February to the last day of February: `AddYears("28.02.2023", 1) = 29.02.2024`. More precisely it *corrects into* a leap year: `28.02.1999 + 1 year = 29.02.2000` (not the plain `28.02.2000`).
- **`AddMonths`** preserves the *day number* and **clamps** end-of-month overflow to the shorter month's last day, never carrying into the next month: `AddMonths("28.02.2011", 12) = 28.02.2012`; `31.01.2008 + 1 month = 29.02.2008`.
- The two therefore **disagree across a leap-year boundary** — a naive age check built on them is wrong around leap days. **Fractional offsets are truncated toward zero, not rounded, and the truncated decimal is then narrowed to the low signed 32 bits like Java `BigDecimal.intValue()`**; it is neither range-rejected nor saturated.

The same amount conversion applies to all six shifts: `AddDays`, `AddMonths`, `AddYears`, `AddHours`, `AddMinutes`, and `AddSeconds` admit an ordinary signed Number operation, truncate its reached decimal toward zero, and retain the low signed 32 bits. Overflow wraps rather than rejecting or saturating, so `4294967303` (`2^32 + 7`) shifts by `7` and `4294967296` shifts by `0`. Sub-day shifts narrow before multiplying by their unit. An empty direct Number amount contributes ordinary numeric zero; a domain-invalid amount produces no temporal value.

The calendar basis of the operand is observable, and no one calendar implementation applies to every temporal consumer. A real value produced by `Date(...)` retains the constructor's model-zone legacy hybrid-calendar identity through legal `AddDays`/`AddMonths`/`AddYears` and `DifferenceInDays`/`DifferenceInMonths`/`DifferenceInYears` consumers. Stored values, fragments, ranges, and each other operation remain governed by their separately stated clauses; this constructed-value rule does not classify them globally. A constructed-Date month/year shift whose nominal field-preserving landing lies in the missing `1582-10-05..14` cutover labels normalizes forward by ten civil labels. Thus `1582-09-10 + 1 month = 1582-10-20`, `1581-10-10 + 1 year = 1582-10-20`, and from `1582-09-10` the constructed dates 15 October and 20 October are respectively zero and one whole month away. From `1581-10-10`, 15 October 1582 is zero whole years/11 whole months away, while 20 October is one year/12 months away. The `AddYears` February-28 correction itself uses Gregorian leap status even on the Julian side: `1499-02-28 + 1 year = 1500-02-28`, although `Date("29", "2", "1500")` is constructible there.

Constructed-Date calendar shifts also retain the exact model-zone instant selected by their particular `GregorianCalendar` mutation; equal decoded labels do not imply equal results. Direct Date comparison resolves both operands to exact instants: a constructed or shifted Date supplies its retained instant, while an ordinary stored Date derives one through the ordinary model-zone parse. `Calendar.DAY_OF_MONTH` carries the source instant's offset into the nominal target and re-fits to the offset actually in force there only when the re-fit preserves the target civil date. Travel direction is not the discriminator: under `Europe/Berlin`, `AddDays(Date("30", "9", "1916"), 1)` carries CEST and lands at `1916-09-30T22:00:00Z`, while `AddDays(Date("1", "3", "1916"), 214)` carries CET into the same target label and lands at `1916-09-30T23:00:00Z`, equal to freshly constructed `Date("1", "10", "1916")`. At the repeated midnight, `AddDays(Date("30", "9", "1916"), 1) == Date("1", "10", "1916")` is therefore false, while the corresponding one-month and one-year comparisons are true. `AddMonths` and `AddYears` use sign-independent compute-time resolution: both signed month routes from 1 September/November 1916 and both signed year routes from 1 October 1915/1917 into 1 October 1916 select the later CET instant. A nominal month/year gap normalizes to its post-gap label. Calendar field mutation preserves the source millisecond except when the leap-to-nonleap February-28 correction deliberately clears the entire clock.

A date shift evaluates an operation-valued amount through the ordinary numeric-expression semantics, including authored order and directional missing provenance. Thus an empty Number field plus `1` supplies the concrete amount `1` marked not-given, while a domain-invalid expression has no amount to apply. For example, `AddDays(StartDate, RoundAccounting([x] / 0, 2))` yields a valueless Date and clears a stale Date target; it does not attach the numeric `berechnungsWertFehler` to that Date target. This is a Date-consumer projection of the invalid numeric operand, distinct from assigning the same expression to a Number target. Payload absence does not itself introduce missingness: with a present source and the fixed invalid amount `1/0`, a numeric extractor over the shift yields fixed zero, so a true comparison is VALUE. With an empty source it yields fillable zero and OMISSION.

An empty direct Number-field amount is different: the generated field read supplies numeric zero with missing provenance. When the Date/DateTime source has a value, the shift therefore retains the same concrete value but marks it not-given; a true downstream comparison fires with OMISSION rather than VALUE. The generated shift evaluates its Date/DateTime source before the numeric amount. In computation, a formal source stops before the amount; in validation, the amount is still reached and a runtime failure there can produce the authored rule’s VALUE error despite the earlier unavailable source. A cause-free empty source still reaches the amount in both phases.

A difference evaluates its first temporal operand before its second. Computation stops when the first operand is formally unavailable; validation still reaches the second operand before classifying the numeric result. A cause-free empty or unreal first result does not itself stop the second operand. This order also applies when a difference is nested in a `Having` filter. The [difference effect checkpoint](../docs/sources/temporal-runtime-fold-probes.md#src-recursive-difference-effects) measures direct, shifted and constructed first sources against a later unresolved DateTime literal for `DifferenceInDays`, in both phases and carriers; the common generated difference template supplies the unit-independent ordering account.

**Sub-day arithmetic** operates on exact integer **milliseconds since epoch**. Stored and constructed Date/Time/DateTime syntax has whole-second precision, but `Now` retains the injected validation clock's millisecond identity:

- `AddHours` / `AddMinutes` / `AddSeconds` require a date-bearing operand whose format exposes the selected time component, preserve that DateTime format, and carry across the day boundary. A Time-only operand is rejected; use `TimeFromDateTime(AddHours(dateTime, amount))` or its Minute/Second counterpart when a Time value is required.
- `DifferenceIn{Hours,Minutes,Seconds}(a, b) = (epochMillis(b) − epochMillis(a)) / unitMillis`, **truncated toward zero** — a reverse difference of −5 h 30 m is **`-5`**, not `-6`, and a `999 ms` residual is `0` seconds. Argument order is `b − a` (same as `DifferenceInDays`).

> **Non-normative implementation note.** Do not erase the operand's calendar basis. A proleptic-Gregorian total function is suitable only for a narrowed consumer/domain whose own clause or proof establishes that equivalence; a constructed-Date consumer needs a supplied legacy-calendar operation or a proof-backed supported profile. `AddMonths`/`AddYears` need the explicit end-of-month clamp and the Feb-into-leap-year correction as *code*, not as an assumed library default. The sub-day family is cleanest after resolution as `Int` epoch-milliseconds with truncating integer division (`Int.tdiv`, toward zero — **not** `Int.fdiv`).

## 3. Constructing dates, and checking validity

`Date(Day, Month, Year)` builds a date from numeric parts (also: a 2-argument form supplying the year from the Base Year, and a 4-argument `Date(Day, Month, Century, ShortYear)` form). Each explicit component may be a field, its matching direct Date extractor in the three-part form, or a quoted decimal string constant; the forms may be mixed. A bare numeric token is not a component literal: it is parsed as an entity name and rejected with `MVK_INVALID_ENTITY`. Day, Month, and complete Year admit only `DayFromDate`, `MonthFromDate`, and `YearFromDate` respectively. The extractor operand uses the ordinary nonliteral Date-expression grammar rather than only a direct field, must resolve to a value whose declared format exposes the selected component after optional Base-Year supplementation — the declared kind is not read, so a TIME- or DATE_TIME-declared field formatted as a complete date is admitted at Day, Month, and Year alike while any clock-formatted field is refused `MVK_WRONG_DATE_FORMAT_FOR_OP` — and is evaluated before its component is passed to the constructor; a direct temporal literal inside the extractor is rejected. Its literal-entry diagnostic follows the [temporal extractor operand gate](#temporal-extractor-operands). An empty extractor source therefore keeps the constructed Date incomplete, while formal unavailability remains exact. After quote removal, a constant is checked as a nonempty sequence of UTF-16 code units accepted by the host decimal-digit predicate, then parsed as an integer. Day and Month have no width restriction and accept respectively `1 ≤ value < 32` and `1 ≤ value < 13`, so leading zeroes of arbitrary length are legal. Complete Year requires exactly four code units and `1800 ≤ value < 2200`; Century requires exactly two and `18 ≤ value < 22`; Short-Year requires exactly two and `0 ≤ value < 100`. Supplementary-plane digits occupy surrogate code units and therefore fail this character-wise gate. A direct Number-field component must have effective maximum fractional digits zero—an omitted maximum passes—admit only nonnegative values by its sign policy or an explicit minimum, and have either the complete stored-length bound for its position or the positional maximum. Day accepts width 2 or maximum 31; Month accepts width 2 or maximum 12; complete Year accepts width 4 or any maximum from 1000 through 9999; Century accepts width 2 or any maximum from 10 through 99; Short-Year accepts width 2 or exactly 99. `maxIntegerDigits` is not the stored-length alternative. A direct String-field component must have maximum length equal to that positional width and either be an extensible enumeration or use exactly one of `[0-9]+`, `[0-9]*`, `\d+`, `\d*`, `[0-9]{width}`, or `\d{width}`; regex-equivalent spellings are rejected. The complete-Year position alone also accepts a temporal field whose exact declared format is `yyyy`, on any date-bearing declared kind: DATE, TIME, and DATE_TIME are admitted alike, the same field is refused at Day, Month, and either split-year position, and every other declared format is refused at Year, so the position and the format each decide admission while the declared kind decides nothing. An admitted String or `yyyy` temporal field is converted from its stored text as a Number; empty keeps the construction incomplete, formal unavailability remains exact, and a present out-of-range component reaches the constructor's unreal-date check rather than being clamped. The four-part form rejects extractors in either split-year position, evaluates Day, Month, Century, then Short-Year, and requires the narrowed Century to be nonzero before forming the year as `Century × 100 + ShortYear`; a present zero Century makes the Date unreal even when Short-Year is positive; a fixed Short-Year zero is present, while an unfilled field or extractor result keeps the construction incomplete. Quoted constants are fixed present inputs and never read document state. `Time(...)` and `DateTime(...)` construct the corresponding values. A constructed date is **invalid** if any referenced part is unfilled, or the parts don't form a real calendar date (`Date("31", "11", "2000")` — November has 30 days; or 30 February).

The extensible-String alternative is a client-interface capability of a String declaration, distinct from an Enumeration declaration; the DM-JSON model format does not expose that flag. Its width requirement remains exact, but it need not carry a digit pattern. Constructor field conversion therefore cannot assume unsigned integer text: it accepts the Java decimal spellings, including a leading sign, leading or trailing decimal point, exponent, and BMP decimal digits, with comma normalized to dot before conversion. Conversion then truncates toward zero and retains the low signed 32 bits. For example `+1` contributes 1, `.5` contributes 0, `2e3` contributes 2000, and `3e9` contributes −1294967296; the declared component width still bounds which tokens can reach a particular position. A nonnumeric token that passed the String's formal checks raises a runtime conversion failure rather than producing an empty component or an unreal date. This account is source-grounded; the client-interface runtime matrix remains external evidence pending ([construction source](../docs/sources/temporal-and-message-probes.md#src-temporal-construction-route)).

A fully present Date must also resolve to a strict host-calendar instant within signed 64-bit milliseconds. A year beyond that range is unreal, not a conversion failure; there is no four-digit runtime year ceiling. For example, an extensible Year `2e8` can construct a real date whose spelling subsequently fails the target's formal format, while `3e8` and `2e9` produce unreal dates. This range distinction is source-grounded and checked against the JDK 21 calendar primitive, not a kernel runtime capture.

Date and Time evaluate their supplied arguments in authored order. In validation, an earlier formally unavailable component does not stop later argument conversion: a later nonnumeric extensible String still raises the enclosing rule's runtime failure, even if the normal result would have been UNKNOWN. Computation instead stops when its field read encounters formal poison. A cause-free non-relevant extractor component does not stop a Date computation from reading later components: a later formal poison still wins. If no later failure intervenes, construction retains non-relevance, so an enclosing `Min` does not substitute its concrete fallback ([component checkpoint](../docs/sources/temporal-runtime-fold-probes.md#src-recursive-date-components)). If no argument throws, formal unavailability and missing-component provenance retain the ordinary constructor meaning. Boolean short-circuiting still decides whether the constructor is reached at all ([rule failure boundary](10-validation-and-polarity.md)).

`Time()` through `Time(Hour, Minute, Second)` supply a leading prefix of zero to three components; every omitted trailing component is the fixed value zero, so `Time()` is midnight and `Time("10", "30")` is `10:30:00`. It is the one call measured whose whole argument list may be empty ([§12](12-concrete-syntax.md#3-the-condition-and-operation-grammar-sketch), [inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-26o-production-close)). Each authored component is statically restricted to its matching field, extractor, or in-range decimal-digit string constant before runtime conversion, and those forms may be mixed across positions. A Number field must have effective maximum fractional digits zero (an omitted maximum passes), admit only nonnegative values by its sign policy or an explicit minimum, and have either maximum stored length 2 or the exact positional maximum (23 for Hour and 59 for Minute or Second); `maxIntegerDigits = 2` is not the stored-length alternative. Admission does not make every stored spelling usable: under the maximum-length-2 profile with no minimum, `5` produces the padded clock component `05`, while stored `"05"` is rejected as `zahlHatFuehrendeNullen` and clears the target. Adding minimum stored length 2 also rejects the unpadded single-digit value as too short, so that combined profile admits the declaration but cannot represent a valid single-digit component. A String field must have maximum length 2 and either be an extensible enumeration or use one of the checker-recognized digit-only patterns `[0-9]+`, `[0-9]*`, `\d+`, `\d*`, `[0-9]{2}`, or `\d{2}`; unlike Number, this carrier accepts and converts `"05"`. An extractor must be `HoursFromTime`, `MinutesFromTime`, or `SecondsFromTime` at the matching component position. Its operand is the ordinary nonliteral temporal-expression grammar, not only a direct field: the source may be any statically admitted Time- or DateTime-bearing expression that exposes the selected component, while a direct temporal literal inside the extractor is rejected. The nested temporal source is evaluated before the extractor call. An empty source therefore reaches the constructor as numeric zero with missing provenance and still makes the constructed Time incomplete; a present temporal expression that yields no value reaches the constructor as fixed numeric zero instead, while formal unavailability remains exact. At runtime a formally unavailable/non-relevant supplied component dominates missingness, a missing supplied component produces an incomplete/not-given no-value, and a fully present but impossible clock produces a distinct present/unreal no-value. `DateTime(date, time)` evaluates Date before Time, retains those Time-side reasons, gives non-relevance precedence over ordinary no-value after both operands are reached, and resolves a real combined wall label in the model zone.

A present clock field, `Time(...)` value, or result of `TimeFromDateTime(...)` carries the date anchor 1970-01-01. If the model declares a Base Year, `YearFromDate` is statically admitted over these Time-valued expressions, but its result is **1970**, even when the configured Base Year differs. That Base Year exemption opens the component-admission gate; it does not replace the constructor's anchor. Missing, unreal and formally unavailable sources retain the ordinary numeric-extractor rules above. This distinction is source-grounded in the [component checker](../../a12-kernel/kernel-tool/kernel-core-parser/src/main/java/com/mgmtp/a12/kernel/core/parser/internal/check/util/DateUtils.java), [Time construction](../../a12-kernel/kernel-rt/kernel-core-runtime/src/main/java/com/mgmtp/a12/kernel/core/rt/_30_8/internal/util/DateUtil.java), and [runtime projection](../../a12-kernel/kernel-rt/kernel-core-runtime/src/main/java/com/mgmtp/a12/kernel/core/rt/_30_8/internal/core/RuntimeController.java); the [reviewed handback](../docs/sources/inbound-handbacks.md#inbound-2026-10-09-extensions) corroborates the clock-field and both constructed-Time forms on both Kernel strategies.

`TimeFromDateTime(source)` requires a DateTime operand whose declared or derived format contains Year, Month, Day, Hour, Minute, and Second. A valueless source is returned with its not-given or non-relevant reason unchanged. For a present source, the operation reads Hour, Minute, and Second in the model zone and constructs a Time value anchored at 1970-01-01; downstream Time consumers therefore observe the retained wall clock, not the source Date or exact instant. When used as the Time argument of `DateTime(date, time)`, the outer constructor still evaluates its Date argument before evaluating this extraction.

`DateFromDateTime(source)` is its Date-valued sibling and requires the same **complete** DateTime operand. It reports the source label's **own** date components with the time dropped: a stored `2024-06-15T00:30:00` extracts to `2024-06-15`, and converting the retained instant to UTC first — which would give `2024-06-14` at a `+0200` model zone — is measured wrong. The result is a **Date**, not a DateTime: it compares against a Date field, against `Today`, and against another `DateFromDateTime`, and it is admitted as a Date-addition operand, while comparing it to `Now` or to a `TimeFromDateTime` result is rejected `MVK_INVALID_COMPARE_TO_DATE`. A valueless source is returned with its not-given or non-relevant reason unchanged. Across the measured `YearFromDate` and `DateFromDateTime` carriers, Number, String, Enumeration, Boolean, Confirm, DateRange, and Custom operands are rejected with `MVK_NO_DATE`; UNKNOWN has no authorable A12 counterpart in this denominator. A temporal declaration whose format lacks the requested component is instead rejected with `MVK_WRONG_DATE_FORMAT_FOR_OP`, measured by `HoursFromTime(Date)` and `DateFromDateTime(Date)` against admitted component-bearing controls. The declared format, not the field kind, decides this temporal capability — measured on cross-kind declarations with each kind on both sides of both outcomes, so it is the gate rather than a gloss on same-kind rows ([§2](#2-addition-and-difference-are-asymmetric-and-calendar-corrected)) — and this two-carrier diagnostic matrix does not establish the unmeasured extractors. The [temporal extractor operand gate](#temporal-extractor-operands) distinguishes field paths, direct literals, and nested expressions. Neither component extractor has a sibling-parallel repeatable spelling in the measured `Projects/Choices` to `Projects/Tasks` topology: for both `DateFromDateTime` and `TimeFromDateTime`, relative and absolute `Choices*/Stamp` operands are refused at the extractor with `MVK_NO_WILDCARDS_ALLOWED`, while removing the star from the otherwise identical paths is refused with `MVK_NO_WILDCARD`. This is a static authoring boundary and does not transfer to the separately admitted sibling-star `FirstFilledValue` family.

<a id="temporal-extractor-operands"></a>

`DateFromDateTime` and `TimeFromDateTime` accept temporal expressions, including `Now` and a complete quoted DateTime literal such as `"05.03.2024T10:30:45"`. Field operands use bare paths; bracketing a field is a parse failure. Literal recognition precedes the extractor-specific gate: text that parses as no temporal value reports `MVK_INVALID_DATE_STRING`, while a recognized Date-only or Time-only literal under either DateTime projection reports `MVK_WRONG_DATE_FORMAT_FOR_OP`. A recognized complete DateTime literal is admitted by both projections.

Numeric component extractors instead reject every recognized direct temporal literal with `MVK_NO_CONST`, even when its temporal kind differs from the selected extractor. Thus `HoursFromTime("01.01.2020")` reaches the constant-position refusal, while `HoursFromTime("2019-01-01")` fails literal recognition first. Nested expressions retain a different admission boundary: `DayFromDate(DateFromDateTime(Now))` and `HoursFromTime(TimeFromDateTime(Now))` are admitted, as are those same nested forms with the complete DateTime literal replacing `Now`. A transformation must preserve the distinction between a direct literal and a nested expression at a numeric extractor's immediate operand.

**Within the measured 135-candidate denominator, a declaration's format string rather than its field kind determines admission and the retained stored-input outcomes.** Every one of the twelve formats in the measured candidate partition above is admitted on every temporal kind, including `HH:mm:ss` on DATE and DATETIME, `yyyy-MM-dd` and `dd.MM.yyyy` on TIME, the fragment format `MM` on TIME, and the ISO datetime format on DATE, each persisted exactly as declared. The denominator measured here is DATE, TIME and DATE_TIME; **DATE_FRAGMENT, which declares its format under its own `formatOfFragment` key and so sat outside that grid, answers the same way** and is established by the peer's measurement rather than by extension from these rows ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-21-corrections)). A refused candidate fails at the model level as an invalid date format however natural it looks for its kind; a TIME field is refused `HH:mm` while being admitted `yyyy-MM-dd`. Each kind does have a single *default* (`HH:mm:ss` for TIME, `yyyy-MM-dd'T'HH:mm:ss` for DATETIME), but a default is not a restriction. One string is a specific trap: the day-first **`dd.MM.yyyy'T'HH:mm:ss`** is refused on every kind, even though the kernel does define it for DateTime-valued **expressions** such as `Now`, the `DateTime(...)` constructor, and a DSL constant. The degenerate case below is one instance of the measured kind/format freedom, and a consumer must not infer a component set from a field's kind.

A DATE field may be declared with eight **component-omitting** formats beside the three complete ones: `yyyy`, `yyyy-MM`, `yyyyMM`, `MM`, `MM-dd`, `MMdd`, `ddMM`, and `dd.MM.`; the complete formats are `yyyy-MM-dd`, `dd.MM.yyyy`, and `yyyyMMdd`. **The eighth is the German short date with its closing dot, and the dot is load-bearing** — `dd.MM.` is admitted on DATE, TIME and DATE_TIME alike and as a `formatOfFragment`, while `dd.MM` without it stays refused on all of them, so a format's trailing separator is part of the string and a vocabulary derived by joining components and stopping cannot produce this member ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-21-corrections)). It is year-free, so it joins `MM`, `MM-dd`, `MMdd`, `ddMM` and `HH:mm:ss` in refusing the 1900 additional check with `MVK_ADDITIONAL_CHECK_INVALID`, on the DATE and DATE_FRAGMENT carriers alike. The DateRange `(format, separator)` allowlist is unaffected and stays at eight pairs: no trailing-separator format is admitted there with any separator. A component-omitting field's stored text is shorter than a complete date and its value denotes an **interval** or a yearless calendar position: a whole calendar year for `yyyy`, a whole month for the two year-month spellings, and a month/day position for the four yearless spellings. A parse or calendar-reality failure reports the format finding. Formal checking first completes the declared format: year-bearing formats supply January and/or day one; day-and-month formats append the model Base Year (default 2000); month-only checking uses the parser’s default year 1970, independently of the model Base Year. The resulting date is subject to the position checks. Thus `yyyy` value `1583`, `yyyy-MM` value `1583-10`, and `MM-dd` value `01-01` under Base Year 1583 report `datumFalsch`; `MM` value `01` remains admitted under that Base Year. The format-completion mechanism is source-backed; these floor discriminators are retained on both engines ([calendar checkpoint](../docs/sources/temporal-runtime-fold-probes.md#src-calendar-expression-family)). Separators and component order are exact: `yyyy-MM` rejects `202006`, `yyyyMM` rejects `2020-06`, `MMdd` rejects `06-15` and reads `0611` as month 6/day 11, while `ddMM` rejects `15-06` and reads `0611` as day 6/month 11. Runtime completion is separate from formal completion: a yearless value receives the model Base Year when read for calculation, and **its day bound follows whether the model declares a Base Year.** With none declared no year is available to decide leapness, so the bound is the month's **greatest possible** day with February at 29: `04-31` and compact `3104` are rejected, while `04-30`, `02-29`, compact `0229`, and day-first compact `2902` are accepted. This is the same yearless day bound the DateRange overlap rule uses. **With a Base Year declared the bound is that month's length in that year**, so the identical `02-29` cell is admitted under Base Year 2024 and formally invalid — `datumFormatFalsch`, at the cell — under Base Year 2023, on models differing in nothing but that field; the leap and undeclared configurations agree, which places the difference in the declared year's leapness rather than in declaring one at all ([checkpoint](../docs/sources/temporal-constant-and-base-year-probes.md#src-yearless-day-bound-reads-the-base-year)). February is the only month whose two answers differ. One consequence is worth stating because it closes a question rather than opening one: no legal document can present an operator with a yearless value its own Base Year cannot complete, since the refusal is at the cell. It is **not** the bound a yearless source *literal* gets: `"29.02."` is refused as a literal on every carrier, including under a leap Base Year, so the stored value admits a February 29 the literal cannot spell ([§1](#1-constant-format-and-the-stringdate-literal-ambiguity-)). These formats compare through the **ordinary** direct-comparison gate with no special rule: component sets need not agree, so a `yyyy` operand compares with a `yyyy-MM` one and with a complete date, while a yearless operand is rejected `MVK_INVALID_COMPARE_TO_DATE` against any year-bearing one unless the model declares a Base Year to supply the year. **That gate reads the declared format's family and not the field's declared kind, which is the same rule a computed target follows** ([`spec/09`](09-computations.md)) and it extends to reading a cell as a value: a DATE-declared field whose format is `HH:mm:ss` compares with a TIME field and is refused against a `yyyy-MM-dd` DATE, while a TIME-declared field whose format is `yyyy-MM-dd` does the exact opposite, each kind appearing on both sides of both outcomes ([checkpoint](../docs/sources/computation-placement-and-constant-probes.md#src-temporal-value-family-is-the-formats-not-the-kinds)). **The DATE_TIME family behaves the same way and is measured separately rather than inherited:** a DATE declared `yyyy-MM-dd'T'HH:mm:ss` compares with a DATE_TIME and is refused against a DATE, a DATE_TIME declared `yyyy-MM-dd` does the exact opposite, and the two ordinary fields refuse each other as the control — so the rule holds across all three date-bearing kinds with each kind on both sides of both outcomes in every family ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-05d)). Equality is the measured operator throughout; only equality requires the two formats to agree on time presence, so a cross-kind pair equality refuses may still be **ordered**. So a temporal cell's **value family** is its format's throughout — admission, the store, and comparison — and an implementation keying the cell's admitted payload on the declared kind marks a cell the Kernel stores and compares as formally invalid, which is a wrong value rather than a wrong diagnostic. The gate is year presence after that supplementation, not format identity. Empty stored text is present and value-free on every one of these formats.

**Computed component-omitting targets are checked after rendering.** The target format can discard the expression’s year, so target checking uses the same format-specific formal completion as stored input. Under Base Year 1583, a month/day shift reaching January 1584 still renders `01-01` and is rejected after completion back into 1583; the month-only target remains admitted. A literal `"29.02.2024"` assigned to `MM-dd` under Base Year 2023 retains an errored `02-29` attempt and poisons its dependent; the identical assignment under Base Year 2024 succeeds. Year/year-month targets reject five-digit attempted years as format failures. Arithmetic itself keeps the intermediate calendar result, including below-floor dates, so returning it to the storage range before assignment succeeds ([calendar checkpoint](../docs/sources/temporal-runtime-fold-probes.md#src-calendar-expression-family)).


A DateTime field may legally be declared with the degenerate **time-only** format `HH:mm:ss`, and such a field is fillable and comparable but is admitted as an operand almost nowhere. Every temporal operation that reads a component refuses it while the identical condition on an ISO-declared sibling is admitted, and the refusals are **three distinct classes** rather than one gate: the component extractors including `TimeFromDateTime` and `DateFromDateTime` draw `MVK_WRONG_DATE_FORMAT_FOR_OP`, `AddHours` and `DifferenceInHours` draw `MVK_INVALID_TIME`, and comparison against `Now` draws `MVK_INVALID_COMPARE_TO_DATE`. **The kernel wants a complete DateTime for all of them, including the time extractor**, which the format does carry; the natural reading that what the format retains is usable and only what it omits is refused is therefore wrong, and it is the same requirement that makes `TimeFromDateTime` refuse a plain Time field. `FieldFilled` and equality against a same-format sibling are admitted, which is what keeps the refusals from being satisfied equally by a field that is simply dead.

```
Invalid(Date(Day, Month, Year))   -- fires on 31.11, 30.02, an unfilled part, …
```

`Valid(Date(...))` and `Invalid(Date(...))` require at least one immediate component entity, including an index-selected entity. A field nested inside an extractor does not satisfy this gate: all-constant and all-extractor constructions are refused with `MVK_ONLY_CONSTANTS_USED`, in validation and computation guards alike. This predicate gate does not restrict ordinary scalar Date construction ([checkpoint](../docs/sources/temporal-runtime-fold-probes.md#src-recursive-date-validity)).

**The truth projections of `Valid` and `Invalid` are strong-Kleene complements, but one full verdict does not determine the other**, because the construction has reason-bearing non-values:

- An **unreal `Date(...)` carries no date value** — it does *not* roll over and does *not* keep an out-of-range label. Its direct numeric date/time extractors and date differences nevertheless produce the actual Number **`0`** with fixed/present provenance. An incomplete construction also produces `0`, but retains not-given/fillable provenance; a fired comparison can therefore be VALUE for unreal input and OMISSION for incomplete input even though the numeric amounts agree. A malformed/formally unavailable construction projects to UNKNOWN instead, never to zero.
- `Valid(Date(...))` = all parts present ∧ well-formed ∧ the date is real → fired **VALUE**.
- `Invalid(Date(...))` = parts well-formed ∧ (not real ∨ some part empty). Its polarity is **directional**: an empty fillable part → **OMISSION**, a present-but-unreal date → **VALUE**. It even fires on an **all-empty** row.
- A **malformed** part suppresses **both** predicates (each goes UNKNOWN; the formal error fires instead). This is the UNKNOWN/UNKNOWN arm of strong-Kleene complementation, not ordinary Boolean false.
- A cause-free non-relevant component also suppresses both predicates. In a computation alternative guard, either predicate falls through to the next alternative; as a common guard, either clears the target without poisoning its dependents. A later formally invalid component still wins over earlier non-relevance and poisons the computation and its dependent reads ([checkpoint](../docs/sources/temporal-runtime-fold-probes.md#src-recursive-date-validity)).
- The decisive non-law is at the full verdict/polarity level: incomplete and unreal constructions both make `Valid` not fire, but `Invalid` must recover **OMISSION** for incomplete and **VALUE** for unreal.
- To fire `Invalid` **only** on a complete-but-impossible date, prefix `AllFieldsFilled(...)`.

The constructor's **calendar-reality test is model-zone-sensitive and uses the legacy hybrid calendar**, not an abstract proleptic-Gregorian `LocalDate`. Kernel 30.8.1 creates a non-lenient `GregorianCalendar` in `modelConfig.timeZone`; the default cutover uses Julian rules before the Gregorian transition, and a zone discontinuity can remove a complete local date. Consequently, UTC `Date("29", "2", "1500")` is real under the Julian side of that calendar, while `Date("30", "12", "2011")` is unreal in `Pacific/Apia` because that local date was skipped. This is separate from the later 1583-10-16 stored/computed-value floor. The zone database is a runtime input not identified by the kernel behavior version alone. A portable implementation must reproduce the pinned legacy calendar, zone, and zone-data behavior or fail closed outside its explicitly supported calendar domain; substituting a zone-free proleptic-Gregorian predicate is not equivalent.

The reason and calendar basis compose through legal temporal producers rather than being rediscovered at each leaf:

- A Date- or DateTime-valued operation carries either a concrete value with its calendar/instant identity or a no-value reason. Incomplete/not-given, present-but-unreal, and non-relevant/malformed provenance must remain distinguishable; non-relevant dominates when a `DateTime(date, time)` combines it with a check-relevant no-value.
- These dimensions also apply to Time construction: a fixed impossible clock has no payload with fixed provenance; an empty component has no payload with missing provenance. Operand-list extrema can select their other value while retaining that distinction. An unknown-year partial-Date interpretation remains non-relevant, rather than neutral absence.
- `DateTime(date,time)` evaluates its arguments in authored order. Computation poison aborts before later arguments; clean absence and cause-free non-relevance do not. Combining a Date and Time into a nonexistent Berlin spring-gap label yields clean no-value, whereas resolving that label as a DateTime literal raises a computation value failure. The retained autumn-fold construction chooses the later occurrence, observed by adding one hour to reach 03:30. These distinctions are measured at the [composition checkpoint](../docs/sources/temporal-and-message-probes.md#src-value-as-date-locus); they do not generalize the pinned profile to other zones.
- `DateFromDateTime`, `TimeFromDateTime`, and legal `Add*` descendants preserve the source no-value reason. Real `Date(...)` descendants preserve the legacy-calendar identity described in §2.
- Numeric component extractors and date differences map incomplete/not-given and present-but-unreal operands to the same amount `0`, but retain fillable versus fixed provenance respectively; they map a non-relevant operand to UNKNOWN.
- The direct date-component family is `DayFromDate`, `MonthFromDate`, `QuarterFromDate`, and `YearFromDate`. For a real source, the quarter is `((month - 1) / 3) + 1` with integer division; the numeric-zero projection of an incomplete or unreal source remains `0` for Quarter just as it does for the direct components.
- After earlier source and partial-precision gates, direct component extraction requires the declared format to carry the selected unit's component letter; the declared kind takes no part in this format gate: Day needs `d`, Month and Quarter need `M`, Year needs `y` unless model Base Year supplies it, Hours/Minutes/Seconds need `H`/`m`/`s`, and the split family `DateFromDateTime`/`TimeFromDateTime` needs a date letter **and** a time letter, which over the admitted vocabulary only `yyyy-MM-dd'T'HH:mm:ss` carries. Failure of this format gate is `MVK_WRONG_DATE_FORMAT_FOR_OP`. **An earlier version of this line added "Date extractors accept Date or DateTime; time extractors accept Time or DateTime", which contradicts the format rule §2 states and is wrong**: over a 108-cell grid at fixed DATE kind, `HoursFromTime` is admitted on the one field declared `HH:mm:ss`, and `DayFromDate` is refused on `yyyy-MM` while admitted on `yyyy-MM-dd` — two formats a three-valued shape classifier cannot tell apart, so the gate is the component set and not the format's shape either. The letters are case-sensitive: `MinutesFromTime` is refused on `MM` and admitted on `HH:mm:ss`. A fourth kind participates on the same rule — a DATE_FRAGMENT declared `yyyy` admits `YearFromDate` and refuses `MonthFromDate` — and a field whose declaration is **absent** answers as its kind's default format allows ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-21-corrections)). **That default extends past fields to every operand carrying no declaration of its own** ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-21b-corrections)): the point-in-time constants `BaseYear`, `Today`, and `Now`, and the derived temporal operands `AddDays`, `AddHours`, `DateFromDateTime`, `TimeFromDateTime`, and `StartOfDateRange`, each admit exactly the extractors their kind's default format carries. `FirstFilledValue`, the temporal extrema, and `ValueAsDate` never reach this gate at all, the parser refusing each in an extraction slot. The separate partially-known Date precision gate runs before format and Base-Year supplementation: `DAY_OPTIONAL` rejects Day, `MONTH_OPTIONAL` rejects Day/Month/Quarter, and `YEAR_OPTIONAL` rejects every date-component extractor. All three partial precisions also reject Hours/Minutes/Seconds. These refusals are `MVK_INVALID_DATE_TYPE`; a Base Year does not waive them. The gate applies equally to a direct or key-selected partial field, while `DateFromDateTime` and `TimeFromDateTime` ask their separate format gate without this numeric precision test ([reviewed handback](../docs/sources/inbound-handbacks.md#inbound-2026-10-09-extensions)).
- Direct date `Min`/`Max` skips check-relevant valueless operands when another concrete value exists; a non-relevant operand propagates non-relevance. This consumer admission does not widen the grammar: a result such as `YearFromDate(Min(...))` remains authoring-rejected where the extractor requires a narrower source form.
- Operand-list `Min`/`Max` and field-list/star `MinValue`/`MaxValue` also admit homogeneous TIME operands or homogeneous full-component DATETIME operands whose declared formats expose comparable component sets. Time selection compares each decoded time-of-day coordinate; DateTime selection compares each resolved physical instant, not its rendered wall label. In both families, check-relevant valueless operands are skipped, an all-empty selection has no value, any reached non-relevant operand propagates non-relevance, and an empty, omitted-tail, or encountered-filter source retains symmetric missing provenance on a selected value. A seconds-level Time difference therefore remains ordered even when a shorter display omits it, and an exact selected DateTime instant remains distinct from an equal-looking stored value on the other side of a model-zone overlap.
- A Date declaration may carry a **date precision** — `DAY_OPTIONAL`, `MONTH_OPTIONAL`, or `YEAR_OPTIONAL` — making it a *partially known date* whose unspecified components are stored as literal `00`. Precision is independent of the declared component set: a `dd.MM.yyyy` declaration exposes all three date components and may still be partially known, so an operand gate reading components alone cannot see it.
- **A partially known date is refused as an operand of `MinValue`/`MaxValue` and of `NumberOfDifferentValues`, on every precision, `MVK_PARTIAL_DATE_NOT_ALLOWED`** — while `FieldValuesNotUnique` and `FirstFilledValue` **admit** every precision. The denominator is the family's **five** field-list operators and the split is three against two, measured in one model with `datePrecision` the only variable across the refused rows and a full-precision control admitted at all five carriers ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-07-dispositions)). The split follows what each operator does with the value: the three refusing carriers compare the decoded date, which a partial has not, while uniqueness compares the exact stored text and first-filled merely selects a cell, so neither decodes. **The refusal is asked inside the per-operand date walk**, after duplicates, the root gate and arity: a partial leader beside a repeated field reports the duplicate class and one alone the arity class; a partial date and a component mismatch answer by position, so `(DATE, yyyy-MM DATE, partial)` reports `MVK_DATEFORMATS_NOT_COMPATIBLE` and its swap `(DATE, partial, yyyy-MM DATE)` this class; and a list whose leader is not date-like is asked only the kind question, so `MaxValue(Title, ApproxDay)` reports `MVK_NOT_SORTABLE` and `NumberOfDifferentValues(Label, ApproxDay)` `MVK_STRING_ENUM_AND_NON_STRING_ENUM` ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-23b-entity-list-operand-reads)). The walk reads a group operand's fields: behind a Date leader a group holding a non-date field draws `MVK_DATE_AND_NONDATE` and one of `yyyy-MM` Dates `MVK_DATEFORMATS_NOT_COMPATIBLE` ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-26i-expansion-order)). `ValueAsDate` is the inverse gate, requiring a partially known source and refusing a fully known one `MVK_INVALID_DATE_TYPE_FOR_OP`; it is the designated route from a partial to a concrete date, selecting the earliest or latest completion.
- Among the direct component extractors, `DayFromDate` refuses a partially known source outright, while `MonthFromDate`, `QuarterFromDate` and `YearFromDate` admit one at `DAY_OPTIONAL`. Upstream prose lists restrictions for these four constructs only; the extrema and distinct-count refusals above are measured and are not in that list, so it must not be read as the complete set of operators that gate on precision.

Temporal format admission deliberately has two strengths. A direct comparison requires matching year presence unless the Base Year supplies `YEAR`, and requires both formats to contain some date component or neither; only `==` and `!=` additionally require both formats to agree on whether they contain any time component. It does not require identical component sets: ordering admits `yyyy-MM` against `yyyy-MM-dd`, Date against DateTime, and `HH:mm` against `HH:mm:ss`, while equality rejects only the Date/DateTime pair among those examples. The `HH:mm` half of that illustration is **not authorable**: the Kernel refuses that format string on a `TimeType`, a `DateType`, and a `DateTimeType` declaration alike, against an admitted `HH:mm:ss` control ([checkpoint](../docs/sources/temporal-and-message-probes.md#src-temporal-operation-granularity-separability)). The rule above is stated as the total function it is, because a reimplementer needs it either way and the gate itself does not consult authorability; the example simply names a component pair no legal model reaches. Every admitted time-bearing format carries all three clock components at once. Temporal operand-list and field-list extrema are stricter: after optional Base Year supplementation their complete six-component sets must be identical, and a DATETIME extremum requires all year/month/day/hour/minute/second components.

`Valid(Field, "CustomTypeName")` and `Invalid(Field, "CustomTypeName")` are the other forms, and no third parses: a lone field, Date field or not, a third operand after the type name, and any single call but `Date(...)`, such as `AddDays(...)` or `DayFromDate(...)`, draw `MVK_UNEXPECTED_TOKEN` ([inbound](../docs/sources/inbound-handbacks.md#src-inbound-2026-10-18)). Static model checking requires a single non-wildcarded value-validation **field** operand whose declared type is String, Enumeration, or extensible Enumeration, and a nonempty type name; it does **not** require registry membership. Each arm has its own diagnostic: a Number, Boolean, Confirm, or **Custom**-declared operand draws `MVK_NO_STRING_OR_ENUM_OR_EXT_ENUM`, a group draws `MVK_NO_GROUPS_ALLOWED`, and a **starred** operand draws `MVK_NO_WILDCARDS_ALLOWED` — while an **unstarred repeatable** operand unbound by its host draws the ordinary `MVK_NO_WILDCARD` instead, so this position carries the same confusable pair the `DateRange` endpoints do and the two have opposite fixes. A Custom-declared field being refused is worth stating on its own: the predicate asks whether a String or Enumeration *value* is a valid instance of a named type, not whether a field already declared as that shape is ([checkpoint](../docs/sources/static-admission-and-class-probes.md#src-validtype-operand-gates)). With a registered validator the two predicates are complementary for a filled value and neither fires for an empty value. An unregistered name is degenerate rather than rejected: both predicates fire for a filled field, each as an ordinary rule message carrying VALUE polarity at the concrete error address, and neither fires for an empty field. The value-specified gate therefore decides before any registry contact, so registration state cannot influence an unspecified value, and the two states in which no usable validator exists — no factory supplied at all, and a factory present that returns nothing for the name — are indistinguishable.

> **Non-normative implementation note.** A bare `Option CalDate` is insufficient: its `none` would collapse incomplete, unreal, and non-relevant constructions even though validity, numeric polarity, and later temporal composition distinguish them. Use a reason-bearing result such as `real (calendarBasis, CalDate) | incomplete | unreal | unknown`, define the two validity verdict projections separately, and give each consuming operation an explicit projection. Their truth projections complement under strong Kleene; `Invalid` is not a unary function of the full `Valid` verdict.

## 4. The Gregorian floor

**Dates before 16 October 1583 are invalid — as stored or computed *values*.** The floor is always-on and exact:

- strict *before*: `1583-10-15` errors, `1583-10-16` is valid;
- a day-optional value completes its omitted day to `01` **before** the check;
- a stored value is first judged real on the legacy hybrid calendar, so a real label below the floor draws the floor's `datumFalsch` and an unreal one the format's `datumFormatFalsch`: `1500-02-29`, `1300-02-29` and `1582-10-04` draw `datumFalsch`, while `1582-10-05`, `1582-10-14` and `1700-02-29` draw `datumFormatFalsch`, and a date range's start the range's own pair of codes ([inbound](../docs/sources/inbound-handbacks.md#src-inbound-2026-10-21));
- a **stored** value below it is the formal error `datumFalsch` (suppressing referencing rules, [§3](02-logic-and-formal-errors.md)); a **computed** one is **ERRORED**; a date **range** floors its *start* the same way.
- It is distinct from the *opt-in* "younger than 1900" additional check.

`DateType.youngerThan1900Check` is a separate opt-in, declaration-owned basic-format check, independent of Date precision and the always-on Gregorian floor. **It is declarable only where the declared format carries a year.** A DATE declaration whose format omits the year — `MM`, `MM-dd`, the compact yearless spellings, or a clock format — is refused at model admission with `MVK_ADDITIONAL_CHECK_INVALID`, and the Kernel's own message names the reason in component terms rather than in kind terms: *for date fields without a year, no additional check may be specified*. The check is not a property of a TIME or DATE_TIME declaration at all: those declaration objects carry a format and annotations and nothing else, so injecting it is rejected by the model deserializer one layer before any consistency gate, naming the declaration type and the property. **Two further declaration kinds carry the check, and they do not agree with each other.** A DATE_FRAGMENT declaration behaves exactly as DATE does — over the twelve admitted fragment formats the five year-free spellings are refused and the seven year-bearing ones admitted — while a DATE_RANGE declaration is **exempt**: all eight admitted `(format, separator)` pairs take the check, the four year-free pairs included. So the year co-requirement is a property of the DATE and DATE_FRAGMENT carriers rather than of the check, and a consumer that enforces it uniformly across the temporal kinds refuses four legal range declarations ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-08)). So a consumer must gate the check on year presence and must not model it as admitted-and-inert anywhere ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-05c)). When enabled, a concrete Date strictly before `1900-01-01` is the formal error `datumFalsch`; `1900-01-01` is valid. Ordinary partial-Date completion and reason preservation happen before this check, so an unknown-year value remains non-relevant rather than being reclassified as an ancient concrete date. The same declared gate classifies an admitted computed FULL-Date target as described in [§11](09-computations.md); partial Date computation targets remain statically rejected and do not create another runtime case.

⚠ The floor is **not** a runtime criterion for the `Date(...)` **construction**. The floor gates stored and computed *values*, not the constructor's reality test. Static component admission and the immediate-entity requirement for validity predicates apply separately.

Also: **a date value is stored and formal-checked in its field's declared `format`, not a canonical wire format** — the same calendar date is well-formed in one field and `datumFormatFalsch` in another. A consumer must read each field's `format` to parse its dates.

## 5. Time zones and the sub-day difference

`DifferenceInHours/Minutes/Seconds` is **absolute-instant subtraction** — `floor(|instant₂ − instant₁| / unit)`, sign from operand order — under the normative Groovy-dynamic behavioral anchor. Generated static-Java is required co-evidence and agrees on the exercised historical cases. No identical-behavior claim is made for the TypeScript/luxon target: a legal strategy split is recorded and never overrides Groovy-dynamic.

The model's configured **`timeZone`** is the DM-JSON key `content.modelConfig.timeZone`; the capitalized `TimeZone` is the *internal* metamodel key code generation copies it into. Absent means `UTC`. An explicit id is model-legal exactly when it is the literal `GMT` or `java.util.TimeZone.getTimeZone(id).getID() != "GMT"`. Known IANA ids, `GMT±HH:MM`, `UTC`, `Zulu`, and `Etc/UTC` are legal. An empty, unknown, or misspelled id that silently collapses to `GMT` is rejected with `MVK_INVALID_TIME_ZONE`.

The normative kernel path applies that id at parse time through legacy `java.util.TimeZone` plus non-lenient `SimpleDateFormat`, not `java.time`. A plain DATE is midnight in the model zone. Across a daylight-saving transition:

- Under **`UTC`**, the wall-clock gap equals the instant gap.
- Under **`Europe/Berlin`**, two datetimes straddling a transition differ by their *physical* elapsed time: `2024-03-31T01:30:00 → 03:30:00` is `DifferenceInHours = 1` (the skipped 02:00 hour), and `2024-10-27T01:30:00 → 03:30:00` is `3` (the repeated hour).

That non-lenient zone-set parse gives every historical transition the following laws:

- **Every gap is a FORMAL error.** A stored wall time that does not exist (`2024-03-31T02:30:00` under Berlin) draws `datumFormatFalsch` — the non-lenient round-trip rejects it — and suppresses a referencing rule exactly like any malformed value. It is **not** rolled forward.
- **Every overlap selects the smaller/after offset.** In an ordinary modern CEST→CET overlap that is CET: `01:30 → 02:30` on `2024-10-27` is `DifferenceInMinutes = 120`, and two stored `02:30` values are instant-equal. In a historical CEMT→CEST overlap the same general rule selects CEST, not CET.
- **Datetime comparison is instant-based too** (`==`/ordering compare the parsed instants), and a **chained `Add{Hours,Minutes,Seconds}` result keeps its exact instant**: `AddHours(01:30 CEST, 1)` lands on the *daylight* side of the ambiguous hour, so it is **not** equal to the equal-looking stored `"02:30:00"` (which re-parses standard) — the pair is 60 real minutes apart. A rendering-based re-parse loses this; the arithmetic is instant-in, instant-out. **Across a computation join the instant is not carried**: a computation reading another computation's DateTime target reads that target's stored rendering as the document's own text would be read, so a result on the daylight `02:30` is read on the standard one. `AddHours(00:30, 2)` computed into one field on `2024-10-27` and read by `DifferenceInHours` from `00:30` gives `3`, and a day shift landing on the daylight `02:30` is shifted two hours further to `04:30` ([checkpoint](../docs/sources/computation-scheduling-probes.md#src-datetime-join)).
- **A `Calendar.DAY_OF_MONTH` landing assumes the source instant's own offset**, not an offset chosen from the signed amount. The nominal target advances the source wall label by whole days while retaining its clock and millisecond. If the offset actually in force at that candidate differs, the target is re-fitted to the actual offset and that re-fit is kept only when it lands on the expected civil date, the source's date plus the amount, not when it merely keeps the raw landing's own date; otherwise the first candidate stands. The two readings part only within the offset delta of midnight: `2024-10-27T00:30 + 1 day` renders `2024-10-28T00:30` and `2024-03-30T23:30 + 1 day` renders `2024-03-31T23:30`, where the raw-date reading gives `2024-10-27T23:30` and `2024-04-01T00:30`, and `DifferenceInDays` steps through the same landing. The spring-gap separator is a pair, not a generic roll-forward rule: `2024-03-30T02:30 + 1 day` starts from CET and renders `2024-03-31T01:30`, while `2023-08-31T02:30 + 213 days` starts from CEST, reaches the same gap, and renders `2024-03-31T03:30`. Adjacent transition probes can therefore resemble a direction or gap-normalization rule only because their source already carries the offset that account would choose. A backward landing onto the 1916 `23:00–24:00` gap supplies the historical control: `1916-05-01T23:30 - 1 day` preserves 30 April and renders `1916-04-30T22:30` CET instead of changing the civil date to 1 May.

## 6. Date fragments and fragment ranges

A **DateFragment** is a deliberately imprecise date. **Its declaration admits the same format vocabulary as every other date-bearing kind, not a narrower fragment-shaped one** — measured over the derived candidate universe under the fragment's own `formatOfFragment` key, `yyyy-MM-dd`, `dd.MM.yyyy`, `yyyyMMdd`, `HH:mm:ss` and the ISO instant included ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-21-corrections)). An earlier version of this line gave the vocabulary as the four conventional spellings `MM`, `yyyy`, `yyyy-MM`, `MM-dd`; those four are what the completion rules below were measured on, and the narrower reading was a definition-driven inference rather than a measurement. A fragment declared with a *complete* date format — a complete date wearing the fragment kind — is therefore admitted, and a clock-declared one is handled at runtime as a clock value rather than through the fragment completion.

- Fragments are **comparable only if both formats include the year or both omit it** (or globally via the Base Year). A missing component defaults to `01`.
- When an operation requires a concrete Date and the model declares a Base Year, a fragment **completes to the earliest concrete date**: missing month becomes `01`, missing day becomes `01`, and missing year becomes the declared Base Year. It then compares, shifts, or extracts **as a plain date**. The fragment format decides which `Add*` apply.

A **fragment-format date range** completes its two endpoints **asymmetrically**:

- the **start** to the interval's *earliest* date, the **end** to its *latest* (missing month → `12`, missing day → the month's last day, leap-aware).
- So a `yyyy` range `2024/2025` denotes `2024-01-01 .. 2025-12-31`.
- With a declared Base Year, an `MM` range uses day `01` and the leap-aware month end in that year, while an `MM-dd` range uses its stated month and day for both endpoint positions. Without a Base Year, same-profile `MM` and `MM-dd` construction equality, inequality, and construction-versus-stored comparison remain authorable and distinguish a change to either ordered endpoint; these observations do not supply a year-bearing instant. Overlap applies [§8](#8-date-ranges-and-overlap)'s uniform-year gate to the whole operand list rather than to a distinguished pair, so without a Base Year any year-bearing operand beside any yearless stored profile is refused with `MVK_DATE_WITH_AND_WITHOUT_YEAR`, and a declared Base Year completes every yearless operand and admits the same list.

**Stored temporal failures use the Date formal codes, and the retained Kernel matrix is bounded by the twelve measured formats and their discriminating values.** There is no Time-specific or DateTime-specific formal code. For every retained value, DATE, TIME, and DATE_TIME agree cell for cell, so field kind does not select among those observed classifiers. The semantic account for an `HH:mm:ss` declaration maps width and component-range failures to the format error and has no date-error branch; the retained rows cover each component and the 24-hour boundary. Hour **24 is not an end-of-day spelling**: `24:00:00` is refused exactly as `25:00:00` is, while `00:00:00` and `23:59:59` are admitted, so the hour's range is 0 through 23 inclusive. At a complete Date or DateTime format, a real value before `1583-10-16` reports the date error, while an unreal component reports the format error before the floor can speak; `yyyyMMdd` therefore admits `15831016`, reports the date error on `15831015`, and reports the format error on `00000615` and `20240231`. The ISO DateTime literal `'T'` is mandatory. These observations do not establish classifier behavior for a format outside the 135-candidate declaration denominator or for an unmeasured stored text inside a measured format.

**Partially known Date values** use literal zero components in a monotone suffix governed by `DateType.datePrecision`. `DAY_OPTIONAL` admits a full Date or an omitted day such as `00.06.2024`. `MONTH_OPTIONAL` additionally admits an omitted month only when the day is also omitted, such as `00.00.2024`. `YEAR_OPTIONAL` additionally admits an omitted year only when month and day are both omitted, namely `00.00.0000`. A lone `0` is never an omission marker, an omitted month with a present day is invalid, and an omitted year with a present month or day is invalid.

**An admitted partially known value is filled.** `FieldFilled` holds and `FieldNotFilled` does not for `2024-06-00` at `DAY_OPTIONAL` and `0000-00-00` at `YEAR_OPTIONAL`, on the validation and the computation arm alike, and `NumberOfFilledFields` counts it, exactly as it counts a component-omitting Date or a DateFragment holding `2024-06`. An interval with no point value is still a value; an implementation that stores only the text and reads presence off a parsed value answers not filled. A value omitting more than its precision admits is the formal failure below and leaves both presence tests unknown ([checkpoint](../docs/sources/temporal-and-message-probes.md#src-partial-date-presence)). The readers that ask the same presence agree: a required field holding `2024-06-00` raises no `mandatoryField`, a group or a once rule's root holding only it has content, and `FieldValuesNotUnique` compares its stored text, so `2024-06-00` beside a fully known `2024-06-01` is unique although both begin on June 1st ([checkpoint](../docs/sources/temporal-and-message-probes.md#src-partial-date-readers)). A selecting reader takes the value as its earliest day: `FirstFilledValue` selects `2024-06-00` as `2024-06-01` and `2024-00-00` as `2024-01-01`, directly, starred, over a group and keyed alike, while an omitted year leaves the selection unknown and ends the walk there as a malformed value does ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-10-02-partial-date-readers)).

**Which formal cause a rejected partial value carries is decided by the declaration first, then by reality.** A **full-precision** declaration reports *any* omission marker as the format error `datumFormatFalsch`, because an omission is not a legal spelling for it at all. A declaration that admits omissions instead splits its rejections in two. The **format** error covers a wrong component width or separator count and an unreal calendar date among the value's **present** components — including an impossible month standing beside a legally omitted day, where the omission is admitted and the month is not. The **date** error `datumFalsch` covers a zero pattern that is not a monotone suffix, a suffix deeper than the declared precision admits, and an admitted value whose **earliest completion** falls below the universal Gregorian floor or the enabled pre-1900 boundary. So an implementation must test the present components' reality *before* their position in time, and both before the precision gate: `1583-10-00` on a `DAY_OPTIONAL` declaration is the date error while `1583-11-00` is admitted, and `2024-13-00` on that same declaration is the format error rather than either omission failure. The two thresholds are indistinguishable from the cause alone and separable only from the declaration.

`ValueAsDate(field, FirstDay|LastDay)` resolves a known-year partial value to the earliest or latest matching concrete Date: an omitted day becomes `01` or the leap-aware month end, an omitted month-and-day becomes January 1 or December 31, and a full value resolves to itself. An omitted year becomes non-relevant before month/day completion, so an enclosing direct comparison evaluates to UNKNOWN rather than ordinary non-firing emptiness; it is not completed with the formal checker's temporary year 2000. `ValueAsDate` is a Date-valued operation. In addition to direct comparisons, the grammar explicitly admits it in the special Date-operand positions of Date addition, Date difference, and the Date argument of `DateTime(...)`; an ordinary Date extractor such as `Day(ValueAsDate(...))` does not admit that operation in its narrower operand grammar. A partial-Date field is **not** readable as a plain Date operand at all: a bare reference to one in an ordinary comparison is rejected `MVK_INVALID_DATE_TYPE` ("it is not allowed to use a partly known date"), which is what `ValueAsDate` exists to bridge.

**The operand's reading locus.** A partial-Date operand may lie **inside a repeatable group**, and it is admitted exactly when the reading rule's own iteration scope binds that group: the same absolute operand path is accepted by a rule whose group is the repeatable one and rejected by a rule at the parent, where the Kernel demands an asterisk (`MVK_NO_WILDCARD`) instead. A **starred** operand is rejected outright, `MVK_NO_WILDCARDS_ALLOWED` reported at `ValueAsDate` itself rather than at the enclosing comparison, so no iteration scope admits one; a group-scope operand is likewise rejected, under [§7](07-repetition-and-iteration.md). Measured on the direct-comparison carrier; a locus verdict does not transfer to the Date-addition, difference, or `DateTime(...)` carriers, which remain unmeasured for this question.

> **Non-normative implementation note.** Model a fragment as `(present-components, format)` and give it a single `completeEarliest : Fragment → CalDate` plus, for ranges, a `completeLatest`. Keep completion a *pure* function separate from comparison, so a fragment "becomes a date" at exactly one place. The start/end asymmetry for ranges is the subtle bit — two different completion functions, chosen by endpoint position.

## 7. The point-in-time and reference sources

- `Today` ignores the time of day — more precisely, it truncates the validation instant to midnight **in the model zone** (a zone-set calendar), so under `Europe/Berlin` the day boundary is Berlin midnight, not UTC midnight. Both `Today` and `Now` read their date on the legacy hybrid calendar: an instant pinned at 1500-03-10T12:00Z reads 29 February 1500, and one at 1582-10-14T12:00Z reads 4 October ([inbound](../docs/sources/inbound-handbacks.md#src-inbound-2026-10-21)). `Now` is the raw validation instant, including any millisecond remainder supplied through `currentDateForTest` or sampled from the wall clock; it is not rounded to authored DateTime precision before comparison or difference. `Now` is a DATETIME. Ordering (`<`, `<=`, `>`, `>=`) against either DATE or DATETIME is legal and compares both operands on the common model-zone timeline, with a DATE interpreted at model-zone midnight. Equality and inequality require the other operand to carry a time component, so `Now == PlainDate` and `Now != PlainDate` are rejected with `MVK_INVALID_COMPARE_TO_DATE`. `Now` remains unsuitable for stable equality: it is legal as a computation result but generated validation may sample a later instant and immediately disagree ([§11](09-computations.md)).
- **`BaseYear` is polymorphic by its typed use:** an explicitly date-typed source receives the base-year *start* (`2020-01-01`); a numeric comparison, ordinary arithmetic expression, or Number computation receives the fixed scale-0 year number (`2020`); and `StartOfDateRange(BaseYear)` / `EndOfDateRange(BaseYear)` are `01.01` / `31.12` of the reference year. It is *model config*, not the clock; **VALUE** polarity.

> **Non-normative implementation note.** Inject the clock (`Today`/`Now`) as an explicit parameter — a `PointInTime` in the evaluation environment — never a global read. This keeps `eval`/`compute` pure and deterministic (essential for reproducible property tests and for the "compute is a function" stance of [`01-data-model.md`](01-data-model.md)). `BaseYear` is model config, resolved by the typed consumer — a small dispatch, not a clock read.

## 8. Date ranges and overlap

Date ranges support only `==` / `!=` (**no ordering**). A stored DATE_RANGE or `DateRange(start, end)` construction may appear on either equality side, against another construction, or as a DATE_RANGE computation result. A construction is not admitted as a date-range overlap or bound-extraction argument and **cannot be nested** inside other constructs.

A DATE_RANGE declaration is statically admitted for exactly eight `(format, separator)` pairs: `dd.MM.yyyy` with `-`, `yyyy-MM-dd` with `/`, `yyyy` with `/`, `yyyy-MM` with `/`, `MM` with `/`, `MM-dd` with `/`, `MM` with the empty separator, and `dd.MM` with `-`.

Every other pair in the complete candidate grid is refused, including separator swaps, every dot separator, every other empty separator, and every `yyyyMM` pair. This declaration allowlist does not by itself establish that every DateRange operation admits every pair.

`interpretationOfYear` may be omitted or set to `FROM` or `TO` on every admitted declaration pair, including year-bearing ones. An omitted key is the standard interpretation; a present but empty token makes the model illegal at deserialization. The accepted declaration is distinct from the effective runtime format.

DateRange document input and runtime reads use two stages. Document conversion first parses text under the field's own format and separator, with missing month/day defaulting to 1 in the converted Date endpoints. Runtime formatting, formal checking and endpoint reads use a shared definition selected in declaration order. For interpreted ranges, the sharing key distinguishes FROM from TO and the additional pre-1900-check flag, but drops the declared format and separator. The first field in that class supplies those runtime details. Standard ranges retain their format/separator distinction. Consequently, reordering declarations can change validity, endpoint values and computed presentation even when a Base Year is configured ([source and four-model observation matrix](../docs/sources/date-range-construction.md#src-date-range-shared-runtime)).

A shared yearless day-and-month format completes endpoints using the declared Base Year, or 2000 when absent. On a wrapping pair, FROM anchors the start and moves the finish into the following year; TO anchors the finish and moves the start into the preceding year. Endpoint calendar validity is checked in its placed year: with effective dotted day-and-month format and Base Year 2020, `01.11-29.02` is valid under TO, but `datumBereichFormatFalsch` under FROM because the finish would be February 29, 2021. This completion must not be generalized to every yearless format: effective month-only format rejects a wrapping pair with `datumBereichNichtGueltig` under either interpretation, with or without Base Year.

Formal date-position checking is separate from endpoint completion. Effective day-and-month formats use Base Year for the always-on floor and the optional pre-1900 check; effective month-only formats use neither the endpoint’s completed year nor Base Year for these checks. Thus both `MM` spellings accept an ordered pair under Base Year 1500 with either flag setting, while still rejecting reversed pairs. Day-and-month ranges with the flag reject Base Year 1899 and accept 1901; their unflagged twins accept both ([retained inbound measurements](../docs/sources/inbound-handbacks.md#inbound-2026-09-08)).

The two stages also explain component loss. With interpreted `dd.MM` declarations first, a later month-only `03/10` input becomes `01.03-01.10` and its end-Day is 1. With interpreted `MM` declarations first, that read becomes `03/10` and positional endpoint completion gives end-Day 31. A later full-Date input can lose its supplied years when rendered through either shared yearless profile; numeric endpoint reads then return the runtime anchor years. An additional-check flag different from the first declaration creates a separate sharing class. Empty numeric endpoint reads compute 0; formal-invalid sources clear their dependent computations. Raw text that conversion could not decode is checked under the effective runtime format, so even a compact-month declaration can report the shared separator's missing-separator class.

A computed DateRange is rendered through the target's shared runtime definition and that text is checked before dependent computations consume it. A valid dotted-FROM wrapping source copied into a month-only TO sharing class therefore produces an errored `11/02` attempt, and a following end-Year computation clears. Ordered input writes `03/10` and the dependent year is 2000 in an unconfigured model. An empty source instead clears the target and permits the dependent numeric read to substitute 0. Formal source poison and target rejection both block the dependent read, but only target rejection retains the attempted text ([crossed-target observation](../docs/sources/date-range-construction.md#src-date-range-shared-runtime)).

Both overlap operators **refuse** an operand whose declaration carries an `interpretationOfYear`, reporting `MVK_INVALID_DATE_RANGE_FORMAT` against the composite declared format. The refusal applies on either operand side of either operator, under a yearless or a year-bearing exact profile, and with or without a declared Base Year, so it is a property of the declaration rather than of the value or its completion. Bound extraction and equality comparison admit the same declaration, so the gate belongs to the two overlap operators alone.

`StartOfDateRange(field)` and `EndOfDateRange(field)` select the stored range's first and second endpoint respectively and expose it as a Date. Extraction is admitted on **every** admitted declaration, including a yearless profile in a model with no Base Year; what is gated is each consumer, because the consumer checks the selected endpoint's resulting format. For a range without year interpretation, that format retains the declaration's date components. A numeric extractor on this uninterpreted range is therefore admitted exactly where that set exposes its component, with the model's declared Base Year supplementing the **year** and nothing else, which is the same admission rule a direct Date field uses and *not* the exact-value gate the comparison consumers below apply: `MonthFromDate` and `QuarterFromDate` on `MM`, `MM-dd`, `dd.MM`, `yyyy-MM`, or a full-Date profile; `DayFromDate` on `MM-dd`, `dd.MM`, or a full-Date profile; `YearFromDate` on `yyyy`, `yyyy-MM`, or a full-Date profile in any model, and additionally on every yearless profile once the model declares a Base Year. Every other pairing in that uninterpreted profile is refused `MVK_WRONG_DATE_FORMAT_FOR_OP` at the extractor, and a declared Base Year never widens the month or day halves, so `DayFromDate` on an uninterpreted `MM` range stays refused in a configured model. A year interpretation is a separate source of year-bearing endpoint format: an `MM-dd` range with `interpretationOfYear: "FROM"` admits `YearFromDate(EndOfDateRange(...))` without a Base Year, while an otherwise identical uninterpreted range refuses year extraction; Hours extraction remains refused. The later [shared-format matrix](../docs/sources/date-range-construction.md#src-date-range-shared-runtime) admits start/end Year and end Day for both interpretations across all eight profiles, without Base Year as well as with it. The interpreted endpoint exposes full-Date components; its actual numeric values follow the two-stage runtime account above. The selection and its component are one authored operand rather than two, because the endpoint alone is not a numeric value; that operand is admitted in a Number **computation** operation on the same terms as in a validation condition, with the ordinary locus rule deciding the target — a row endpoint computes a field inside its own repeated group, while a scalar endpoint computes either. Like a direct temporal component, an endpoint component is a **non-expandable scale-0** Number operation, so assigning it to a fractional Number target is refused `MVK_INVALID_COMPARE_DEC_PLACES`, the one waivable code. At runtime the computed value is the selected endpoint's component under the ordinary rules of this family, including from an unconfigured yearless range, whose retained labels are read directly: an unplaced range computes the real number `0` rather than clearing, and a formally invalid range clears the reading computation's target while a sibling computation over a clean operand in the same row still computes its own value. Comparing a selected endpoint with a full Date, whether a literal or `Today`, follows the ordinary direct temporal admission rule, so only a **yearless** profile with no Base Year is refused `MVK_INVALID_COMPARE_TO_DATE`; every year-bearing profile is admitted, including the incomplete year-only `yyyy` profile. Comparing two selected endpoints follows the same rule, which admits `MM` against `MM-dd` and refuses `MM` against `yyyy`; at runtime each fragment is first completed by its endpoint position, so a month-only start equals a month-and-day start exactly when that day is the month's first. An empty range stays empty. Ordinary formal invalidity makes validation UNKNOWN and poisons computation with the same cause before either endpoint is selected. The validation-scoped required-empty finding remains the existing exception: it is UNKNOWN in validation and stays empty in computation. The ordinary operand is a non-wildcard, non-category DATE_RANGE field, either direct or selected by a **semantic index** — `StartOfDateRange(Rows/Window For "k")` and its field-keyed form are admitted, as are a keyed operand of the overlap predicate and of stored range equality, at a nonrepeatable locus, at an iterating one, and even when the keyed group is the group being iterated. A **starred** operand is refused `MVK_NO_WILDCARDS_ALLOWED` at either locus, so no wildcard form of this operand exists, and a **group** operand is refused `MVK_NO_WILDCARD`. `BaseYear` is the separately typed source described above, while a `DateRange(start, end)` construction is not admitted here.

At this carrier the shared wildcard gate is measured rather than carried over: a **starred** endpoint draws `MVK_NO_WILDCARDS_ALLOWED`, while an **unstarred repeatable** field or a group operand draws `MVK_NO_WILDCARD`, and an arity other than two is a parse refusal, `MVK_UNEXPECTED_TOKEN`.

Each `DateRange` endpoint is a bare A12 `entitySpec` reference, including a literal- or field-keyed semantic-index selection; a bracketed calculation is illegal there. `Today`, `BaseYear`, an `Add*` operation, and a date literal in either endpoint position are refused with `MVK_UNEXPECTED_TOKEN`.

A starred field is refused with `MVK_NO_WILDCARDS_ALLOWED`; an unstarred group with `MVK_NO_WILDCARD`; and a starred group or the rule-context group with `MVK_NO_GROUPS_ALLOWED`. A top-level outer-iteration marker is refused with `MVK_INVALID_OUTER_ITERATION`, while the same marker is admitted inside a `Having` filter that supplies its iteration.

After the entity-reference gate, each endpoint is admitted by its **declared format** alone: the format must have at least one date component and no time component, and the endpoint's declared kind takes no part. A TIME- and a DATE_TIME-declared field each carrying `yyyy-MM-dd` are admitted in the start position, in the finish position, and as both endpoints at once, beside the DATE-declared control; a DATE-declared field whose format is `HH:mm:ss`, a TIME declared the same, and a DATE_TIME declared the stamp format are all refused, as are a Number, a String, a DateRange field, a partial DATE, and endpoint formats with different component sets. Every refusal is `MVK_WRONG_DATE_FORMAT_FOR_OP`. Each declared kind therefore appears on both sides of both outcomes, which is what makes this the gate rather than a gloss on same-kind rows, and it is measured at this carrier rather than transferred from the operand families that share the rule ([checkpoint](../docs/sources/computation-placement-and-constant-probes.md#src-daterange-endpoint-reads-the-format)).

DATE and DATE_FRAGMENT may mix, and different lexical format spellings are legal when their component sets agree. Literal- and field-keyed semantic-index endpoints are admitted, but semantic indexing is not the only way to read a field below a repeatable group.

An ordinary unstarred endpoint that crosses a repeatable group is governed by the enclosing rule's iteration scope. With the error field outside that repeated group it is refused with `MVK_NO_WILDCARD`; moving the error field inside the repeated group admits it. This is a rule-locus condition shared with other operators, not a DateRange-construction restriction. **The claim is measured across the DateRange carriers rather than transferred between them:** the overlap predicate, stored range equality, an extracted endpoint compared against a fixed Date, a pair of extracted endpoints, a numeric component of an extracted endpoint, and the two-endpoint construction all admit the same repeatable operand from inside the repeated group and all refuse it `MVK_NO_WILDCARD` from outside, on one model differing only in the error field's placement. Each refusal names the offending operand rather than a neighbouring one, which is what isolates the carrier under test. The six agree, and that is agreement between independent measurements rather than an inference from a shared mechanism, so a carrier absent from this list is not covered by it — neighbouring gates in this family do vary by carrier. At the numeric-component carrier the locus gate also reports **before** the component gate: a row operand whose profile withholds the requested component still draws `MVK_NO_WILDCARD` from a non-iterating locus rather than the format class. The retained filter control instead admits an explicit outer-iteration marker and does not establish ordinary crossed-repeatable endpoint admission from filter context alone. Overlap tests treat endpoints as **inclusive (closed intervals)**.

Equality or inequality additionally requires the two resulting DateRange operands to expose the same declared date-component set. A component mismatch between otherwise valid constructions is refused with `MVK_INVALID_COMPARE_TO_DATE_RANGE`; it is not evaluated by completing the coarser range into the finer one. With a Base Year, this admits matching `MM` or matching `MM-dd` constructions but still refuses `MM` beside `yyyy-MM` and `MM-dd` beside full Date. Mixing those component profiles inside one construction instead yields `MVK_WRONG_DATE_FORMAT_FOR_OP`.

The same gate governs two **stored** DATE_RANGE fields compared with each other, and it reads only the component set: the declaration's lexical spelling never enters it. Over the eight admitted declarations that leaves five component classes, and each class's spellings cross freely — `yyyy-MM-dd` against `dd.MM.yyyy`, `MM` with slash against `MM` with the empty separator, and `MM-dd` against `dd.MM`. Every pair drawn from two classes is refused, including `dd.MM.yyyy` against `dd.MM`, which shares a separator and differs only in components. The refusal is symmetric in the authored order and identical for `==` and `!=`. Where the pair is admitted, the comparison decides on retained identity rather than stored text, so the two spellings of one class agree exactly when their resolved endpoints or their retained yearless labels agree.

DateFragment endpoints use [§6's asymmetric fragment-range completion](#6-date-fragments-and-fragment-ranges): a start completes to its earliest local date and a finish to its latest, so `yyyy` endpoints become January 1 and December 31 respectively, `yyyy-MM` or Base-Year-resolved `MM` endpoints span the selected month, and Base-Year-resolved `MM-dd` endpoints retain their stated day. The completed local labels are resolved under the model's accepted zone profile, and DateRange equality or inequality compares both ordered resolved endpoints. The [`yyyy` checkpoint](../docs/sources/date-range-construction.md#src-date-range-year-fragment-construction), [`yyyy-MM` checkpoint](../docs/sources/date-range-construction.md#src-date-range-year-month-fragment-construction), and [Base-Year checkpoint](../docs/sources/date-range-construction.md#src-date-range-base-year-fragment-construction) establish calendar labels and comparison outcomes, not externally exposed exact endpoint instants.

**Both overlap operators admit their operands by year class, and apply no component-set gate.** Every compared operand must include the year or none may; a mix is refused `MVK_DATE_WITH_AND_WITHOUT_YEAR`. The gate reads the whole operand list rather than a distinguished pair, so a list of three or more is refused on any mix, and every declared spelling of one yearless component set behaves alike. **Uniform year-carrying is nevertheless not sufficient, because the walk reduces each reference to its *distinct format spellings* before it asks the year question at all** ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-21-corrections)): a single reference expanding to two differently-spelled **dated** ranges is refused under this same class although neither is yearless. Measured on the value-list carrier with a group operand — a group of two ranges declared `dd.MM.yyyy` and `yyyy-MM-dd` is refused where a group whose members share one spelling is admitted — so it is a property of the expansion the reference contributes. **An explicitly written pair of two differently-spelled dated range *fields* is admitted**, which bounds the rule to a single reference's own expansion ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-21b-corrections)): the same two declarations that are refused when reached through one group reference are admitted when named as two fields, and a pair of unrelated top-level range fields at two dated spellings is admitted too. The two carriers are asked different questions — the distinct-spelling reduction runs inside one reference's expansion and compares format *strings*, while the cross-reference test beside it compares year-bearing *booleans*, to which a spelling difference is invisible. Two walks run in a fixed order and only the second has a Base-Year escape: a per-operand walk asks first whether each expanded field is a date-range declaration (`MVK_NO_DATE_RANGE`) and then whether its `interpretationOfYear` is `FROM` or `TO` (`MVK_INVALID_DATE_RANGE_FORMAT`), and it completes before the agreement walk begins — so a list both wrong in kind and inconsistent about the year answers with the kind class, and a declared Base Year, which disables the agreement walk, leaves a year-interpreting range refused exactly as before. For `AtLeastOneDateRangeOverlaps` the list is the scalar together with its `In` list, so the gate spans both sides and a completed fragment is admitted as scalar or as list member. A declared Base Year completes each yearless operand and therefore admits every list, including `yyyy-MM-dd` beside `MM`; within one year class the operator admits differing component sets outright, unlike the equality gate above. A completed yearless operand occupies the Base Year alone, so an exact operand naming another year is disjoint from it, while an exact range spanning into the Base Year still meets the completion.

Without a Base Year an all-yearless list is admitted as well, and compares month/day labels directly with no completion: a month-only endpoint spans day `01` through that month's yearless maximum last day, February reaching `29` because no year decides leapness, and both ends stay closed. A configured Base Year instead makes the stored value itself completable and therefore falsifiable, so `02-29` under Base Year 2023 is `datumBereichFormatFalsch` rather than any overlap verdict. The [mixed-year checkpoint](../docs/sources/date-range-construction.md#src-date-range-mixed-year-overlap) and [yearless-overlap checkpoint](../docs/sources/date-range-construction.md#src-date-range-yearless-overlap) establish both accounts on either codegen strategy.

Their list-admission ordering is carrier-specific. After all authored operand reads, `DateRangesOverlap` checks duplicate/overlapping references, roots, categories, field-only shape, then multiplicity; a sole unstarred field reports `MVK_PARAMSIZE_INVALIDFN`. Its range-kind/interpretation walk and year agreement follow. `AtLeastOneDateRangeOverlaps` first checks the subject list for duplicates, roots and common base type, then requires exactly one unstarred field (`MVK_INVALID_PARAMETER_FOR_DATE_RANGE_COMPARISON`) and value validation. A literal member list then reports `MVK_NO_CONST`. An entity member list checks its own duplicates and roots, matches the subject base type, checks cross-list duplicates, and checks member value validation before the combined range-kind/interpretation and year gates. Thus a member of the wrong base type can win over a cross-list duplicate. These combined precedence distinctions are source-derived from Kernel 30.8.1 `CheckFeldListenBedingungImpl` and `CheckFeldListeUndWerteListenBedingungImpl`; external calibration remains pending.

The two overlap predicates differ in **shape** ⚠:

- **`DateRangesOverlap(op0, op1, …)`** is **any-pair** among *all* operands' kept, filled ranges (one growing set): a list-internal pair fires even when a scalar operand is disjoint, and a same-cell self-pair via scalar + star fires on every filled row.
- **`AtLeastOneDateRangeOverlaps(scalar In list…)`** is genuinely **scalar-vs-list**: two list cells overlapping *each other* do **not** fire.

**The scalar slot admits only a scalar, and rejects every other form with one class.** A plain star, a `Having`-filtered star, a fixed group, a starred group, and a star above a nonrepeatable terminal are each refused `MVK_INVALID_PARAMETER_FOR_DATE_RANGE_COMPARISON` in the scalar position, while the identical operand is admitted in the `In` list — so the refusal belongs to the slot and not to the form. A kind gate reports ahead of it: a group whose expansion mixes kinds is refused `MVK_VARYING_TYPES_NOT_ALLOWED` in that position instead. So does an operand's read, in either slot: an index that cannot be read, `MVK_INDEX_VALUE_INVALID`, answers ahead of the slot's gate whether it stands beside the starred scalar or alone in the `In` list ([inbound](../docs/sources/inbound-handbacks.md#inbound-2026-09-26h-list-reads)).

**The `In` list is an entity list of its own before it meets the scalar**, in the order [§6](06-strings-and-enumerations.md) gives the value-list quantifiers' value list: its own repeat, then its root, then its base type against the scalar's, and only then a repeat across the two sides ([checkpoint](../docs/sources/group-list-and-capacity-probes.md#src-count-placement-overlap-list-grid)). A list naming only a root draws `MVK_ROOT_GROUP_REFERENCED` though the scalar lies inside that root, starred or fixed, and `Term In Term, /Lot*` draws `MVK_DUPLICATE_PARAM2` for the containment inside the list rather than the scalar's repeat beside it. `Term In Term, Serial` and `Term In Serial`, over a String `Serial`, draw `MVK_VARYING_TYPES_NOT_ALLOWED`, and `Term In Serial, Serial` draws `MVK_DUPLICATE_PARAM1`, the list's own repeat answering first. All of these, and a repeat across the two sides, answer ahead of the field walk above, so beside a scalar carrying an `interpretationOfYear` a root-only list, a repeat in the list and a list of another base type each draw their own class, and only an admissible list reaches `MVK_INVALID_DATE_RANGE_FORMAT` ([checkpoint](../docs/sources/group-list-and-capacity-probes.md#src-overlap-field-walk-order)). `DateRangesOverlap` instead asks its group refusal over the whole list first: a group draws `MVK_NO_GROUPS_ALLOWED` though an interpreted field or a field of another kind is written before it, and beside a year mix.

An admitted group operand contributes every DateRange declaration in its recursive subtree at every instantiated row below the operand’s own repetition depth.

For both: intervals are **closed** (back-to-back periods sharing a boundary day overlap); an **inverted** range (start after end) **never** overlaps. Validation skips empty or formally unavailable cells. Computation skips empty cells but aborts on a reached formally invalid cell, as detailed below.

Their validation firing polarity is scan- and operand-shape-sensitive:

- `DateRangesOverlap` fires **OMISSION** exactly when the scan has processed a kept, filled range from a filter-bearing operand at or before the first overlapping pair; otherwise it fires **VALUE**. A filtered operand with no kept, filled range does not taint a later firing.
- `AtLeastOneDateRangeOverlaps` resolves the scalar first and does not read the list when that scalar is unusable. Otherwise it visits list operands in authored order, visits each operand's cells in its canonical address order, and stops at the first overlap. It fires **OMISSION** exactly when that first matching list operand carries a filter; otherwise it fires **VALUE**. An earlier filtered but disjoint list operand does not taint a later unfiltered match, and a later filtered match cannot change an earlier unfiltered result.

A group operand expands in declaration-major recursive model order, with each declaration's rows in canonical row order. For validation, changing order inside an unfiltered group cannot change the predicate's truth or polarity. For computation, the order is observable: an invalid second-row value of the first declared field aborts before an overlapping first-row value of the next field can decide the guard ([overlap guard checkpoint](../docs/sources/computation-scheduling-probes.md#src-overlap-computation-guards)).

In validation, an empty, malformed, or formally unavailable scalar of `AtLeastOneDateRangeOverlaps` collapses directly to no fire; overlaps internal to the list cannot rescue it. Stored inverted ranges are normally rejected by their field's formal check and therefore skipped, while the resolved interval relation independently returns false if an inverted pair reaches it.

**Computation guards preserve ordered failure reachability.** Both predicates visit operands in authored order and stop at the first deciding overlap. `DateRangesOverlap` compares each reached filled range with earlier filled ranges; `AtLeastOneDateRangeOverlaps` reads its scalar first and compares each reached list value only with that scalar. An empty or absent scalar makes the latter guard false without reading the list. A reached formally invalid scalar or list value poisons the computing target and any dependent computation that reads it; an invalid value after a deciding overlap remains unread. When no later table alternative supplies a value, a clean false guard instead leaves the target empty, which a dependent Number expression may substitute with zero under [§9](09-computations.md). Both predicates consume fresh computed values under that section's scheduling rules.

Filtered operands use the computation iterator's **one-kept-successor lookahead** from [§7](07-repetition-and-iteration.md): the iterator evaluates filters through the next kept row before supplying the current row's range to the overlap search. A dropped row's invalid range is never read. A filter failure reached during lookahead aborts before the pending range is compared; the prefetched successor's range itself remains unread until the search requests it. Consequently, with overlapping first and second rows, an invalid third-row filter can poison the any-pair search while a scalar already overlapping the first row lets the scalar-versus-list search succeed. Replacing that third-row filter failure with an invalid range and a healthy filter lets both searches succeed. These computation distinctions also apply to the yearless interval domain; they do not manufacture a year or reuse validation's unavailable-cell skipping ([checkpoint](../docs/sources/computation-scheduling-probes.md#src-overlap-computation-guards)).

## 9. DateTime rides the date-format definition — but the operand gates are PER-OPERATOR ⚠

The date **extractors** (`DayFromDate`, …) accept a DateTime operand and see its **DATE part** (times ignored). The time extractors (`HoursFromTime`, `MinutesFromTime`, `SecondsFromTime`) likewise accept either Time or DateTime and see only the **TIME part** (the DateTime date is ignored). Beyond the extractors, the earlier blanket claims ("differences see the date part; arithmetic is rejected") are **wrong per-operator** — probe-corrected (kernel 30.8.1, 2026-07-18):

- **`DifferenceInDays` accepts DateTime operands and is TIME-OF-DAY AWARE**, but its general rule is a signed **model-zone calendar-step count**, not unconditional subtraction on zone-free wall labels. The kernel orders the resolved legacy `Calendar` values, qualifies its whole-year candidate through the same corrected `Calendar.YEAR` mutation used by `AddYears`, makes a `yearDifference × 365` lower-bound jump with `Calendar.DAY_OF_MONTH`, advances by single calendar days until the next landing passes the later operand, and then restores authored argument order (`b − a`). The year qualification therefore uses the sign-independent later/post-gap `YEAR` landing described above, while every lower-bound or residual `DAY_OF_MONTH` landing assumes the offset of the instant from which that particular step starts and preserves milliseconds. The familiar wall-seconds quotient happens to agree with the maintained controls: `23:00 → 01:00` next day is **0**, not the date-part 1, while the equal-wall-time Berlin `2024-03-30T12:00 → 2024-03-31T12:00` is **1** despite only 23 elapsed instant hours. It is not a generally equivalent formula, even within Berlin: `2024-03-30T02:30 → 2024-03-31T01:45` counts **1** because one calendar-day addition lands at `01:30` before the second operand, whereas Δ wall-label seconds is only 23 h 15 m and would truncate to 0; the long-range source-offset separator `2023-04-01T02:30 → 2024-04-05T02:30` counts **369**, not the **370** produced by a direction-selected landing. A short overlap qualifier can self-correct through the residual loop, but the long spring-gap span `2003-03-31T02:30 → 2024-03-31T03:00` separates the year resolver: compute-time qualification counts **7670**, while direction-selected gap qualification counts **7671**. Across a whole-date discontinuity the distinction is sharper: in `Pacific/Apia`, `2011-12-29T12:00 → 2011-12-31T12:00` is one zone-calendar day because a single `DAY_OF_MONTH` step skips 30 December, whereas a proleptic wall-label coordinate would incorrectly return two. **Mixed `(datetime, date)` pairs are legal** — the date reads as midnight in the model zone.
- **`DifferenceIn{Months,Years}` REJECT a DateTime operand** at code generation (`MVK_WRONG_DATE_FORMAT_FOR_OP`) — date-only.
- **`AddDays` accepts a DateTime operand and is TIME-PRESERVING** (`15T22:00 + 1 = 16T22:00`); a special-hour landing follows the source-offset/refit rule (§5). **`AddMonths` / `AddYears` REJECT a DateTime operand** at code generation.
- **`DifferenceIn{Hours,Minutes,Seconds}` REJECT a plain DATE operand** — DateTime-only, mirror-image of the months/years gate.
